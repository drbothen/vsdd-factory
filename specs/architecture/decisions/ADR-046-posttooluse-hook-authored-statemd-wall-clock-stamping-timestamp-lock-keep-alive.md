# ADR-046: PostToolUse hook-authored STATE.md wall-clock stamping (timestamp + lock keep-alive)

> **STATUS: ACCEPTED.** Ratified by the human (acting as senior architect) 2026-08-25, together with three binding design decisions — (1) identity model stays email-based with the trim/config-scope bugs fixed, (2) precompact-flush's PreCompact renewal is brought under the same holder-identity gate, (3) a renewal-should-have-fired-but-failed condition is made observable via a diagnostic event — all incorporated into this v1.1 revision. This ADR remains **design-only**: no hook source, registry entry, or `.factory/policies.yaml` content has been touched to produce this document; ratification authorizes implementation via the Work Spec / File-Change Plan below, to be carried out in a follow-up implementation burst (S-17.05, scope-expanded — see Rollout / Migration Note).

## Context

Two fields in `.factory/STATE.md` frontmatter are wall-clock values that every agent writing STATE.md must currently manage by hand, and both are enforced by dedicated PreToolUse WASM guards that **block** the write rather than **fix** it:

1. **`timestamp:`** (top-level) — must be byte-different from the on-disk value on every `Edit`/`Write`/`MultiEdit` to `.factory/STATE.md`. Enforced by `verify-state-timestamp-refresh` (`crates/hook-plugins/verify-state-timestamp-refresh/`, registry entry `verify-state-timestamp-refresh` in `hooks-registry.toml`, priority 143) via byte-comparison (ADR-025 §Decision 12 §12.2), not datetime parsing.
2. **`factory_lock.expires_at`** — while a lock is held (i.e., `factory_lock.holder` is non-empty in the proposed content), this must also advance byte-different from on-disk. This is the same guard's Step 8 (module-doc Steps 4–8; the lock-expiry arm — BC-5.40.001 PC4 "mid-burst TTL renewal"). BC-5.40.001 Invariant 1 states "state-manager is the sole writer" of the `factory_lock` block and its PC4 explicitly assigns the renewal act to `state-manager`. **Scope note (F-010, added v1.1):** this ADR's identity model is email-based (`git config user.email`), so every "sole writer" / "only the holder renews" claim in this document — including BC-5.40.001 Invariant 1 as restated above — holds **modulo email collision**: two concurrent sessions authenticated under the same git email (e.g., two terminal tabs on the same laptop, or two CI runners sharing a service identity) are indistinguishable to every identity check in this system and can renew, or be treated as holding, each other's lock. See Rationale §"Residual risk" for the accepted-risk disposition.

Both are pure **detectors of agent forgetfulness**, not producers of the correct value. When an agent forgets, the write is blocked and the agent must go back, compute the current UTC time (or invoke `factory-lock-write.sh renew`), and retry the edit — friction that is entirely mechanical and that an agent has no reason to ever get right or wrong: the correct value is always "now," and it is knowable only by whatever runs at write-time, not by the agent's own reasoning.

Separately, `verify-factory-lock` (`crates/hook-plugins/verify-factory-lock/`, registry entries `verify-factory-lock` and `verify-factory-lock-bash` at priority 142) is the PreToolUse guard that enforces the cross-session single-writer invariant on the `factory-artifacts` orphan branch (BC-4.13.001). Its `guard_logic` decision tree resolves the caller's identity via `host::exec_subprocess(["git", "config", "user.email"])` and compares it against `factory_lock.holder`:

- **PC1 ForeignLockHeld** — foreign holder, lock unexpired → `Block`.
- **PC2 LockExpired** — `now >= expires_at` → `Continue`, **for any caller**, not just the original holder.
- **PC3 self-held** — caller email equals holder → `Continue`.
- **PC4/PC6/PC7** — malformed/read-failure/identity-failure → `Continue` (fail-open).

Feasibility for a PostToolUse fix has already been established in a prior read-only investigation, re-verified here:

- WASM plugins can read wall-clock UTC in the sandbox (`chrono::Utc::now()` is already used inside `verify-factory-lock`'s `guard_logic` function, in the `is_expired(now, expires_at)` comparison; the dispatcher's WASI context is not clock-locked, per `crates/factory-dispatcher/src/invoke.rs`).
- `HookResult` (`crates/hook-sdk/src/result.rs`) is `Continue | Block { reason } | Error { message }` — there is **no** modified-input path, so a PreToolUse plugin structurally cannot inject the correct value before the write lands; only a **PostToolUse** plugin can rewrite the file after the tool's own write completes.
- PostToolUse plugins can write `.factory/` files today: the `regression-gate` registry entry declares both `read_file` and `write_file` capabilities scoped to `.factory/regression-state.json` and mutates it after every qualifying tool call. The same `host::write_file` capability model applies to a new STATE.md-scoped PostToolUse plugin.
- PostToolUse plugins can also resolve caller identity via `exec_subprocess` (LOW fix, v1.1 — precedent corrected from an unnamed "multiple registry entries" claim to a named one): `verify-factory-lock` itself proves the `git config user.email` call pattern works from within the WASM sandbox (it is a PreToolUse plugin, not PostToolUse, but its `exec_subprocess` capability declaration and `GuardCallbacks` injection pattern are what the new PostToolUse stamper and the amended `precompact-flush` (Decision 3, below) both reuse); `precompact-flush` (`crates/hook-plugins/precompact-flush/`, registered `PreCompact`, not `PostToolUse`) already declares an `[hooks.capabilities.exec_subprocess]` block with `binary_allow = ["git"]` and `env_allow = ["HOME", "GIT_CONFIG_GLOBAL", "XDG_CONFIG_HOME", "PATH", "SSH_AUTH_SOCK"]` — a superset of `verify-factory-lock`'s own `env_allow`, confirming no new registry capability is required to add a `git config user.email` call to `precompact-flush`'s existing subprocess surface.

## Decision

We will move both wall-clock fields from agent-authored to **hook-authored**, via a new native WASM **PostToolUse** plugin, and correspondingly retire the PreToolUse detector that exists only to catch agents failing to author them by hand.

1. **New plugin `stamp-state-timestamp`** (`crates/hook-plugins/stamp-state-timestamp/`, SS-04 Plugin Ecosystem), registered as a `PostToolUse` hook matching `^(Edit|Write|MultiEdit)$`, capability-scoped to `.factory/STATE.md` only (mirroring the existing `read_file`/`write_file` `path_allow` pattern used by `regression-gate` and the `read_file` pattern used by `verify-state-timestamp-refresh`). After every qualifying tool call that actually landed a write to `.factory/STATE.md`, the plugin:
   - **(a) Unconditionally re-stamps `timestamp:`** to `chrono::Utc::now()` formatted as RFC-3339 UTC (`YYYY-MM-DDTHH:MM:SSZ`, matching the existing frontmatter format produced by `factory-lock-write.sh`'s `_epoch_to_iso` helper). This field carries no identity concern — advancing it is safe regardless of who wrote the file — so it is stamped on every invocation with no gating. **Insertion point (LOW fix, v1.1):** the stamper MUST locate and rewrite the **first** `timestamp:` line found in the open frontmatter region (between the opening `---` and the closing `---`), mirroring `factory-lock-write.sh`'s own first-match awk pattern (its `_update_expires_at` helper's single-target `fence==1 && /^factory_lock:/`-then-inner-match rewrite style) — not a global replace-all, so a `timestamp:`-shaped string that happens to appear in the STATE.md body (outside frontmatter) is never touched.
   - **(b) Conditionally renews `factory_lock.expires_at`** via a new shared pure function, `factory_lock::renew_lock_if_holder<F, I>(content: &str, resolve_identity: I, now_fn: F) -> Result<(RenewOutcome, Option<SkipReason>), LockError>` where `F: Fn() -> DateTime<Utc>` and `I: FnOnce() -> IdentityResolution` (Work Spec — new addition to the existing `factory-lock` crate, alongside today's identity-blind `renew_lock`). **F-001, v1.4 — signature decisively corrected:** v1.1–v1.3 declared this function's return type as the bare tuple `(RenewOutcome, Option<SkipReason>)` while simultaneously requiring the malformed-`expires_at` branch (below) to return `Err(LockError::Malformed(..))` — impossible for a bare tuple, and `SkipReason` has no `Malformed` variant to substitute. This revision resolves the contradiction: the function returns `Result<(RenewOutcome, Option<SkipReason>), LockError>`, mirroring the existing `renew_lock_with_now -> Result<RenewOutcome, LockError>` it wraps. **F-001, v1.4 — identity parameter decisively made lazy, not eager:** v1.1–v1.3 also described `caller_identity: IdentityResolution` as an already-resolved value "supplied by the effectful caller" — which cannot satisfy this same Decision's own "without calling `exec_subprocess`" guarantee for the malformed and already-expired branches (an already-resolved value implies `exec_subprocess` already ran, unconditionally, before this function was ever invoked). The parameter is corrected to `resolve_identity: I where I: FnOnce() -> IdentityResolution` — a caller-supplied closure (the WASM plugin's `|| classify_identity_resolution(host::exec_subprocess(["git","config","user.email"]))`, mirroring the existing `now_fn` injectable-clock pattern `renew_lock_with_now` already uses) that `renew_lock_if_holder` invokes **at most once, and only when the decision tree actually reaches the identity-comparison step** — i.e., only when `holder` is non-empty, `expires_at` parses, and `now < expires_at`. `IdentityResolution` itself is unchanged: one of `Resolved(String)` (the trimmed caller email) or `Failed(String)` (the resolution error, e.g. `exec_subprocess` error, non-zero exit, empty stdout — see F-006, Decision 2 below, for where this (exit_code, stdout) → `IdentityResolution` classification is actually implemented, as a single shared function the closure calls, rather than being re-derived per call site). The function's decision tree evaluates, in this order — **holder-present → malformed(skip, no exec) → already-expired(skip) → identity-match (`resolve_identity()` called here, and only here)** (F-004, v1.3 — corrected: v1.1/v1.2 labeled this order "expired-check → holder-present → identity-match," which both omitted the malformed-`expires_at` arm from the label entirely and put the expiry check ahead of the presence check; the detailed bullets below, and all three downstream BCs — BC-4.17.001, BC-7.07.001, BC-5.40.001 — have always specified holder-present → malformed → already-expired → identity-match; this revision restates the label to match the detail, not the reverse):
     - **No-lock-held check, evaluated FIRST via `renew_lock_if_holder`'s own call to `flp::parse_factory_lock(content)`:** `Ok(None)` — the `factory_lock` key is absent from the frontmatter, or present but fully null/empty with no sub-fields at all (`crates/factory-lock-parse/src/lib.rs`'s own `Ok(None)` arms) — means no lock is held; `renew_lock_if_holder` returns `Ok((RenewOutcome::NoOp, None))` (F-001, v1.4 — restated inside the `Result`/`Option` wrapper established above), without evaluating malformed-ness, expiry, or identity at all — `resolve_identity` is never called. **Corrected, F-P56-001, v1.23:** prior revisions mislabeled this "if `holder` is empty" and claimed it was "inherited from `renew_lock`'s existing presence-precheck" — both wrong. `flp::parse_factory_lock` never returns `Ok(Some(LockState { holder: "", .. }))`: an empty-string `holder`, or an absent `holder` with `locked_at`/`expires_at` present, is a structural defect that function's own holder-validation match arm rejects with `Err(MalformedLockBlock("factory_lock.holder is empty string"))` / `Err(MalformedLockBlock("factory_lock.holder field is absent"))` — routing to case 1 below, `Err(LockError::Malformed(msg))`, not this 0th no-lock-held case. `renew_lock`'s own presence pre-check (`has_factory_lock_key`, `crates/factory-lock/src/lib.rs`) tests only whether the literal `factory_lock:` key line is present in the frontmatter — it never inspects `holder`'s value — so it cannot be the source of an "empty holder → NoOp" behavior; `renew_lock` itself routes an empty-string holder through `parse_factory_lock` to `Err(LockError::Malformed)`, exactly as `renew_lock_if_holder` does.
     - **Malformed-`expires_at` reconciliation, evaluated SECOND, before any expiry check or identity resolution (F-008, v1.1; corrected F-P13-001, v1.9):** if the `factory_lock` block's `expires_at` sub-field is present but unparseable as ISO-8601 (EC-007), `renew_lock_if_holder` MUST return `Err(LockError::Malformed(msg))` **without calling `resolve_identity` (hence without triggering `exec_subprocess`) at all** (F-001, v1.4 — the `Err(..)` variant is now type-valid, since the function's return type is the `Result`-wrapped tuple established above, not the bare tuple v1.1–v1.3 declared; the lazy `resolve_identity` closure is what makes "without calling `exec_subprocess`" literally true, rather than merely aspirational) — the same no-exec-on-skip guarantee the already-expired precheck below gives for the expired case. **This `Err` is produced by a NEW check `renew_lock_if_holder` layers ABOVE the unchanged `renew_lock_with_now` path, not by the existing `renew_lock`/`renew_lock_with_now` itself (F-P13-001, v1.9 — corrected; struck the previously inaccurate parenthetical "(and the existing `renew_lock`)", which wrongly implied the wrapped function also returns this `Err` for a date-unparseable value):** `renew_lock_with_now` (`crates/factory-lock/src/lib.rs`, unchanged by this Decision) never date-parses `expires_at` at all — it treats the sub-field as an opaque `String` and only byte-compares it (its existing Step 4 spurious-renewal guard / Step 5 `rewrite_expires_at`); its own `LockError::Malformed` is surfaced only via the wrapped `parse_factory_lock`'s `MalformedLockBlock` and fires ONLY for STRUCTURAL defects — a missing/empty `expires_at` field or a missing closing fence — NEVER for a structurally-present-but-date-unparseable value such as `"not-a-date"`. Left to `renew_lock_with_now` alone, a structurally-present-but-ISO-unparseable `expires_at` falls through to the function's existing compute-and-write path and returns `Ok(RenewOutcome::Renewed(new_content))` — i.e., it would **silently rewrite** the malformed value to a fresh future timestamp, exactly the repair/silent-relock hazard this bullet exists to forbid (see the divergent-liveness-reads paragraph immediately below). `renew_lock_if_holder` therefore layers a NEW `factory_lock_parse::parse_iso8601` check on top of the unchanged `renew_lock_with_now` sequence, specifically to catch this case before it ever reaches that silent-rewrite path; the case-1 TRIGGERING CONDITION (ISO-8601 unparseability of a present `expires_at`) is RE-DERIVED at this wrapper layer, NOT propagated or inherited from `renew_lock_with_now` — the two functions share the `LockError::Malformed` error TYPE (the same enum variant), not a shared derivation of WHEN it fires. (`verify-factory-lock`'s own `parse_iso8601` is a separate, local function of that plugin's crate, distinct from the canonical `factory_lock_parse::parse_iso8601` the new wrapper check above uses — see Decision 2/F-004's precedent for pinning a single canonical shared-crate home to a symbol, applied here to `parse_iso8601` as well.) `verify-factory-lock`'s own `parse_iso8601` failure path treats an unparseable `expires_at` as **effectively unlocked** (PC4/EC-005 fail-open — the guard cannot evaluate `is_expired` and defaults to `Continue` for any caller). A stamper that "fixed" the same malformed value by writing a fresh future timestamp would silently convert a state `verify-factory-lock` reads as unlocked into one that is actually re-locked for another 45 minutes with no caller ever having legitimately re-acquired it — a divergent-liveness-reads defect. The stamper must read malformed-`expires_at` the same way the guard does: **not a lock it may renew**, only a schema defect it must warn about and leave alone (advisory `log_warn`, no write). **Both call sites map `Err(LockError::Malformed(msg))` identically (F-001, v1.4):** `host::log_warn` with the message, no `host::write_file`, no block — for `precompact-flush` specifically, this also means the flush proceeds unblocked (matching its pre-existing BC-7.07.001 EC-012/PC3 malformed-downgrade requirement, now literally satisfiable by this `Result`-returning signature rather than contradicted by it).
     - **Already-expired precheck, evaluated THIRD, after the malformed check has passed (so `expires_at` is confirmed parseable) and before any identity resolution is attempted:** if `holder` is non-empty, `expires_at` parses, and `now >= expires_at` (the identical expiry test `verify-factory-lock`'s PC2 `LockExpired` already applies) → `Ok((RenewOutcome::NoOp, Some(SkipReason::AlreadyExpired)))` (F-001, v1.4 — restated inside the `Result` wrapper), **without calling `resolve_identity` (hence without triggering `exec_subprocess`) at all.** An already-expired self-held lock is never renewed or resurrected. This aligns with `verify-factory-lock`'s own self-eviction semantics: once `now >= expires_at` the lock is free for takeover by **any** caller (PC2), so the renewal gate must not silently re-materialize it just because the current writer's git email happens to still equal the stale `holder` (e.g., a brand-new session on the same laptop under the same git identity, which never itself ran `/factory-lock`). `SkipReason` gains this third variant alongside `NotHolder` and `IdentityResolutionFailed` below. **Accepted consequence — "keep-alive boundary starvation" (folded in, v1.3):** a session that legitimately holds the lock and is mid-edit exactly as `expires_at` ticks past `now` receives `AlreadyExpired`, not a renewal — its own in-flight edit does not extend its lock. This is by design, not an oversight: the anti-resurrection guarantee this precheck exists to provide (Decision 5's Rationale — an already-expired lock must be free for **any** caller to take over, never silently re-materialized for the stale holder) is incompatible with also special-casing "but renew it if the still-in-flight caller happens to be the original holder," since `renew_lock_if_holder` cannot distinguish "the original holder's own late-arriving edit" from "a new session that merely shares the stale holder's git email" (F-010) — both present as the same `Resolved(email) == holder` shape. The mitigation is operational, not architectural: a burst should renew well before the 2700s TTL lapses (the stamper renews on every qualifying write, not just once), so a holder whose single edit genuinely spans the entire TTL window is already an outlier the existing `factory-lock-write.sh renew` break-glass path (Decision 3's "one intentionally identity-blind path" note) remains available to recover from.
     - **Not expired — call `resolve_identity()` (the ONLY point in the decision tree where it is invoked) and compare, evaluated FOURTH and LAST:**
       - `Resolved(email)` and `email == holder` (byte-equal, both sides passed through the canonical trim — see identity-model note below) → proceed with the existing renewal computation, returning `Ok((RenewOutcome::Renewed(new_content), None))` on a genuine advance, or `Ok((RenewOutcome::NoOp, None))` on the pre-existing byte-identical same-wall-clock-second spurious-renewal guard (`renew_lock_with_now`'s existing Step 4, F-007, unchanged by this Decision) — both are the **success** case: identity matched, renewal was actually attempted.
       - `Resolved(email)` and `email != holder` → `Ok((RenewOutcome::NoOp, Some(SkipReason::NotHolder)))` (F-001, v1.4 — restated inside the `Result` wrapper). This is the **expected, correct** outcome when a non-holder caller was legitimately let through by `verify-factory-lock`'s PC2 (`LockExpired`) — `expires_at` is left untouched, exactly as v1.0 specified.
       - `Failed(reason)` → `Ok((RenewOutcome::NoOp, Some(SkipReason::IdentityResolutionFailed { reason, holder: lock_state.holder.clone(), locked_at: lock_state.locked_at.clone(), expires_at: lock_state.expires_at.clone() })))` (F-001, v1.4 — restated inside the `Result` wrapper; **F-P21-001, v1.10 — `SkipReason::IdentityResolutionFailed` corrected from a bare-`String` tuple variant to this struct variant,** carrying the `lock_state: LockState` `renew_lock_if_holder` already parsed, via its own call to `flp::parse_factory_lock`, at the holder-present step above (F-P25-001, v1.11 — type corrected from the previously-cited `FactoryLock`; `LockState` is `flp::parse_factory_lock`'s actual `Ok(Some(..))` payload type — see the canonical five-case table's note below for the full type/sourcing correction) — see the canonical five-case table's note and Decision 4 below for why). This is the **ambiguous** case (the caller might genuinely be the holder, but identity could not be confirmed) that Decision 4 (below) makes observable.

     **F-001, v1.4 — canonical five-case return-value table** (the contract both call sites and the downstream BCs align to):

     | # | Condition | Return | `resolve_identity()` invoked? |
     |---|---|---|---|
     | 1 | Malformed `expires_at` (holder present) | `Err(LockError::Malformed(msg))` | No |
     | 2 | `AlreadyExpired` (holder present, `expires_at` parses, `now >= expires_at`) | `Ok((RenewOutcome::NoOp, Some(SkipReason::AlreadyExpired)))` | No |
     | 3 | `NotHolder` (not expired, resolved email ≠ holder) | `Ok((RenewOutcome::NoOp, Some(SkipReason::NotHolder)))` | Yes |
     | 4 | `IdentityResolutionFailed` (not expired, resolution failed) | `Ok((RenewOutcome::NoOp, Some(SkipReason::IdentityResolutionFailed { reason, holder, locked_at, expires_at })))` — the three non-`reason` fields are `lock_state.holder`/`.locked_at`/`.expires_at`, already parsed at the holder-present step, not re-derived (F-P21-001, v1.10) | Yes |
     | 5 | Success (not expired, resolved email == holder) | `Ok((RenewOutcome::Renewed(new_content), None))`, or `Ok((RenewOutcome::NoOp, None))` on the same-second byte-identical guard | Yes |

     (A sixth, pre-existing, zero-th case — `flp::parse_factory_lock` returns `Ok(None)`, i.e. the `factory_lock` block is entirely absent or fully null/empty (no sub-fields at all), no lock held at all — returns `Ok((RenewOutcome::NoOp, None))` without reaching any of the five numbered checks above; unchanged from today's `renew_lock` and not itself one of this Decision's five outcomes. **Corrected, F-P56-001, v1.23:** this zero-th case is narrower than "`holder` empty" as prior revisions stated. An empty-string `holder`, or an absent `holder` with `locked_at`/`expires_at` present, is `Err(MalformedLockBlock(..))` from `flp::parse_factory_lock` (confirmed: `crates/factory-lock-parse/src/lib.rs`'s holder-validation match arm), which routes to case 1 in the table above — `Err(LockError::Malformed(msg))`, advisory `host::log_warn`, no write, `resolve_identity` never called — not this zero-th case. The outcome is behaviorally benign either way (no renewal, no identity check, no write), but case 1 surfaces the anomaly via advisory while the zero-th case passes silently; the two are not identical.)

     **F-P21-001, v1.10 — `SkipReason::IdentityResolutionFailed` enriched to carry the lock snapshot, closing a data-flow gap in Decision 4's event.** Decision 4 (below) requires both call sites to emit a `factory.lock.renewal_indeterminate` event carrying `holder`/`locked_at`/`expires_at` alongside the `resolution_error` reason. Prior to this revision, case 4's return value was the bare-`String` variant `SkipReason::IdentityResolutionFailed(reason)` — which gives the caller `reason` only; `RenewOutcome::NoOp` carries nothing. Neither `stamp-state-timestamp` nor `precompact-flush` independently re-parses the `factory_lock:` block to source the three lock fields — doing so would violate this Decision's own single-source design (`renew_lock_if_holder` is the one function that parses the lock; call sites consume its return value, they do not re-derive it) and would let the two call sites drift if one implementer re-parsed and the other left the fields blank. `SkipReason::IdentityResolutionFailed` is therefore corrected to a struct variant — `IdentityResolutionFailed { reason: String, holder: String, locked_at: String, expires_at: String }` — populated from the same `lock_state: LockState` that `renew_lock_if_holder` already holds in scope by the time the decision tree reaches case 4. **Type and sourcing corrected (F-P25-001, v1.11):** this `lock_state` is `flp::parse_factory_lock`'s `Ok(Some(lock_state))` result (the `LockState` type `factory-lock-parse` actually exports — NOT `FactoryLock`, the distinct struct `crates/factory-lock`'s own `parse_lock` wrapper produces by field-by-field conversion; the two types have byte-identical field sets — `holder`/`locked_at`/`expires_at` — but are not the same type and `flp::parse_factory_lock` never yields the latter). Nor is this `lock_state` reachable as "Step 2 of the wrapped `renew_lock_with_now` sequence," as prior revisions of this ADR stated: `renew_lock_with_now`'s own Step-2 parse binds a **private local** inside that function's body, which a wrapping `renew_lock_if_holder` cannot reach into. `renew_lock_if_holder` instead performs its **own** independent call to `flp::parse_factory_lock(content)` — once, before evaluating any of its holder-present/malformed/already-expired/identity-match checks — and it is *this* self-sourced `lock_state: LockState` the decision tree carries forward to case 4. The identity-comparison step is reached only after the holder-present, malformed, and already-expired checks have all passed, each of which requires `renew_lock_if_holder`'s own `lock_state` to already be parsed. Populating the three fields costs no additional parse and no additional I/O beyond this one self-parse; it is a pure struct-literal construction from data already on the stack. Both call sites then emit the event by destructuring the returned variant directly — never by independently reading or parsing `.factory/STATE.md`'s `factory_lock:` block a second time — making the sourcing mechanism unambiguous and identical at both call sites by construction, not by convention. (This correction is orthogonal to, and does not disturb, the single-source/no-re-parse guarantee itself: it is still true that neither `stamp-state-timestamp` nor `precompact-flush` ever parses `factory_lock:` — only that the parse `renew_lock_if_holder` performs is its own, not an artifact of the wrapped function.)
   - **Tool-write-success check (F-013, v1.1):** the stamper only proceeds to stamp when the triggering `PostToolUse` payload indicates a landed write, not a failed tool invocation. Concretely: if `payload.tool_response` is `null`/absent, or is a JSON object carrying a top-level `"error"` key with a non-null value, the stamper treats the call as failed and returns `Continue` without touching STATE.md. This generic, tool-name-independent check (rather than guessing at Edit/Write/MultiEdit-specific success-shape field names, which are not pinned down anywhere in `crates/hook-sdk`) covers the common failure shapes (Edit `old_string` not found, Write permission denied). **Accepted residual (explicitly, not deferred):** if a tool fails in a way that returns a `tool_response` with no `error` key and no other failure signal, the stamper will re-stamp `timestamp:` on what is effectively a no-op edit. This is bounded and self-correcting — a single spurious wall-clock advance with no other content change, corrected by the very next real edit — and does not violate any BC-5.40.001 invariant (nothing requires `timestamp:` to change if and only if other content changed). It is accepted here rather than engineered around because a fully reliable success signal is not available in the current ABI without inventing tool-specific field-name assumptions that would themselves be a drift risk.
   - Both arms share a single `host::read_file(".factory/STATE.md")` **and a single, composed `host::write_file`** — not two independent per-arm writes (**F-P10-001, HIGH, v1.8 — corrected:** v1.0–v1.7 described the two arms as "independently gated ... each with its own `host::write_file` call (or no-op), not a single joint success/failure." That is a deterministic lost-update: `renew_lock_if_holder` is a *pure* function fed whatever `content: &str` it is called with; if that argument is the SAME shared read PC1 also reads — which still carries the pre-PC1 `timestamp:` value — then a `Success` outcome's `RenewOutcome::Renewed(new_content)` (the FULL file content, only `expires_at` changed — confirmed at `crates/factory-lock/src/lib.rs`'s `renew_lock_with_now` Step 5/`rewrite_expires_at`) does not know about, and therefore does not carry forward, whatever PC1 already wrote. On the primary held-lock-mid-burst path — both arms fire — PC1's `write_file` advances `timestamp:` to T1 on disk; PC2's subsequent `write_file` of its own `new_content`, built from the stale T0 read, then overwrites disk back to T0 — clobbering PC1's guarantee on exactly the writes where a lock is held. The fix is not to change `renew_lock_if_holder`'s signature or return shape — both are correct and unchanged — but to change what the stamper FEEDS it and to stop performing two writes):
     1. **Apply PC1's transform first, in memory, to the shared read.** If the `timestamp:` anchor is present, Decision 1(a)'s first-match rewrite produces `content_after_pc1` (the shared read with only its `timestamp:` line advanced). If the anchor is absent (missing-anchor case below), `content_after_pc1` is identical to the shared read — PC1 contributes no change.
     2. **Feed `content_after_pc1` — never the raw shared read — into `renew_lock_if_holder`:** `renew_lock_if_holder(content_after_pc1, resolve_identity, now_fn)`. Because PC1 only ever rewrites the `timestamp:` line and never touches the `factory_lock:` block, `content_after_pc1` parses identically to the raw read for every input `renew_lock_if_holder`'s own decision tree (Decision 1(b), unaffected by this fix) inspects — feeding it PC1's output changes nothing about which of the five cases fires, only what a `Renewed` outcome's `new_content` contains.
     3. **Perform exactly ONE `host::write_file`,** its content selected as follows:

        | PC1 fired (anchor present)? | PC2 result | Content written |
        |---|---|---|
        | Yes | `Ok((Renewed(new_content), _))` | `new_content` — carries BOTH the timestamp advance and the `expires_at` renewal, because PC2 rewrote `content_after_pc1`, not the raw read |
        | Yes | `Ok((NoOp, _))` or `Err(Malformed(..))` | `content_after_pc1` — PC1's timestamp advance stands alone; a renewal skip or malformed-lock error never suppresses it (per-arm fail-open scoping below, unchanged) |
        | No (missing-anchor case) | `Ok((Renewed(new_content), _))` | `new_content` — PC2's result, computed against the raw read since PC1 contributed nothing |
        | No | `Ok((NoOp, _))` or `Err(Malformed(..))` | **no write** — neither arm produced a change |

        A `Malformed`/`IdentityResolutionFailed` PC2 outcome still emits its own advisory (`host::log_warn` / the Decision 4 event) independently of which row of this table applies — the advisory and the write are separate concerns; the advisory never gates whether row 2's `content_after_pc1` write happens.

     **Call-site asymmetry (F-P10-001, v1.8):** this composition requirement is specific to `stamp-state-timestamp` — the one call site with two concerns (PC1 + PC2) sharing one read and one write. `precompact-flush` (Decision 3) has only ONE concern, renewal, so it is correct, and unaffected by this fix, for it to feed `renew_lock_if_holder` its own single `host::read_file` result directly, with no prior transform to preserve — `RenewOutcome::Renewed`'s full-file-content return shape is exactly right there (single caller, single write, nothing else has touched the content first). The lost-update was never in `renew_lock_if_holder` itself; it was in the stamper's call site feeding the function the wrong INPUT.

     Per-arm fail-open scoping is otherwise unchanged (F-002, v1.4) and now maps onto the table above:
     - **Fully-structural failures — suppress BOTH arms:** `host::read_file` error, non-UTF-8 content, or unparseable/malformed frontmatter (no opening/closing `---` fence at all, or the fence cannot be located). Neither arm has any content to operate on, so both PC1 (`timestamp:` stamping) and PC2 (`factory_lock.expires_at` renewal via `renew_lock_if_holder`) are skipped, and the single composed `host::write_file` is never attempted.
     - **Missing `timestamp:` anchor line — suppresses ONLY the PC1 timestamp-stamping arm** (the "No" rows of the table above: `content_after_pc1` equals the raw read). If the frontmatter otherwise parses (opening/closing `---` fence located, content is valid UTF-8) but no existing `timestamp:` line is found to rewrite in place, Decision 1(a)'s first-match rewrite has nothing to target — this ADR does not mandate line-insertion recovery for a wholly absent anchor, only in-place rewrite of an existing line — so PC1 is skipped for that invocation. This has **zero effect** on PC2: `renew_lock_if_holder` operates entirely on the separate `factory_lock:` block and neither reads, writes, nor otherwise depends on the `timestamp:` line's presence in any way. PC2 MUST still be evaluated against whatever `content_after_pc1` resolves to, and renewed if applicable, even when PC1 is suppressed for this reason — the two arms remain **independently gated** (each still fires, skips, or errors on its own conditions), but per the fix above their outputs are now composed into the single write in the table, never raced as two separate `host::write_file` calls.
   - A stamping failure — on either arm, independently — never blocks or corrupts the agent's original write; it just means the next qualifying write attempt (or, for a logged-but-not-written `Malformed`/`IdentityResolutionFailed` outcome, the advisory) tries again.

2. **Identity model: email-based, with two resolution bugs fixed (human decision 1, v1.1).** The identity key stays `git config user.email` — no session-scoped or process-scoped identity is introduced (see Rationale §"Residual risk" for what this does and does not guarantee). Two defects the pass-1 adversarial review found in how that identity is resolved and compared are fixed as part of this Decision, not deferred to the implementer's discretion:
   - **F-004 — canonical trim.** `factory-lock-write.sh`'s `acquire` mode strips the git-config output with `tr -d '\n'` (its `HOLDER="$(git config user.email 2>/dev/null | tr -d '\n')"` assignment); `verify-factory-lock`'s comparison uses its own `trim_git_email` helper (`raw.trim_end().to_string()`). These are **declared equivalent for the git-email domain** (a `user.email` config value is a single line with no embedded newlines by construction — `tr -d '\n'` removing all newline bytes and `trim_end()` removing only trailing whitespace produce byte-identical output for any single-line input with at most a trailing newline, which is the only shape `git config user.email` ever emits). The new `stamp-state-timestamp` plugin and the amended `precompact-flush` (Decision 3, below) MUST both call `verify-factory-lock`'s `trim_git_email` function (promoted to a shared location — Work Spec: the `factory-lock` crate, the SAME shared module `renew_lock_if_holder` (this Decision) and `classify_identity_resolution` (F-006, below) live in — so all three WASM call sites — `verify-factory-lock`, `stamp-state-timestamp`, `precompact-flush` — use the literal same function, not three independently-typed re-implementations; F-P7-001, v1.7, decisively pins the single home this bullet previously left as a two-option choice) rather than re-deriving the trim logic. If the bash side's algorithm ever needs to change to something not equivalent to `trim_end()` for the git-email domain (e.g., to tolerate a multi-line value), the WASM-side canonical trim must change in lock-step — this is a standing cross-language invariant, not a one-time fix.
   - **F-005 — identical config-scope resolution.** Acquire-time resolution runs in bash (`factory-lock-write.sh acquire`, invoked as a `Bash` tool call from the project root) and renew-time resolution runs inside the WASM sandbox (`exec_subprocess(["git","config","user.email"])`, `env_allow=[HOME, GIT_CONFIG_GLOBAL, XDG_CONFIG_HOME]`). These are confirmed, by inspection of `crates/factory-dispatcher/src/host/exec_subprocess.rs` (the subprocess-spawn call site applies `command.current_dir(cwd)`) and `crates/factory-dispatcher/src/invoke.rs` (`host_ctx.cwd` is bound to `CLAUDE_PROJECT_DIR`, the project root), to resolve `git config user.email` **from the same working directory** — the project root — in both paths. Because git's config-value discovery for an unqualified `git config <key>` is **directory-tree-based** (walk up from cwd to find `.git/`, then apply local → global → system precedence), not environment-variable-based, `env_allow=[HOME, GIT_CONFIG_GLOBAL, XDG_CONFIG_HOME]` is sufficient to reproduce the same repository-local-vs-global resolution the bash path gets for free from running in the same directory — **no `GIT_DIR` or additional env var is required** for this equivalence to hold. This closes the gap the pass-1 review flagged: a project using a repo-local `git config --local user.email` override (distinct from the operator's global email) resolves to the **same** value at acquire time and at every renewal time, because both paths query the same `.git/` from the same cwd. **Standing invariant:** any future change to how the dispatcher spawns `exec_subprocess` (or to how bash tool calls are invoked) that decouples either path's cwd from the project root breaks this equivalence silently; the Work Spec (below) adds a regression test — set a repo-local `user.email` distinct from the global value, and assert both the bash-invoked acquire path and a WASM-mocked renew path resolve to the repo-local value — specifically to catch that class of regression. **`PostToolUse`-path cwd dependence (folded in, v1.3):** this entire equivalence argument reduces to "`host_ctx.cwd` is non-empty and bound to the project root at the moment `exec_subprocess` runs." `verify-factory-lock` already proves this holds on the `PreToolUse` dispatch path; this ADR is the first design to run an identity-resolving `exec_subprocess` call on the **`PostToolUse`** path (`stamp-state-timestamp`) and, via Decision 3, the **`PreCompact`** path (`precompact-flush`) — two dispatch points this equivalence claim had not previously been exercised against. The Work Spec's regression test above MUST therefore assert `host_ctx.cwd` non-emptiness and project-root binding specifically on the `PostToolUse` invocation path the new stamper uses (not only re-confirm the pre-existing `PreToolUse` case `verify-factory-lock` already covers) — an empty or unbound `cwd` on that path would silently degrade `git config user.email` to global-only resolution, reintroducing the repo-local-override gap this bullet exists to close, specifically for the mechanism this ADR adds.
   - **F-006 — shared `(exit_code, stdout) → IdentityResolution` classifier (folded in, v1.3, MED).** As drafted in v1.1/v1.2, `IdentityResolution` was described only as a value "supplied by the effectful caller" — leaving the actual classification of an `exec_subprocess` result (`(i32, String, String)` — exit code, stdout, stderr — or a top-level `exec_subprocess` error) to be re-derived independently inside each WASM plugin. The pass-2 review found this defeats the "shared function guarantees identical behavior" claim this Decision otherwise makes for `trim_git_email` and `renew_lock_if_holder`: `precompact-flush`'s existing injectable closure signature (`ES: Fn(&str, &[&str]) -> Result<(i32, String, String), String>`, Decision 3) and the new `stamp-state-timestamp`'s (as-yet-unspecified) signature are not even shaped the same, so two independent re-implementations of "what counts as a resolved vs. failed identity" were free to drift — including the single most load-bearing rule in the whole classification: **a zero exit code with empty stdout is a `Failed` resolution, not a `Resolved("")`.** (A caller with no configured `user.email` returns exit 0 and empty stdout from `git config user.email`; treating that as `Resolved("")` would compare an empty string against a non-empty `holder` on every check, always yielding `NotHolder` — the wrong, silently-non-alarming outcome — instead of the correct `IdentityResolutionFailed`, which is the only outcome Decision 4 makes observable.) This ADR now mandates a single function, `factory_lock::classify_identity_resolution(exec_result: Result<(i32, String, String), String>) -> IdentityResolution`, defined in the **same** shared module as `trim_git_email` and `renew_lock_if_holder` (Work Spec: the `factory-lock` crate). Its rule, applied in this order: an `Err(exec_error)` (the `exec_subprocess` call itself failed — binary not found, timeout, sandbox denial) → `Failed(exec_error)`; `Ok((exit_code, _, stderr))` with `exit_code != 0` → `Failed("git config user.email exited {exit_code}: {stderr}")`; `Ok((0, stdout, _))` with `trim_git_email(stdout)` empty → `Failed("git config user.email returned empty stdout")`; `Ok((0, stdout, _))` with `trim_git_email(stdout)` non-empty → `Resolved(trim_git_email(stdout))`. Both `stamp-state-timestamp` and the amended `precompact-flush` MUST call this one function on their raw `exec_subprocess(["git","config","user.email"])` result rather than pattern-matching the tuple themselves. **Test-vector coverage mandated (Work Spec):** `factory-lock`'s unit test module MUST cover all four input shapes as explicit test vectors — `exec_subprocess`-level error (including a timeout-shaped error string), non-zero exit code, zero-exit-empty-stdout, and zero-exit-non-empty-stdout — and both `stamp-state-timestamp`'s and `precompact-flush`'s own test suites MUST assert they invoke this shared classifier (not an inline reimplementation) on their respective `exec_subprocess` call sites.
   - **F-010 — residual risk, accepted.** Email is not a session identity. Two sessions authenticated under the same git email — same laptop, two terminal tabs; or a CI runner and a human sharing a service account — are indistinguishable to every check in this system (`verify-factory-lock`'s PC3, the new stamper's holder-match, and the amended `precompact-flush`'s holder-match all reduce to the same string comparison) and can each renew, or be treated as holding, the other's lock. This is **not a regression introduced by this ADR** — it is the pre-existing property of an email-keyed lock, made more visible because renewal becomes automatic. It is accepted, not engineered around, because introducing a stronger identity (session/process-scoped token) is a materially larger design (BC-6.23.001 acquire/release semantics would need to change) that is out of scope for a keep-alive-only ADR. Every "sole writer" / "only the holder renews" claim in this document is understood to mean **modulo email collision**.

3. **Extend the identity gate to `precompact-flush`'s renewal (human decision 2, v1.1) — the fourth un-gated renewal actor.** The pass-1 adversarial review found that this ADR's v1.0 "three current mechanisms" survey (Rationale, below) missed a fourth: `precompact-flush` (`crates/hook-plugins/precompact-flush/src/lib.rs`, registered `PreCompact`, priority 100) calls `factory_lock::renew_lock(&state_md_content)` at its Step 4 (module-doc "Canonical execution order," `//! 4. Check factory_lock: block via renew_lock(state_md_content)`) unconditionally — the existing `renew_lock` function gates only on **presence** of a non-empty `holder`, with **no identity check at all** (see `crates/factory-lock/src/lib.rs`'s `renew_lock_with_now` function). Left unamended, this ADR's central claim ("only the holder renews, mechanically enforced for the first time") would be false the moment a PreCompact event fires during a foreign-but-expired-and-since-reacquired-by-someone-else lock window, because `precompact-flush` would renew whatever `factory_lock` block happens to be on disk regardless of who is running the current session. We will:
   - Route `precompact-flush`'s Step 4 through the **same** `factory_lock::renew_lock_if_holder` function introduced in Decision 1(b) above — one canonical identity-gated renewal implementation shared by both the new `stamp-state-timestamp` plugin and the amended `precompact-flush`, rather than two independently-typed identity-comparison implementations that could drift.
   - `precompact-flush` resolves its own caller identity via `exec_subprocess(["git", "config", "user.email"])` before calling `renew_lock_if_holder` — the **same** git-subprocess call pattern it already uses for `git worktree list --porcelain` and `git -C <wt> add -A` (its `ES: Fn(&str, &[&str]) -> Result<(i32, String, String), String>` injectable closure signature in `run_plugin_with_mock_and_cwd` already threads `exec_subprocess` through; one more call is additive, not a new capability). Confirmed workable on the `PreCompact` event specifically: `precompact-flush` already performs three other `git` subprocess calls (`worktree list`, `add -A`, `diff --cached`) inside the very same `PreCompact`-triggered invocation, proving the WASM sandbox's `exec_subprocess` surface is live and unrestricted-by-event-type at that point in the plugin's execution.
   - **No new registry capability is required.** `precompact-flush`'s existing `[hooks.capabilities.exec_subprocess]` block (`binary_allow = ["git"]`, `env_allow = ["HOME", "GIT_CONFIG_GLOBAL", "XDG_CONFIG_HOME", "PATH", "SSH_AUTH_SOCK"]`) is already a superset of what `git config user.email` needs (see F-005 above — only `HOME`/`GIT_CONFIG_GLOBAL`/`XDG_CONFIG_HOME` matter for config resolution; `PATH`/`SSH_AUTH_SOCK` are already present for the push step).
   - **"Three current mechanisms" corrected to four** (Rationale, below, updated in place): `factory-lock-write.sh renew` (bash, manual, identity-blind by design since renewal there is a deliberate human/agent act), `verify-state-timestamp-refresh`'s Step 8 (being retired by Decision 5, below — never itself renewed anything, only detected staleness), the new `stamp-state-timestamp` (Decision 1, identity-gated from birth), and `precompact-flush`'s PreCompact renewal (pre-existing, was identity-blind, now identity-gated by this Decision). After this ADR, `factory-lock-write.sh renew`'s manual mode remains the **one** intentionally identity-blind path — because it is an explicit, deliberate human/agent-invoked act, not an automatic side effect of an unrelated tool call, the same tolerance-for-manual-unguarded-action reasoning the original Rationale gives for why today's laxity was acceptable applies to it unchanged.
   - **BC-7.07.001 amendment required** (Companion Amendments, below) — the identity gate on `precompact-flush`'s renewal step is a behavioral change to that plugin's contract, not merely an internal refactor, since it changes what `precompact-flush` does with a foreign lock block during a PreCompact event.

4. **Make renewal-should-have-fired-but-failed observable (human decision 3, v1.1).** Renewal stays best-effort/non-blocking — a failed or skipped renewal never blocks the agent's write or the PreCompact flush (unchanged from v1.0's friction-removal goal). But the one case that is genuinely dangerous to leave silent — `SkipReason::IdentityResolutionFailed` from Decision 1(b)/3 above, i.e. a **self-held lock is present** (non-empty `holder`) and the plugin's own identity resolution **failed** (as opposed to succeeded-but-mismatched, which is the correct, expected `NotHolder` outcome) — is now surfaced:
   - Both `stamp-state-timestamp` and the amended `precompact-flush`, on receiving `SkipReason::IdentityResolutionFailed { reason, holder, locked_at, expires_at }` from `renew_lock_if_holder` (F-P21-001, v1.10 — struct variant; all four fields are destructured directly from the returned variant, never independently re-parsed from `.factory/STATE.md`'s `factory_lock:` block — see the canonical five-case table's note above and the F-P21-001 paragraph following it), call `host::emit_event("factory.lock.renewal_indeterminate", &[("plugin", <plugin_name>), ("holder", holder), ("locked_at", locked_at), ("expires_at", expires_at), ("resolution_error", reason)])` (the `emit_event` wrapper at `crates/hook-sdk/src/host.rs`, event naming consistent with the existing `factory.lock.acquired`/`factory.lock.released`/`factory.lock.stolen` events from BC-6.23.001).    - The same code path also calls `host::log_warn` with a human-readable message ("RenewalIndeterminate: factory_lock held by {holder}, but this session's identity could not be confirmed ({reason}); expires_at was NOT renewed — if this session is the holder, the lock may expire mid-burst") so the condition is visible in the dispatcher's internal log even in an environment with no event-sink tooling configured.
   - This closes F-011 (silent mid-burst lock loss): previously, an identity-resolution failure during renewal was indistinguishable, from the outside, from a legitimate `NotHolder` skip or a healthy `Renewed` — an agent whose lock silently stopped renewing had no signal until the lock actually expired and a foreign write blocked it, confusingly, well after the root cause. Now the ambiguous case has its own event and log line the moment it first occurs.
   - **Non-goal:** this Decision does not add an event for the `NotHolder` case (successfully-resolved, correctly-not-renewed) — that is working-as-designed, not a failure, and emitting an event for every legitimate non-holder skip (e.g., during a `LockExpired` window with a new holder churning through many STATE.md edits) would be noise, not signal.

Under this ADR's own design, agents stop authoring `timestamp:`/`expires_at` by hand (Decision 1) — so if both entries are registered, **every** qualifying STATE.md write proposes a `timestamp:`/`expires_at` byte-identical to on-disk (the agent never advances them), which is precisely the staleness condition `verify-state-timestamp-refresh` exists to `Block` on. The write is blocked at `PreToolUse` and never lands; the `PostToolUse` stamper, which only ever runs after a tool call's write has already landed, **never executes**. This is not redundancy — it is a block-before-stamp regression that fails every STATE.md edit closed, and it is exactly the failure mode a "both present, ship in the same release, never split across two rc cuts" merge window (Rollout / Migration Note, below) could produce if the guard's deregistration and the stamper's registration land in the same release but the deregistration is accidentally dropped from the diff. A green CI pipeline gives no signal that this has happened unless the registry-invariant gate treats both-present as a hard failure symmetric with both-absent — which is why the gate is XOR, not OR.

## Rationale

**Why PostToolUse, not a smarter PreToolUse guard.** The `HookResult` ABI gives PreToolUse plugins exactly two useful outcomes: `Continue` or `Block`. There is no "continue, but here is the corrected payload" outcome. A PreToolUse guard can only ever be a better detector of agent forgetfulness — never a fix for it. Only a PostToolUse plugin, which runs after the tool's write has already landed on disk, can rewrite the two fields to their correct values, which is the actual goal ("agents never manage them and can't get them wrong").

**Why the identity gate on `expires_at`, when the current system doesn't have one.** This is the one place this ADR is *stricter* than the status quo, and it is deliberate. **Four** current mechanisms (corrected from v1.0's count of three, v1.1 — see Decision 3) were checked for a "renewal is holder-gated" invariant, and none of them actually provide one:
- `factory-lock-write.sh renew` performs no identity check at all — it renews `expires_at` unconditionally whenever a `factory_lock` block with an `expires_at` sub-field is present, regardless of who invokes the script. (Remains identity-blind by design after this ADR — see Decision 3's "one intentionally identity-blind path" note.)
- `verify-state-timestamp-refresh`'s Step 8 also performs no identity check — it only requires that whatever `expires_at` value is proposed differ, byte-for-byte, from on-disk; it does not care whether the proposed value came from the recorded holder or from someone else. (Retired by Decision 5.)
- `precompact-flush`'s `PreCompact` renewal (`factory_lock::renew_lock` call at its Step 4) also performs no identity check today — it renews `expires_at` for whatever `factory_lock` block is present, regardless of whose session is triggering the compaction event. **v1.0 of this ADR missed this fourth mechanism**; Decision 3 (v1.1) closes it by routing this call site through the same `renew_lock_if_holder` gate the new stamper uses.
- `verify-factory-lock`'s PC2 (`LockExpired`) deliberately allows **any** caller through once `now >= expires_at`, precisely so a hung/dead session cannot deadlock the branch forever. (This is a guard behavior, not a renewal path, and is untouched by this ADR.)

Put together, the current system's real invariant is weaker than "only the holder may renew" — it is "the write must land, and if it renews `expires_at` it must be to a genuinely new value," with no check on *whose* write that is. That is tolerable today only because the act of renewing is a **manual, deliberate** step (an agent literally runs `factory-lock-write.sh renew` or hand-edits the line) or, in `precompact-flush`'s case, an infrequent, single-branch, local-only operation whose blast radius has been small in practice — but is not *architecturally* small, which is exactly why Decision 3 closes it rather than leaving it as accepted risk. Automating renewal into something that fires on **every** qualifying write (or every compaction event) would otherwise change the risk profile: a non-holder writer who was legitimately let through during a `LockExpired` window (BC-4.13.001 PC2) would, on a naive "renew whenever a `holder` is present" design, silently resurrect and extend a foreign, dead holder's lock — a lock the same caller (or anyone else) was *just* told is expired-and-free. That is a strictly worse outcome than today's manual flow, where the renewal is at least a conscious act by whoever is following the state-manager burst discipline. The identity gate closes exactly this gap, and does so cheaply: `verify-factory-lock` already proves the `git config user.email` comparison pattern works in this WASM sandbox, so both the new stamper and the amended `precompact-flush` reuse it (via the shared `renew_lock_if_holder` function and the shared `trim_git_email` helper — see Decision 2/F-004) rather than inventing new, independently-typed comparisons. This also **operationalizes** BC-5.40.001 Invariant 1 ("state-manager is the sole writer" of the `factory_lock` block, modulo email collision per F-010) as a mechanical check rather than a documentary convention — now enforced uniformly across every automatic renewal path, not just the new one.

**Residual risk (F-010, v1.1).** The identity gate is an email-equality check, not a session-identity check. See Decision 2's F-010 sub-bullet for the accepted-risk disposition: two sessions sharing one git email are indistinguishable to this gate. Every occurrence of "sole writer," "only the holder renews," and "mechanically enforced" in this ADR should be read with that qualifier.

**Why the TTL must be sourced, not reinvented (F-006, v1.1 — corrected to name the real ground truth).** v1.0 of this ADR asserted a single canonical `TTL_SECONDS` constant already existed to source from; the pass-1 review found that ground truth is actually **three independently-typed literals**, none of them a shared canonical const: a bare `Duration::seconds(2700)` literal inside `factory_lock`'s `renew_lock_with_now` function (`crates/factory-lock/src/lib.rs`); a differently-named `LOCK_RENEWAL_TTL_SECS: u64 = 2700` constant in `precompact-flush` (`crates/hook-plugins/precompact-flush/src/lib.rs`); and `TTL_SECONDS=2700` in `factory-lock-write.sh`, declared non-configurable per S-17.01's AC-007 ("This constant MUST NOT be configurable by users."; BC-5.40.001 Invariant 2, "The TTL value is not configurable by users."). None of the three today is a re-export of a shared source — a silent drift risk the first time any one of them is edited without the other two. This ADR now mandates, not merely suggests: (a) a new `pub const TTL_SECONDS: u32 = 2700` defined once in the `factory-lock` crate (the crate all three existing sites either already depend on or logically should — `precompact-flush` already depends on `factory-lock` for `renew_lock`/`RenewOutcome`/`LockError`); (b) `factory_lock::renew_lock_with_now`'s bare `Duration::seconds(2700)` literal migrated to `Duration::seconds(TTL_SECONDS as i64)`; (c) `precompact-flush`'s `LOCK_RENEWAL_TTL_SECS` constant either removed in favor of importing `factory_lock::TTL_SECONDS` directly, or retained as a re-export — but **not** a blind `pub use factory_lock::TTL_SECONDS as LOCK_RENEWAL_TTL_SECS;` (folded in, v1.3): the three literals are not just independently-declared, they are **independently-typed** — canonical `factory_lock::TTL_SECONDS` is `u32`, `precompact-flush`'s existing `LOCK_RENEWAL_TTL_SECS` is `u64`, and `renew_lock_with_now`'s own `Duration::seconds(...)` argument is `i64` (already handled correctly by clause (b)'s explicit `as i64` cast above). A bare `pub use` re-export silently narrows every existing `u64`-typed use of `LOCK_RENEWAL_TTL_SECS` in `precompact-flush` to `u32`, which can fail to compile at an arithmetic call site expecting `u64` (or, worse, compile with an implicit lossy cast if one is inserted carelessly to fix the error) — a type-level break masquerading as a "just re-export the same value" refactor. The implementer MUST instead retype the migration site with an explicit cast, `pub const LOCK_RENEWAL_TTL_SECS: u64 = factory_lock::TTL_SECONDS as u64;` (or update the constant's every downstream use site to `u32` if `u64` was never actually load-bearing there — an implementer choice, but the cast must be explicit and reviewed either way, never an unexamined `pub use`); (d) `factory-lock-write.sh`'s bash-side `TTL_SECONDS=2700` left as a documented bash-side mirror with an explicit cross-reference comment pointing at the Rust canonical const (bash cannot import a Rust const, so this remains a manual-parity literal, not a build-time-generated one — a further follow-up that generates the bash literal from the same source at build time is not mandated here). **CI-gating drift check mandated, not manual (F-006 continued):** a CI check (Work Spec — a `cargo test` asserting `factory_lock::TTL_SECONDS == 2700` plus a `grep`-based script step in `.github/workflows/ci.yml` asserting `factory-lock-write.sh`'s `TTL_SECONDS=2700` literal is still exactly `2700`) MUST fail the build if the bash literal and the Rust canonical const diverge — replacing v1.0's unspecified "the implementer picks" framing with an enforced invariant.

**Why `timestamp:`/`expires_at`'s comparison semantics are `>=`, not strictly-greater, and "idempotent" is scoped precisely (F-007, v1.1).** v1.0's H1 title and the Verification Properties this ADR feeds (Companion Amendments, below) used "idempotent" and "strictly greater" language for both stamped fields at second-precision wall-clock resolution — but two writes to STATE.md within the same wall-clock second produce **byte-identical** `chrono::Utc::now().format("%Y-%m-%dT%H:%M:%SZ")` output, so "the new value is strictly greater than the old value" is unprovable (and false, as a byte-comparison claim) for same-second writes, on both fields. This ADR resolves the ambiguity by **decision**, not by upgrading precision: the comparison predicate for both `timestamp:` and `factory_lock.expires_at` is **`>=`** (new value not less than old value; same-second byte-identical writes are treated as a no-op-equivalent success, not a failure), and "idempotent" is scoped to describe **only the `expires_at` arm's existing byte-identical-suppression behavior** (`renew_lock`'s Step 4 spurious-renewal guard, which already suppresses a write when the recomputed `expires_at` is byte-identical to on-disk — unaffected by this correction, since that guard already used equality, not strict inequality). The `timestamp:` arm is **not** claimed idempotent — it is unconditionally re-stamped on every qualifying call (Decision 1(a)) and is expected to produce a new byte value on almost every real invocation; the rare same-second collision is accepted as a harmless no-op write, not a violated invariant. Sub-second (millisecond) precision was considered and rejected as unnecessary: no downstream consumer of `timestamp:` or `expires_at` parses sub-second precision, and adopting it would be a format change with no consumer benefit, purely to manufacture a "strictly greater" guarantee no test or BC actually depends on.

**Why takeover safety is preserved.** Auto-renewal fires only as a side effect of an **actual write** by the **recorded holder** (or, for `precompact-flush`, an actual PreCompact-triggered git operation by a session whose resolved identity matches the holder — Decision 3). A dead or hung holder's session is not writing anything, by definition — so its lock's `expires_at` is never touched by the stamper, continues to reflect its original (stale) value, and `is_expired(now, expires_at)` in `verify-factory-lock` continues to evaluate against the real wall clock exactly as it does today. Nothing about this design gives a hung session a way to keep its lock alive without itself performing a write; the expiry-based takeover path (BC-4.13.001 PC2) is untouched.

**Why the "no new CAS/race handling" claim is scoped to the locked case only (F-012, v1.1 — corrected).** v1.0 claimed no new CAS/race handling was needed at all; the pass-1 review correctly found this argument only holds **while a lock is actually held**. The factory lock is opt-in (`factory_lock` is absent from STATE.md's frontmatter unless a burst discipline chooses to acquire one), so in the **unlocked** state — no `factory_lock` block present, or an expired one — `verify-factory-lock` imposes no exclusivity at all (its `Ok(None)` / PC2 paths both return `Continue` for any caller), and two concurrent sessions can both be mid-Edit against STATE.md at the same time with no lock to serialize them. This is a **pre-existing** risk (any two sessions editing STATE.md concurrently without a lock held can already race today, with or without this ADR — `stamp-state-timestamp`'s read-modify-write of two frontmatter lines is not meaningfully riskier than the agent's own read-modify-write of the rest of the file in the same window), not one this ADR introduces or materially worsens: the stamper's own re-read-and-rewrite happens synchronously inside the same `PostToolUse` invocation immediately after the tool's write lands, the identical timing window the agent's own edit already occupied. This ADR's "no new CAS/race handling is needed" claim is therefore **re-scoped**: it holds for the locked case (argument below, unchanged) and is **explicitly not extended** to claim the unlocked case is race-free — that pre-existing gap is out of scope for a keep-alive-only ADR whose purpose is to correct wall-clock fields the agent already had to manage by hand, not to add exclusivity where none was chosen. `verify-factory-lock` fires on **every** `Edit|Write|MultiEdit|Agent` dispatch and **every** `Bash` `git push … factory-artifacts`, unconditionally reading and evaluating the STATE.md lock block regardless of what file or command is actually being invoked. While a foreign unexpired lock **is** held, no other session's mutating tool call of any kind succeeds — so by the time this PostToolUse plugin's write to STATE.md executes, the calling session is, for the whole span of that burst, the only actor able to mutate `.factory/` at all. The stamper's own write is a single local re-read-then-rewrite of two frontmatter lines with no cross-process contender in that window; the actual cross-session hazard this system defends against (concurrent pushes to the `factory-artifacts` orphan branch) is handled by the pre-existing fetch-then-force-with-lease CAS push in the `state-burst` skill (BC-5.40.001 PC5), which this ADR does not touch.

**Why acquire/release/CAS-push stay out of scope.** `factory-lock-write.sh acquire` and `factory-lock-write.sh clear` mutate STATE.md via direct file I/O inside a Bash-tool-invoked shell script (`mv "$tmpfile" "$file"`), not via a Claude Code `Edit`/`Write`/`MultiEdit` tool call — so the new PostToolUse plugin, scoped to those three tool names, never even observes an acquire or a clear. Lock *lifecycle* (who becomes holder, when the lock is released, the CAS-push discipline for pushing the resulting commit) is untouched by this ADR; only the *keep-alive* renewal that happens as a side effect of ordinary STATE.md content edits during an already-held lock moves to the hook.

## Consequences

### Positive

- Agents can never author a stale `timestamp:` or a stale `factory_lock.expires_at` — both fields are structurally correct on every write, eliminating an entire class of `TimestampStale`/`LockExpiryStale` block-and-retry cycles.
- `state-manager` (and any other agent editing STATE.md) no longer needs to remember to hand-run `factory-lock-write.sh renew` mid-burst; BC-5.40.001 PC4's obligation moves from a documentary "state-manager MUST renew" instruction to a mechanically-guaranteed property.
- Net reduction in guard surface: one PreToolUse plugin with zero remaining function (`verify-state-timestamp-refresh`) is retired, and priority slot 143 is freed.
- The identity gate makes the "only the holder renews" invariant true for the first time, **across all automatic renewal paths** (v1.1 — extended from "the one place renewal actually happens" now that Decision 3 brings `precompact-flush` under the same gate) — today it is documentary (BC-5.40.001 Invariant 1) and unenforced at either renewal call site; after this ADR it is mechanically enforced at both, modulo the accepted email-collision residual (F-010).
- A silent-failure blind spot closes (v1.1, Decision 4): a renewal that should have fired but couldn't be confirmed due to identity-resolution failure now emits `factory.lock.renewal_indeterminate` plus a `log_warn`, rather than failing invisibly until the lock's later, confusing expiry.

### Negative / Trade-offs

- A new WASM plugin is a new artifact to build, register, test, and maintain (a fifth STATE.md-touching guard/stamper alongside `verify-factory-lock`, the retired `verify-state-timestamp-refresh`, `precompact-flush`, and `regression-gate`'s sibling pattern — count corrected v1.1 to include `precompact-flush`, which v1.0 undercounted) — though its logic is narrow (two frontmatter-line rewrites, one identity comparison) and reuses proven building blocks (`factory_lock_parse::extract_frontmatter`, the `exec_subprocess` git-email pattern, and — v1.1 — the shared `renew_lock_if_holder`/`trim_git_email` functions also used by the amended `precompact-flush`; v1.3 adds the shared `classify_identity_resolution` classifier, F-006, to this same reused-building-blocks list).
- The Rust unit test module in `verify-state-timestamp-refresh/src/lib.rs` and `plugins/vsdd-factory/tests/verify-state-timestamp-refresh.bats` assert the *old* block-on-staleness behavior and must be retired or rewritten against the new stamper's behavior (a stamper that always succeeds and never blocks needs a different assertion shape: "after the tool call, STATE.md's `timestamp:`/`expires_at` differ from what the agent's payload proposed" rather than "the tool call was blocked"). `plugins/vsdd-factory/tests/validate-state-structure/pass-real-state-md-snapshot.bats` is unaffected — it validates structural shape, not the staleness-detection behavior.
- `timestamp:` and `factory_lock.expires_at` become **inherently non-deterministic, wall-clock-derived** frontmatter values, more so than today (today they are at least agent-chosen strings that a snapshot test could pin for a single burst; after this ADR they are stamped by the hook at whatever instant the dispatcher's PostToolUse fires). Any test that snapshot-asserts an exact STATE.md byte sequence including these two fields will need to mask or exclude them going forward — this is a strict superset of the masking already required today (both fields were already wall-clock-derived in intent; this ADR only moves *who* writes the correct value, not the fact that the value is time-dependent). **v1.1 addition (F-007):** the comparison predicate for both fields is `>=`, not strictly-greater — a same-wall-clock-second re-invocation produces a byte-identical, not-strictly-newer value; tests asserting monotonic strict advancement across sub-second invocations must account for this.
- The same-file-rewrite hazard is new in kind, if not in fact: no existing hook today rewrites the very file a tool call just wrote. Mitigated by keeping the rewrite to a single-line-per-field replacement (mirroring `factory-lock-write.sh`'s own `_update_expires_at` awk pattern) — since the agent no longer authors these two lines at all, there is no remaining agent-vs-hook collision to race against on the *next* edit either (the agent's `old_string`/`new_string` fragments for STATE.md content no longer need to touch these two lines). **Unlocked-state concurrent-write risk (F-012, v1.1):** this mitigation covers the locked case; the pre-existing, accepted unlocked-state concurrent-write risk (see Rationale §"no new CAS/race handling") is not newly introduced by the stamper but is not eliminated by it either.
- Retiring `verify-state-timestamp-refresh`'s registry entry without deleting its crate leaves dead code in the tree until a follow-up cleanup story lands; this is an explicit, bounded, human-visible deferral (see Boundaries below), not a silent one.
- **Scope expansion (v1.1, Decision 3):** the implementation touches a second existing crate (`precompact-flush`) in addition to the single new `stamp-state-timestamp` crate v1.0 scoped — this is a real increase in review surface and test-authoring effort for the implementing story (S-17.05), not a cosmetic one; see Decision 3's "Scope-expansion impact on delivery" note.

## Alternatives Considered

- **Option "smarter PreToolUse guard that auto-corrects":** Rejected — structurally impossible. `HookResult` has no "continue with modified payload" variant; a PreToolUse plugin can only `Continue` (unmodified) or `Block`. There is no ABI path to inject a corrected value before the tool's own write executes.
- **Option "keep `verify-state-timestamp-refresh` registered, but make its Block message tell the agent to just accept whatever the hook will fix":** Rejected — once the stamper makes staleness structurally unreachable, the guard can never fire (the condition it blocks on no longer occurs), so keeping it registered is pure dead weight on the dispatcher's PreToolUse tier for every STATE.md edit, with no compensating safety benefit.
- **Option "renew `expires_at` unconditionally on every write, without an identity check" (mechanizing today's status quo laxity as-is):** Rejected — this ADR found that today's laxity is tolerable only because renewal is a conscious manual act; automating it unconditionally would let a non-holder writer (legitimately admitted via `verify-factory-lock` PC2 `LockExpired`) silently resurrect a foreign holder's expired lock on every subsequent write, which is a strictly worse outcome than the status quo. The identity-gated design was chosen instead, at the modest cost of one additional `exec_subprocess` call already proven safe elsewhere.
- **Option "fold the keep-alive into `verify-factory-lock` itself" (extend the existing PreToolUse guard rather than add a new PostToolUse plugin):** Rejected — `verify-factory-lock` is architecturally read-only by BC-4.13.001 Invariant 4 ("NEVER writes STATE.md") and runs PreToolUse, before the agent's own write has landed; even if it were made to write, PreToolUse timing means it would be stamping the *pre-write* on-disk content, not the content the agent is about to produce, which does not solve the "agent forgot to advance `timestamp:` in its own edit" problem at all. A dedicated PostToolUse plugin, timed after the write lands, is required.
