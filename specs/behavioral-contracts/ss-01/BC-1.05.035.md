# Behavioral Contract BC-1.05.035: factory-dispatcher::host::exec_subprocess::resolves_binary_to_absolute_path_before_allow_check — load-time trusted-prefix resolution before binary_allow match; CWE-706 closure via load-time-resolution + path-substitution; TOCTOU residual risk accepted under threat model

## Description

**ADR-015 Awareness (added per E-9 v1.7 Post-Audit Amendment, propagated to BC at v1.22 per TD-VSDD-074):**
This BC's denial-path postcondition references the existing `internal.capability_denied` event name. Per ADR-015 D-15.2 reverse-DNS naming requirement and gap-analysis-w16-subprocess.md §"Existing denial-path telemetry" lines 341-351, this event MUST be renamed to `vsdd.capability.denied.exec_subprocess.v1` to map to the `audit` category per ADR-015 D-15.2 registry line 329 (`vsdd.capability.denied.* | audit`). The current name is INTERIM. The S-9.07 implementer (or the SS-01 implementer of any host-emit-fix story) MUST rename `internal.capability_denied` → `vsdd.capability.denied.exec_subprocess.v1` before merge. No new OQ filed; rename target is unambiguous per gap-analysis amendment.

**v2.0 security model — load-time resolution (replaces v1.x canonicalize-first approach):** The dispatcher resolves each `binary_allow` basename entry to an absolute path at registry-load time via a hardcoded trusted-prefix list (ADR-043 Decision 1). The resolved absolute path is stored in the in-memory `ExecSubprocessCaps`. At spawn time, the guest-supplied `cmd` is matched by basename against the resolved allow-list entries; `binary_allowed` returns `AllowResult::Allowed(resolved_path)` on a match (see Postconditions for all three `AllowResult` variants). That resolved path — NOT the guest `cmd` — is used for all subsequent checks (`is_shell`, `refuse_setuid`) and the final `Command::new` call. `Path::canonicalize()` is NEVER called (ADR-043 Decision 1 normative no-canonicalize rule). This closes the structural CWE-706 gap (guest `cmd="/tmp/evil/git"` executes `/usr/bin/git`, not the evil path). Decision 3 explicitly repairs the setuid gate (BC-1.05.004), which was inert for bare-name cmd values: Decision 1 resolves allow-list entries at load time but does NOT change the path received by `refuse_setuid` in `run()`; Decision 3's full-substitution rule explicitly threads the resolved path from `binary_allowed` through `run()` to `refuse_setuid` (ADR-043 Decision 3). This repair is NOT incidental — it requires an explicit code change in `run()` (ADR-043 Comment 3 correction). See the TOCTOU analysis below for the separate TOCTOU threat and its accepted-risk disposition.

**Denial-path emit symmetry with BC-1.05.036 (LOW-P50-001):** The `emit_denial` function at `exec_subprocess.rs::emit_denial` calls `ctx.emit_internal(ev)`, which routes through the same best-effort `internal_log.write` path documented in BC-1.05.036. All four runtime denial paths governed by this BC — `no_exec_subprocess_capability`, `binary_not_on_allow_list`, `shell_bypass_not_acknowledged`, `setuid_or_setgid_binary` — are best-effort. The v1.x fifth denial path `binary_canonicalize_failed` is retired. Load-time `BINARY-UNRESOLVABLE-ABSOLUTE-MISSING` and `BINARY-UNRESOLVABLE-NAME-NOT-FOUND` warns are emitted via the separate `internal.load_warn` event class (ADR-043 Decision 2), not via `emit_denial`.

**TOCTOU analysis — path substitution closes CWE-706, NOT TOCTOU; TOCTOU is an accepted residual risk:** Path substitution and TOCTOU are independent threats that require different controls; this paragraph corrects the erroneous v2.0 claim that "path substitution closes the TOCTOU window."

*CWE-706 (baseline confusion — closed by path substitution):* A guest passes `cmd="/tmp/evil/git"` against `binary_allow=["git"]`. The `binary_allowed` check extracts basename `"git"`, matches the resolved entry, and returns `AllowResult::Allowed("/usr/bin/git")`. `Command::new("/usr/bin/git")` is called — not the guest path. This is what path substitution closes: the guest cannot dictate which binary is spawned by naming an arbitrary absolute path with a matching basename.

*CWE-362 (TOCTOU via symlink swap — residual risk, accepted):* The TOCTOU threat is: at load time `Path::exists("/opt/homebrew/bin/git")` succeeds; the resolved path `/opt/homebrew/bin/git` is stored; later at spawn time `Command::new("/opt/homebrew/bin/git")` executes; the OS follows the symlink at `execve()`. An attacker who can write to `/opt/homebrew/bin/` (verified user-writable: `drwxrwxr-x zious:admin` per ADR-043 §Negative) can repoint the symlink between the `Path::exists()` call and the `execve()` call. `Command::new` receives the dispatcher-controlled path (`/opt/homebrew/bin/git`) but the target of that symlink has been swapped. What would close this threat: `Path::canonicalize()` at check time, which resolves the symlink to the Cellar target and pins it — but ADR-043 Decision 1 normatively prohibits this because Cellar paths become dangling after `brew upgrade`.

*Accepted-risk disposition:* This TOCTOU window is accepted under the threat model stated in ADR-043 §Negative: (1) the window between `Path::exists()` at registry load time and `execve()` at spawn time spans the full plugin execution lifecycle — bounded by `timeout_ms` (5000 ms for standard sync plugins; 8000 ms for `session-start-telemetry`; unbounded for `async=true` plugins) — and requires the attacker to repoint the symlink within that window; (2) exploitation requires the attacker to be in the `admin` group (or be the session user) to write to `/opt/homebrew/bin/` — a capability that already confers many direct session-compromise vectors (shell config, Python packages, etc.); (3) the dispatcher's primary security boundary is the `binary_allow` capability gate preventing WASM plugins from calling undeclared binaries; it does not claim to defend against a locally-compromised session user. Directories that are NOT user-writable (`/usr/bin`, `/bin`, `/usr/local/bin`, `/usr/sbin`, `/sbin` — all `drwxr-xr-x root:wheel`) cannot have their entries swapped by an unprivileged attacker; however, if an entry in such a directory is itself a symlink pointing to a user-writable target, the TOCTOU window applies at the symlink-target level. The residual window exists only for `/opt/homebrew/bin` and `/opt/homebrew/sbin` on macOS. This risk is named, bounded, and accepted.

**Platform scope — `#[cfg(unix)]` (ADR-043 Decision 1):** The load-time resolution mechanism specified by this BC (ADR-043 Decisions 1–5) is explicitly scoped to Unix targets (`#[cfg(unix)]`). On Windows (`x86_64-pc-windows-msvc`), none of Decisions 1–5 apply; the dispatcher retains current behavior: `Command::new(bare_name)` with OS PATH lookup at spawn time. Bare-name `binary_allow` entries continue to work on Windows exactly as today; no operator change is required to ratify this ADR. The setuid gate (`refuse_setuid`) remains an unconditional no-op on Windows (BC-1.05.004 EC-001). Windows binary resolution (trusted-prefix variants, `.exe`/`PATHEXT` suffix handling) is a future architecture work item; see ADR-043 §Downstream Routing.

## Preconditions

1. Plugin calls `vsdd::exec_subprocess`.
2. Plugin has a valid `Capabilities.exec_subprocess` block.
3. A `cmd` argument is provided.

## Postconditions

1. The dispatcher MUST use the load-time-resolved absolute path (from ADR-043 Decision 1 registry-load trusted-prefix resolution) for ALL capability checks and the spawn call in `exec_subprocess.rs::run`. No `Path::canonicalize()` call is made (ADR-043 Decision 1 no-canonicalize rule — see Invariant 1). The resolved path is propagated through ALL of the following in the call chain: (a) `binary_allowed(resolved_path, &caps.binary_allow)` at `exec_subprocess.rs::run` (binary_allowed call) instead of raw `cmd` — returns `AllowResult` per ADR-043 Decision 3: `AllowResult::BinaryUnresolvable` → `run()` returns `BINARY_NOT_FOUND = -6` directly (no `execute_bounded` call, no `emit_denial`); `AllowResult::Denied` → `emit_denial("binary_not_on_allow_list")` → CAPABILITY_DENIED (-1); `AllowResult::Allowed(resolved_path)` → proceed; (b) `is_shell(resolved_path)` at `exec_subprocess.rs::run` (is_shell call) instead of raw `cmd` — ensures the shell-bypass check operates on the dispatcher-resolved basename. Note: for any reachable case, `basename(resolved_path) == basename(cmd)` because `binary_allowed` matching already guarantees this; `is_shell(resolved_path)` and `is_shell(cmd)` produce identical results on all matched inputs. The unclosable shell-bypass residual (operator entry whose basename is not a shell name but resolves to a shell via symlink) is independent — see EC-007; (c) `refuse_setuid(resolved_path)` at `exec_subprocess.rs::run` (refuse_setuid call) instead of raw `cmd` — ensures setuid check operates on the real binary's absolute path, not a CWD-relative bare name (see BC-1.05.004 v2.0 Postcondition 3); (d) `execute_bounded(resolved_path, args, ...)` at `exec_subprocess.rs::run` (execute_bounded call) instead of raw `cmd`, ensuring `Command::new(resolved_path)` at `exec_subprocess.rs::execute_bounded` (Command::new call) spawns only the dispatcher-approved binary. The raw guest `cmd` string is discarded after basename extraction and NEVER passed to `Command::new`. This closes the structural CWE-706 gap: a guest supplying `cmd="/tmp/evil/git"` against `binary_allow=["git"]` resolved to `/usr/bin/git` executes `/usr/bin/git`, not the guest path. (See Postcondition 2 for the INVALID_ARGUMENT pre-resolution guard.)
2. If `read_wasm_string` returns Err (non-UTF-8 byte sequence in WASM memory), the existing host-call error path returns `codes::INVALID_ARGUMENT` (-4) before any resolution or allow-list check. (NOTE: NUL bytes are valid UTF-8 and pass `read_wasm_string`; NUL-containing paths are now handled by the allow-list miss path at step (2) of the Precedence Ladder — the load-time resolution produces no entry for a NUL-containing name, so `binary_allowed` returns `AllowResult::Denied` → CAPABILITY_DENIED (-1). The v1.x canonicalize-EINVAL NUL path is retired.)
3. If a `binary_allow` entry cannot be resolved at registry-load time, the dispatcher handles this gracefully via ADR-043 Decision 2 per-plugin degradation: (a) at load time, emits an `internal.load_warn` event with one of two **distinct reason strings** (ADR-043 Decision 2 / D-6), `plugin_name`, and `binary_name`; stores a `BINARY_UNRESOLVABLE` sentinel in the in-memory allow-list entry; **PC3(b):** When `binary_allowed` returns `AllowResult::BinaryUnresolvable` — an allow-listed entry whose original basename matches `cmd` but which could not be resolved to an absolute path at registry-load time — `run()` returns `Err(codes::BINARY_NOT_FOUND)` (-6) directly. `execute_bounded` is not called. `emit_denial` does not fire. The load-time `internal.load_warn` with `reason="BINARY-UNRESOLVABLE-NAME-NOT-FOUND"` is the sole diagnostic event for this path.

   **Reason string 1 — `"BINARY-UNRESOLVABLE-ABSOLUTE-MISSING"`:** the entry was already an absolute path (`Path::is_absolute()` = true); `Path::exists()` returned false. Applies to any plugin regardless of PATH declaration. Distinct from NAME-NOT-FOUND — diagnostics can identify misconfigured absolute entries vs. missing-from-prefix basenames.

   **Reason string 2 — `"BINARY-UNRESOLVABLE-NAME-NOT-FOUND"`:** the entry was a basename (not an absolute path); it was not found via either search path (see per-plugin scoping below). **Per-plugin user-PATH scoping (ADR-043 Decision 1 D-1 revised, v1.5 ordering):** for plugins that declare `PATH` in `exec_subprocess.env_allow` (the 39 WITH-PATH plugins — all legacy-bash-adapter plugins and non-adapter native-WASM plugins with PATH declared), the dispatcher searches `std::env::var("PATH")` FIRST; on user-PATH success it emits `"RESOLVED-from-user-PATH"` advisory warn and proceeds normally (not an error). If user PATH fails, the trusted-prefix list is tried as fallback; on trusted-prefix success it emits `"RESOLVED-from-trusted-prefix-fallback"` advisory warn and proceeds (not an error). Only if BOTH user PATH AND trusted-prefix fail is `"BINARY-UNRESOLVABLE-NAME-NOT-FOUND"` emitted. (Rationale for user-PATH-first ordering: trusted-prefix-first would silently downgrade `bash` from the user's 5.x Homebrew version to the system 3.2.57 for the 37 adapter plugins on macOS — the opposite of the intended behavior.) For plugins that do NOT declare `PATH` in `exec_subprocess.env_allow` (the 5 WITHOUT-PATH plugins: `session-start-telemetry`, `capture-commit-activity`, `validate-factory-path-staging`, `verify-factory-lock`, `verify-factory-lock-bash`), the user-PATH search is NOT attempted; resolution uses the trusted-prefix list only, and `"BINARY-UNRESOLVABLE-NAME-NOT-FOUND"` is emitted immediately on miss. This preserves those plugins' existing trust model: they do not forward `PATH` to subprocess, so user PATH is not in their trust domain (ADR-043 §Rationale D-1 scoped fallback). Control C-9 (ADR-043 §Controls) asserts that `RESOLVED-from-user-PATH` does NOT occur for a WITHOUT-PATH plugin.

   **Behavior change from v1.x:** the previous canonicalize-fail path returned `CAPABILITY_DENIED` (-1) with `emit_denial("binary_canonicalize_failed")`. That path is retired. Missing-binary conditions are now surfaced via load-time warn + `BINARY_NOT_FOUND = -6` at spawn, not via a runtime canonicalize failure. Tests previously asserting `INTERNAL_ERROR` (-99) for missing-binary `cmd` must now assert `BINARY_NOT_FOUND = -6` (ADR-043 Decision 5 code). Note: ADR-043 Decision 5 also introduces `SPAWN_FAILED = -7` for non-NotFound `spawn()` errors, and narrows `INTERNAL_ERROR = -99` to post-spawn failures only.
4. **No new runtime error path is introduced for symlink-resolved targets.** A resolved allow-list path that is itself a symlink (e.g., `/opt/homebrew/bin/git` → Cellar) is stored verbatim; `Command::new` follows the symlink at spawn time. A guest `cmd` whose basename does NOT match any resolved allow-list entry → `binary_allowed` returns `AllowResult::Denied` → existing `emit_denial("binary_not_on_allow_list")` at `exec_subprocess.rs::run` (allow-list miss arm) → CAPABILITY_DENIED (-1). This aligns with the existing 4 denial paths (`no_exec_subprocess_capability`, `binary_not_on_allow_list`, `shell_bypass_not_acknowledged`, `setuid_or_setgid_binary`) and avoids introducing a novel error-code pairing.

**Precedence ladder (v2.0 — rewritten per Option C security-model adjudication; canonicalize step retired; load-time resolution introduced; step (1) cause-collapse note retained from LOW-P51-001):** When multiple validation conditions could fire, the host applies them in this order: (1) Non-UTF-8 byte sequence in `cmd` (per `read_wasm_string` at `host/memory.rs::read_wasm_string`) → `Err(INVALID_ARGUMENT -4)` — NUL bytes are valid UTF-8 and pass to step (2). **Cause-collapse note (LOW-P51-001, retained):** `read_wasm_string` can fail for three distinct `HostCallError` variants, all of which collapse to the same `codes::INVALID_ARGUMENT` (-4) at `exec_subprocess.rs::register` (INVALID_ARGUMENT return arm) via the catch-all `Err(_) =>` arm: (a) `HostCallError::MemoryOverflow` — integer overflow from `start.checked_add(len as usize)` at `memory.rs::read_wasm_bytes` (checked_add); (b) `HostCallError::OutOfBounds { ptr, len, memory_size }` — span extends past current Wasm linear memory size at `memory.rs::read_wasm_bytes` (OutOfBounds check); (c) `HostCallError::InvalidUtf8` — `String::from_utf8` rejects the byte sequence at `memory.rs::read_wasm_string` (from_utf8). All three variants are silently erased to the same `-4` return code; the three distinct root causes are indistinguishable to the caller. v1 known limitation. (2a) `binary_allowed(cmd, &caps.binary_allow)` returns `AllowResult::Denied` (guest cmd's basename does not match any allow-list entry) → `emit_denial("binary_not_on_allow_list")` at `exec_subprocess.rs::run` (allow-list miss arm) → `Err(CAPABILITY_DENIED -1)`. (2b) `binary_allowed` returns `AllowResult::BinaryUnresolvable` (a `BINARY-UNRESOLVABLE` sentinel was stored at load time for the entry whose basename matches cmd's basename — stored for either BINARY-UNRESOLVABLE-ABSOLUTE-MISSING or BINARY-UNRESOLVABLE-NAME-NOT-FOUND outcomes) → `run()` returns `BINARY_NOT_FOUND = -6` directly; `execute_bounded` is NOT called on this arm; `emit_denial` does NOT fire on this arm. **NUL-byte paths** pass `read_wasm_string` (step 1) and reach step (2a): a NUL-containing name will not match any allow-list entry → `AllowResult::Denied` → CAPABILITY_DENIED (-1). The v1.x separate EINVAL canonicalize-failure path for NUL bytes is retired. (3) `binary_allowed` returns `AllowResult::Allowed(resolved_path)` → proceed through `is_shell(resolved_path)`, `refuse_setuid(resolved_path)`, then `execute_bounded(resolved_path, ...)`. Per `crates/factory-dispatcher/src/host/exec_subprocess.rs::run` (binary_allowed call) and BC-1.05.005/BC-1.05.032 sibling contracts.

**Panic semantics (v1 known limitation):** Any panic arising within the host-call body propagates uncaught to the wasmtime host-call boundary. Wasmtime converts the Rust panic to a wasmtime `Trap` and propagates it to the plugin caller. No `catch_unwind` wraps the host-call surface in `exec_subprocess.rs`. The functions in the prescribed allow-check/spawn chain (`Command::new`, `command.spawn`) do not have documented panic vectors on the inputs this BC governs — `Command::new` is an infallible builder. Accordingly, panics from this call chain would indicate a stdlib programming error or an `unwrap()`/`expect()` introduced in a future helper, not a normal runtime failure mode. The `internal.host_function_panic` event class (`INTERNAL_HOST_FUNCTION_PANIC` at `internal_log.rs::INTERNAL_HOST_FUNCTION_PANIC`) is declared as a `pub const` but has zero emit call sites in `exec_subprocess` or any other host function (confirmed: grep of `crates/factory-dispatcher/src/` finds only the const declaration at `internal_log.rs::INTERNAL_HOST_FUNCTION_PANIC` and one re-export at `lib.rs::INTERNAL_HOST_FUNCTION_PANIC` — no call sites). Panics in host calls are therefore unobservable in v1. Track host-call panic-handling decision in **OQ-W16-008** (v1: panic propagates as wasmtime Trap; v2 candidate: `catch_unwind` wrapper emitting `INTERNAL_HOST_FUNCTION_PANIC` before re-raising). See EC-014.

## Invariants

1. The load-time-resolved absolute path (ADR-043 Decision 1 trusted-prefix resolution) MUST be propagated through the entire exec_subprocess capability-check chain — `binary_allowed`, `is_shell`, `refuse_setuid`, and `execute_bounded` — on every invocation. The raw guest `cmd` string is consumed only for basename extraction during the `binary_allowed` match and is then discarded. `Path::canonicalize()` MUST NOT be called at any point in this chain (normative per ADR-043 Decision 1 no-canonicalize rule): resolved paths are stored verbatim as the stable symlink path from the trusted-prefix scan, preserving correctness across `brew upgrade` Cellar version changes. **Threat scope of this invariant:** this invariant closes CWE-706 (basename confusion — guest cannot dictate which binary is spawned by supplying an arbitrary absolute path with a matching basename). It does NOT close TOCTOU (CWE-362); the TOCTOU residual risk for user-writable symlink directories is accepted under the threat model documented in the TOCTOU analysis section of the Description above. **Platform scope:** This invariant applies on Unix targets (`#[cfg(unix)]`) only; on Windows, ADR-043 Decisions 1–5 are not applied and the load-time resolution step does not occur — see the Platform scope note in the Description.

## Edge Cases

| ID | Description | Expected Behavior |
|----|-------------|-------------------|
| EC-001 | `cmd = "../etc/passwd"` (literal path traversal); `binary_allow = ["bash"]` (resolved to `/bin/bash`) | Basename of `"../etc/passwd"` is `"passwd"`; does not match resolved entry basename `"bash"` → `binary_allowed` returns `AllowResult::Denied` → `emit_denial("binary_not_on_allow_list")` → CAPABILITY_DENIED (-1). Traversal paths are denied at the allow-list step, not via a separate traversal guard. Note: `..` in a guest cmd does NOT bypass this check because the dispatcher never evaluates the path on disk before the allow-list check; only the basename is compared. |
| EC-002 | `cmd` is a symlink pointing to a non-allow-listed binary (e.g., guest supplies `cmd="./my-git"` where `./my-git` symlinks to `/etc/passwd`); `binary_allow = ["bash"]` (resolved to `/bin/bash`) | Basename of `"./my-git"` is `"my-git"`; does not match `"bash"` → allow-list miss → CAPABILITY_DENIED (-1). The symlink target is never evaluated (no canonicalize call). Even if the guest had named the symlink `"bash"`, the resolved entry (`/bin/bash`) would be spawned, not the symlink. |
| EC-003 | `cmd` is a valid absolute path; `binary_allow = ["git"]` (resolved to `/usr/bin/git`) | Basename of `cmd` matches resolved entry basename → `binary_allowed` returns `AllowResult::Allowed("/usr/bin/git")` → proceed. `Command::new("/usr/bin/git")` spawned regardless of what full path the guest supplied. |
| EC-004 | `binary_allow = ["nonexistent-binary-xyz"]`; no such binary in any trusted-prefix directory | **Without-PATH plugin:** at load time, trusted-prefix search is the only search; `"BINARY-UNRESOLVABLE-NAME-NOT-FOUND"` warn emitted immediately on miss; `BINARY_UNRESOLVABLE` sentinel stored. **With-PATH plugin (v1.5 ordering):** user PATH is searched FIRST; if user PATH also misses, trusted-prefix is tried as fallback; `"BINARY-UNRESOLVABLE-NAME-NOT-FOUND"` emitted only if both user PATH AND trusted-prefix fail. In both cases: at spawn time, `binary_allowed` returns `AllowResult::BinaryUnresolvable` for the sentinel → `run()` returns `BINARY_NOT_FOUND = -6` directly; `execute_bounded` not called; `emit_denial` does not fire. NOT `CAPABILITY_DENIED`. |
| EC-005 | `cmd` contains NUL byte; `binary_allow = ["bash"]` | NUL bytes are valid UTF-8 and pass `read_wasm_string`. Basename extraction at `PathBuf::from(cmd).file_name()` will produce a basename that does not match any sane allow-list entry — no allow-list entry has a NUL-containing basename, so `binary_allowed` returns `AllowResult::Denied` (not `AllowResult::BinaryUnresolvable` — the sentinel arm requires that cmd's basename match a stored-entry name, which NUL-containing inputs cannot produce) → `emit_denial("binary_not_on_allow_list")` → CAPABILITY_DENIED (-1). On platforms where NUL-containing path strings cause `file_name()` to return unusual results, the `AllowResult::Denied` path handles them consistently. No separate NUL-path guard is required. |
| EC-006 | `cmd = ""` (empty string); `binary_allow = ["bash"]` | `PathBuf::from("").file_name()` returns `None`; `unwrap_or_else(\|\| cmd.to_string())` fallback produces basename `""`; no allow-list entry matches `""` → allow-list miss → CAPABILITY_DENIED (-1). |
| EC-007 | `binary_allow=["/opt/tools/runner"]`; `/opt/tools/runner` is a symlink to `/bin/bash`; guest `cmd` has basename `"runner"`; no `shell_bypass_acknowledged` | `binary_allowed` returns `AllowResult::Allowed("/opt/tools/runner")`; `is_shell("/opt/tools/runner")` extracts basename `"runner"` → not in `SHELL_NAMES` → bypass check skipped → `Command::new("/opt/tools/runner")` executes bash without `shell_bypass_acknowledged`. **Structurally unclosable residual** under ADR-043's no-canonicalize rule: resolving the symlink target would identify `bash`, but canonicalize is prohibited (ADR-043 Decision 1). Operator mitigation: avoid allow-list entries whose basename is not a known shell name but resolves to a shell binary. Flag in operator documentation; not a dispatcher enforcement gap. |
| EC-008 | `cmd = "/"` or `cmd = "."` (no-final-component paths); `binary_allow = ["bash"]` | `PathBuf::from("/").file_name()` returns `None`; fallback basename is `"/"`. No allow-list entry matches `"/"` → allow-list miss → CAPABILITY_DENIED (-1). Same path for `"."`. [edge-case] |
| EC-009 | `cmd = "/usr/bin"` (directory); `binary_allow = ["bin"]` (resolved to `/usr/bin` if that directory is in trusted prefix — unusual config) | Basename `"bin"` matches allow-list entry `"/usr/bin"` → `binary_allowed` returns `AllowResult::Allowed("/usr/bin")`; `Command::new("/usr/bin")` reaches `command.spawn()` → `Err(PermissionDenied/EACCES, raw_os=13)` (measured) → `SPAWN_FAILED = -7` per ADR-043 Decision 5 (PermissionDenied/EACCES on a directory is a non-NotFound `spawn()` Err variant → SPAWN_FAILED, not INTERNAL_ERROR; INTERNAL_ERROR = -99 is narrowed to post-spawn failures only). No emit_denial; no CAPABILITY_DENIED. Track in **OQ-W16-005**. [known-limitation] |
| EC-010 | `cmd = "/tmp/evil/git"` (arbitrary absolute path with matching basename); `binary_allow = ["git"]` (resolved to `/usr/bin/git`) | Basename `"git"` matches → `binary_allowed` returns `AllowResult::Allowed("/usr/bin/git")`; `Command::new("/usr/bin/git")` executes. Guest's supplied path `/tmp/evil/git` is discarded. This is the primary security invariant: path substitution ensures only the dispatcher-approved binary is spawned. |
| EC-011 | `args` bytes contain non-UTF-8 byte sequences (e.g., `args = [b"\xFF\xFE"]`) | At `exec_subprocess.rs::decode_args` (from_utf8_lossy call): non-UTF-8 bytes silently replaced with U+FFFD. Asymmetric with `cmd` strict UTF-8. v2 known limitation — track in **OQ-W16-008**. [known-limitation] |
| EC-012 | `binary_allow = ["passwd"]` (resolved to `/usr/bin/passwd`); guest `cmd` has basename `"passwd"` | Allowed. Operator MUST audit `binary_allow` entries — the allow-list controls which basename is permitted, and load-time resolution controls which specific binary is spawned; a plugin with `binary_allow = ["passwd"]` will always execute `/usr/bin/passwd` (or whichever trusted-prefix location resolves first). Operator auditing responsibility, not a dispatcher enforcement gap. [security-operator-audit] |
| EC-013 | A panic arises within the host-call body | Panic propagates to wasmtime Trap boundary. **v2 known limitation:** no `catch_unwind` in `exec_subprocess.rs`. `INTERNAL_HOST_FUNCTION_PANIC` const declared at `internal_log.rs::INTERNAL_HOST_FUNCTION_PANIC` with zero call sites. Track in **OQ-W16-008**. [known-limitation] |
