# BC-5.41.001: wave-gate writes verified HANDOFF.md with all 9 base required fields (+epic_status on EPIC-COMPLETE wave) and anti-fabrication cross-checks before declaring wave closed

## Description

When the `wave-gate` skill is invoked to close wave N (where N > 0), it must produce a `HANDOFF.md` artifact on the `factory-artifacts` branch before the wave is considered closed. Every field in `HANDOFF.md` must be cross-checked against an external verifiable source (git or filesystem) — no field may rely solely on in-context memory. Missing or unverifiable fields cause `wave-gate` to block and surface the specific gap to the operator. This BC closes the fabricated-SHA failure class documented in issues #170 and #173.

## Preconditions

1. The `wave-gate` skill is invoked with intent to close wave N (N >= 1).
2. The `factory-artifacts` orphan branch is accessible via `git`.
3. Wave identity is determinable from real substrate: for product pipelines, `sprint-state.yaml` wave-group ordering (derived by `wave-scheduling` skill dependency-order); for the self-referential engine, STATE.md frontmatter `current_step:` field. No phantom `current_wave:` frontmatter field is referenced — this field does not exist.
4. The factory lock is held by the invoking session OR is absent. Lock held: `STATE.md` `factory_lock.holder` matches invoking session identity per BC-5.40.001 PC4. Lock absent: `factory_lock:` block is absent/null in STATE.md — wave-gate may proceed without a lock guard; `factory_lock_holder` field in HANDOFF.md is set to `null`. Both states are valid preconditions for wave-gate invocation.
5. Harness version >= v2.1.105 (for PreCompact/PostCompact event support in downstream hooks).

## Postconditions

1. **HANDOFF.md written**: A `HANDOFF.md` file is written to the `factory-artifacts` branch root (or `.factory/` path on that branch) containing all 9 base required fields specified in ADR-026 §Decision 2 (plus `epic_status: complete` conditionally on the EPIC-COMPLETE wave).

2. **All 9 base required fields present; `epic_status: complete` additionally required on EPIC-COMPLETE wave**: The following 9 base fields are present and non-empty (unless explicitly allowed to be null):
   - `wave_id` — integer derived from sprint-state.yaml dependency-order topo-sort ordinal (product pipelines) OR STATE.md `current_step:` pass number (engine) — there is no `current_wave:` field.

     **Algorithm: wave-group-ordinal model.** `wave_id` is derived as: count the number of completed terminal wave groups in sprint-state.yaml + 1. A "completed terminal wave group" is a maximal contiguous block of terminal stories (merged / withdrawn / cancelled) that is followed by at least one non-terminal entry — i.e., a terminal→non-terminal **transition** in the wave-ascending story list. Under P-WAVE-BARRIER-INVARIANT, one contiguous terminal block = one completed wave; therefore `wave_id = completed_wave_groups + 1`, which equals the number of terminal→non-terminal transitions + 1. This is **NOT** the leading-terminal-story-count + 1 (which would give ~121 on the real sprint-state.yaml with 103 merged stories in one contiguous block); it counts wave GROUPS (transitions), not individual terminal stories. For vsdd-factory's real sprint-state.yaml (103 merged stories in one contiguous block followed by non-terminal stories): completed_wave_groups = 1, so wave_id = 2. The `parse-sprint-state.sh` `derive_wave_id` function (counting terminal→non-terminal transitions) is the canonical implementation of this wave-group ordinal. Per ADR-026 §Wave-Identity Derivation. This model is correct under the two preconditions below.

     **P-WAVE-BARRIER-INVARIANT** *(explicit precondition — previously implicit)*: Wave_id derivation assumes the wave-gate barrier invariant holds — all stories in wave k reach terminal status (merged / withdrawn / cancelled) before any story in wave k+1 leaves draft or pending. This invariant is enforced upstream by the `validate-wave-gate-completeness` and `validate-wave-gate-prerequisite` hooks (registered in `hooks-registry.toml`) and by BC-4.10.001 ("validate-per-story-adversary-convergence WASM hook MUST block wave-gate dispatch when any story lacks convergence clearance"). The wave-group-ordinal derivation is sound under this invariant because under P-WAVE-BARRIER-INVARIANT each completed wave produces exactly one contiguous terminal block, and each such block is followed by a non-terminal entry (the transition point), making completed_wave_groups = terminal→non-terminal transition count a correct measure of completed waves.

     **P-SPRINT-STATE-WAVE-ORDER** *(explicit precondition — previously implicit)*: sprint-state.yaml entries are ordered by wave (file order == dependency-wave order). If per-entry wave-level information is present (e.g., a `wave:` field on each entry), derivation SHOULD use it directly — taking the minimum wave number among non-terminal stories — rather than relying on file order. If only statuses and file order are present (no per-entry wave field), file-order==wave-order is a precondition of the algorithm and violations MUST fail loud (hard error surfaced to operator), not silently return a wrong ordinal.

     **Documented design boundary (not deferred work):** A full Kahn-DAG-level derivation — computing wave ordinals from explicit dependency edges, with no reliance on file order or the barrier invariant — would make `wave_id` derivation order-free and invariant-free. This is a known optional design evolution. It is NOT required while VSDD enforces the wave-gate barrier invariant (P-WAVE-BARRIER-INVARIANT above). This boundary is documented here to distinguish "soundly scoped given invariants" from "deferred work." No tech-debt-register entry is needed; no future-story anchor is required.
   - `last_verified_develop_sha` — 40-character lowercase hex string
   - `active_bcs` — non-empty list of strings (each a BC file path). **Semantics: existence-only, NOT lifecycle-filtered.** The field lists all BC `.md` files resolvable in the BC directory at handoff time (`find "$BC_DIR" -name "*.md"`). The name "active" refers to the set of BCs present/available in the spec corpus at wave close — it does NOT mean only BCs with `lifecycle_status: active`. The anti-fabrication cross-check (PC3) enforces file existence only: each path must resolve to a real file. Retired, deprecated, or removed BCs whose files are still present in the directory are included; BCs whose files have been physically deleted from the directory are not (they would fail the PC3 existence check). If a lifecycle-filtered subset is ever required, that must be a future behavioral change with an explicit postcondition amendment.
   - `next_wave_stories` — list of objects with `{id, status}` keys
   - `open_decisions` — list of objects with `{id, anchor_type, anchor_ref}` keys (may be empty list)
   - `pending_fixes` — list of objects with `{finding_id, pr_or_issue_ref}` keys (may be empty list)
   - `process_gaps` — list (may be empty)
   - `precompact_flush_sha` — 40-char hex OR explicit `null`. Three-state rule (wave-agnostic for log-present+valid case):
     1. **Log genuinely absent** (`test -f` false): null permitted for wave_id=1 (silent, normal first-wave); null permitted for wave_id>1 with advisory warning only (no hard block per PC5).
     2. **Log present but last-line corrupt** (FIELD-4 absent/empty/≠`commit`): stale entry; treat as log-absent per DI-025; null permitted any wave_id.
     3. **Log present + last-line FIELD-4 == `commit`**: null is a HARD BLOCK via `PrecompactShaMismatch` for **any wave_id including wave_id=1**; non-null must equal FIELD-2 SHA, mismatch is also a HARD BLOCK. The wave_id=1 carve-out does NOT override a present+valid log.
   - `factory_lock_holder` — string matching `factory_lock.holder` in `STATE.md` when lock is held; `null` when `factory_lock:` block is absent or holder is absent/null (lock not held)
   - `epic_status` — string `"complete"`; **CONDITIONAL**: required ONLY on the final/EPIC-COMPLETE wave (when all sprint-state.yaml stories have terminal status AND `next_wave_stories: []`); MUST be ABSENT (not `null`, not any value — genuinely absent) on all non-final waves. Presence of `epic_status` on a non-final wave is a malformed HANDOFF.md (causes `UnexpectedEpicStatus` from the validate-wave-handoff-completeness gate).

3. **Anti-fabrication cross-checks pass**:
   - `wave_id` matches the value computed by wave-handoff from sprint-state.yaml topo-sort ordinal (product) or STATE.md `current_step:` (engine) — no `current_wave:` field exists; cross-check is against the derived value, not a stored field
   - `last_verified_develop_sha` == output of `git rev-parse origin/develop` at handoff time
   - Each path in `active_bcs` resolves to an existing file under `.factory/specs/behavioral-contracts/`
   - Each `id` in `next_wave_stories` exists in `STORY-INDEX.md`
   - `factory_lock_holder` == `STATE.md` `factory_lock.holder` (read from git) when lock is held; null in HANDOFF.md is correct when STATE.md `factory_lock:` block is absent/null

4. **Block on missing/failing fields**: If any required field is absent or any anti-fabrication check fails, `wave-gate` blocks wave close, surfaces the specific failing fields and checks to the operator, and does NOT write a partial `HANDOFF.md`.

5. **`precompact_flush_sha` hard cross-check (F-12)**: `wave-gate` MUST cross-check `precompact_flush_sha` against the append-log file `.factory/hooks/precompact-flush-log` — specifically the LAST LINE of that file. The log line has four space-separated fields: `<ISO-timestamp> <SHA> <cycle>/<step> commit`. The canonical/primary corroboration is a structured field read: wave-gate reads FIELD-2 (the SHA) and FIELD-4 (the `commit` token) from the last line. wave-gate is a SHELL skill and therefore MAY exec `git cat-file -t <SHA>` to independently verify the object type, but this git exec is a permitted shell-context capability, NOT the sole or mandatory method — the FIELD-4 pre-embedded token provides sufficient corroboration (consistent with BC-5.41.003 and DI-025 which specify FIELD-4 as the canonical corroboration for WASM/shell contexts alike):
   - **File exists; last-line FIELD-4 == `commit` and FIELD-2 SHA is valid**: `precompact_flush_sha` MUST equal FIELD-2 of the LAST LINE of `.factory/hooks/precompact-flush-log` (read via literal filesystem read, not operator attestation). A mismatch or a null `precompact_flush_sha` when the log contains a valid commit SHA is a HARD BLOCK — `wave-gate` rejects the handoff with `PrecompactShaMismatch`. This rule applies to **any wave_id including wave_id=1**; the wave_id=1 carve-out does not override a present+valid log. Fabricated or null SHAs that contradict the log MUST block regardless of wave number.
   - **SHA in log but FIELD-4 is absent, empty, or not the literal string `commit`** (indicating log corruption or truncation): treat the log entry as stale and skip it; fall through to the genuinely-absent case below.
   - **File genuinely absent** (verified by `test -f .factory/hooks/precompact-flush-log` returning false): `precompact_flush_sha: null` is permitted for wave_id=1 (silent, normal first-wave case; no log means no PreCompact ever fired). For wave_id > 1 with no flush log: advisory warning only; operator must confirm no PreCompact fired; `wave-gate` surfaces the warning but does not hard-block (the absence is mechanically verified, not attested).
   - **Non-null SHA when log is absent or corrupt is VALID**: A non-null `precompact_flush_sha` value when the log is genuinely absent or its last line is corrupt (FIELD-4 absent/empty/≠`commit`) is VALID — no corroboration is possible in those cases, so anti-fabrication only HARD-BLOCKs on a positive mismatch against a present+valid log (per ADR-026 §Decision 2). A non-null SHA with no log to check against is not a violation; it is simply unverifiable and permitted.
   - **Rationale**: An unchecked null SHA is exploitable at any wave number — a hallucinating session could write `precompact_flush_sha: null` to bypass the flush guarantee even on wave_id=1 if a PreCompact fired mid-wave. The log file is the mechanical ground truth; wave_id is a discriminator ONLY in the log-absent case.

6. **Commit to factory-artifacts**: After all checks pass, `wave-gate` commits `HANDOFF.md` to the `factory-artifacts` branch with a commit message: `HANDOFF wave-<N> <ISO-timestamp>`.

7. **validate-wave-handoff-completeness gate passes**: After writing `HANDOFF.md`, the `validate-wave-handoff-completeness` WASM gate (BC-4.14.001) is invoked as a PostToolUse gate and must return `Continue` before the wave is declared closed.

8. **EPIC-COMPLETE operator surfacing**: When `wave-gate` detects EPIC-COMPLETE (all entries in `sprint-state.yaml` have terminal status — merged, withdrawn, or cancelled — and no pending/draft entries remain), before exiting 0 it MUST write the following message to stdout so the operator is explicitly notified:
   ```
   EPIC-COMPLETE: All stories in sprint-state.yaml have reached terminal status.
   Epic <epic-id> is complete. No wave-state.yaml written for next wave.
   HANDOFF.md committed to factory-artifacts with epic_status: complete.
   ```
   Where `<epic-id>` is derived from the cycle identifier in `STATE.md` `current_cycle:` field. A silent exit 0 on EPIC-COMPLETE is a specification violation — the operator must receive explicit confirmation that the epic has ended, not merely the absence of an error.

9. **HandoffMissing — block wave-close when no HANDOFF.md is present on factory-artifacts**: If `wave-gate` is invoked to close a wave but `HANDOFF.md` is absent from the `factory-artifacts` branch (i.e., no prior verified HANDOFF.md exists at the root or `.factory/` path of that branch), `wave-gate` MUST:
   - Return `Error("HandoffMissing")` and surface a human-readable message: `HandoffMissing: no verified HANDOFF.md found on factory-artifacts at wave-close; write HANDOFF.md via wave-handoff before closing the wave`.
   - NOT declare the wave closed.
   - NOT write any partial HANDOFF.md in this state (the file must be produced by the full wave-handoff flow, not patched in-place).

   **Semantic boundary with HandoffIncomplete (BC-4.14.001):**
   - `HandoffMissing` is a SHELL wave-gate error code. It fires when `HANDOFF.md` is **absent** on `factory-artifacts` at wave-close time. This check is performed by the shell `wave-gate` skill before invoking any WASM gate.
   - `HandoffIncomplete` is a WASM gate error code (BC-4.14.001 / `validate-wave-handoff-completeness`). It fires when `HANDOFF.md` IS present but required fields are missing or malformed. Per BC-4.14.001 EC-011, the WASM gate is NOT triggered on HANDOFF.md absence — it validates a write payload, not file presence. The WASM gate therefore can never emit `HandoffMissing`.
   - The two codes are disjoint: `HandoffMissing` = file absent; `HandoffIncomplete` = file present but incomplete. Neither subsumes the other.

   **Integration fixture**: The integration test `test_wave_close_blocked_without_handoff` (exercising VP-081 Postcondition A) asserts that the shell wave-gate returns `Error("HandoffMissing")` when wave-close is attempted with no verified HANDOFF.md present on factory-artifacts. This BC is the defining source for that error code.

10. **HANDOFF.md MUST be written via the Claude Code Write tool as part of an agent-orchestrated subcommand flow**: The `wave-handoff` skill operates via a four-step agent-orchestrated sequence. Bash redirection (`>`, `>>`, `} >`, `tee`) is forbidden as primary or fallback write path for `HANDOFF.md` — shell redirection emits no `PostToolUse` event, which silently bypasses the `validate-wave-handoff-completeness` gate (F-S1802-02).

    **Four-step agent-orchestrated flow (ADR-026 §Decision 8)**:
    1. **`--emit-handoff` bash subcommand**: The `wave-handoff` skill assembles the complete HANDOFF.md payload — all 9 base required fields plus `epic_status` if applicable — with all anti-fabrication cross-checks performed (PC3), and emits the assembled payload to stdout. This subcommand does NOT write any file; it only produces output for the agent to consume.
    2. **Agent Write tool invocation**: The orchestrating agent invokes the Claude Code native `Write` tool with the payload from step 1, targeting `${ARTIFACTS_WT}/HANDOFF.md`. This is the ONLY permitted write path for `HANDOFF.md`. The Write tool emits a `PostToolUse` event upon completion.
    3. **PostToolUse gate fires**: The `validate-wave-handoff-completeness` WASM gate (BC-4.14.001) fires automatically on the Write tool call via the PostToolUse hook registration. The gate validates the written HANDOFF.md payload; a gate failure blocks progression (PC7).
    4. **`--commit` bash subcommand**: After the Write tool completes and the gate passes, the `--commit` bash subcommand stages and commits the wave artifacts. **The presence check is CONDITIONAL on the wave path:**

       - **HAS-NEXT-WAVE path** (non-final wave; `next_wave_stories` is non-empty): `--commit` MUST verify that BOTH `HANDOFF.md` AND `wave-state.yaml` are present on disk at `${ARTIFACTS_WT}` before staging. If EITHER file is absent, it MUST abort with a hard error (see EC-016 for Write tool unavailability; EC-017 for HANDOFF.md absent at commit time). Both files are staged and committed in ONE atomic git commit.

       - **EPIC-COMPLETE path** (final wave; `epic_status: complete` / `next_wave_stories: []`): `wave-state.yaml` is intentionally not produced on this path (PC8, BC-5.41.002 PC3 EPIC-COMPLETE exception). `--commit` MUST verify that `HANDOFF.md` is present on disk at `${ARTIFACTS_WT}/HANDOFF.md`; if absent, it MUST abort with `HandoffFileAbsent` (EC-017). `--commit` MUST stage `HANDOFF.md` ALONE and create ONE atomic git commit. If a stale `wave-state.yaml` exists on disk (e.g., from a prior non-final wave invocation), `--commit` MUST remove it before staging so the commit contains only `HANDOFF.md`. A single-file (HANDOFF.md-only) commit on the EPIC-COMPLETE path is NOT a BC-5.41.002 PC6 atomicity violation — PC6 forbids splitting the wave-close into TWO separate commits; it does not require `wave-state.yaml` to exist when the epic is complete.

    **Fail-loud, no silent fallback**: If the `Write` tool is unavailable at invocation time (e.g., tool not registered in the current tool set), the `wave-handoff` skill MUST fail with a hard error and a human-readable message:
    ```
    HandoffWriteToolUnavailable: HANDOFF.md must be written via the Write tool (Claude Code native tool call); bash redirection is forbidden. Ensure the Write tool is available in the current harness context.
    ```
    The skill MUST NOT silently fall back to bash redirection or any other bash-side write mechanism. A fallback write would bypass the PostToolUse gate and violate this postcondition. Cross-reference EC-016 (below) for the unavailability edge case.

    **Architectural anchor**: ADR-026 §Decision 8 — Write-tool-only mandate and agent-orchestrated four-step flow.

    **Write-path verification**: The agent MUST verify that the written content is byte-identical to the `--emit-handoff` payload before the `--commit` subcommand is invoked (step 4). This prevents truncated or corrupted writes from being committed silently. If content verification fails, the skill MUST surface a hard error identifying the byte-count discrepancy before attempting to commit.

## Invariants

1. **No in-context memory assertions**: Every `HANDOFF.md` field value must be derivable from an external source (git, filesystem, index file). A field whose value cannot be cross-checked must be omitted or flagged with an explicit `TBD` + operator action item — not silently populated from in-context reasoning.

2. **Wave cannot be closed without a passing HANDOFF.md**: The wave-gate's "declare wave closed" step is gated behind this BC's Postconditions. A wave-gate invocation that skips HANDOFF.md production is a specification violation.

3. **HANDOFF.md is a singleton per wave boundary**: There is one `HANDOFF.md` on `factory-artifacts` (not wave-scoped files). Each wave close overwrites the previous HANDOFF.md with the new wave's verified state. Git history preserves prior HANDOFF.md versions.

4. **Anti-fabrication is not optional**: The cross-check against `git rev-parse origin/develop` for `last_verified_develop_sha` must execute as a literal shell command, not be inferred from in-context knowledge of the SHA. Same for filesystem existence checks on `active_bcs` paths.
