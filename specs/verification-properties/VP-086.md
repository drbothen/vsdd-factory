# VP-086: Dispatcher Exit-2 Propagation for PreCompact Block-Intent

## Property

When a plugin registered under `event = "PreCompact"` in `hooks-registry.toml` exits with
code `2` (block-intent), the `factory-dispatcher` binary MUST propagate `block_intent = true`
in its response to the Claude Code harness, causing the harness to defer (block) the pending
context compaction.

Formally:
- **Precondition 1:** `factory-dispatcher` receives a `PreCompact` event from the harness.
- **Precondition 2:** At least one plugin is registered under `event = "PreCompact"`.
- **Precondition 3:** The PreCompact plugin exits with code 2.
- **Postcondition (PC4):** `factory-dispatcher` output encodes `block_intent = true` (or equivalent blocking response) to the harness. The harness defers compaction.
- **Negative postcondition:** If no PreCompact plugin is registered, the dispatcher exits 0 with zero plugins run — no block, no error (EC-003 of BC-1.15.001).
- **Crash postcondition (on_error = "continue"):** If the plugin crashes without emitting exit code 2, the dispatcher exits 0 (fail-open) — compaction proceeds (BC-1.15.001 EC-004).

## Why This VP Is Safety-Critical

This is the linchpin of the PreCompact flush mechanism. If the dispatcher silently drops
exit-2 block-intent on PreCompact events:

- `precompact-flush.sh` can return exit 2 (flush failure) but the harness proceeds with
  compaction regardless.
- The entire PreCompact blocking mechanism (ADR-026 Decision 6, CAP-032 Part B) becomes
  a silent no-op.
- Context loss occurs with no warning to the operator.

This failure mode is structurally invisible — the hook runs, returns 2, but nothing is
blocked. A test that only checks `exit_code == 2` from the hook would miss this. The VP
must verify the full dispatcher → harness propagation path.

## Invariant Classification: Safety (Block-Intent Propagation Barrier)

The correctness of CAP-032 Part B depends entirely on exit-2 block-intent being faithfully
propagated from the PreCompact plugin through the dispatcher to the harness. This is a
safety property with no acceptable false-negative rate.

## Feasibility Assessment

**Feasible as bats integration test.** The factory-dispatcher is a compiled binary in
`target/debug/factory-dispatcher` (or `target/release/` in CI). Bats tests can:

1. Build the dispatcher via `cargo build -p factory-dispatcher` in the test setup.
2. Write a minimal TOML registry fixture pointing to stub scripts.
3. Pipe synthetic PreCompact event JSON to the dispatcher stdin.
4. Assert on the dispatcher exit code and stdout.

This is structurally identical to existing bats tests that exercise the dispatcher with
synthetic event payloads. The test does NOT require the Claude Code harness to be running —
it exercises the dispatcher-side propagation logic in isolation.

**Scope clarification for S-18.00:** S-18.00 determines whether `PreCompact` is already
enumerated in the dispatcher event-type enum. If absent, S-18.00 adds it. Either way,
S-18.00's bats test for this VP verifies the propagation.

## Relationship to VP-082

VP-082 verifies that `precompact-flush.sh` commits before compaction and exits 2 on failure
(hook behavior). VP-086 verifies that the dispatcher faithfully propagates that exit 2 to
the harness (dispatcher behavior). These are distinct test scopes at different architectural
layers.
