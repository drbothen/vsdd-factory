# VP-116: Shard-Cap Comparison Arithmetic Is Overflow-Safe and Boundary-Inclusive for All Symbolic Sizes

## Property Statement

The native shard-cap gate's core arithmetic — deciding whether a pending `Edit`/`Write`/`MultiEdit`
projects over the cap — is proven correct by bounded model checking over symbolic inputs, so it is
free of arithmetic overflow/underflow and is exactly boundary-inclusive.

1. **Overflow/underflow freedom.** `projected_size = current_shard_bytes + payload_bytes`, where
   `payload_bytes` is the net delta of the pending call (`content` length for `Write`; the summed
   `len(new_string) - len(old_string)` net delta for `Edit`/`MultiEdit`, which may be negative —
   BC-1.18.005 §EC-005). The computation MUST use checked/saturating integer semantics: a
   net-negative `MultiEdit` that would underflow `current_shard_bytes` saturates to a non-negative
   `projected_size` (never wraps), and a pathologically large payload never wraps a `u64`
   `projected_size`. For all symbolic `(current_shard_bytes, payload_bytes)` in the bounded domain,
   no panic and no wrap occurs.

2. **Boundary inclusivity.** `projected_size <= shard_cap_bytes ⇒ Continue` (no roll) and
   `projected_size > shard_cap_bytes ⇒ roll` — the boundary is inclusive (BC-1.18.005 §EC-002:
   equal does not roll; §EC-003: cap+1 rolls). For every symbolic `shard_cap_bytes`, the decision
   function partitions the input space at exactly `shard_cap_bytes`.

This VP proves the *shape* of the comparison and its arithmetic safety, which is locked NOW. The
concrete numeric `shard_cap_bytes` is **PROVISIONAL-until-F4** (BC-1.18.005 §Postcondition 6): the
proof is parameterized over a symbolic cap and holds unchanged whatever value the F4 synthetic
calibration harness locks — the harness changes fixture inputs, never this proof obligation.

### Why Kani

The decision is a pure integer function of `(current_shard_bytes, payload_bytes, shard_cap_bytes)`
with no I/O — exactly the class Kani verifies exhaustively (arithmetic overflow/underflow + boundary
correctness) rather than sampling. This is the strongest available method for the cap comparison and
is independent of the provisional numeric constants. Kani CLI version alignment may defer actual
execution to CI (same posture as VP-070).

## Proof Harness Skeleton

```rust
// crates/factory-dispatcher/tests/kani_shard_cap_arithmetic.rs
// VP-116: BC-1.18.005 PC3/PC4/EC-002/EC-003/EC-005

#[kani::proof]
fn proof_projected_size_never_overflows() {
    let current: u64 = kani::any();
    let delta: i64 = kani::any();
    kani::assume(current <= 1 << 40);           // bounded shard domain
    kani::assume(delta.unsigned_abs() <= 1 << 40);
    let projected = shard_manager::projected_size(current, delta); // saturating
    assert!(projected <= current.saturating_add(1 << 40));         // no wrap
}

#[kani::proof]
fn proof_boundary_inclusive() {
    let projected: u64 = kani::any();
    let cap: u64 = kani::any();
    let rolls = shard_manager::over_cap(projected, cap);
    assert_eq!(rolls, projected > cap);          // == never rolls; +1 always rolls
}
```
