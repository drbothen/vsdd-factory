# VP-109: Full-Recovery Split Recovers Every Chained Entry With Zero Data Loss and Correct Newest-First Ordering

## Property Statement

For any `last_amended` raw value classified `Eligibility::PriorChainSplit` (one or more inline
` [Prior: <date> (vX.Y) — ...]` bracket entries following a current entry):

1. `migrate_file` re-emits the CURRENT entry (everything before the first ` [Prior:` marker) as
   the new `last_amended` value, unchanged in substance (D-1144-escaped per PC3).
2. Every chained historical entry is relocated into the `changelog:` sequence as a new list item,
   PREPENDED in newest-of-the-priors-first order — the entry nested immediately inside the current
   entry's bracket becomes the first (topmost) new item, the next-nested entry becomes the second,
   and so on.
3. No entry's substantive text is truncated, reworded, or reordered relative to its neighbors
   (verbatim preservation, modulo the D-1144 escape pass).
4. Every PRE-EXISTING `changelog:` item is left byte-for-byte untouched, appearing after all N
   newly-inserted items.
5. A `[Prior history → <file>-amendment-history.md]` static pointer note is NEVER mistaken for a
   chain marker and never triggers a split (negative control).

### Why unit-test

`migrate_file`'s PC7 path (`split_tail_entries` + `parse_dated_entry` in
`crates/last-amended-migrate/src/migrate.rs`) is a deterministic, file-scoped transformation
exercised end-to-end against tempfile fixtures — no property-based generator is required to reach
full branch coverage of the split/order/preserve/negative-control decision space; the BC's original
`proptest` candidate (randomized chain length/content) remains a listed Property-Test Upgrade
Candidate in VP-INDEX.md §Property-Test Upgrade Candidates for future hardening, but is not a
precondition for this VP's initial registration since the four fixed fixtures already exercise the
full order/preservation/negative-control decision table.
