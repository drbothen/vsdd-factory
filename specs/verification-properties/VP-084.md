# VP-084: PreCompact Flush Commit Is Lifecycle-Distinct From State-Manager Burst Commit

## Property

A PreCompact flush commit on `factory-artifacts` (produced by `precompact-flush.sh`)
is a lifecycle-orthogonal event that MUST NOT be counted as a state-manager burst commit
for TD-VSDD-053 single-commit-per-burst enforcement.

Formally:
- **Precondition:** A PreCompact hook fires mid-wave and `precompact-flush.sh` commits
  to `factory-artifacts` with message matching `PreCompact flush <cycle>/<step> <ISO-timestamp>`
  (canonical format per ADR-026 §Decision 6 step 4; the old `wave-<N>` form is obsolete).
- **Subsequent state-manager burst:** The state-manager performs a normal burst (Commits
  A/B/C/D/E sequence) after the PreCompact flush.
- **Postcondition A:** The `validate-burst-log` hook does NOT fire `MULTI_COMMIT_CHAIN_NOT_ALLOWED`
  for the PreCompact flush commit + the subsequent state-manager burst commit, even if
  both appear in consecutive `git log factory-artifacts` positions.
- **Postcondition B:** The burst-log entry for the state-manager burst contains exactly
  ONE logical burst commit citation. The PreCompact flush commit is NOT cited as a
  Commit A/B/C/D/E step.
- **Postcondition C:** The `MULTI_COMMIT_CHAIN_NOT_ALLOWED` detector fires ONLY for
  state-manager bursts where two consecutive commits both contain "backfill" / "Stage N" /
  "Stage N+1" in their commit messages — NOT for PreCompact prefix commits.

## Invariant Classification: Invariant (Lifecycle Boundary)

This invariant ensures that the factory's TD-VSDD-053 multi-commit-chain detector does not
produce false-positive blocks due to the presence of legitimate PreCompact flush commits in
the `factory-artifacts` history.

## Proof Harness Skeleton (Integration / Bats)

**F-P5-004 note:** The real artifact for `validate-burst-log` is `hook-plugins/validate-burst-log.wasm`, registered in `hooks-registry.toml` as a native WASM plugin invoked via the factory-dispatcher (event: PostToolUse; tool: Edit|Write for burst-log structural validation + Bash for ADR-029 §Decision 1 chain detection). There is no `validate-burst-log.sh` shell script. The harness MUST invoke the WASM plugin through the dispatcher by piping a synthetic PostToolUse event JSON — the same path used in production. Direct `bash ... .sh` invocation is incorrect and would silently test nothing.

```bash

# Anchor: precompact_flush_does_not_trigger_multi_commit_chain_block

@test "PreCompact flush commit followed by state-manager burst does not trigger TD-VSDD-053" {

    assert_success
```

## Feasibility Assessment

**Two-layer proof architecture (ADR-029 §Decision 8).** VP-084 is proven by two
complementary and non-redundant test layers. Neither layer alone is sufficient:

**Layer 1 — Pure-Rust unit tests (`exemption.rs` Section 1): load-bearing proof of
`is_precompact_flush_exempt` and `check_multi_commit_chain`.**

These tests call the pure functions directly with controlled synthetic inputs. They are the
load-bearing proof vehicle for the 3-case exemption decision logic:
- Case (a): log present, FIELD-4=`commit`, SHA match → exempt (AC-001).
- Case (b): log present, FIELD-4 corrupted → treat as absent → exempt on prefix alone (AC-003).
- Case (c): log absent → exempt on prefix alone (AC-002).
- SHA-mismatch with valid FIELD-4 → NOT exempt (AC-004).
- Case-sensitive prefix; no trailing space → NOT exempt (AC-005 / EC-006).

These tests are mutation-sensitive: forcing `is_precompact_flush_exempt → return false`
causes the SHA-mismatch test (AC-004) to incorrectly return `true` (mutant kills test).
Forcing `return true` causes the case-sensitive / lowercase test to pass (mutant kills test).
The pure-logic layer is the correct VSDD location for exemption-decision proof: pure-core
logic is verified at the unit level, without I/O.

**Layer 2 — Bats integration tests (`vp084-proof.bats`): load-bearing proof of
dispatcher injection plumbing + chain-detection discrimination end-to-end.**

The bats tests set up real git repos at `$CLAUDE_PROJECT_DIR/.factory`, invoke the
factory-dispatcher binary with qualifying PostToolUse Bash events, and assert on
the dispatcher's block/continue output. They prove:
- Test 1: PreCompact HEAD in real git repo → dispatcher injects non-sentinel `head_subject`
  → WASM reads injected context → chain detector does NOT fire → Continue (correct real-world
  topology; proves injection plumbing delivers the right context to the WASM).
- Test 2: Same for `validate-dispatch-advance` (symmetric implementation, INV2).
- Test 3 (negative control / mutation anchor): Sentinel chain in real git repo → dispatcher
  injects sentinel `head_subject` + `head_parent_subject` → WASM reads injected context →
  chain detector fires → MULTI_COMMIT_CHAIN_NOT_ALLOWED block. This test IS mutation-resistant
  against "always Continue" mutations: if the chain-detection path is disabled or the WASM
  reads empty context (fail-open), Test 3 fails because no block is emitted.

**Non-tautology argument (ADR-029 §Decision 8 mutation finding).**

The mutation `is_precompact_flush_exempt → return false` leaves all three bats tests GREEN.
This is expected and is NOT a defect in the bats tests. The reason: real PreCompact flush
subjects (`PreCompact flush <cycle>/<step> <ISO-TS>`) contain no "backfill", "Stage 1", or
"Stage 2" tokens — they are non-sentinel. The MULTI_COMMIT_CHAIN block fires only when BOTH
head_subject and head_parent_subject are sentinel. A non-sentinel HEAD subject cannot trigger
the block regardless of the exemption, so forcing the exemption to `return false` for a
non-sentinel PreCompact subject changes nothing: the block would not fire either way. The
bats tests verify that the PreCompact topology produces the correct real-world outcome
(no block) via the full dispatcher→WASM path, which is what Postcondition A and C assert.
Postcondition B (burst-log citation clarity) is verified structurally in the burst-log.md
fixture. The tests are non-tautological at the suite level because Test 3 (negative control)
fails when the chain-detection path is broken.

**The exemption is not dead code.** The exemption is a defense-in-depth layer. It ensures
that if the `contains_sentinel` predicate is ever broadened (e.g., a cycle name that contains
a sentinel word, or a future TD-VSDD-053 extension), PreCompact flush commits remain protected
by an explicit, documented named exemption. Removing the exemption would create a future
correctness hazard with no detection mechanism other than a new failing production block.

**F-P5-004 closure note:** Prior harness versions called `bash plugins/vsdd-factory/hooks/validate-burst-log.sh`, which does not exist. The `validate-burst-log` plugin is a native WASM crate (confirmed by hooks-registry.toml: `plugin = "hook-plugins/validate-burst-log.wasm"`). The corrected harness uses the dispatcher binary path, which is the correct verification surface for a WASM plugin.

The key implementation requirement is that the `validate-burst-log` and
`validate-dispatch-advance` WASM plugins MUST be updated to exempt commits with the
`PreCompact flush ` message prefix (the canonical exemption prefix per ADR-026 §Decision 10;
covers all `<cycle>/<step>` forms; the old `PreCompact flush wave-` form is obsolete and
MUST NOT be used as the exemption pattern — it would miss non-wave engine-context commits)
from the MULTI_COMMIT_CHAIN detector, using the three-gate corroboration logic in
BC-5.41.003 PC1 (SHA match + field-4 equals `commit` + genuine-absence fallback).
This exemption MUST be implemented in S-18.04 alongside the hook itself.

The precompact-flush-log four-field entry MUST be present in the bats test setup for
case (a) (log present, SHA matches, field-4 = `commit`) to be exercised in the integration
path. The pure-Rust unit tests in `exemption.rs` Section 1 already exercise all three cases
directly at the function level.
