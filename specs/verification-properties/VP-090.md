# VP-090: precompact-flush-log Pruning — prune to Most-Recent-500 Entries When Count Exceeds 1000, Via precompact-flush-prune.sh

## Property

When the `precompact-flush-log` file (`.factory/hooks/precompact-flush-log`) exceeds 1000
entries, the pruning mechanism MUST reduce the file to the most-recent 500 entries, discarding
the oldest entries. This pruning is implemented by `precompact-flush-prune.sh`, invoked by
the `check-state-health` skill (not by `precompact-flush.sh` itself).

### §1 Pruning Threshold and Target

- **Threshold:** Pruning fires ONLY when the current entry count EXCEEDS 1000 lines. At
  exactly 1000 lines or fewer, no pruning occurs.
- **Target:** After pruning, the file contains exactly the MOST-RECENT 500 entries (i.e.,
  the last 500 lines of the file before pruning, which represent the 500 most recent flush
  events in chronological order). All entries before these 500 are discarded.
- **Entry preservation invariant:** No entry that is within the most-recent-500 set is
  ever discarded by pruning. Pruning never touches the last line (the authoritative SHA for
  BC-5.41.003 validation). The last line after pruning is the same as the last line before
  pruning.

- **Precondition:** `precompact-flush-log` has 1001 or more entries.
- **Postcondition (PC1):** After `precompact-flush-prune.sh` runs, the file has exactly 500
  entries — the 500 most recent ones in the same chronological order. The last line is
  unchanged.

### §2 Boundary Condition — No Pruning at or Below Threshold

- **Precondition:** `precompact-flush-log` has exactly 1000 entries (threshold, not exceeded).
- **Postcondition (PC2):** `precompact-flush-prune.sh` runs and exits 0 without modifying
  the file. Entry count remains 1000.

- **Precondition:** `precompact-flush-log` has 999 entries (below threshold).
- **Postcondition (PC2b):** Same as PC2 — no modification.

### §3 Invocation Context — check-state-health, Not precompact-flush.sh

The pruning step is invoked by `check-state-health` skill, NOT by `precompact-flush.sh`.
`precompact-flush.sh`'s PC8/Inv3 govern append-only growth; Inv7 explicitly defers pruning
to a separate `precompact-flush-prune.sh` helper invoked by `check-state-health`.

- **Postcondition (PC3):** `precompact-flush.sh` contains no call to
  `precompact-flush-prune.sh` and no count-check logic. The flush script remains focused on:
  commit → append → push (Inv3 canonical order). Pruning is orthogonal to flush correctness.

### §4 Atomic Write — No Partial-Prune State

The prune operation MUST be atomic with respect to the file: either the file is pruned to
500 entries, or it remains at its pre-prune state. A partial write that leaves the file in
an inconsistent state (e.g., truncated mid-line) is a specification violation.

- **Postcondition (PC4):** After pruning, `precompact-flush-log` is a valid log file: all
  lines are complete 4-field entries in the canonical format
  `<ISO-timestamp> <SHA> <cycle>/<step> commit`. No partial lines exist. The file is valid
  UTF-8 with a trailing newline.

## Why This VP Matters

BC-7.07.001 Inv7 documents an explicit production-grade deferral per Canonical Principle
Rule 3: pruning is deferred to S-18.04 AC-N with a concrete story anchor and a defined size
budget (~120 bytes/line × 1000 entries ≈ 120KB — acceptable as a bridge). Without pruning,
`precompact-flush-log` grows unboundedly. At high PreCompact event frequency (e.g., long
pipeline runs), the file could grow large enough to:
1. Cause the `validate-burst-log` WASM plugin to read a large log on every PostToolUse event.
2. Exceed any line-count assumption in the `check-state-health` skill.

The pruning obligation is anchored in ADR-026 §Crash-Consistency Design item 4. This VP
ensures that when S-18.04 AC-N ships, the pruning behavior is specified and testable.

DI-025 is cited because the pruning operation touches `precompact-flush-log`, which is the
append-only corroboration log for the DI-025 lifecycle-orthogonality exemption. Pruning must
preserve the last-line invariant (the most-recent SHA must survive pruning) to maintain DI-025
corroboration integrity.

## Proof Harness Skeleton (Unit Test / Bats)

```bash
# File: plugins/vsdd-factory/tests/precompact-flush-prune.bats
# Anchor: precompact_flush_log_pruning

@test "precompact-flush-prune.sh prunes log to most-recent 500 when count exceeds 1000" {
    # Setup: create precompact-flush-log with 1001 synthetic entries (4-field format)
    #        Entry 1 is oldest (timestamp 2026-01-01T00:00:00Z sha_0001 v1.0/S-1.01 commit)
    #        Entry 1001 is newest (timestamp 2026-12-31T23:59:59Z sha_1001 v1.0/S-18.05 commit)
    generate_log_fixture 1001 > "$TEST_LOG_FILE"
    bash plugins/vsdd-factory/hooks/precompact-flush-prune.sh "$TEST_LOG_FILE"
    # Assert: file now has exactly 500 lines
    LINE_COUNT=$(wc -l < "$TEST_LOG_FILE")
    [ "$LINE_COUNT" -eq 500 ]
    # Assert: last line is still entry 1001 (the most recent)
    LAST_LINE=$(tail -1 "$TEST_LOG_FILE")
    echo "$LAST_LINE" | grep -q "sha_1001"
    # Assert: first line is now entry 502 (the 502nd oldest = 500th from the end)
    FIRST_LINE=$(head -1 "$TEST_LOG_FILE")
    echo "$FIRST_LINE" | grep -q "sha_0502"
}

@test "precompact-flush-prune.sh does not prune when count is exactly 1000" {
    # Setup: 1000-entry log
    generate_log_fixture 1000 > "$TEST_LOG_FILE"
    BEFORE=$(md5 < "$TEST_LOG_FILE")
    bash plugins/vsdd-factory/hooks/precompact-flush-prune.sh "$TEST_LOG_FILE"
    AFTER=$(md5 < "$TEST_LOG_FILE")
    # Assert: file unchanged
    [ "$BEFORE" = "$AFTER" ]
}

@test "precompact-flush-prune.sh does not prune when count is 999" {
    generate_log_fixture 999 > "$TEST_LOG_FILE"
    BEFORE=$(wc -l < "$TEST_LOG_FILE")
    bash plugins/vsdd-factory/hooks/precompact-flush-prune.sh "$TEST_LOG_FILE"
    AFTER=$(wc -l < "$TEST_LOG_FILE")
    [ "$BEFORE" -eq "$AFTER" ]
}

@test "precompact-flush-prune.sh produces valid 4-field entries after pruning" {
    generate_log_fixture 1500 > "$TEST_LOG_FILE"
    bash plugins/vsdd-factory/hooks/precompact-flush-prune.sh "$TEST_LOG_FILE"
    # Assert: every line has exactly 4 space-separated fields
    # Assert: field-4 of every line is the literal string "commit"
    while IFS= read -r line; do
        FIELD_COUNT=$(echo "$line" | awk '{print NF}')
        [ "$FIELD_COUNT" -eq 4 ]
        FIELD4=$(echo "$line" | awk '{print $4}')
        [ "$FIELD4" = "commit" ]
    done < "$TEST_LOG_FILE"
}

@test "precompact-flush.sh does not call precompact-flush-prune.sh" {
    # Assert: precompact-flush.sh source does not contain a call to precompact-flush-prune.sh
    # This confirms §3 (pruning is orthogonal to flush)
    grep -q "precompact-flush-prune" plugins/vsdd-factory/hooks/precompact-flush.sh
    assert_failure  # grep should find NOTHING
}
```

## Feasibility Assessment

**Fully feasible as bats unit tests.** `precompact-flush-prune.sh` is a shell script helper
that operates on a plain text file (one log entry per line). All four properties can be
verified by:

1. Generating synthetic log fixtures with a known number of entries (helper function using
   `seq` + `printf`).
2. Invoking `bash plugins/vsdd-factory/hooks/precompact-flush-prune.sh <logfile>` directly.
3. Asserting on line count, first/last line content, 4-field format correctness, and the
   absence of pruning logic in `precompact-flush.sh`.

No live dispatcher or git repository is required for pruning verification. The `tail -500`
implementation pattern is straightforward and idempotent.

**Precondition for test execution:** `precompact-flush-prune.sh` must exist at
`plugins/vsdd-factory/hooks/precompact-flush-prune.sh` and be callable as a standalone
script accepting a log file path as its first argument. This is the S-18.04 AC-N deliverable.
