# VP-083: Completeness Gate Is No-Op on Wave-1 or Non-HANDOFF.md Writes

## Property

The `validate-wave-handoff-completeness` WASM gate MUST return `Continue` (not block)
in two specific conditions that must not create false-positive blocking:

1. **Wave-1 no-op (PAYLOAD-ONLY) — CONDITIONAL on NOT EPIC-COMPLETE (F-P25-002):** When
   `wave_id == 1` in the HANDOFF payload YAML AND the payload is NOT in EPIC-COMPLETE context
   (i.e., `next_wave_stories` is non-empty or absent) — the gate reads `wave_id` directly from
   the YAML inside `handoff_content` (F-A005: `GateContext` carries only `file_path` and
   `handoff_content`; no external `is_first_wave` field exists). Wave-1 identity is derived
   INSIDE `check_handoff_completeness` from the parsed `wave_id` value. No filesystem, git,
   sprint-state.yaml, or factory-artifacts read is performed to determine first-wave status.
   The shell wave-handoff skill (BC-5.41.001) is responsible for deriving `wave_id` from real
   substrate and embedding it in the HANDOFF payload YAML before writing.

   **Single-wave EPIC-COMPLETE exception:** When `payload.wave_id == 1` AND
   `next_wave_stories: []` (EPIC-COMPLETE context) — the wave-1 no-op does NOT apply. The gate
   evaluates the EPIC-COMPLETE branch (PC2a) and validates `epic_status: complete` regardless
   of `wave_id`. This is because a single-wave epic whose only wave is wave 1 can legitimately
   reach terminal status without proceeding to wave 2. On such a write, skipping the EPIC-COMPLETE
   branch would leave `epic_status` never validated — the completeness gate's purpose (preventing
   an incomplete handoff from being committed) would be a no-op on the single-wave-final case.
   The EPIC-COMPLETE discriminator is PAYLOAD-ONLY (`next_wave_stories: []` from the current
   payload), so evaluating it at wave_id==1 is sound and preserves pure-parse purity.
   Per ADR-026 §Decision 9, the canonical evaluation order is: (1) non-HANDOFF.md → no-op;
   (2) EPIC-COMPLETE detection → validate epic_status if true, even at wave_id==1; (3) wave_id==1
   AND NOT EPIC-COMPLETE → no-op; (4) wave_id>1 → full validation.

2. **Non-HANDOFF.md target write (wave-agnostic):** When the gate fires on a Write/Edit event
   whose target file is NOT `HANDOFF.md` (e.g., other `factory-artifacts` file writes such
   as STATE.md, wave-state.yaml, etc.). The gate performs no field validation and returns
   `Continue` unconditionally for non-HANDOFF.md targets at ANY wave — including wave 1 and
   wave_id-absent — because the non-HANDOFF.md check precedes any wave_id evaluation
   (BC-4.14.001 PC4/Inv3). The WASM gate is a pure-parse gate operating on the Write/Edit
   payload; it cannot perform a filesystem probe to determine HANDOFF.md file-absence.

The gate blocks ONLY when:
- The target file being written IS `HANDOFF.md`, AND one or more required fields are
  missing or malformed; OR
- `wave_id` is ABSENT from the payload → gate FAILS CLOSED: proceeds to full validation,
  blocking with `HandoffIncomplete: ["wave_id"]` (absent `wave_id` is NOT treated as wave-1); OR
- EPIC-COMPLETE context is detected (`next_wave_stories: []`) AND `epic_status` is absent or
  invalid — this applies even when `wave_id == 1` (single-wave EPIC-COMPLETE case).

Formally:
- **Postcondition (payload.wave_id == 1, NOT EPIC-COMPLETE):** `Continue`. No block. Wave-1 no-op (applies when `next_wave_stories` is non-empty or the payload does not assert EPIC-COMPLETE).
- **Postcondition (payload.wave_id == 1, EPIC-COMPLETE — `next_wave_stories: []`):** Gate evaluates PC2a. If `epic_status: complete` present and valid → `Continue`. If `epic_status` absent → `MissingEpicStatus` block. If `epic_status` present but not `complete` → `HandoffIncomplete: epic_status malformed` block.
- **Postcondition (payload.wave_id > 1, non-HANDOFF.md write):** `Continue`. No block.
- **Postcondition (payload.wave_id > 1, HANDOFF.md write, all fields present):** `Continue`.
- **Postcondition (payload.wave_id > 1, HANDOFF.md write, field missing):** `HandoffIncomplete(<field_name>)` block.
- **Postcondition (wave_id ABSENT from payload):** Gate FAILS CLOSED — proceeds to full validation; blocks with `HandoffIncomplete: ["wave_id"]` (and any other missing required fields). Does NOT return `Continue`.

## Invariant Classification: Invariant (No False-Positive Block)

A false-positive block on wave-1 or on normal file writes would block the factory
from operating at all. This invariant ensures the gate is safe to deploy without
disrupting existing pipelines.

// Anchor: no_false_positive_on_wave_1

use validate_wave_handoff_completeness::{check_handoff_completeness, GateContext, GateResult};

// NOTE (F-A005): GateContext has been reduced to payload-only fields:
//   GateContext { file_path: String, handoff_content: Option<String> }

// struct (eliminated by F-A005). Wave-1 identity is derived PAYLOAD-ONLY INSIDE

// boolean is needed or accepted. The shell wave-handoff skill (BC-5.41.001) derives
// `wave_id` from real substrate and embeds it in the HANDOFF payload before writing.
// The WASM gate is a CONSUMER of `wave_id` in the YAML content — it does not accept

#[test]
fn wave_1_no_op_no_handoff() {
    // Non-HANDOFF.md path: gate fires on a different file → Continue unconditionally.
    // wave_id does not matter — the non-HANDOFF.md check (step 1) precedes all wave_id logic.
    let ctx = GateContext {
        file_path: "factory-artifacts/SOME_OTHER_FILE.md".to_string(),
        handoff_content: None,
    };
    assert_eq!(check_handoff_completeness(&ctx), GateResult::Continue);
}

#[test]
fn wave_1_no_op_even_with_handoff_present() {
    // NOTE (F-P25-002): this no-op applies ONLY when the payload is NOT in EPIC-COMPLETE context
    // (i.e., next_wave_stories is non-empty or not present as an empty list). When wave_id==1
    // AND next_wave_stories:[] (EPIC-COMPLETE), the gate evaluates PC2a — see
    // `wave_1_epic_complete_validates_epic_status_present` below.
    //
    // Wave-1 identity is derived from `wave_id: 1` in handoff_content (F-A005 payload-only).
    // next_wave_stories is non-empty → NOT EPIC-COMPLETE → wave-1 no-op applies.
    let ctx = GateContext {
        file_path: "factory-artifacts/HANDOFF.md".to_string(),
        handoff_content: Some("wave_id: 1\nnext_wave_stories:\n  - {id: S-02.01, status: pending}\n".to_string()),

#[test]
fn wave_1_epic_complete_validates_epic_status_present() {

#[test]
fn wave_1_epic_complete_blocks_malformed_base_field() {
    // F-P32-002 + F-A005: DISCRIMINATING fixture proving EPIC-COMPLETE branch (step 2 per
    // ADR-026 §Decision 9 Inv3) fires BEFORE the wave-1 no-op (step 3).
    //
    // Setup: handoff_content has wave_id==1 + next_wave_stories:[] (EPIC-COMPLETE) +
    // last_verified_develop_sha is an empty string (treated as a malformed/missing base field
    // per BC-4.14.001 PC7 / EC-004). Wave-1 identity is derived from `wave_id: 1` in the
    // handoff_content YAML (F-A005 payload-only). No is_first_wave field exists.
    //
    // Expected: gate BLOCKS with HandoffIncomplete on the empty last_verified_develop_sha.
    //
    // Why this is discriminating: if the gate had short-circuited on the wave-1 no-op (step 3)
    // before reaching full validation, it would return Continue (no block). A Block result is
    // therefore a direct witness that:
    //   (a) the gate DID NOT short-circuit on wave-1 no-op, AND
    //   (b) the EPIC-COMPLETE branch (step 2) was entered and full base-field validation ran.
    //
    // The prior two EPIC-COMPLETE fixtures test epic_status presence/absence on otherwise-valid
    // payloads; they do not distinguish "gate reached EPIC-COMPLETE branch" from "gate happened
    // to check epic_status by coincidence". This fixture eliminates that ambiguity.
    //
    // Also corroborates BC-4.14.001 PC7/EC-004 (F-P32-001): empty scalar = malformed base field.
    let ctx = GateContext {
        file_path: "factory-artifacts/HANDOFF.md".to_string(),
        // wave_id:1 + next_wave_stories:[] (EPIC-COMPLETE) + last_verified_develop_sha is empty
        // (malformed base field per BC-4.14.001 EC-004) + epic_status: complete (present and valid)
        handoff_content: Some(
            "wave_id: 1\nnext_wave_stories: []\nepic_status: complete\nlast_verified_develop_sha: \"\"\n".to_string()
        ),
    };
    let result = check_handoff_completeness(&ctx);
    assert!(matches!(
        result,
        GateResult::Block { code: "HandoffIncomplete", .. }
    ), "Expected HandoffIncomplete block: gate must enter EPIC-COMPLETE branch (step 2) and \
        run full base-field validation; empty last_verified_develop_sha is malformed (EC-004). \
        If gate returned Continue, it short-circuited on wave-1 no-op (step 3) — evaluation \
        order violation per ADR-026 §Decision 9 Inv3.");
    // Additionally verify the block message names last_verified_develop_sha as the failing field
    if let GateResult::Block { message, .. } = result {
        assert!(message.contains("last_verified_develop_sha"),
            "HandoffIncomplete block must name 'last_verified_develop_sha' as the malformed field");
    }
}

## Feasibility Assessment

**Feasible as Rust unit test.** The gate logic is a pure function over a `GateContext`
struct containing only `file_path: String` and `handoff_content: Option<String>` (F-A005
payload-only API — `is_first_wave` and `close_wave_mode` fields were eliminated). No
filesystem or git access at the unit level — `wave_id` is read from the HANDOFF YAML
content inside `handoff_content`, and wave-1 identity is derived internally by
`check_handoff_completeness` from the parsed `wave_id` value. The fail-closed path
(absent `wave_id` in the YAML → HandoffIncomplete) is equally testable as a unit test:
supply a payload with wave_id absent and assert the Block result. The integration-level
git-SHA cross-check is tested separately in VP-081 integration harness at
`tests/integration_test.rs`.

WASM fuel consumption is bounded: the gate parses only HANDOFF.md frontmatter fields
(not the body) and does not perform I/O beyond `host::read_file` on the target path.
