# VP-139: Staged Roll Self-Heals an Index-After-Truncate Crash (E-SHD-007)

## Property Statement

BC-1.18.006's staged four-step roll (read → publish sealed shard → atomic-truncate canonical →
publish index) has three distinct crash points. This VP covers the THIRD: step (d) index publish
fails AFTER step (c) atomic-truncate succeeded (`E-SHD-007`).

1. **Post-crash state is a metadata gap, never data loss.** When the index publish (step (d)) fails
   after the canonical truncate (step (c)) succeeded, the canonical file is CORRECTLY fresh and
   empty (safe for all future writes — no over-cap risk) and the sealed shard file exists correctly
   on disk, but `<artifact-stem>.shard-index.toml` has not yet recorded the new `[[shard]]` entry —
   a discoverability-METADATA gap ONLY (BC-1.18.006 §Postcondition 1 step (d) / §EC-011).
   Whole-corpus glob-based readers (`<stem>*.md`) still find the sealed file regardless of index
   membership, so NO reader-visible data loss occurs.

2. **Self-healing index reconciliation.** On the next dispatch attempt, BEFORE evaluating any new
   trigger, the gate reconciles the index by scanning the filesystem for sealed-shard files matching
   the artifact's naming convention that are absent from the index, and appends the missing entries
   (BC-1.18.006 §Postcondition 1 step (d) recovery). No operator intervention is required.

3. **Reconciliation is append-only-tail and idempotent.** The missing `[[shard]]` entry is APPENDED
   to the index tail with its correct monotonic `seq` — never rewriting or reordering any existing
   entry (BC-1.18.006 §Postcondition 5). Re-running reconciliation against an already-consistent
   index is a no-op: a sealed shard already present in the index is not appended a second time, so
   no duplicate `[[shard]]` entry is ever produced.

4. **Post-recovery census holds.** After reconciliation, every sealed shard on disk has exactly one
   corresponding `[[shard]]` index entry and every index entry corresponds to a real sealed file —
   the index is a faithful, gap-free, duplicate-free record of the sealed shards.

### Why integration

Inducing a step-(d) partial write and observing the next dispatch's filesystem-scan reconciliation
are real-substrate filesystem/process properties across two invocations — the fault-injection
integration class VP-124 / VP-133 / VP-138 use; a pure unit test cannot express the FS-scan
detect-and-append recovery.

## Proof Harness Skeleton

```rust
// crates/factory-dispatcher/tests/shard_roll_eshd007_recovery_test.rs
// VP-139: BC-1.18.006 PC1 step (d) / EC-011 / PC5 — E-SHD-007 self-healing index reconciliation

#[test]
fn test_BC_1_18_006_EC011_index_after_truncate_crash_is_metadata_gap_not_loss() {
    let cx = DispatchHarness::with_cycle_fixture(current_bytes = 45_000, cap = 49_152);
    cx.inject_fs_failure_at_step_d();                       // index publish fails after truncate
    let _ = cx.dispatch_write("decision-log.md", payload = 5_000);
    assert_eq!(cx.byte_len("decision-log.md"), 0);          // canonical correctly fresh
    assert!(cx.path_exists("decision-log.0001.md"));        // sealed shard on disk
    assert!(cx.read_shard_index("decision-log").shards.iter().all(|s| s.seq != 1)); // index gap
    assert!(cx.glob("decision-log*.md").contains("decision-log.0001.md")); // glob still finds it
}

#[test]
fn test_BC_1_18_006_EC011_next_dispatch_reconciles_index_append_only_idempotent() {
    let cx = DispatchHarness::with_cycle_fixture(current_bytes = 45_000, cap = 49_152);
    cx.inject_fs_failure_at_step_d(); cx.dispatch_write("decision-log.md", payload = 5_000);
    cx.clear_fs_failure();
    cx.dispatch_write("decision-log.md", payload = 100);    // next dispatch reconciles first
    let idx = cx.read_shard_index("decision-log");
    assert_eq!(idx.shards.iter().filter(|s| s.seq == 1).count(), 1); // appended once, no dup
    cx.reconcile_index("decision-log");                     // second reconciliation is a no-op
    assert_eq!(cx.read_shard_index("decision-log").shards.len(), idx.shards.len());
}
```
