### S-21.25 — Fuel-headroom WARN event (new tracked story)

**Scope:** Deliver ADR-039 §Decision 5 Mitigation 1, currently a live MUST-requirement with
zero owning story and zero live code (abandoned branch `fix/fuel-exhaustion-fail-loud`). On
`PluginResult::Ok`, if `fuel_consumed > 0.9 × cap`, the dispatcher MUST emit a WARN-level
structured event: `"fuel-headroom-warning: plugin consumed ≥90% of budget; next larger input
may trap — recalibrate fuel_cap"`, carrying `plugin_name`, `fuel_consumed`, `fuel_cap`, and
`headroom_ratio` fields. The check belongs in the `Ok` path of the invocation result handler,
in the invoke module (`crates/factory-dispatcher/src/invoke.rs`), after
`fuel_consumed_from_store` is computed. Test coverage: positive control (`fuel_consumed`
just above 90% of `cap` → WARN fires with correct fields), negative control (`fuel_consumed`
well below 90% → no WARN), and boundary control (`fuel_consumed` exactly at 90% — inclusive or
exclusive threshold MUST be decided and asserted, not left ambiguous; ADR-039's own wording
("> 0.9 × cap") is strict-greater-than, so exactly 90% MUST NOT fire — assert this explicitly).

**Phase-2-independent scope, per operator direction:** this story is fully independent of the
6 split seams above. Mitigation 1 requires only the pre-existing `fuel_cap` registry field
(shipped well before S-21.10/S-21.11 — `fuel_cap` predates the `failure_policy` axis entirely,
per ADR-042) and the already-correct fuel-exhaustion detection path
(`Trap::OutOfFuel` → `fuel_consumed_from_store`). It does not touch `failure_policy`,
`on_error`, `execute_tiers`'s block-decision loop, or `legacy-bash-adapter` at all. It can be
implemented, tested, and merged in any order relative to S-21.19–S-21.24.

**ADR-039 anchor:** §Decision 5, "Mitigation 1 — Fuel-headroom warning" (lines 754–759 of
ADR-039 v1.14). Mitigation 2 (the ≥574 KB production-scale fixture) is already delivered
(S-21.07, commit e94767bc) and is NOT part of this story's scope — Mitigation 1 only.

**BC status — routing note (architect cannot author BCs; product-owner's domain per
CLAUDE.md Agent Routing Table):** no existing BC governs this WARN-emission behavior. Before
this story enters Phase 3 TDD, **product-owner MUST author a new BC** (next collision-free ID
in the SS-01 range, e.g. `BC-1.03.019` — story-writer/product-owner to confirm at authoring
time against BC-INDEX.md's live state) covering: the `fuel_consumed > 0.9 × cap` predicate
(strict inequality), the four required event fields, the `Ok`-path-only scope (a `Timeout`
outcome is a distinct, already-handled case — this event is specifically the near-miss
warning, not the exhaustion block/advisory itself), and negative/boundary controls. This is a
genuine cross-agent routing surface (BC authoring is out of architect's domain), not a
deferred decision this plan leaves unresolved — the scope, predicate, and event-field
contract are fully specified above and in ADR-039 §Decision 5 itself; only the formal BC
document needs authoring.

**Tasks (indicative, for story-writer to formalize):** (1) implement the `> 0.9 × cap` check
in `invoke.rs`'s `Ok`-path result handler; (2) emit the structured WARN event with the four
required fields via the existing `InternalLog`/lifecycle-event mechanism (same family as
`break_glass.activated`, `plugin.log`, etc.); (3) write positive/negative/boundary-control
tests; (4) CHANGELOG entry.

**BCs:** TBD — new BC to be authored by product-owner (see routing note above); traces to
ADR-039 §Decision 5.

**Subsystems:** `[SS-01]` (invoke module only).

**Depends on:** `[]` — fully independent, no hard prerequisite. (Soft/logical relationship to
S-21.10/S-21.11's fuel-exhaustion work exists only in that they share the same
`fuel_consumed_from_store` measurement primitive, but neither reads nor writes the other's
code paths.)

**Blocks:** none.

**Points:** 5 (small-to-medium: one predicate + one structured event + boundary-tested
coverage; no registry schema change, no cross-crate wiring).

## 8. Atomicity-Constraint Resolution (F-S2119-P1-001) — 2026-08-20

### 8.1 The finding

S-21.19's pre-TDD adversarial convergence pass raised BLOCKER **F-S2119-P1-001**: a
split-integrity, CWE-636 atomicity violation. BC-1.03.017 v1.18 Invariant 7 + PC11
(`test_no_on_error_block_without_fail_closed_when_3arg_executor`) require the executor's
enforcement-active state and the five `on_error="block"` targeted plugins'
`failure_policy="fail-closed"` annotations to be atomic — mechanically un-mergeable to exist
apart, on any single commit tree. PC11 is a **design-flow-independent** static scan of
`crates/factory-dispatcher/src/executor.rs`'s real block-decision chain, not a
registry-scoped or runtime check: the moment any block-decision site in that chain references
`.failure_policy` for a `Timeout` outcome, PC11 treats the executor as "enforcement-active,"
regardless of which registry file is loaded at runtime or how the data reaches that site.

As originally drafted, S-21.19 (wave 6) wired the extended 3-arg decision function directly
into `execute_tiers`/`execute_tier`'s real block-decision call site — making the executor
enforcement-active from the moment S-21.19 merged. The five targeted plugins' annotations,
however, land downstream: S-21.21/S-21.23 (wave 7, calibration + break-glass prerequisite) and
S-21.24 (wave 8, the actual annotation commits). Between S-21.19's merge and S-21.24's merge,
`develop` therefore carried a live, undetected, multi-wave CWE-636 fail-open window — the exact
state PC11 exists to make mechanically impossible. S-21.19's own Task 5 "ATOMICITY GATE" note
additionally mischaracterized this window as "vacuously satisfied" because "no plugin is
annotated yet"; this is false — vacuous truth requires an empty quantified set, and the
five-plugin set is fixed and non-empty, so "zero of five annotated" makes PC11's universal
assertion FALSE, not vacuously true.

### 8.2 Resolution chosen: capstone-owned enforcement flip (refined Option A)

**Refined by the ADR-044 v1.1 Addendum — see §8.7.** This subsection's "the wiring event moves
to S-21.24" describes the EXHAUSTION-LEG-ONLY half of the picture as of 2026-08-22; the
error-exit leg's wiring moves to S-21.21 instead (§8.7). Read both together.

**The enforcement-active wiring event moves from S-21.19 to S-21.24.** S-21.19 retains
authorship of the extended 3-arg `plugin_fail_closed` function and the
`PluginOutcome.failure_policy` field, both fully unit-tested — but as a **standalone, callable
pure function** that is never invoked from `execute_tiers`/`execute_tier`'s real block-decision
call site within this story. Populating `PluginOutcome.failure_policy` at construction sites is
retained in S-21.19 (inert data plumbing, not a "block-decision site... deciding to block" —
does not trip PC11). The actual wiring — replacing the real call site's 2-arg invocation with
the 3-arg form — becomes a new Task 0 in **S-21.24**, landed only after all five plugins'
annotations are already known-present (S-21.21's calibration + S-21.23's break-glass mechanism,
both wave 7; the three non-Agent plugins' and two Agent-gate plugins' actual registry
annotations, already S-21.24's own Tasks #27/#28 in the original plan). This makes
"annotate-before-flip" hold by wave-schedule construction alone — no same-commit choreography
is needed, and at no commit does PC11 ever observe "enforcement-active + any of the five
unannotated."

Full rationale, the two rejected alternatives (folding the five plugins' calibration into
S-21.19; hiding the wiring behind a flag), and the Decision/Consequences analysis are recorded
in **ADR-044** (`.factory/specs/architecture/decisions/ADR-044-split-topology-enforcement-flip-capstone-ownership.md`),
which extends ADR-039 §Decision 3 for the split-topology delivery context. In summary: folding
the five plugins into S-21.19 was rejected because three of the five require S-21.21's
AMD-002 wiring-fix/calibration and S-21.23's break-glass mechanism to already exist to be
meaningful, so folding would re-merge three of the six seams (9+9+7=25 pts, well over the
~13-pt per-seam ceiling) and defeat the split's purpose. Hiding the wiring behind a flag was
rejected because PC11's design-flow-independent detector is a static source scan that would
either still trip on the flagged-but-present reference, or require weakening PC11's own
detection logic — reopening the exact gaming vector PC11 exists to close.

### 8.3 Why this is minimally invasive to the approved topology

This resolution changes **zero** `depends_on`/`blocks` edges, **zero** wave assignments, and
**zero** story IDs. The six-seam DAG the operator approved is unchanged (§2's dependency graph
and wave-schedule table stand as originally written). Only intra-story task/AC content moves
between two of the six already-existing seams (S-21.19 → S-21.24). The ~2-point redistribution
(§0, §1) is a scope shift, not a scope increase — the combined S-21.19+S-21.24 point total is
unchanged (12 before and after).

### 8.8 Calibration-Ownership Matrix (F-S2121-P5-001 adjudication — 2026-08-23)

**Finding (HIGH, F-S2121-P5-001):** BC-1.03.017 v1.23 Precondition 6 and H1 assert that BOTH
(i) the one-time calibration-sufficiency confirmation (Task 4) AND (ii) the durable standing CI
regression gate (Task 5a) are OWNED BY S-21.22 — and that this ownership applies to ALL SIX
ADR-039 §Decision 2 fail-closed validators (both adapter classes). This is semantically
impossible under the plan's own allocation: S-21.22's mandate (§1 S-21.22 Scope; §6 Task #26
resolution) is native-WASM calibration ONLY — one plugin (`validate-cross-site-correspondence`).
The five `legacy-bash-adapter.wasm`-hosted plugins are calibrated exclusively by S-21.21 (§1
S-21.21 Scope; §3 AC-007 bash-adapter leg; §6 Task #1–#5/#26 resolution). The BC's
"S-21.22 owns both" assertion for all six validators either double-assigns or orphans the five
bash-adapter plugins' sufficiency evidence — a CWE-636 sufficiency gap if an implementer
reads BC and plan as authoritative.

**Authoritative ruling — calibration-ownership matrix:**

| Plugin set | Adapter class | One-time calibration confirmation (Task 4) | Durable standing CI regression gate (Task 5a) |
|------------|---------------|-------------------------------------------|-----------------------------------------------|
| Five bash-adapter plugins: the five `legacy-bash-adapter.wasm`-hosted `on_error=block` validators named in ADR-039 §Decision 2 | `legacy-bash-adapter.wasm` | **S-21.21** — performed during Tasks #6–#15 after the AMD-002 `timeout_ms` wiring fix is GREEN, against the wired code path, using the `ceil(observed_max × 1.5)` formula | **S-21.21** — Task 5a: frozen `pc6-sufficiency-snapshot/` regression assertion committed alongside the calibration, per Precondition 6(ii); not re-run against live-growing files |
| `validate-cross-site-correspondence` | native WASM | **S-21.22** — Tasks #1–#5, production-scale corpus calibration (≥574 KB fixture + live corpus files) | **S-21.22** — Task 5a: frozen `pc6-sufficiency-snapshot/` regression assertion, per Precondition 6(ii) |

**Why this allocation is determined by the plan's existing structure, not a new decision:**

The plan already establishes this unambiguously:
- §6 assigns Task #26 (flip `validate-cross-site-correspondence`) solely to S-21.22. Tasks
  #27–#32 (flip the five bash-adapter plugins using S-21.21's calibrated values) belong to
  S-21.24.
- §1's S-21.22 Scope states explicitly: "Calibrate `validate-cross-site-correspondence`'s
  `fuel_cap` … Fully independent of Nodes B/C (no `legacy-bash-adapter` involvement)."
- §1's S-21.21 Scope states explicitly: "run per-plugin bash-adapter calibration for the five
  `legacy-bash-adapter.wasm`-hosted plugins."
- S-21.21 and S-21.22 both run in wave 7 with no `depends_on` edge between them (fully
  parallel seams). Routing S-21.21's five-plugin sufficiency gates to S-21.22 would create
  a false sequential dependency between two parallel seams — a DAG violation — and inflate
  S-21.22's scope beyond its native-WASM-only mandate.

**Design choice: per-calibrating-story ownership, not a single aggregate gate:**

Each calibrating story (S-21.21, S-21.22) owns both the one-time confirmation and the
durable CI gate for the plugins within its scope. A single S-21.22-owned aggregate gate
would: (1) force S-21.22 to run after S-21.21, breaking the wave-7 parallelism; (2) block
S-21.21's own 3-CLEAN convergence (BC-5.39.001) on a gate it does not own; (3) put S-21.22
in scope for bash-adapter calibration logic it has no architectural basis to perform.
Per-story ownership means each seam is fully self-contained at convergence — when S-21.21
merges 3-CLEAN, its five-plugin sufficiency is demonstrably correct; when S-21.22 merges
3-CLEAN, the native-WASM plugin's sufficiency is demonstrably correct. S-21.24's own
regression sweep (Task 0 precondition checks) then has firm, already-verified per-plugin
evidence to build on.

**Cross-reference to §6:** the Task-Ownership Resolution in §6 resolves the Task #26 overlap
(S-21.22 sole owner) and Task #27–#32 ownership (S-21.24). This §8.8 extends that resolution
to the Precondition 6 sufficiency-gate ownership dimension, which was not covered by §6's
original Task-overlap scope.
