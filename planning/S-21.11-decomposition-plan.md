# S-21.11 Phase-2 Re-Decomposition Plan

6 sub-stories plus 1 new tracked story, overriding the story's own prior standing "unified
scope, no split" human decision (recorded 2026-08-19 in S-21.11's own banner). This document
is the authoritative decomposition; story-writer implements it into actual sub-story spec
files, state-manager updates STORY-INDEX.md/ARCH-INDEX.md and STATE.md, and product-owner
authors the one new BC this plan identifies as needed (S-21.25).

### S-21.25 — Fuel-headroom WARN event (new tracked story)

**Scope:** Deliver ADR-039 §Decision 5 Mitigation 1, currently a live MUST-requirement with
zero owning story and zero live code (abandoned branch `fix/fuel-exhaustion-fail-loud`). On
`PluginResult::Ok`, if `fuel_consumed > 0.9 × cap`, the dispatcher MUST emit a WARN-level
structured event: `"fuel-headroom-warning: plugin consumed ≥90% of budget; next larger input
may trap — recalibrate fuel_cap"`, carrying `plugin_name`, `fuel_consumed`, `fuel_cap`, and
`headroom_ratio` fields. The check belongs in the `Ok` path of the invocation result handler,
in the invoke module (`crates/factory-dispatcher/src/invoke.rs`), after
`fuel_consumed_from_store` is computed. Test coverage: positive control (`fuel_consumed`
just above 90% of `cap` → WARN fires with correct fields), negative control (`fuel_consumed`
well below 90% → no WARN), and boundary control (`fuel_consumed` exactly at 90% — inclusive or
exclusive threshold MUST be decided and asserted, not left ambiguous; ADR-039's own wording
("> 0.9 × cap") is strict-greater-than, so exactly 90% MUST NOT fire — assert this explicitly).

**Phase-2-independent scope, per operator direction:** this story is fully independent of the
6 split seams above. Mitigation 1 requires only the pre-existing `fuel_cap` registry field
(shipped well before S-21.10/S-21.11 — `fuel_cap` predates the `failure_policy` axis entirely,
per ADR-042) and the already-correct fuel-exhaustion detection path
(`Trap::OutOfFuel` → `fuel_consumed_from_store`). It does not touch `failure_policy`,
`on_error`, `execute_tiers`'s block-decision loop, or `legacy-bash-adapter` at all. It can be
implemented, tested, and merged in any order relative to S-21.19–S-21.24.

**ADR-039 anchor:** §Decision 5, "Mitigation 1 — Fuel-headroom warning" (lines 754–759 of
ADR-039 v1.14). Mitigation 2 (the ≥574 KB production-scale fixture) is already delivered
(S-21.07, commit e94767bc) and is NOT part of this story's scope — Mitigation 1 only.

**BC status — routing note (architect cannot author BCs; product-owner's domain per
CLAUDE.md Agent Routing Table):** no existing BC governs this WARN-emission behavior. Before
this story enters Phase 3 TDD, **product-owner MUST author a new BC** (next collision-free ID
in the SS-01 range, e.g. `BC-1.03.019` — story-writer/product-owner to confirm at authoring
time against BC-INDEX.md's live state) covering: the `fuel_consumed > 0.9 × cap` predicate
(strict inequality), the four required event fields, the `Ok`-path-only scope (a `Timeout`
outcome is a distinct, already-handled case — this event is specifically the near-miss
warning, not the exhaustion block/advisory itself), and negative/boundary controls. This is a
genuine cross-agent routing surface (BC authoring is out of architect's domain), not a
deferred decision this plan leaves unresolved — the scope, predicate, and event-field
contract are fully specified above and in ADR-039 §Decision 5 itself; only the formal BC
document needs authoring.

**Tasks (indicative, for story-writer to formalize):** (1) implement the `> 0.9 × cap` check
in `invoke.rs`'s `Ok`-path result handler; (2) emit the structured WARN event with the four
required fields via the existing `InternalLog`/lifecycle-event mechanism (same family as
`break_glass.activated`, `plugin.log`, etc.); (3) write positive/negative/boundary-control
tests; (4) CHANGELOG entry.

**BCs:** TBD — new BC to be authored by product-owner (see routing note above); traces to
ADR-039 §Decision 5.

**Subsystems:** `[SS-01]` (invoke module only).

**Depends on:** `[]` — fully independent, no hard prerequisite. (Soft/logical relationship to
S-21.10/S-21.11's fuel-exhaustion work exists only in that they share the same
`fuel_consumed_from_store` measurement primitive, but neither reads nor writes the other's
code paths.)

**Blocks:** none.

**Points:** 5 (small-to-medium: one predicate + one structured event + boundary-tested
coverage; no registry schema change, no cross-crate wiring).
