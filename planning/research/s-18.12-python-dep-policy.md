## Reasoning

### 1. Option C (preflight acceptance) is the weakest, not the strongest

The current AC-004 model assumes a runtime preflight (`python3 -c "import yaml"`) makes a third-party dependency safe. **It does not**, for two compounding reasons:

- **A preflight cannot remediate under PEP 668.** When the check detects that PyYAML is missing, the script in most modern environments **cannot install it**: system/Homebrew/Debian `python3` carry the `EXTERNALLY-MANAGED` marker and `pip install` refuses without `--break-system-packages` or a venv (PEP 668, Final; Homebrew adopted the marker in early 2023; Debian/Ubuntu likewise). So the preflight only converts a *later* runtime crash into an *earlier* error message. It does not restore portability — it just relocates the failure. This is exactly the L-S18 failure mode.
- **It violates the tool's own contract.** Permitting Python (even gated) directly contradicts `SKILL.md`'s "no language runtime beyond bash." A portability lint that markets "pure bash" but green-lights Python-with-a-preflight is not enforcing the promise it advertises.

### 2. The stdlib-vs-third-party distinction is real and large — and is why B is defensible

- **Stdlib modules (`json`, `csv`, `argparse`, `re`) ship with every `python3`.** If `python3` is present, its stdlib is present. The deep-research synthesis put it directly: "we can treat Python stdlib modules as present when Python itself is present, acknowledging that pathological misconfigurations could break this but that such cases are rare." No mainstream OS or CI image strips core stdlib.
- **Third-party PyPI packages (PyYAML) are precisely what breaks.** They require `pip install`, which is exactly the operation PEP 668 blocks on externally-managed interpreters. The recorded failure (PyYAML on macOS CI) is the canonical instance.
- Therefore, **if any Python relaxation is ever warranted, the correct line is stdlib-only (Option B)** — it would have prevented the L-S18 failure while keeping the genuinely-portable subset. B is the technically-grounded middle.

### 3. macOS makes the case for A stronger than "just forbid third-party"

A subtlety that pushes past B toward A: on a clean macOS, **`python3` is not guaranteed to exist at all.** Apple removed bundled Python 2 in macOS 12.3 (Monterey) and **has never bundled Python 3**. `/usr/bin/python3` is a *stub* that prompts the user to install the Xcode Command Line Tools; the real interpreter only appears after CLT/Xcode (an outdated 3.9.6) or Homebrew/python.org install. So "Python stdlib is always present" holds on CI runners (GitHub Actions ubuntu/macos images ship python3) but **not** on an arbitrary developer macOS. For a tool whose differentiator is "runs anywhere with just bash + POSIX utilities," depending on `python3` being present is itself a portability liability independent of the package question.

### 4. Shell-portability practice does not *mandate* A — so A here is a product-identity choice, not a universal law

The broad ecosystem (Google Shell Style Guide, ShellCheck, autotools) **does not categorically forbid** calling Python from shell. Google mandates bash for *executables* and focuses on safe bash; external-command/interpreter dependencies are treated as a deployment/system-administration concern rather than a style-lint rule. ShellCheck lints bash correctness, not interpreter-dependency policy. So neither A nor B is "the one true answer" industry-wide. **What tips this specific decision to A is the tool's self-description.** A guard's job is to enforce the contract the artifact claims. `SKILL.md` claims pure bash; the guard should make that true.

### 5. Given the lesson's root cause, both A and B prevent recurrence — so honor the contract

The L-S18 root cause was a **third-party** package + PEP 668. Both A (forbid all) and B (forbid third-party, allow stdlib) prevent it; only C leaves the door open. Between A and B, the deciding factor is the existing `SKILL.md` promise and the macOS "python3 may be absent" fact, both of which favor A. Per the VSDD Standing Rule (spec wins; the more-specific/stricter artifact governs), the guard aligns to `SKILL.md` (A), and AC-004 is brought into alignment — not the reverse.

## Concrete guidance for the guard + spec reconciliation

- **Guard rule:** Flag any invocation of `python`, `python2`, `python3`, `pip`, `pip3` (and, consistent with the contract, `jq`, `node`, `perl`, `ruby`, etc.) in the wave-handoff skill scripts. Match on command tokens at statement start and in command substitutions/pipes.
- **AC-004 amendment (route to product-owner):** Replace the preflight-acceptance criterion with a forbid-all criterion that matches `SKILL.md`. Preserve the L-S18 rationale as the motivating example.
- **If an escape hatch is ever demanded:** Define it as B (an explicit stdlib-only allowlist: `json`, `csv`, `argparse`, etc., with `import` of anything else rejected). Do **not** reintroduce C. But the production-grade default that matches the advertised identity is A.

## Sources

Primary sources verified:

- **PEP 668 — Marking Python base environments as "externally managed"** (Status: Final). Defines the `EXTERNALLY-MANAGED` marker; pip must refuse system installs outside a venv when the marker is present. https://peps.python.org/pep-0668/ (verified via WebFetch 2026-06-30)
- **Homebrew PEP 668 adoption (early 2023) / `error: externally-managed-environment`** — pythonspeed.com, Jeff Geerling, mac.install.guide (verified via WebSearch 2026-06-30): Homebrew added the marker in early 2023; pip 23.0+ enforces it; recommended remedies are venv/pipx/uv, with `--break-system-packages` reserved for ephemeral/CI use.
- **macOS Python situation** — Jamf, macmule, Apple Community (verified via WebSearch 2026-06-30): Apple removed bundled Python 2 in macOS 12.3 (Monterey); Python 3 was never bundled; `/usr/bin/python3` is a stub prompting Xcode CLT install (which ships an outdated 3.9.6).

Synthesized (Perplexity `sonar-deep-research`, reasoning_effort=high, 2026-06-30):

- Prevailing shell-portability guidance does not categorically forbid Python; Google Shell Style Guide / ShellCheck focus on safe bash, treating interpreter dependencies as deployment concerns.
- "Treat Python stdlib modules as present when Python itself is present" — stdlib-vs-third-party is the load-bearing distinction.
- "Option C therefore faces significant obstacles" — a preflight cannot install missing third-party packages under externally-managed markers; it degrades to an earlier error, not working software.
- Forbidding Python entirely "is the most defensible and maximizes portability ... but imposes a strong constraint that may be at odds with developer expectations."
