### PR-001 — BLOCKER — security / sequencing

**The "this unblocks SEC-001" premise does not hold. A FilePerms bypass of the same class remains, and it is unfixable anywhere in the 44.x line.**

`cargo deny check advisories` against this branch still reports:

```
error[vulnerability]: WASI hard links and renames bypass wasmtime-wasi's FilePerms for destination
    ID: RUSTSEC-2026-0188   (aliases: GHSA-4ch3-9j33-3pmj, CVE-2026-58494)
    wasmtime-wasi v44.0.3 -> factory-dispatcher v0.0.1
    patched = [">= 46.0.1", ">= 45.0.3, < 46.0.0", ">= 36.0.12, < 37.0.0", ">= 24.0.11, < 25.0.0"]
    cvss = "CVSS:3.1/AV:L/AC:L/PR:L/UI:N/S:C/C:N/I:H/A:N"   (scope-changed, integrity: High)
    date = 2026-06-24
```

Note the patched set: **there is no 44.0.x fix.** The 44 series was not backported for this one.

This matters because it is precisely the threat model the PR is built around. The body argues that `DirPerms::all() + FilePerms::READ` is the vulnerable configuration, that SEC-001 will introduce exactly that configuration, and therefore that this bump must land first so "the guard it was written to build" is not inoperative from its first commit. That reasoning is sound — but it is aimed at only one of the two FilePerms-bypass advisories. After this PR merges, a WASM hook plugin holding a read-only preopen can still bypass `FilePerms` on the **destination** of a hard link or rename, with `I:H` and a changed scope. SEC-001 would still ship into a live host-integrity hole; the failure mode this PR exists to prevent is only half-prevented.

Suggested fix — no diff change needed, but the PR body must stop asserting completeness:

1. Correct the sequencing section to state this bump is **necessary but not sufficient** for SEC-001, naming `RUSTSEC-2026-0188` as the remaining blocker.
2. Record that clearing it requires leaving 44.x entirely (minimum `45.0.3`; `47.0.3` also clears `RUSTSEC-2026-0222` per PR-005). That is a real manifest-level move with real risk, legitimately out of this PR's scope.
3. Per Canonical Principle Rule 3, attach that move to a **concrete story ID scheduled before SEC-001** — not "next ecosystem advance", not the tech-debt register. If SEC-001 can land first, say so explicitly so the next reviewer of SEC-001 sees the residual risk instead of inheriting a "this was already handled" impression from this PR.

Not a request to widen the diff. A request that a security PR not leave behind a body that would let the next agent conclude the trap is closed.

### PR-002 — BLOCKER — verification evidence

**No CI has run on this head SHA. The only gate that compiles the changed Windows dependency edges has never executed.**

```
gh api repos/.../commits/a66964aa.../check-runs --jq .total_count   ->  0
gh pr checks 770                                                   ->  "no checks reported"
gh run list --branch fix/wasmtime-wasi-cve-2026-47261               ->  (empty)
```

`ci.yml` triggers on `pull_request: branches: [main, develop]` with **no `paths:` filter**, so a run is expected here and its absence is itself worth diagnosing (queued? Actions disabled for the branch? push/PR race?).

Decision-relevant rather than cosmetic because of PR-004: 12 dependency edges were redirected onto `windows-sys 0.52.0`, and `windows-sys` compiles **only** under `cfg(windows)`. The author's local gate run (macOS) and the `validate` job (ubuntu + macos) cannot compile a single line of it. The only gate that can is the `windows-x64` leg of the `build-dispatcher` matrix (`ci/platforms.yaml`: `x86_64-pc-windows-msvc`, `run_tests: true`) — and it has not run. Merging on local-gate evidence alone ships a shipped-platform dependency change with zero compile coverage.

Suggested fix: get a CI run on this SHA and confirm the `windows-x64` leg is green before merge. If Actions did not trigger, force a run and note in the body why the first one was missing. Do not merge on the local gate table alone.

### PR-003 — MAJOR — description accuracy

**The commit message states a fact that is false, and it becomes the permanent record of a security remediation after squash-merge.**

```
windows-sys v0.59.0               removed (superseded by v0.53.0)
```

There is no `windows-sys 0.53.0` anywhere in the resulting graph — or in the previous one. The eight former `0.59.0` consumers were moved to **`0.52.0`**, an entry that already existed on `develop`. Since the lockfile *is* the entire reviewable artifact, a reviewer reconciling body against diff has to stop and re-derive the change — the opposite of what a security changelog is for.

### PR-004 — MAJOR — description accuracy / undisclosed movements

**"36 crates, all patch-level" is not what the diff does. Three movements are cross-minor downgrades, none disclosed.**

| Consumer | Dependency | Before | After |
|----------|-----------|--------|-------|
| `rustix 1.1.4`, `tempfile`, `errno`, `is_terminal_polyfill` (4 edges) | `windows-sys` | `0.61.2` | `0.52.0` |
| `hyper-util` | `socket2` | `0.6.3` | `0.5.10` |
| `prost-derive` | `itertools` | `0.14.0` | `0.11.0` |

Total `windows-sys 0.52.0` references go from 2 to 14.

To be explicit about what I am *not* claiming: I reproduced the lockfile byte-for-byte from `develop` with the targeted `--precise` command, so this is cargo's own resolver unifying range requirements (`windows-sys = ">=0.52, <0.62"` in `rustix`/`tempfile`/`errno`; `">=0.52, <=0.59"` in `cap-primitives`) onto an already-activated version. Nothing was hand-edited, and `cargo deny` reports no advisory against any of the three downgraded crates. The defect is disclosure, not the resolution.

Why still MAJOR: in a lockfile-only security PR, the body's crate table is the reviewer's only practical defense against a supply-chain surprise hidden among 177 changed lines. A table saying "all patch-level" trains the reader to skim, and three minor-level downgrades — one pulling a Windows FFI binding back to a November-2023 release on a platform we ship — are exactly what should not be skimmed.

Suggested fix: add the three rows above, labelled as resolver-unification downgrades, with one sentence noting they are cargo's own output from the targeted `--precise` command (verifiable framing, lets a reviewer accept them quickly).

### PR-007 — MINOR — process gap (out of scope for this diff; needs a story anchor)

`deny.toml` exists at repo root, correctly configured for cargo-deny 0.19 with `[advisories] ignore = []` and `db-urls` pointed at RustSec — but no workflow invokes it. Correctly out of scope — the body's "do not widen scope" is right. But per Canonical Principle Rule 3 this needs a real story anchor, not a mention, because the same gap will hide the next advisory. Route to devops-engineer for a `cargo deny check advisories` CI job, sequenced with PR-001's version move (the job stays red until `RUSTSEC-2026-0188`/`0222` clear, so the two are coupled and should be planned together).

### PR-008 — NITS — provenance method for the bats attribution

Conclusion right, method suboptimal. The body cites `git stash` + re-run on bare develop. For a lockfile-only diff a stronger and safer argument exists: a `Cargo.lock` edit cannot remove story rows from `.factory/stories/sprint-state.yaml`, so the failures are structurally unattributable to this change — which is what I verified directly by reading the file (only `S-21.01`..`S-21.06` present). Given that `git stash` across worktrees is a known destructive-interference mode, I would not normalize stash round-trips as the standard provenance technique for out-of-scope test failures.

Suggested fix: cite the structural argument plus the `sprint-state.yaml` read; keep the stash re-run as corroboration only.

### PR-009 — NITS — volatile line-number citations

The body pins `invoke.rs:320-331`, `invoke.rs:325-327`, `resolver_loader.rs:582`. TD-VSDD-091 (anti-volatile-pin) targets exactly this decay pattern. A PR body is a point-in-time snapshot so this is genuinely minor — but the SEC-001 argument in PR-001 will be re-read months from now, when those offsets are wrong.

Suggested fix: cite the enclosing function name alongside the line range so the anchor survives the next diff.
