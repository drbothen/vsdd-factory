# S-25.02 F1 Delta Analysis: Artifact Sharding Layer 2 — Size-Triggered Shard Rotation for Cycle Artifacts

## 1. Impact Boundary

### 1.1 What the feature actually changes

- **New shard-append mechanism** for three append-only cycle artifacts per active cycle:
  `decision-log.md`, `burst-log.md`, `lessons.md` (as scoped in the story narrative today —
  see OQ-1 on whether this set should grow). Each becomes a *family* of capped shard files plus
  one shard index, instead of one unbounded file.
- **A deterministic, mechanistic size-trigger** — either (a) a new PreToolUse WASM hook that
  inspects the target artifact's current byte size before an Edit/Write/MultiEdit is applied, or
  (b) a append-helper library function invoked by whatever currently performs the append (today:
  direct Edit/Write tool calls by state-manager/story-writer/architect — there is no existing
  "append helper" abstraction in the codebase; this would be new). Per AC-002, no LLM-side size
  awareness is permitted — this must be enforced identically to how `validate-factory-path-staging`
  and other PreToolUse guards are enforced today (dispatcher-mediated, not prompt-mediated).
- **Roll-before-write semantics** (AC-003): if the next appended block would exceed the shard
  cap, the mechanism creates shard N+1 and writes there — never writes past the cap.
- **A shard index file per sharded artifact** (`.factory/<artifact>/shard-index.toml`, per the
  story's tentative path), published atomically (temp+rename) in the SAME commit as the new shard
  (AC-004) — this directly composes with TD-VSDD-053 single-commit-per-burst.
- **A retention/compaction companion policy** (AC-005) bounding total shard count per artifact.
- **A Cohort B fail-closed flip** on exactly three registry entries once the above eliminates
  the input-size class that made them fail-open-only: `validate-burst-log` (Edit/Write arm),
  `regression-gate`, `convergence-tracker` — pending the AC-006 name correction above.
- **How readers/validators find the active shard vs. archived shards**: this is the single
  biggest UNSPECIFIED design surface in the current story draft. Neither the story nor ADR-047
  §8b specifies: (a) whether existing shard-UNAWARE validators (everything except the Cohort B
  three) continue reading a stable "current" file path (e.g. a symlink or a well-known
  `decision-log.md` that is always the latest/active shard) or must be updated to read the index;
  (b) how a human or agent doing `grep -n "D-1234" .factory/cycles/*/decision-log.md` finds a
  D-NNN that has rolled into an archived shard — today this is one `grep`, post-sharding it
  becomes "search across all shards named by the index," a workflow change with no migration
  note in the story. Story AC-007 asserts "existing shard-unaware validators MUST continue to
  work (they simply validate individual shards instead of the monolithic file)" — this requires
  EITHER a stable current-shard alias path, OR a rewrite of every validator's `path_allow`/file
  discovery logic. The story does not commit to which. This is Open Question OQ-2.

## 2. Precondition Assessment (detailed)

The story text frames the data-dependency as: "Layer 1 forensics must be collected BEFORE
finalizing the Layer-2 shard cap formula. Do NOT hardcode the cap from theoretical estimates
alone; use the WORST-CASE fuel-per-byte from production plugin.indeterminate events."

What exists today (2026-09-05, 48h post-merge):
- `cause` classification is present and usable (699 fuel / 9 epoch) — confirms fuel exhaustion,
  not epoch/wall-clock timeout, is the dominant failure mode, consistent with the story's own
  "worst-case fuel-per-byte" framing (epoch timeouts are wall-clock-bound and would suggest a
  different tuning axis).
- `artifact_path` is present — usable for per-file event attribution (used in §0's table above).
- **What is NOT present in the current event schema**: the artifact's byte size *at the moment
  of the fuel-exhausting invocation*, and the specific plugin's fuel-consumed-before-exhaustion
  value. The `plugin.indeterminate` event carries `plugin_name`, `artifact_path`, `cause`,
  `failure_policy` — not a `bytes_at_invocation` or `fuel_consumed` field. Without
  size-at-invocation, the WORST_CASE_FUEL_PER_BYTE term in AC-001's formula cannot be computed
  directly from this event stream alone; it can only be approximated by correlating event
  timestamps against git history of the artifact's size at that commit (possible, but requires a
  dedicated calibration script — not yet written, and not scoped as a task in the current story
  draft's Task list).
- 48 hours of production data is a **thin but non-zero** sample. It is enough to confirm the
  failure mode is real and dominant (fuel, not epoch) and to rank which files are the biggest
  contributors, but it is **not enough for a statistically defensible worst-case percentile**
  (e.g., p99 fuel-per-byte) — a longer observation window (the story itself doesn't specify a
  minimum window) or a synthetic calibration harness (feeding known-size fixtures through the
  Cohort B plugins in isolation and reading fuel-consumed from `plugin.timeout`/`plugin.completed`
  telemetry) would materially de-risk the formula. A synthetic harness is arguably STRICTLY
  BETTER for worst-case calibration than waiting on more production days, since it can construct
  adversarial (super-linear-validator-triggering) inputs directly rather than hoping production
  writes happen to exercise the worst case.

**Verdict: READY TO ACTIVATE (F2), with a *task*, not a *blocker*, added to the F2 architecture
elaboration burst.** The precondition in the story's BACKLOG note ("BC status: pending PO
authorship pending ... Layer-1 INDETERMINATE production data") should be read as satisfied in
the qualitative sense (the failure mode is confirmed live and dominant-cause-fuel is confirmed)
but the quantitative calibration work (deriving `PRACTICAL_FUEL_CEILING` /
`WORST_CASE_FUEL_PER_BYTE` / `MAX_SINGLE_RECORD_BYTES` / `SAFETY_MARGIN` as concrete numbers) is
NOT yet done and should be an explicit F2 architect task — either (a) a synthetic calibration
harness (recommended — faster, adversarial-input-capable, doesn't require waiting), or (b) an
extended production observation window (2-4 weeks) if the human prefers empirical-only
calibration. This does not block starting F2; it is F2's own first work item.

## 6. Open Design Questions (human/architect adjudication required before/at F2)

- **OQ-1 (scope width):** Confirm whether S-25.02's file-scope stays exactly
  `{decision-log.md, burst-log.md, lessons.md}` per cycle (as the story narrative states today) or
  should be widened to cover the two largest actual production contributors observed
  (`BC-INDEX.md` at 45.2% of events, `session-checkpoints.md` at 19.5%). Widening to
  `session-checkpoints.md` is architecturally trivial (it's already a `.factory/cycles/<cycle>/`
  append-only file, same shape as the three named files). Widening to `BC-INDEX.md` is NOT
  trivial — it's a structured catalog with cross-references (BC IDs, subsystem counts), not a
  pure append log; sharding it would need a different mechanism (e.g. per-subsystem BC-INDEX
  shards) and is arguably out of scope for "cycle artifact" sharding entirely, possibly warranting
  its own follow-up story rather than scope creep into S-25.02.
- **OQ-2 (reader/validator addressing):** How do shard-UNAWARE validators and humans locate
  content that has rolled into a non-current shard? Options: (a) a stable alias/symlink to the
  current shard so unmodified validators keep working, with a separate whole-corpus mode for
  validators that must see history; (b) update every validator's file-discovery logic to consult
  the shard index. AC-007's "existing shard-unaware validators MUST continue to work" claim needs
  one of these two mechanisms named explicitly — the story does not currently pick one.
- **OQ-3 (`/compact-state` interaction):** `/compact-state` currently APPENDS to burst-log.md/
  lessons.md/session-checkpoints.md as part of its STATE.md-slimming function. Does it need
  amendment to be shard-aware (write to "current shard"), or does it call through the same
  append-helper S-25.02 introduces (in which case it gets shard-awareness for free)? Needs an
  explicit answer at F2; not mentioned in the current story draft.
- **OQ-4 (calibration method):** Synthetic calibration harness (recommended — fast, can construct
  adversarial worst-case inputs against the Cohort B plugins directly) vs. extended production
  observation window (slower, empirically "real" but the current 48h sample is too thin and this
  repo's own commit cadence makes a multi-week wait costly). Recommend the harness; human should
  confirm.
- **OQ-5 (AC-006 plugin-name correction):** Confirm `validate-burst-log` (Edit/Write arm only) is
  the correct Cohort B flip target in place of the non-existent `validate-burst-log-structure`
  name currently in both ADR-047 §8b and the story's AC-006. This is a factual correction, not a
  judgment call, but it changes ADR-047 text and should go through the same erratum-class
  amendment process used for the S-25.04 BC-4.16.001 correction (ADR-047 v1.5's own precedent).
