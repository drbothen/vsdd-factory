## Part A — Findings

### F-P11-001 — BLOCKER — VP-099 title and description assert leading-only anchor; both-ends convention not reflected (CLOSED same-session)

**POLICY:** POLICY 9 (VP title is canonical and propagates to verification-architecture.md + verification-coverage-matrix.md atomically); POLICY 4 (description-bearing anchor-prose derives from target SoT)
**Location:** VP-099.md §Title, §Property Statement, §Invariant Description; VP-INDEX catalog row (line ~477) and §Traceability Appendix row (line ~546)
**Issue:** The VP-099 v1.0 title read "hooks-registry Tool-Filter Anchoring Invariant — Every tool= Value Starts With ^ or Carries # intent: Comment" and the body description stated "every tool= value in hooks-registry.toml starts with ^ (regex anchor) or is a comment-annotated intentional broad match." This described LEADING-ONLY anchoring.

However, the pass-6 and pass-7 fix chain (commits e0464b7b, 3d065c4e, d2c08920) established BOTH-ENDS anchoring as the canonical convention: every tool= value must either match `^...$` (fully anchored at both start and end) or carry `# intent:` comment. The implementation and test fixtures (as of 0a7af81d) enforce both-ends anchoring, not leading-only.

VP-099 therefore described an ALREADY-SUPERSEDED invariant. Any downstream document that cited VP-099 for the anchoring convention would silently inherit the stale leading-only form. This is a specification drift blocker: the implemented behavior was more restrictive than the spec claimed, creating a gap where a regression to leading-only anchoring could pass VP-099 validation while violating the actual convention.

- architect: VP-099 v1.1 — title corrected to "hooks-registry Tool-Filter Anchoring Invariant — Every tool= Value Is Fully Anchored (^...$) or Carries # intent: Comment"; §Property Statement and §Invariant Description updated to both-ends form; input-hash updated.
