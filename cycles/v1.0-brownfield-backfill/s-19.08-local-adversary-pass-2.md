## Part A — Findings

### F-P2-001 — HIGH — [regression class: guard-bypass reintroduction] extract_frontmatter reconstruction-base truncation (OPEN — routed implementer)

**Location:** `crates/hook-plugins/verify-state-timestamp-refresh/src/lib.rs` — `extract_frontmatter` wiring in Edit/MultiEdit dispatch paths  
**Observation:** The `extract_frontmatter` wiring passes a truncated string — frontmatter bytes only, plus a synthetic `\n---\n` delimiter — as the `on_disk_content` reconstruction base for `extract_edit_proposed` and `extract_multiedit_proposed`. When the proposed Edit/MultiEdit specifies an `old_string` that targets body content (any content after the closing `---` delimiter), the match against the truncated base fails. The failure path resolves as `ProposedContent::FailOpen` → `Continue`, meaning the plugin exits without blocking the edit — even for files ≤64 KiB where the cap-raise guard is supposed to be active and reliable.  
**Root cause:** Invariant 7 ("frontmatter-only extraction") mandates that field parsing reads only the frontmatter block. This governs the `last_modified` timestamp extraction step. It does not govern the reconstruction base for the `old_string` match in the Edit/MultiEdit guard path. The truncation was applied too broadly.  
**Impact:** Any Edit/MultiEdit whose `old_string` anchors to body content — including legitimate structural edits to the state file body — silently bypasses the timestamp-staleness guard. This is a re-introduction of the FailOpen guard-bypass class that the wiring was designed to close.  
**Fix required:** Keep the full file content as the Edit/MultiEdit reconstruction base. Use the frontmatter-derived slice only where genuinely required (timestamp field extraction). No API surface change; internal wiring adjustment only.  
**Routing:** implementer  
**Status:** OPEN — remediation burst pending
