## Part A — Findings

### F-P5-001 — MEDIUM — Single write_all: non-atomic sink flush under partial-write (CLOSED same-session)

**POLICY:** BC-3.08.001 Invariant 6 (plugin.abandoned event schema atomicity); POLICY 11 (positive-control gate discipline)
**Location:** vsdd_sink.rs `flush_sink_file` function
**Issue:** The `flush_sink_file` function used a single `write_all()` call to write the complete JSONL content to the sink file. Under partial-write conditions (OS-level interruption, out-of-disk-space, or write-through failure), `write_all()` can return an error after partial bytes are written, leaving the sink file in a corrupt state (truncated mid-JSONL-line). Subsequent reads by the drain loop would find malformed JSON and fail silently. The correct pattern requires either (a) write to a temp file and rename (atomic swap), or (b) open with `O_APPEND` and write individual events atomically.
**Fix:** implementer 70c5a3f2: `flush_sink_file` rewritten to use `O_APPEND` individual event writes, preventing partial-write corruption.
**Status:** CLOSED same-session — implementer 70c5a3f2
**Routing:** implementer

### O-P5-2 — LOW — Observation: drain loop error path drops events silently (accepted-with-record)

**Location:** vsdd_sink.rs drain loop
**Issue:** When `flush_sink_file` returns an error, the drain loop logs the error but continues processing remaining events. Events that fail to flush are silently dropped. BC-3.08.001 does not require durability guarantees on the drain loop, so this is acceptable behavior, but the implementation lacked a counter increment at the drop site, making it impossible to detect event loss via metrics.
**Accepted-with-record:** BC-3.08.001 does not mandate zero-drop under I/O failure. Tracking via counter deferred; non-blocking.

### O-P5-3 — LOW — Observation: VSDD_SINK_FILE env var resolution timing (accepted-with-record)

**Location:** vsdd_sink.rs initialization
**Issue:** `VSDD_SINK_FILE` is resolved at module init time, not at the point of first event emission. If the environment variable is set after module load (e.g., by a test harness that sets it dynamically), it would not be picked up. This is an accepted design constraint (init-time resolution is intentional for performance).
**Accepted-with-record:** Init-time resolution is intentional per BC-3.08.001 design; test harnesses set the env var before process start. No action needed.
