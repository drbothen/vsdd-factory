## Part A — Findings

### F-P1-001 — MEDIUM — [doc-accuracy] read_file.rs two-linker comment misrepresents ptr==0 dual-path semantics

**Location:** `crates/factory-dispatcher/src/host/read_file.rs` — two-linker duality comment added by cca7cf6a  
**Observation:** The doc comment added in cca7cf6a's D20 fix described the two register paths (test-path `setup_linker`/`Linker<HostContext>` vs production-path `setup_host_on_store_data`/`Linker<StoreData>`) as behaving differently with respect to byte-copy. Specifically, the comment claimed the test path performs no byte-copy and that `read_owned_bytes` returns "0" for non-empty content. This is inaccurate: `write_wasm_bytes` copies the payload to guest memory at address 0 on both paths; the `ptr == 0` guard in each `register` implementation yields `Vec::new()` regardless of content, causing bytes to be discarded in both cases. The two paths converge at `Vec::new()` via the same ptr==0 guard — the comment falsely implied behavioral divergence.  
**ADR-025 §Decision 17 status:** The underlying architectural claim (two-linker duality: read_prefix registered on test-path linker in S-19.06 but absent from production-path linker; D19 closes the production gap) is ACCURATE. The inaccuracy is entirely in the comment describing side-effects — no spec-vs-code divergence, no architect involvement required.  
**Fix required:** Rewrite the two-linker comment to accurately describe the shared ptr==0 guard and Vec::new() discard semantics for both paths. Sibling-sweep `read_prefix.rs`.  
**Routing:** implementer (comment correction; read_prefix.rs sibling sweep)  
**Status:** CLOSED — implementer 4ecba42d (comment rewritten with exact dual-path semantics: both paths yield Vec::new() via ptr==0 guard; write_wasm_bytes copies at guest address 0 on both paths); read_prefix.rs swept — no matching inaccurate comment present.
