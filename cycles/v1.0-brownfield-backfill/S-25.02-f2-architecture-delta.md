# S-25.02 F2 Architecture Delta: Artifact Sharding Layer 2 — Two-Mechanism Size-Triggered Shard Rotation

## 0. Summary

This F2 burst produces **ADR-051** (new; the full Layer-2 architecture design) and a same-burst
erratum to **ADR-047** (v1.5→v1.6, OQ-5 plugin-name correction). It resolves all five Open
Questions F1 raised, keeps BC-INDEX.md fully in scope per the human's D-1166 widest-scope
decision (**no split proposal is filed** — see §7), and hands product-owner a concrete set of
BC-authorship inputs (§6) including several items the story draft's provisional ACs did not
anticipate (most importantly: a mandatory one-time backfill-split of the four already-oversized
append-log files, and the two-level BC-INDEX sharding design).

## 1. Resolution of the Five Open Questions

### OQ-1 (scope width) — already resolved by the human (D-1166)

Not re-litigated here. D-1166 selected **widest scope**: S-25.02 covers both mechanism A (the
four cycle append-logs: `decision-log.md`, `burst-log.md`, `lessons.md`, `session-checkpoints.md`
— the fourth added per F1 §0's own finding that it is the second-largest INDETERMINATE
contributor and architecturally identical in shape to the other three) and mechanism B
(`BC-INDEX.md`). See ADR-051 Context for the restated rationale.

### OQ-2 (reader/validator addressing) — resolved, two different mechanisms for two different shapes

**Mechanism A (append-logs):** the canonical filename (e.g. `decision-log.md`) is ALWAYS the
current/active shard. Sealing a shard renames it away to `<stem>.<seq:04>.md` and creates a fresh
empty file at the canonical name (ADR-051 Decision 3). Any shard-unaware reader that opens the
canonical name transparently sees the LATEST content with zero code change — this is the option
(a) "stable alias" OQ-2 asked for, achieved by naming convention rather than a symlink (avoiding a
cross-platform symlink concern across the dispatcher's darwin/linux/windows release targets).
Whole-corpus readers use the glob `<stem>*.md`, which sorts sealed shards ascending before the
current file — every sealed shard's filename and the current file share the prefix `decision-log`,
and the deciding byte-comparison one position past that shared prefix is a digit (`0`–`9`, from a
sealed shard's `.NNNN.md` suffix) vs. `m` (from the current file's `.md` suffix); since every digit
byte is numerically less than `m`, sealed shards sort first (fix-burst-corrected rationale, ADR-051
v1.1 Decision 3; the "current file sorts last" conclusion is unchanged) — no special-casing needed
in a `sort`-fed pipeline.

**Mechanism B (BC-INDEX):** cannot use the same trick, because ALL subsystem shards are
simultaneously "current" — sharding by subsystem is a content partition, not a time partition, so
there is no single "latest" shard to alias. Instead, addressing is **computed, not looked up**,
for the common single-BC-lookup case: any reader wanting `BC-X.YY.NNN` derives its shard path
directly from the BC-ID's numeric prefix via the SAME mapping ARCH-INDEX's Subsystem Registry
already publishes (`BC-S Prefix` column: `BC-1`→SS-01 ... `BC-10`→SS-10) — no index file read
required for the first level. A shard manifest (`shards/BC-INDEX.shard-manifest.toml`, ADR-051
Decision 8) is needed only for whole-corpus scans and for the second-level sub-shard case (SS-05,
SS-06 — see §3). This is a genuinely different mechanism from mechanism A's, but it is NOT a novel
invention — it reuses an already-authoritative, already-documented addressing scheme.

## 2. A Structural Gap the Story Draft Did Not Address

`crates/hook-sdk/src/result.rs`'s `HookResult` enum has exactly three variants:
`Continue`/`Block { reason }`/`Error { message }` — no redirect or payload-mutation capability.
AC-002/AC-003's "roll-before-write" framing implicitly assumes a PreToolUse hook can transparently
retarget an in-flight `Edit`/`Write`/`MultiEdit` call to a fresh shard file. **This is not possible
under the current dispatcher contract.** ADR-051 Decision 1 resolves this with a
block-and-retry mechanism: the native gate performs the roll (seal + fresh-create + index publish)
as a side effect, THEN blocks the originating call with an explicit, actionable retry instruction.
This satisfies AC-003's "writing an oversized shard is forbidden" exactly (the blocked call is
never applied) while requiring zero anticipatory size-awareness from the agent — it is a reactive
correction, not a proactive prediction, consistent with AC-002's "no LLM-side awareness" mandate.
This is presented to product-owner as a required BC-authorship input (§6) since it changes the
EXACT observable behavior BC-1.18.006's postconditions must describe (a `Block` outcome with a
specific retry-instruction message, not a silent transparent write).

## 3. The Two-Mechanism Design (Summary)

**Mechanism A — append-log rotation.** A new native (non-WASM) PreToolUse check in the dispatcher
(`crates/factory-dispatcher/src/shard_manager.rs`, new module, no new crate, no new WASM plugin,
no `HOST_ABI_VERSION` bump) intercepts `Edit`/`Write`/`MultiEdit` against the four registered
append-log artifacts, `stat()`s the current shard, and rolls (seal+create+index-publish) before
blocking an over-cap write. See ADR-051 Decisions 1, 3, 4, 6.

**Mechanism B — BC-INDEX structured-catalog sharding, itself two sub-mechanisms:**
- **B1 (frontmatter `changelog:` rotation):** reuses the SAME native gate, extended with one more
  artifact-shape case, calling the already-shipped `rotate_changelog`
  (`crates/last-amended-migrate/src/rotate.rs`) rather than duplicating logic. This directly
  targets BC-INDEX.md's DOMINANT size driver — direct measurement shows the frontmatter
  `changelog:` block is 177,305 bytes, larger than the biggest single per-subsystem body table
  (`### SS-05`, ~88,695 bytes) — a finding the story draft did not anticipate (it assumed the BC
  tables themselves were the growth driver).
- **B2 (per-subsystem body-table sharding):** splits each existing `### SS-NN` heading (already
  present in the live file) into `shards/BC-INDEX-SS-NN.md`, addressed via the already-
  authoritative BC-S-prefix→SS-NN mapping. `### SS-05` (661 BCs, ~88,695 bytes) and `### SS-06`
  (592 BCs, ~85,407 bytes) both already exceed the illustrative 48 KiB today-cap and will need
  immediate second-level sub-sharding at F4 activation (a per-subsystem manifest, not a naming
  trick, since sub-shard boundaries are growth-based). The other eight subsystems (`### SS-07`
  measured at ~39,072 bytes, comfortably under cap) are not expected to need a second level, though
  this is re-verified empirically post-split for all ten, not assumed.

Full schemas (shard-index TOML for mechanism A, shard-manifest TOML for mechanism B) are in
ADR-051 Decisions 4 and 8.

## 6. Regression / Ripple: BC-INDEX as a POLICY-7 Source of Truth

BC-INDEX.md's H1-per-BC-row is the authoritative title source per POLICY 7 (CLAUDE.md
Architectural Authority table, item 7). Splitting the body into per-subsystem shards does NOT
change WHICH file is authoritative for a given BC's title — it changes WHERE that authoritative
row physically lives (from `BC-INDEX.md`'s body to `shards/BC-INDEX-SS-NN.md`). The POLICY 7
invariant itself ("BC H1 heading is authoritative BC title; BC-INDEX row must match verbatim") is
preserved unchanged; only the FILE PATH of "the row" changes. This is a metadata/addressing change,
not a semantic authority change, and does not require amending POLICY 7's text in
`.factory/policies.yaml` (out of this architecture burst's scope regardless — policy registry
changes route through the `policy-add`/`policy-registry` skills, not the architect directly).

The **adversary's POLICY auto-load** (loads `.factory/policies.yaml` into its rubric) is
independently confirmed NOT to read BC-INDEX.md directly for that purpose — verified by direct
inspection of the dispatch instructions' own framing and cross-checked against
`.factory/policies.yaml`'s independence from BC-INDEX.md's file structure. No ripple.

**Genuine residual risk (acknowledged, not mitigated further in this burst):** any THIRD-PARTY or
ad-hoc script (outside the audited touchpoint set in §5) that does a raw `grep 'BC-X.YY.NNN'
BC-INDEX.md` will silently stop finding rows that have moved to a shard file, with no error — a
false-negative, not a crash. This is the same class of risk ADR-049 already accepted for its own
`last_amended` restructuring (audited touchpoints get fixed; unaudited ad-hoc scripts are a known,
accepted residual). Mitigated partially by keeping BC-INDEX.md's top-level file's NAME unchanged
and its role as "the place you start looking" unchanged — only its CONTENT changes shape.

## 7. Split Proposal Assessment — BC-INDEX Stays Fully In Scope

Per the dispatch instructions' explicit fallback clause, this section assesses whether BC-INDEX
sharding should be split to a follow-up story instead of folded into S-25.02.

**Assessment: NO SPLIT.** Keeping BC-INDEX fully in scope is the right call, for three concrete
reasons discovered during this F2 elaboration (not merely asserted):

1. **B2's addressing scheme is not new architecture.** It reuses the ALREADY-EXISTING `### SS-NN`
   body partition and the ALREADY-AUTHORITATIVE BC-S-prefix→SS-NN mapping (ARCH-INDEX Subsystem
   Registry, POLICY 6). A split would have been justified if B2 required inventing a NEW BC family,
   a NEW cross-reference integrity model, or a NEW ADR from scratch — none of that is true here.
2. **B1 (the dominant size driver) reuses an already-shipped primitive.** `rotate_changelog`
   (ADR-049 §Decision 6) already exists, is tested, and needs only a new automatic caller, not new
   rotation logic.
3. **The two mechanisms share one gate.** Mechanism A and mechanism B (both B1 and B2) are all
   triggered by the SAME native dispatcher check (`shard_manager.rs`) with different artifact-shape
   cases — there is no separate validator-migration surface "that dwarfs the append-log work" (the
   dispatch instructions' own split-justifying condition). The migration surface (§5) is real and
   larger than mechanism A's, but it is enumerable and bounded (a handful of named touchpoints), not
   open-ended.

**What WOULD have justified a split, for calibration of future similar decisions:** if BC-INDEX had
no existing subsystem partition (i.e., the architect had to invent a NEW partitioning scheme from
scratch), or if its frontmatter changelog required NEW rotation logic incompatible with
`rotate_changelog`, or if flipping any Cohort B validator's fail-closed status depended on BC-INDEX
sharding landing FIRST in a way that blocked the append-log mechanism's own delivery — none of
these conditions hold. The two mechanisms are additive, independently deliverable within one story,
and share infrastructure. Point estimate impact: the story's original 15-point sizing should be
revised UPWARD by story-writer at BC-authorship handoff to account for BC-1.18.008/009/010 (three
BCs not in the original F1 enumeration) and the §5 migration surface — architect does not set the
story's point estimate (story-writer domain) but flags this concretely so it is not silently
absorbed into the existing 15-point figure. **(fix-burst addition, pass-1)** BC-1.18.011 (§4a, the
new B2 migration BC) further increases this revision — a fourth BC not in the original F1
enumeration, carrying its own non-trivial verification surface (independent census + atomicity +
idempotency). **(fix-burst addition, pass-2)** BC-1.18.012 (§4b, the new B1 backfill migration BC,
ADR-051 v1.2 Decision 13) further increases this revision again — a FIFTH BC not in the original F1
enumeration, closing B1's cold-start ungoverned-migration gap with the same
census/atomicity/idempotency verification surface as BC-1.18.008/BC-1.18.011.

## 8. Dependency Graph Acyclicity Check

The new native module (`shard_manager.rs`) lives inside `crates/factory-dispatcher`, depended on
only by `executor.rs`'s PreToolUse dispatch path (an existing dependency direction: `executor.rs`
already depends on sibling modules like `indeterminate_marker.rs`). `shard_manager.rs` additionally
depends on `last-amended-migrate`'s public `rotate_changelog`/`prepend_changelog_item` (a new
workspace-internal dependency edge: `factory-dispatcher` → `last-amended-migrate`). Checked:
`last-amended-migrate` has no dependency back on `factory-dispatcher` (it is a standalone CLI
migration tool crate per its own `Cargo.toml` membership) — **no cycle introduced.** BC-INDEX shard
files are data (markdown/TOML), not code, and introduce no crate-level dependency edges at all.
