## 1. Trigger-Scope Tradeoff (F1 §4 item 1)

### Recommendation: (A) Broad — `PostToolUse ^Bash$`, unconditional internal check, no command-text pre-filter

Register the companion on `event = "PostToolUse"`, `tool = "^Bash$"` (fires on every completed Bash
dispatch), and — this is the sub-decision F1's own option-(A) framing left open — do **not** gate
the internal `git diff --cached --name-only` / `git branch --show-current` check behind any
command-text heuristic at all, including a broadened one. Run both `host::exec_subprocess` calls
unconditionally on every invocation.

### Why not option B (narrow, gated on the `git\s+(add|stage)` text detector)

Option B's internal gate would only ever fire the post-hoc inspection on payloads the detective
mirror's OWN sibling (BC-4.16.001) already recognized as `git add`/`stage` text — which, for a
purely-preventive PreToolUse guard, means those cases are typically **already blocked before
execution**. The residual value a post-hoc mirror exists to capture is precisely the complement of
that set: staging that occurs through git plumbing, aliases, wrapper scripts, or any invocation
BC-4.16.001's text-based detector under-matches (its own documented residual-risk class, Invariant
6 Accepted Residuals) or that reaches the index through a mechanism that never contains the literal
substring `add`/`stage` adjacent to `git` at all. Gating the companion on the same text detector
would make it a near-tautological confirmation of BC-4.16.001's own successes and functionally
blind to BC-4.16.001's own documented failure modes — the opposite of what a detective mirror is
for.

### Why not a broadened-but-still-textual internal gate (e.g., "payload contains the substring `git`")

I considered a middle option — narrowing internally to "some form of `git` appears in the payload"
rather than the strict `add|stage` subcommand match — as a cheaper proxy for "this dispatch could
plausibly have touched the index." Rejected: it still assumes the staging mechanism's invocation
text is visible and git-shaped in the completed command. A script (`python3 fix_index.py`, a Make
target, an IDE-driven git plumbing call, a pre-existing background process) can leave `.factory/`
staged on a product branch without the triggering Bash payload containing the word `git` at all.
Because the check being performed is against **actual index state**, not payload text, any
internal text-based pre-filter reintroduces a version of the same under-match risk class the
mirror exists to close, just at a different filter boundary.

### Cost justification

The unconditional check costs two `host::exec_subprocess` calls (`git diff --cached --name-only`,
`git branch --show-current`) per completed Bash dispatch. Both operations read only git's index
metadata and current-branch pointer — output size and execution cost are governed by the number of
currently-staged paths and repository ref state, not by the size of `.factory/` cycle artifacts
(the actual resource-exhaustion driver ADR-039/047 were written to address) or by the size of the
triggering Bash payload. This is the same "bounded input" classification `validate-factory-path-staging`
itself received for Cohort A-immediate treatment (ADR-047 §D8a: "Bounded — reads file path from
Bash tool params") — substituting "staged-path list from the git index + branch name from git HEAD"
for "file path from Bash tool params." Neither scales with cycle-artifact size. The added latency
is two fast, local git plumbing calls; there is no read of any large file.

### POLICY 22 determination: PENDING-HUMAN-RATIFICATION

This is a new plugin, not an amendment to an already-ratified crash-safety model — BC-4.16.001's
own model is byte-identical/unchanged (AC-003), and the generic marker/gate mechanism (BC-1.18.001
invariant 4) is reused verbatim with zero mechanism changes, exactly as F1 §2 point 1 established.
On that basis alone the trigger-scope choice would be an ordinary architect-owned design decision
within the F1/F2 scope ADR-047 §D8a explicitly delegates ("This ADR does not select among these
options; that is the follow-up story's F1/F2 scope").

I am nonetheless flagging it `PENDING-HUMAN-RATIFICATION` because:

1. **No dominant option exists.** Option A trades a small, bounded per-dispatch cost for
   detection completeness; Option B trades completeness for a smaller cost. Both are internally
   coherent; the correct answer is a judgment call about how much steady-state overhead
   (~2 extra `exec_subprocess` calls on every Bash tool call, session-wide) is acceptable to close
   a residual-risk class this project has already formally accepted once (BC-4.16.001 Invariant 6
   Accepted Residuals) rather than closed.
2. **This project's own precedent routes exactly this class of decision through explicit human
   confirmation.** ADR-047 v1.1/v1.2 reserved Cohort A membership to "EXACTLY THREE validators...
   No other validator is in Cohort A unless explicitly confirmed by the human at the F3 spec
   gate." ADR-039 §AMD-001's adapter-class bifurcation was itself ratified via POLICY 22 rather
   than applied by architect fiat, despite being a comparably mechanical-sounding classification
   call. The pattern in this codebase is: architect classifies and recommends; the human ratifies
   before a NEW validator's coverage/enforcement posture goes live.
3. **This is the exact failure class S-25.04 exists to close.** `validate-factory-path-staging`'s
   own zero-enforcement gap traces to an under-scrutinized event/tool registration choice that
   nobody flagged for explicit confirmation before it shipped. Silently picking Option A here
   without surfacing the tradeoff would repeat the same pattern this story is meant to fix, just
   with the failure mode inverted (over-triggering cost risk instead of silent non-enforcement
   risk).

**What IS finalized regardless of which option the human ratifies:** the plugin's identity, event
type (`PostToolUse`), tool pattern (`^Bash$`), `failure_policy = "fail-closed"`, `on_error =
"continue"`, priority, crate name, and its status as the ADR-039 §Decision 2 seventh member
(native-WASM, fuel-axis-only) are unaffected by A-vs-B — both options share the same registration
shape; they differ ONLY in the plugin's internal branch on whether to run the git-index check
unconditionally or behind a text pre-filter. Product-owner can author BC-4.16.002's structural
content (Preconditions 1/3, Postconditions PC1-PC4, Invariants, Traceability, Architecture Anchors)
now. Only Precondition 2's exact trigger-condition text (does the check run on every completed
Bash dispatch, or only on ones whose payload text matched a git-mutation heuristic) is provisional
pending ratification — draft it against my Option A recommendation, marked
`PENDING-HUMAN-RATIFICATION`, so the BC is ready to finalize the instant ratification lands rather
than needing a second F1/F2 round-trip.

**Proposal for the orchestrator to bring to the human:** *"S-25.04's new post-hoc `.factory/`
git-staging detective validator can run its index/branch check on every completed Bash dispatch
(complete coverage, ~2 extra lightweight git calls per Bash tool call session-wide) or only on
Bash dispatches whose command text looks like `git add`/`git stage` (cheaper, but structurally
blind to exactly the under-match/alternate-staging-path residual risk the validator exists to
catch — BC-4.16.001's own Accepted Residuals). Architect recommends the complete-coverage option.
Ratify?"*

## 2. Companion Validator Identity (F1 §4 item 2)

### 2.1 Crate / plugin name

**Recommended: `validate-factory-path-staged`** (supersedes the story's placeholder
`validate-factory-path-staging-write`).

Justification: F1 correctly flagged the `-write` suffix as a misnomer — this validator inspects
git staging state, not artifact-write content. `validate-factory-path-staged` preserves the
`validate-factory-path-*` naming family established by ADR-031 §Decision 3 (the same discipline
that already distinguishes `validate-factory-path-staging` from the unrelated
`validate-artifact-path` crate to avoid registry/cargo-output collisions) while using the **past
participle** ("staged" — a completed state being inspected) to linguistically distinguish it from
the sibling's **gerund** ("staging" — an action about to happen, inspected before it runs). This
mirrors the PreToolUse/PostToolUse split exactly and requires no reader to consult a comment to
understand which member of the pair is which. Verified no collision: no existing crate or
`hooks-registry.toml` entry uses this name; `crates/hook-plugins/validate-factory-path-staging/`
is the only extant sibling.

- **Crate path:** `crates/hook-plugins/validate-factory-path-staged/`
- **Cargo package name:** `validate-factory-path-staged`
- **WASM artifact:** `hook-plugins/validate-factory-path-staged.wasm`
- **Structure:** mirror the sibling exactly — `src/lib.rs` (testable pure-core + WASM entry logic),
  `src/main.rs` (WASI `_start` wrapper per the existing crate's own `[[bin]]` convention),
  `src/tests.rs`, a `tests/proptest_*.rs` fixture for path-matching coverage (reuse
  BC-4.16.001's `.factory/` case-insensitive path-matching predicate verbatim per Invariant 4 —
  it is pure and directly reusable, not merely pattern-mirrored). `Cargo.toml` dependencies:
  `vsdd-hook-sdk` (workspace path dep, same as sibling), `serde`/`serde_json` (workspace),
  `proptest` (dev-dependency, workspace-pinned version, matching sibling's `"1.6"`).

### 2.2 Priority number

**Recommended: `priority = 161`.**

Live-registry evidence (literal grep against `plugins/vsdd-factory/hooks-registry.toml`, same
evidence discipline the registry's own comments already use — TD-VSDD-096 pattern): priority
values 150 through 160 are fully occupied (`150`=validate-artifact-path, `151`=validate-index-cite-refresh,
`152`=validate-burst-log [both its Edit|Write and Bash arms share 152], `153`=validate-state-structure,
`154`=validate-dispatch-advance [both arms], `155`=validate-stable-anchors, `156`=validate-closes-completeness,
`157`=validate-policies-schema, `158`=validate-trajectory-tail-cell-completeness,
`159`=verify-state-timestamp-advisory, `160`=lint-registry-async-invariant). No entry exists for
priority `161`-`209` (the next occupied value is `210`, `convergence-tracker`). `161` is therefore
the lowest free slot in the same sequential low-100s allocation band already used for this
registry's PreToolUse/PostToolUse validator tier — the identical "lowest free slot above N"
convention the registry's own `validate-trajectory-tail-cell-completeness` (158) and
`verify-state-timestamp-advisory` (159) comments already document and apply.

### 2.3 Registration shape

```toml
[[hooks]]
name = "validate-factory-path-staged"
event = "PostToolUse"
tool = "^Bash$"
plugin = "hook-plugins/validate-factory-path-staged.wasm"
priority = 161
timeout_ms = 5000
on_error = "continue"

[hooks.capabilities.exec_subprocess]

env_allow = ["HOME", "GIT_CONFIG_GLOBAL", "XDG_CONFIG_HOME"]
```

(`exec_subprocess` capability block copied verbatim from the sibling's own registry entry — same
host capability surface: `git diff --cached --name-only` and `git branch --show-current` need
nothing beyond what `git branch --show-current` already requires.)

### 2.4 `failure_policy = "fail-closed"` — confirmed, unconditional, no S-21.24 dependency

This is the entire point of the story (AC-001). Set unconditionally at S-25.04 delivery, mirroring
`validate-factory-path-staging`'s own Cohort A-immediate treatment: this validator's input (staged
git index paths + current branch name) is bounded independent of `.factory/` cycle-artifact size,
so no Layer-2-sharding dependency applies, and per AC-004 the ADR-039 §Decision 2 roadmap
*registration* act is independent of S-21.24's Phase-4 enforcement wiring (§3 below).

### 2.5 `on_error = "continue"` — confirmed, matches the sibling, NOT weakened

Justification for keeping `on_error = "continue"` despite this being the validator whose entire
purpose is a structurally-reachable fail-loud trigger: `on_error` and `failure_policy` are
deliberately separate, non-unified axes (ADR-039 §Decision 1). `on_error` governs genuine plugin
**crashes** (Trap::UnreachableCodeReached, host-ABI mismatch, deserialization failure) — a
different failure class from **resource exhaustion** (Timeout{Fuel}/Timeout{Epoch}/OutputTooLarge),
which is what `failure_policy = "fail-closed"` routes to `write_indeterminate_marker`. The
fail-loud guarantee this story exists to deliver is carried entirely by `failure_policy`, which is
already correctly set (§2.4); `on_error` does not need to change to achieve it. Setting
`on_error = "block"` would add no protective value here — this is a detective PostToolUse check;
its own crash cannot retroactively undo the already-completed Bash dispatch, exactly the same
reasoning BC-4.16.001 Invariant 2 and every other PostToolUse validator in this registry already
apply — and would introduce an unexplained deviation from the sibling's posture and from this
registry's established PostToolUse convention (`validate-burst-log`, `validate-state-structure`,
`validate-dispatch-advance`, `verify-state-timestamp-advisory` — all `on_error = "continue"`).
ADR-039 §Decision 2 states this combination is "the intended steady-state for most validators":
`on_error = "continue"` (crash = advisory) AND `failure_policy = "fail-closed"` (exhaustion =
block), simultaneously. `validate-factory-path-staged` follows that steady-state exactly.

### 2.6 Fuel/timeout calibration values

- **Calibration class: native-WASM, fuel-axis-only** (confirmed — see §3.2 below). The crate calls
  `host::exec_subprocess` directly from its own WASM code (same architectural pattern as the
  sibling `validate-factory-path-staging` and as `validate-cross-site-correspondence`), **not**
  via `hook-plugins/legacy-bash-adapter.wasm`. Per ADR-039 §Decision 2/§AMD-001, this places it in
  the "fuel-axis calibration applies and is sufficient" class, not the dual
  fuel+`timeout_ms`-p99-formula class mandated for the five `legacy-bash-adapter.wasm`-hosted
  §Decision 2 members.
- **`fuel_cap`:** `max(observed_max × 1.5, 50_000_000)` per ADR-039 §Decision 4's target-statistic
  rule for hard-block (fail-closed) boundary validators — i.e., `fuel_cap = 50_000_000` in
  practice, since `observed_max` for two lightweight `exec_subprocess` calls plus a fixed-size
  path-list scan will sit far below the `50_000_000` floor (this validator does not read any
  `.factory/` cycle artifact — its resource profile is fundamentally smaller than the six
  §Decision 2 validators the formula's corpus requirements were written for; see §3.2's calibration-
  corpus note).
- **`timeout_ms`:** `5000` (matches the sibling's own value exactly; two local git plumbing calls
  complete well within this budget; no dual p99_ms×2.0/30s-floor host-wall-clock formula applies —
  that formula is scoped to `legacy-bash-adapter.wasm`-hosted plugins only, per §2.6's calibration-
  class determination above).

### 2.7 Branch-detection-failure invariant (resolves F1 §3's flagged open item)

F1 §3 flagged as TBD "whether fail-open or fail-closed on branch-detection failure specifically."
This is mechanically answerable now by mirroring the sibling: **fail-open** on branch-detection
failure (git unavailable, detached HEAD, non-zero exit from `git branch --show-current`), matching
BC-4.16.001 Invariant 3 exactly. Rationale for the mirror: an uncertain branch state is not, on its
own, evidence of a `.factory/`-on-product-branch violation; the same "uncertain state is not a
blocking condition" principle BC-4.16.001 already establishes for its own PreToolUse check applies
identically to this PostToolUse mirror. This is distinct from the plugin's own cannot-complete
case (fuel/epoch/OutputTooLarge on the `exec_subprocess` calls themselves), which is what
`failure_policy = "fail-closed"` routes to the marker mechanism — branch-detection failure is a
clean, completed `PluginResult::Ok` outcome with an inconclusive answer, not a resource-exhaustion
INDETERMINATE outcome.

### 3.2 Calibration-corpus note (new, scoped to this validator only)

The six existing §Decision 2 members' mandatory calibration corpus (Decision 4: `lessons.md`
≥4000 lines, `STATE.md`/`decision-log.md` at current live size, the ≥574 KB fixture) is built

staged-path list** and the trivial `git branch --show-current` call. I direct the eventual
formal-verifier/test-writer calibration pass to use a *different*, validator-specific corpus: a
synthetic worst-case index state with a large number of simultaneously staged paths (e.g., ≥500

calibration-methodology note, not an open architect question — the ADR-039 §Decision 4 formula
(`max(observed_max × 1.5, 50_000_000)`) still governs; only the input corpus that produces
`observed_max` differs, because this validator's resource driver is index cardinality, not
artifact byte size.
