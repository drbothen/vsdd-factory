# S-25.04 F1 Delta Analysis: Close `validate-factory-path-staging` Zero-Enforcement Gap

## 0. Headline Finding (read this first)

The S-25.04 story text and ADR-047 §Decision 8a's "Known Gap" note describe option (a) as a
"new PostToolUse companion validator that mirrors `validate-factory-path-staging`'s `.factory/`
path-staging check **on the artifact-write side**." Ground-truthing `validate-factory-path-staging`
against its own authoritative behavioral contract (**BC-4.16.001**, not any BC-1.18.xxx file) shows
this framing is imprecise in a way that matters for BC authorship:

`validate-factory-path-staging` does **not** validate the *content* of a `.factory/` artifact write.
It is a narrow **git-staging exclusivity guard** (INV-E21-001, capability CAP-034, issue #342): a
`PreToolUse ^Bash$` plugin that inspects a Bash payload for a `git add`/`git stage` command and, if
any argument resolves to a `.factory/`-rooted path **and** the current branch is a product branch
(not `factory-artifacts`), blocks the command before it runs. There is no "artifact write" for this
validator to validate — the thing it's protecting is exclusive git-tracking of `.factory/` content
between the `factory-artifacts` orphan branch and product branches.

Given that, the companion validator that actually closes the enforcement gap is **not** a generic
Edit/Write/MultiEdit `.factory/`-write validator. It is the natural **post-hoc detective mirror** of
the same git-staging-exclusivity concern: a `PostToolUse ^Bash$` plugin that, after a Bash command
completes, inspects the *actual* git index/branch state (e.g. `git diff --cached --name-only` +
`git branch --show-current` via `host::exec_subprocess`, the same host function
`validate-factory-path-staging` itself already uses) to detect whether a `.factory/` path ended up
staged on a product branch — catching (a) false negatives in BC-4.16.001's text-based
command-parsing heuristics, and (b) the PreToolUse guard's own cannot-complete case, which today has
no marker-write trigger at all (BC-1.18.001 invariant 4).

This reframing changes the BC-authorship plan (§3 below): the companion validator's own check-logic
belongs as a **new sibling of BC-4.16.001** (same capability CAP-034, subsystem SS-04) — not a new
BC-1.18.00x under SS-01, as the story's placeholder guess suggested. The SS-01 BCs (BC-1.18.001/004)
need only the narrow amendments already anticipated by the story: they define the *generic*
INDETERMINATE/marker mechanism, which already applies automatically to any qualifying PostToolUse
fail-closed plugin, including this new one.

## 2. Option Confirmation (Spec-Side)

**Option (a) is confirmed as the correct closure**, with the semantic correction in §0 folded in.
Reasoning:

1. **Structural fit.** BC-1.18.001's marker-write mechanism is already generic over "any PostToolUse
   plugin with `failure_policy = fail-closed`." Adding a second PostToolUse fail-closed plugin needs
   zero mechanism changes — this is precisely what makes option (a) the lowest-risk closure (as ADR-047
   itself argues) and confirms the story's Architecture Compliance Rules table ("no second marker file
   or duplicate gate mechanism — reuse `write_indeterminate_marker`/`validate-unvalidated-mutation-marker`
   verbatim") is achievable exactly as written.

2. **No self-lock risk introduced.** The companion fires PostToolUse (detective, not preventive) — a
   PostToolUse hook cannot retroactively block the write it observes (ADR-039 §Decision 3's own
   framing: "PostToolUse cannot retroactively undo a completed write"). This mirrors why
   `validate-factory-path-staging` itself was judged Cohort A-immediate-safe: no self-lock class is
   introduced by a detective PostToolUse validator regardless of its `on_error`/`failure_policy`
   values, unlike the two PreToolUse `^Agent$` Cohort A-deferred validators.

3. **Option (b) remains correctly out of scope.** Changing `on_error` on the *existing* PreToolUse
   validator would require re-litigating the self-lock-avoidance analysis (ADR-047 §D8a "Why the
   partition?") and is explicitly deferred by the story's own Architecture Compliance Rules table.
   Nothing in this F1 pass surfaces a reason to reopen that.

4. **The one correction needed is scope, not mechanism.** The story/ADR's "artifact-write side"
   phrasing (loosely analogous to how BC-1.18.001 talks about "artifact_path... of a PostToolUse
   payload") invites authoring a companion whose check-logic doesn't correspond to anything
   `validate-factory-path-staging` actually protects. §0's git-index-inspection framing is option (a)
   as originally intended, made precise against BC-4.16.001's actual postconditions — it is not a
   different option, and does not require re-litigating the option (a)/(b)/(c) selection made by
   ADR-047 or re-opening S-25.04's own AC-002/AC-003 scope guarantees (no second marker mechanism, no
   change to the existing validator).

No infeasibility was found for option (a). No escalation to option (b) is warranted.

## 3. BC Authorship Plan

### (i) BC-1.18.001 invariant 4 — clarification amendment

Add one clause to invariant 4 (no rewrite of the existing sentence): state explicitly that the
"PostToolUse-only" marker-write trigger is a property of the *event type* a fail-closed plugin is
registered on, not an enumerated/closed set of plugins — and forward-cite the new companion BC as a
second concrete instantiation (the Arm 1/Arm 2 gate plugin itself is NOT such an instantiation; it is
registered `failure_policy = "fail-open"` per ADR-047 §Decision 4, so it never reaches this path —
this distinction is worth stating to prevent a future reader conflating "the gate" with "a
marker-writing plugin"). Version bump only; no postcondition, wire-format, or mechanism content
changes.

### (ii) BC-1.18.004 postcondition 4 — count amendment

PC4's "Layer-1 effective fail-closed count at S-25.01 merge: ZERO" statement is historically accurate
and MUST NOT be rewritten to describe a different point in time (POLICY-19-style anti-volatile-pin
discipline: it is a dated, event-scoped statement). The amendment adds a new, clearly-dated
companion statement: "Layer-1 effective fail-closed count at S-25.04 merge: **N**" (N to be
determined by whatever else Cohort A/roadmap state exists at that time — at minimum 1, for the new
companion validator; `validate-factory-path-staging` itself remains ZERO per its own unchanged
registration). This preserves both statements as accurate historical anchors rather than overwriting
one with the other.

### (iii) New BC — confirmed required; recommended ID **BC-4.16.002** (not BC-1.18.005)

A new BC is required — the companion validator has genuine check-logic (post-hoc `.factory/`
git-staging detection) that no existing BC specifies. Recommended placement, contra the story's
provisional guess:

- **Subsystem: SS-04** (Hook Plugin SDK / WASM plugin development — same subsystem as BC-4.16.001
  and the existing `validate-factory-path-staging` crate; ARCH-INDEX Subsystem Registry, POLICY 6).
- **Capability: CAP-034** (Nested Worktree Path Exclusivity) — same capability as BC-4.16.001, per
  the Capability Anchor Justification discipline (S-7.01): this validator's purpose is a second
  enforcement instantiation of INV-E21-001, not a new capability.
- **ID: BC-4.16.002** (next sequential slot in the BC-4.16.xxx family; BC-4.16.001 is the only
  existing member).
- **Why not BC-1.18.005:** the BC-1.18.xxx family is capability CAP-041 (Validation Integrity:
  INDETERMINATE Outcome, Durable Mutation Marker, Next-Advance Gate) — a different capability
  concerned with the *generic dispatcher mechanism*, not with any single plugin's check semantics.
  Placing the companion's check-logic BC there would conflate "the mechanism a plugin's failure
  triggers" with "what the plugin checks" — exactly the two concerns BC-1.18.001 and BC-4.16.001
  already keep cleanly separated for the *existing* validator. S-25.04's companion should follow the
  same separation, not collapse it.

**Expected scope of BC-4.16.002** (pending architect confirmation of the two items in §4):

- **Preconditions:** PostToolUse fires on `^Bash$` (or a narrower tool/priority pattern — architect
  TBD, §4); dispatcher has invoked the companion plugin; `host::exec_subprocess` capability is
  granted for `git diff --cached --name-only` and `git branch --show-current` (or equivalent) —
  mirroring BC-4.16.001 Precondition 3's `host::exec_subprocess` dependency.
- **Postconditions:** PC-Block — after the triggering Bash command completes, if `git diff --cached
  --name-only` contains a path matching `^\.factory/` (case-insensitive, mirroring BC-4.16.001
  Invariant 4) AND the current branch is a product branch, the plugin returns a blocking outcome
  (exit_code semantics per its own `on_error`) with a message structurally analogous to BC-4.16.001
  PC1's `FactoryPathOnProductBranch` message. PC-Pass — branch is `factory-artifacts`, or no
  `.factory/` path is staged. PC-Indeterminate-trigger — when this plugin's own WASM execution
  cannot complete (fuel/epoch/OutputTooLarge) and `failure_policy = fail-closed`, the dispatcher
  reaches `write_indeterminate_marker` (BC-1.18.001 PC4) — this is the AC-001 closure criterion
  itself, stated as this BC's own trigger-condition postcondition, with BC-1.18.001 as the generic
  mechanism it invokes.
- **Invariants:** mirrors BC-4.16.001 Invariants 2-4 (fail-open-on-crash is NOT applicable here —
  this plugin is fail-closed by design, per AC-001; conservative/case-insensitive path matching;
  branch-detection-failure handling — TBD whether fail-open or fail-closed on branch-detection
  failure specifically, since that failure mode is distinct from the plugin's own WASM
  cannot-complete case and needs its own explicit ruling).
- **Edge cases:** at minimum, the four EC-001..EC-004 already sketched in the story (renamed to match
  the corrected git-index-inspection semantics), plus a dedicated case for "PostToolUse fires on a
  Bash command that is NOT a git command at all" (fast pass, mirroring BC-4.16.001 PC4).
- **Related BCs:** BC-4.16.001 (sibling — detective/post-hoc companion, not a replacement),
  BC-1.18.001 (composes with — this BC's own INDETERMINATE-trigger postcondition invokes BC-1.18.001's
  generic mechanism), BC-5.43.001 (adjacent third layer, different mechanism — cite for
  disambiguation, not composition).

## 4. Architect-Dependency Flag (CRITICAL)

The following BC-authorship items are blocked on architect decisions and MUST NOT be guessed by
product-owner. I (product-owner) will not author final BC-4.16.002 postconditions until these are
resolved:

1. **Exact event/tool pattern and trigger scope.** Two candidate designs exist and have materially
   different fuel/performance and correctness profiles:
   - **(A) Broad:** `PostToolUse ^Bash$` on every Bash dispatch, with the plugin's own logic
     narrowing internally (run `git diff --cached --name-only` + branch check unconditionally, or
     only when the completed command text itself looked like a git-mutating command). Simpler
     registry entry; higher steady-state `exec_subprocess` call volume (every Bash PostToolUse pays
     the cost of two subprocess calls unless internally short-circuited).
   - **(B) Narrow:** `PostToolUse ^Bash$` but internally gated on the SAME command-text detection
     BC-4.16.001 Precondition 2 already uses (reuse the `git\s+(add|stage)` detector against the
     *same payload*, post-execution) — only running the git-index inspection when the completed
     command was itself a `git add`/`git stage` invocation. Cheaper; but does NOT catch cases where
     a DIFFERENT command (e.g. a script, a `git commit -a`, or a bypass path BC-4.16.001's own
     detector under-matches) staged a `.factory/` path without itself being detected as `git
     add`/`git stage` text — arguably the more valuable failure mode to catch, since exact-text
     under-match is precisely BC-4.16.001's own documented residual-risk class (Accepted Residuals,
     Invariant 6).
   This is a genuine architectural tradeoff (detection completeness vs. per-dispatch fuel/latency
   cost) that only the architect can adjudicate — it determines this BC's own Precondition 1/2 text
   and its ADR-039 fuel-axis calibration corpus (§4 item 2 below scales differently under (A) vs (B)).

2. **Crate name, priority number, and ADR-039 §Decision 2 roadmap placement.** Per the story's own
   AC-001, naming is "TBD at F2." I need: (a) the canonical plugin `name`/crate path (the story's
   placeholder `validate-factory-path-staging-write` is a reasonable candidate but not architect-
   confirmed — the git-index-inspection framing in §0 may suggest a more accurate name, e.g.
   `validate-factory-path-staged-on-product-branch` or similar); (b) its `priority` value relative to
   the existing `validate-factory-path-staging` (140) and the Arm 1/Arm 2 gate plugins, so the
   Architecture Anchors and hooks-registry.toml AC text can cite a concrete, collision-free number;
   (c) explicit confirmation that this validator calibrates on the fuel-axis-only formula (native-WASM
   class, not `legacy-bash-adapter.wasm`-hosted) for its ADR-039 §Decision 2 roadmap-extension entry —
   this follows directly from it calling `host::exec_subprocess` the same way `validate-factory-path-
   staging` itself does, but the architect should state it explicitly rather than have product-owner
   infer it, since ADR-039's adapter-class bifurcation (§AMD-001) is architect-owned normative content.

Both items are cross-component design decisions (detection strategy tradeoff; registry/roadmap
placement) — they are not mechanical lookups I can resolve from existing artifacts, and guessing
either would risk authoring BC-4.16.002 postconditions the architect later has to walk back (the
exact "TODO for architect" anti-pattern the production-grade default warns against is avoided here by
naming the *specific* decision and *why* it's architect-scoped, not by silently picking one).
