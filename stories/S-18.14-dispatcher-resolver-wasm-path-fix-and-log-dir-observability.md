# S-18.14 — Dispatcher resolver WASM path resolution fix (TOML-parent-relative) + log_dir observability

## Summary

Fix `resolver_loader::load_registry` to resolve relative `plugin` paths against
the TOML file's parent directory (`CLAUDE_PLUGIN_ROOT` at runtime) instead of the
process working directory (CWD). Also emit `log_dir` in the `dispatcher.started`
event payload using the already-present `InternalLog::log_dir()` accessor.

**Root cause of regression:** The dispatcher is invoked by Claude Code with CWD set
to the host project directory (e.g., `/Users/<user>/project/`). WASM plugin files
live under `CLAUDE_PLUGIN_ROOT` (e.g., `~/.claude/plugins/cache/…/vsdd-factory/<ver>/`).
Resolving `plugin = "hook-plugins/vsdd-context-resolvers.wasm"` against CWD produces a
path that does not exist, causing `path.canonicalize()` to return `Err(ENOENT)`.
Empirical evidence: 8,560 `resolver.load_error` events for `wave_context` across
recent dispatcher sessions, with zero successful loads since rc.21.

**Status:** DRAFT — spec-complete. Scoped adversarial spec review next before `ready`.

**Release note:** The operator-level cached dispatcher (`~/.claude/plugins/cache/…/`) picks
up this fix only after an rc release is cut. Develop-branch edits do not affect the cached
plugin. A release MUST be cut after this story merges (out-of-band delivery note, not a
deferral).

Scope: SMALL (8 pts). Epic E-18 (context-durability). Priority P0 (HIGH code defect — production
regression observed empirically). Wave W10 (standalone, no blocking deps, can proceed
independently).

## Narrative

As a factory operator, I want the dispatcher to correctly locate WASM resolver
artifacts relative to the plugin root directory (where they actually live), so that
`wave_context` and all other context resolvers load successfully on every dispatch
and the contextual hook pipeline functions as designed.

As a factory platform engineer, I want `dispatcher.started` to include the absolute
`log_dir` path, so that observability tooling can locate the dispatcher's internal
log directory without needing to re-run the seven-level ADR-024 resolution algorithm.

## Acceptance Criteria

### AC-001 — INV-8: TOML-parent-relative path resolution in `load_registry`
`resolver_loader::load_registry` resolves relative `entry.plugin` paths against
`path.parent()` (where `path` is the parameter name in `load_registry`'s signature;
alias: `let toml_parent = path.parent();` mirroring `registry.rs::resolve_plugin_paths`
which computes `let base = path.parent()`). The normative implementation pattern is:
```rust
if let Some(base) = path.parent() {
    if entry.plugin.is_relative() {
        entry.plugin = base.join(&entry.plugin);
    }
}
// None arm: path.parent() returns None only for a bare component path (e.g. "foo");
// in that case entry.plugin passes through unchanged to get_or_compile.
```
The `is_relative()` guard is NORMATIVE (required for precedent-consistency with
`registry.rs::resolve_plugin_paths` and for implementation intent-clarity; a bare
unconditional `base.join(&entry.plugin)` would behave identically on all platforms
because `PathBuf::join` replaces the base with any absolute component). Correct Rust
semantics: `Path::is_relative()` ≡ `!Path::is_absolute()`. A Windows rooted-but-not-
absolute path such as `\foo` has `is_absolute()`=false, therefore `is_relative()`=TRUE —
the guard IS taken and `base.join("\foo")` is called, producing `\foo` via join-replacement
(same as the input; harmless). A genuinely absolute path (`/x` on POSIX, `C:\x` on Windows)
has `is_absolute()`=true, therefore `is_relative()`=false — the guard is NOT taken and the
path passes through to `get_or_compile` unchanged. The resolved path feeds the single
`get_or_compile` call site (functional anchor: `resolver_loader::load_registry`). The
resolved path then feeds both the `fail_closed: true` and `fail_closed: false`
error-handling arms identically (the fail_closed divergence is in the post-call error
`match`, not at separate call sites).
When `entry.plugin` is genuinely absolute (`is_relative()`=false), it passes through to
`get_or_compile` unchanged (the guard is not taken — no joining). When `entry.plugin` is
rooted-but-not-absolute on Windows (`is_relative()`=true), the guard IS taken and
`base.join(entry.plugin)` = `entry.plugin` via join-replacement (harmless).

(traces to BC-1.13.001 invariant 8)

### AC-002 — INV-8: CWD-relative resolution must differ from TOML-parent-relative resolution
In the unit test for AC-001, the test constructs a synthetic `resolvers-registry.toml`
with a relative `plugin` path (e.g., `hook-plugins/vsdd-context-resolvers.wasm`),
places the WASM artifact at `<TOML-parent>/<rel>` (not at `<CWD>/<rel>`), and asserts
that the resolved WASM path is TOML-parent-relative. The test additionally asserts that
a CWD-relative resolution of the same relative path would yield a non-existent path,
proving the test distinguishes the corrected behavior from the prior bug.

(traces to BC-1.13.001 invariant 8)

### AC-003 — PC-9 / EC-010: Zero `resolver.load_error` when artifacts present at TOML-parent-relative path
With `resolvers-registry.toml` present, valid, and the referenced WASM artifact
existing at `<TOML-parent>/<relative-plugin-path>` (and NOT at `<CWD>/<relative-plugin-path>`),
`load_registry` completes with zero `resolver.load_error` events for the affected
resolver. The `wave_context` regression scenario — WASM at `CLAUDE_PLUGIN_ROOT/hook-plugins/`
but not at `<user-project-CWD>/hook-plugins/` — produces no load error.

(traces to BC-1.13.001 postcondition 9; witnesses EC-010)

### AC-004 — PC-9 / EC-010: Both fail_closed error-handling arms receive the TOML-parent-relative resolved path
The single `get_or_compile` call in `load_registry` receives the TOML-parent-relative
resolved path regardless of the entry's `fail_closed` setting. As a result: when
`fail_closed: true` (default), a resolver whose WASM is absent at CWD but present at
TOML-parent-relative path loads successfully; when `fail_closed: false`, the same
scenario also loads successfully. Neither arm falls back to CWD-relative resolution or
emits a `LoadWarning` when the file exists at the correct location. (The fail_closed
divergence governs error handling AFTER the single `get_or_compile` call returns, not
path resolution.)

(traces to BC-1.13.001 postcondition 9; witnesses EC-010)

### AC-005 — PC-10: `dispatcher.started` payload includes non-empty `log_dir` field (absolutized at emission)
The `dispatcher.started` event emitted in `main.rs` at the `DISPATCHER_STARTED`
emission site includes a `log_dir` string field. The field value is produced by:
```rust
std::path::absolute(internal_log.log_dir())
    .unwrap_or_else(|_| internal_log.log_dir().to_path_buf())
    .display()
    .to_string()
```
(`internal_log` is `Arc<InternalLog>`.) The `.display().to_string()` form MUST be used
— it produces an owned `String` and is the correct sibling of `registry_path.display().to_string()`
already used at the same site. The `.to_string_lossy().as_ref()` form is FORBIDDEN:
it borrows from a dropped temporary and does not compile. The absolutization MUST
occur at the `DISPATCHER_STARTED` emission site in `main.rs`, NOT inside the
`InternalLog::log_dir()` accessor (which stays verbatim).
Functional anchors (TD-VSDD-091): `std::path::absolute`, `DISPATCHER_STARTED` (event
name constant), `InternalLog::log_dir()` (verbatim path accessor). The field is:
- Present unconditionally on every startup (not behind a feature flag, not optional)
- Non-null and non-empty
- Absolute whenever CWD is accessible (the common/contractual case) — produced by
  `std::path::absolute(internal_log.log_dir())`
- On the rare CWD-inaccessible fallback: equals the verbatim return of
  `InternalLog::log_dir()` (which may itself be absolute depending on construction)

(traces to BC-1.13.001 postcondition 10)

### AC-006 — PC-10: `log_dir` field present in dispatcher log for each invocation
A freshly-started dispatcher invocation writes a `dispatcher.started` JSONL event whose
JSON object contains key `"log_dir"` with a non-empty string value. Verifiable by
parsing the most recent line from `<log_dir>/dispatcher-internal-YYYY-MM-DD.jsonl`
after dispatch and confirming `log_dir` key presence.

(traces to BC-1.13.001 postcondition 10)

### AC-007 — Integration: `wave_context` resolver loads in production-like fixture
Using the production `vsdd-context-resolvers.wasm` artifact (when present at
`workspace_root/plugins/vsdd-factory/hook-plugins/vsdd-context-resolvers.wasm`) and
a synthetic `resolvers-registry.toml` whose `plugin` value is a relative path to that
artifact, calling `load_registry` with the absolute TOML path succeeds and the returned
`ResolverRegistry` contains one registered resolver named `wave_context`. Zero
`LoadWarning` entries are returned. The synthetic `resolvers-registry.toml` MUST be
written at a location whose parent directory actually contains
`hook-plugins/vsdd-context-resolvers.wasm` — either `plugins/vsdd-factory/` (where
the real artifact lives) or a tempdir copy that preserves the `hook-plugins/` sibling
directory — so that `path.parent().join("hook-plugins/vsdd-context-resolvers.wasm")`
resolves to the real artifact. Writing the TOML to an unrelated tempdir whose parent
does not contain `hook-plugins/` defeats the test's purpose. (If the WASM artifact is
not yet built, the test is skipped with `eprintln!("SKIP: …")` — identical to the
existing skip pattern in
`wasi_integration_tests::test_wave_context_resolver_wasm_injects_context`.)

(traces to BC-1.13.001 postcondition 1; witnesses INV-8 and PC-9 end-to-end)

- **S-18.04a-prereq** (write_file.rs cwd alignment) — related CWD-alignment pattern in `invoke.rs`; the same class of CWD-vs-plugin-root confusion exists in resolver loading

**Key lesson from S-12.04:** `get_or_compile` is designed to receive an already-resolved
absolute path and call `path.canonicalize()` on it. The canonicalize step requires the file
to exist. The bug is NOT inside `get_or_compile`; it is in the calling code in `load_registry`
that passes `&entry.plugin` (relative) directly to `get_or_compile` instead of first joining
with `path.parent()` (the TOML file path parameter). The fix is in `load_registry`, not in `get_or_compile`.

**Reference implementation — mirror `registry.rs::resolve_plugin_paths` (POLICY 4):**
The `hooks-registry.toml` loader already uses exactly this pattern to resolve hook plugin
paths: `registry.rs` computes `let base = path.parent()` then calls
`parsed.resolve_plugin_paths(base)`, which iterates entries and does
`entry.plugin = base.join(&entry.plugin)` for each relative path. This is governed by sibling
contract BC-1.01.004 (hooks-registry plugin path resolution), which carries the
idempotent-absolute-passthrough guarantee: if `entry.plugin` is already absolute,
`base.join(absolute)` in Rust's `PathBuf::join` semantics returns the absolute path unchanged
(the absolute component replaces the base). The implementer MUST mirror this proven pattern
using `if let Some(base) = path.parent() { if entry.plugin.is_relative() { entry.plugin = base.join(&entry.plugin); } }`
(alias: `let toml_parent = path.parent();` with `if let Some(base) = toml_parent`)
— rather than hand-rolling a divergent join. BC-1.01.004 EC-001/EC-002 idempotent-absolute-passthrough
guarantee must be preserved: absolute paths pass through to `get_or_compile` unchanged.

**Key lesson from S-18.00/S-18.02 (WASM gate stories):** Changes to `main.rs` startup
sequence must preserve the existing event emission order. The `dispatcher.started` event
(line ~232–245 in `main.rs`) must still be emitted BEFORE `match_plugins` is called. Adding
the `log_dir` field is an additive `.with_field(…)` call on the existing `InternalEvent`
chain — no reordering required.

## Architecture Compliance Rules

Extracted from `architecture/module-decomposition.md` and ADR-024:

1. **Factory-agnostic dispatcher (BC-1.13.001 INV-1):** `crates/factory-dispatcher/` MUST
   NOT gain a compile-time dependency on any per-factory resolver crate. All resolver
   logic lives in WASM plugins loaded at runtime.

2. **CWD is the host project directory, NOT the plugin root (ADR-024 §Decision 1 Addendum):**
   `CLAUDE_PROJECT_DIR` (CWD) and `CLAUDE_PLUGIN_ROOT` are distinct paths. Code in
   `resolver_loader.rs` MUST resolve relative `entry.plugin` paths using the normative
   `if let Some(base) = path.parent()` pattern (alias `let toml_parent = path.parent();`) —
   mirroring `registry.rs::resolve_plugin_paths` which computes `let base = path.parent()`
   — NOT using `std::env::current_dir()`. The `is_relative()` guard inside the `if let Some`
   arm is prescribed for precedent-consistency with `registry.rs::resolve_plugin_paths` and
   implementation intent-clarity, NOT for Windows-portability per se (a bare unconditional
   `base.join()` behaves identically on all platforms because `PathBuf::join` replaces the
   base with any absolute component). The `None` arm (when `path.parent()` returns `None`,
   i.e. the TOML path is a bare component) passes `entry.plugin` through unchanged.
   Correct Rust semantics: `Path::is_relative()` ≡ `!Path::is_absolute()`.
   On Windows, a rooted-but-not-absolute path (`\foo`) has `is_absolute()`=false and therefore
   `is_relative()`=TRUE — the guard IS taken and `base.join("\foo")` produces `\foo` via
   join-replacement (same result as a bare join; harmless). A genuinely absolute path
   (`/x`, `C:\x`) has `is_relative()`=false — the guard is NOT taken and the path passes
   through unchanged. Windows is a supported release target; these semantics are correct
   for all Windows path forms.

3. **No `println!` in production Rust code (CLAUDE.md):** Use `eprintln!` (already the pattern
   in `resolver_loader.rs`) or `tracing::*!`. The `log_dir` field is added to the `InternalLog`
   event chain — no new `println!` calls.

4. **Single-call-site fix discipline (TD-VSDD-060):** There is a SINGLE `get_or_compile` call
   site in `load_registry` (functional anchor: `resolver_loader::load_registry`). The path-join
   (`if let Some(base) = path.parent() { if entry.plugin.is_relative() { entry.plugin = base.join(&entry.plugin); } }`)
   must precede that single call so the resolved absolute path feeds both the
   `fail_closed: true` and `fail_closed: false` error-handling arms identically; the
   fail_closed divergence is in the post-call error `match`, not at separate call sites.
   TD-VSDD-060 sibling-sweep confirms no second production call site (the second
   `get_or_compile` occurrence inside the `#[cfg(test)]` module is test-only and is not a
   production fix site). AC-004 / RG-003 remain valid: their point is that the single
   resolved path feeds both arms' success paths identically, NOT that there are two join sites.

5. **`dispatcher.started` event emission order and absolutization (BC-1.12.001 / S-18.00 lesson):** The
   `dispatcher.started` JSONL event must be emitted before `match_plugins`. Adding
   `log_dir` is an additive `.with_field("log_dir", ...)` change to the `InternalEvent::now(DISPATCHER_STARTED)`
   builder chain — preserve all existing fields; do not reorder. The `log_dir` value MUST be
   computed via `std::path::absolute(internal_log.log_dir()).unwrap_or_else(|_| internal_log.log_dir().to_path_buf()).display().to_string()`
   at the emission site (produces an owned `String` — the `.display().to_string()` form is the
   correct sibling of `registry_path.display().to_string()` already used at the same site;
   `.to_string_lossy().as_ref()` is FORBIDDEN — it borrows from a dropped temporary and does not
   compile). The `InternalLog::log_dir()` accessor stays verbatim (NOT stored absolutized inside
   the struct).
