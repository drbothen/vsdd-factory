# S-19.02 — verify-factory-lock FINDING-1: frontmatter-only STATE.md read + raised byte budget

**Epic:** E-19 — Post-rc.22 Operator Hardening
**Wave:** 1 (P0 defect; begin immediately; no E-19 predecessor)
**Depends on:** none
**Priority:** P0 (functional defect — lock gate silently degraded in every operator install where STATE.md exceeds 64 KiB; this is production state for the vsdd-factory repo at rc.22)
**Subsystem anchor:** SS-04 (Plugin Ecosystem) owns the `verify-factory-lock` WASM hook plugin crate.

## Narrative

The `verify-factory-lock` PreToolUse WASM guard (S-17.02; BC-4.13.001) is the single-writer enforcement mechanism for the factory-artifacts orphan branch. It reads `.factory/STATE.md` via `host::read_file` with a 64 KiB cap (`STATE_MD_MAX_BYTES = 65536`), then parses the `factory_lock:` YAML frontmatter block.

**The defect:** In the vsdd-factory repo at rc.22, STATE.md is approximately 90 KB — larger than the 64 KiB cap. `read_file.rs::read_bounded()` returns `ReadErr::TooLarge` when the file's on-disk size exceeds `max_bytes`, emitting `internal.capability_denied reason=output_too_large` and returning `OUTPUT_TOO_LARGE (-3)` to the plugin. The plugin maps any non-zero `read_file` return as `StateReadError` and emits a WARN log, then falls back to Continue (fail-open per ADR-025 Decision 7). The lock gate is therefore **silently bypassed on every PreToolUse Edit/Write/MultiEdit/Agent dispatch** in any install where STATE.md has grown beyond 64 KiB.

Evidence from `.factory/logs/dispatcher-internal-2026-07-04.jsonl`: traces `a4b26f12`, `bcc3e6ef`, `cf4c2e4d`, `2551d7db` each show `internal.capability_denied reason=output_too_large` on `plugin_name=verify-factory-lock`, confirming STATE.md is consistently exceeding the cap in the production rc.22 install.

**Fix direction:**

**BC-4.13.001 v1.15 Phase-A amendment LANDED (product-owner, E-19 pass-1 fix burst). Spec-first, code follows.** The amendment raises Precondition 3 `max_bytes` from 65536 to 262144 (256 KiB) and extends Invariant 9 with the frontmatter-only-parsing mandate. This story implements the Phase-A code changes to bring the plugin into conformance with BC-4.13.001 v1.15 Phase-A and ADR-025 Decision 14.

**Phase-A scope:** This story covers Phase-A of BC-4.13.001 v1.15 (raise `STATE_MD_MAX_BYTES` to 262144; frontmatter-only parsing). Phase-B (S-19.07) migrates `verify-factory-lock` from `host::read_file` to `host::read_prefix`; Phase-A is complete when this story merges, and remains independently unregressed until Phase-B (S-19.07) merges.

**AC-001 (cap raise) alone closes FINDING-1:** `read_bounded()` checks `metadata.len()` BEFORE reading any bytes — if the cap is below the file's on-disk size, the read fails immediately and returns `OUTPUT_TOO_LARGE`, before the frontmatter parser is ever invoked. A frontmatter-only parser cannot compensate for an under-sized cap, because the read never returns bytes. The fix is to raise `STATE_MD_MAX_BYTES` to 262144 so the cap is above any realistic STATE.md size (worst-case observed <200 KB under the 500-line compaction discipline per ADR-026; the 262144-byte cap gives ≥25% headroom over the observed range). The BC carries the dated checkpoint for audit purposes; this story carries the range argument. Cite: ADR-025 Decision 14.

**AC-003 (frontmatter-only extraction) is contract-mandated parser hygiene:** BC-4.13.001 v1.15 Phase-A Invariant 9 mandates that the guard MUST abort scanning after the second `---\n` delimiter and MUST NOT parse file body content. The lock verdict is derived exclusively from the frontmatter region. AC-003 implements this invariant — not as a workaround for the byte-cap defect, but as the required parsing discipline. The `max_bytes = 262144` cap (Precondition 3) ensures the host read succeeds; Invariant 9 ensures the parser ignores the body.
