# S-7.07 — Misdirected-Report Resumption Hazard — burst-agent stand-down protocol on unexpected inbound

**Epic:** E-7 — Process Codification (Self-Improvement)
**Source:** D-868 SHADOW-CHAIN-EVENT, D-869 item (6)(c)
**Depends on:** S-7.06 (which codifies the spawning gate and retirement signal; this story adds the complementary defensive rule inside the burst agents themselves)
**Priority:** P1 (closes the receiver-side protocol gap that S-7.06's sender-side retirement alone cannot fully close)
**Subsystem anchor:** SS-05 (Pipeline Orchestration) + SS-06 (Skill Catalog — agent prompts)

## Narrative

- **As a** vsdd-factory burst-class agent (adversary, architect, state-manager) that has completed its assigned task and delivered its report
- **I want** a mandatory stand-down protocol: when any message arrives after my report is delivered, I acknowledge the message and take no further action — regardless of message origin or content
- **So that** a misdirected inter-agent report or any other unexpected message cannot reactivate me into performing unauthorized work

The ADR-032 cascade shadow-chain (D-868) was triggered because an inter-agent report was
mistakenly routed to a stale fix-burst-1 agent instead of the orchestrator. The receiving
agent, having no stand-down instruction, treated the incoming message as a new task and resumed
execution. The spawning gate (S-7.06) prevents the downstream spawning, but it does not prevent
the receiving agent from taking other unauthorized actions (reading files, drafting content,
writing to orchestrator under a false context).

This story adds the receiver-side defense: every burst-class agent prompt now contains an
explicit protocol rule for handling unexpected post-delivery inbound messages. The rule is
independent of S-7.06 — together they form a defense-in-depth pair.

Additionally, the report-routing rule is codified: burst agents report ONLY to the orchestrator.
Any message delivered to a burst agent that did not originate from the orchestrator's dispatching
session MUST be treated as an unexpected inbound and trigger the stand-down protocol.

## Edge Cases

| ID | Scenario | Expected Behavior |
|----|----------|-------------------|
| EC-001 | The orchestrator legitimately retries a dispatch to the same agent session after a transient error (not a post-retirement scenario) | Stand-down rule applies only after report delivery; a dispatch sent BEFORE report delivery is a legitimate new task — the rule must clarify the post-delivery precondition |
| EC-002 | An agent is dispatched for a second task in the same session explicitly (e.g., multi-pass review where the orchestrator dispatches pass-N+1 to the same agent) | Legitimate if orchestrator sends a new dispatch payload before the agent sends its final report; the stand-down rule triggers only AFTER the report is delivered |
| EC-003 | The POST-RETIREMENT-STAND-DOWN keyword appears in the orchestrator session transcript as part of an expected stand-down acknowledgment | Orchestrator reads the acknowledgment and confirms retirement; the cascade log records the retirement event |
