# S-21.25: Fuel-headroom WARN event (ADR-039 §Decision 5 Mitigation 1 — >90% fuel-consumption early-warning signal)

## Narrative

- **As a** factory pipeline operator running `.factory/` writes and other WASM-validated hook
  plugins under a finite `fuel_cap`
- **I want** the dispatcher to emit a WARN-level structured event whenever a plugin's invocation
  completes successfully (`PluginResult::Ok`) having consumed more than 90% of its configured
  `fuel_cap`
- **So that** I get advance, actionable notice — "this plugin is close to trapping; recalibrate
  `fuel_cap`" — before an actual `Timeout { cause: Fuel }` exhaustion hits me on a larger future
  input, without waiting for the ADR-039 Phase 4 fail-closed enforcement flip (S-21.19–S-21.24)
  to land first

## Acceptance Criteria

### AC-001: Threshold predicate fires WARN on `Ok`, integer-exact comparison, no panic at degenerate `fuel_cap=0` (traces to BC-1.03.019 PC1, Invariant 3, EC-002)

When `invoke_plugin` returns `PluginResult::Ok { fuel_consumed, .. }` and the extracted pure
predicate `fuel_headroom_exceeded(fuel_consumed, fuel_cap)` —
`fuel_consumed.saturating_mul(FUEL_HEADROOM_WARNING_DEN) > fuel_cap.saturating_mul(FUEL_HEADROOM_WARNING_NUM)`
(the integer-exact equivalent of `fuel_consumed > 0.9 × fuel_cap`, using named constants
`FUEL_HEADROOM_WARNING_NUM = 9` / `FUEL_HEADROOM_WARNING_DEN = 10` per Invariant 3) — returns
`true`, the dispatcher MUST emit exactly one WARN-level structured event before `invoke_plugin`
returns. The predicate MUST NOT panic at the degenerate `fuel_cap = 0` input (theoretically
unreachable via `Ok` per EC-002, but the arithmetic MUST be defensively safe regardless).

- **Test:** `test_fuel_headroom_warn_fires_above_90_percent()` — call
  `check_and_emit_fuel_headroom_warning(&host, "test-plugin", &Ok(PluginResult::Ok { exit_code: 0,
  stdout: String::new(), stderr: String::new(), elapsed_ms: 0, fuel_consumed: 18_500_000 }),
  20_000_000)` (92.5%) directly — no real WASM invocation required; assert exactly one
  `plugin.fuel_headroom_warning` event present in `ctx.drain_events()`
- **Test:** `test_fuel_headroom_warn_predicate_no_panic_at_zero_fuel_cap()` — call
  `fuel_headroom_exceeded(1, 0)` directly (the pure fn, no `HostContext`/event plumbing needed);
  assert it returns `true` (conservative) without panicking (defensive `saturating_mul` guard,
  EC-002)

### AC-002: Exact-90% boundary does NOT fire (traces to BC-1.03.019 PC2, EC-001)

When `fuel_consumed == fuel_cap × 0.9` exactly (e.g., `fuel_consumed = 18_000_000`,
`fuel_cap = 20_000_000`), `fuel_headroom_exceeded` MUST evaluate false and no event MUST be
emitted. This is a dedicated negative-control test, not incidental float-rounding behavior —
ADR-039 §Decision 5's own wording (`fuel_consumed > 0.9 × cap`) is strict-greater-than.

- **Test:** `test_fuel_headroom_warn_exact_90_percent_does_not_fire()` — call
  `check_and_emit_fuel_headroom_warning(&host, "test-plugin", &Ok(PluginResult::Ok { exit_code: 0,
  stdout: String::new(), stderr: String::new(), elapsed_ms: 0, fuel_consumed: 18_000_000 }),
  20_000_000)` directly; assert zero `plugin.fuel_headroom_warning` events emitted. A second,
  purely-pure assertion `assert!(!fuel_headroom_exceeded(18_000_000, 20_000_000))` covers the
  predicate in isolation.

### AC-003: Below-threshold negative control (traces to BC-1.03.019 PC3)

When `fuel_consumed <= 0.9 × fuel_cap` by any margin (e.g., 50%), no event MUST be emitted.

- **Test:** `test_fuel_headroom_warn_below_threshold_does_not_fire()` — call
  `check_and_emit_fuel_headroom_warning(&host, "test-plugin", &Ok(PluginResult::Ok { exit_code: 0,
  stdout: String::new(), stderr: String::new(), elapsed_ms: 0, fuel_consumed: 10_000_000 }),
  20_000_000)` directly; assert zero `plugin.fuel_headroom_warning` events emitted

### AC-004: Non-`Ok` outcomes never fire this event, including genuine 100%-fuel `Timeout` (traces to BC-1.03.019 PC4, EC-006)

`PluginResult::Timeout { .. }` (either `TimeoutCause::Fuel` or `TimeoutCause::Epoch`) and
`PluginResult::Crashed { .. }` MUST NEVER trigger this event, regardless of the `fuel_consumed`
value those variants carry — including the genuine exhaustion case where
`fuel_consumed == fuel_cap` (100%, trivially `> 0.9 × cap`), which is the actual near-miss's
"came true" outcome and is governed exclusively by sibling BC-1.03.002/BC-1.03.017, not this BC.
`check_and_emit_fuel_headroom_warning` takes `result: &Result<PluginResult, InvokeError>` (the
same shape `invoke_plugin`'s own tail binding produces) precisely so this AC is directly testable
with a hand-constructed synthetic `PluginResult` — it does not require driving a real WASM
invocation to a `Timeout`/`Crashed` outcome.

- **Test:** `test_fuel_headroom_warn_timeout_fuel_100_percent_does_not_fire()` — call
  `check_and_emit_fuel_headroom_warning(&host, "test-plugin", &Ok(PluginResult::Timeout { cause:
  TimeoutCause::Fuel, stderr: String::new(), elapsed_ms: 0, fuel_consumed: 100, fuel_cap: 100 }),
  100)` directly; assert zero `plugin.fuel_headroom_warning` events emitted (the check point's
  `if let Ok(PluginResult::Ok { .. }) = result` gate excludes every other variant structurally,
  not merely by a fuel-ratio computed from any variant)
- **Test:** `test_fuel_headroom_warn_crashed_does_not_fire()` — call
  `check_and_emit_fuel_headroom_warning(&host, "test-plugin", &Ok(PluginResult::Crashed {
  trap_string: "unreachable".into(), stderr: String::new(), elapsed_ms: 0, fuel_consumed: 100 }),
  100)` directly (a non-fuel, non-epoch trap); assert zero `plugin.fuel_headroom_warning` events
  emitted

### AC-005: Uniform coverage of both `Ok` sub-shapes via a single centralized check point (traces to BC-1.03.019 PC5, EC-005)

The check MUST fire identically for `PluginResult::Ok { exit_code: 0, .. }` (the WASI
clean-exit path) and `PluginResult::Ok { exit_code != 0, .. }` (the `I32Exit` non-zero-exit path
inside `classify_trap`). The check MUST be performed exactly once, at a single centralized point
in `invoke_plugin` after its internal `match call_result { .. }` has produced the final
`PluginResult` — **not** duplicated inline inside each of the two `Ok`-constructing branches. This
is delivered as a single extracted shell, `check_and_emit_fuel_headroom_warning`, called from
exactly one call site in `invoke_plugin`, immediately preceded by a `// SINGLE-EMIT-SITE` marker
comment (see Task 6/7).

**AC-005's regression guard is redesigned a second time in this story's v1.2** (F-S2125-P2-001,
HIGH; supersedes the v1.1 redesign). The v1.1 fix (F-S2125-P1-001) replaced the impossible
`"emit_fuel_headroom_warning("` literal-count scan with a `// SINGLE-EMIT-SITE` marker-count scan
— but left the scanning test itself *inside* `invoke.rs`'s own `#[cfg(test)] mod tests`, using
`include_str!` on `invoke.rs` from within `invoke.rs`. Because the test's own source line contains
the needle string literal `"// SINGLE-EMIT-SITE"` (it has to, to name what it's counting),
`include_str!`ing the file that contains that literal counts BOTH the production marker comment
AND the test's own needle string — 2, never 1. Worse, it is RED/GREEN-inverted: at RED time (before
Task 9 adds the production marker) the count is 1 (the needle alone) so the `== 1` assertion
*passes* when it should fail; at GREEN time (after Task 9) the count is 2 (marker + needle) so the
assertion *fails* when it should pass. The guard could never be made to exhibit correct RED-before/
GREEN-after semantics while it lived in the file it was scanning.

**v1.2 fix:** the source-scan test is relocated OUT of `invoke.rs` entirely, into a new, separate
Rust integration-test file: `crates/factory-dispatcher/tests/fuel_headroom_single_emit_site.rs`
(sibling to this crate's existing `tests/bundle_orphan_check.rs`, which already establishes the
`include_str!`-a-source-file-from-`tests/`-for-a-structural-regression-guard pattern used here).
This file `include_str!("../src/invoke.rs")`s the production source from outside it, so the only
occurrence of the literal marker string counted is the one production comment — the scanning file
itself never contains that literal substring as written. To close the self-match risk completely
(so that if this test file's contents are ever copy-pasted alongside `invoke.rs`, or `invoke.rs`
is ever merged into a single-file crate, the guard remains correct), the needle is constructed at
compile time rather than written as a literal: `concat!("// SINGLE", "-EMIT-SITE")` — the two
half-tokens `"// SINGLE"` and `"-EMIT-SITE"` never appear concatenated in the test file's own
source text, only the assembled `&str` value does, at runtime, after `concat!` has run. RED/GREEN
semantics are now correctly tied to the production marker's existence: **RED** (before Task 9
adds the marked call site to `invoke_plugin`) — `invoke.rs` contains zero occurrences of the
marker, `count == 0 != 1`, test fails; **GREEN** (after Task 9) — `invoke.rs` contains exactly one
occurrence (the production call site), `count == 1 == 1`, test passes. The new file is a plain
`#[test] fn` (no `#[cfg(test)] mod tests`, no shared fixtures) and needs no `HostContext`/host
plumbing — it is a pure string scan over `include_str!`'s output. A future edit that duplicates
the checked call site by copy-pasting the marked line (the realistic accidental-duplication
failure mode this guard exists to catch — e.g., pasting the same `// SINGLE-EMIT-SITE` + call pair
into `classify_trap` or the `Ok(())` arm) reproduces the marker a second time in `invoke.rs` and
correctly fails the count (`2 != 1`); an edit that adds an *unmarked* second call site is outside
this mechanical guard's coverage and remains a code-review discipline concern (Architecture
Compliance Rules).

- **Test:** `test_fuel_headroom_warn_ok_exit_code_zero_fires()` — call
  `check_and_emit_fuel_headroom_warning(&host, "test-plugin", &Ok(PluginResult::Ok { exit_code: 0,
  stdout: String::new(), stderr: String::new(), elapsed_ms: 0, fuel_consumed: 19_000_000 }),
  20_000_000)` directly (WASI clean-exit shape, 95%); assert event fires with `exit_code` context
  unaffected. Lives in `invoke.rs`'s own `#[cfg(test)] mod tests`.
- **Test:** `test_fuel_headroom_warn_ok_exit_code_nonzero_fires()` — call the same function with
  `PluginResult::Ok { exit_code: 1, .. }` (the `I32Exit` non-zero-exit shape) at the same 95%
  reading; assert event fires identically to the `exit_code:0` case. Lives in `invoke.rs`'s own
  `#[cfg(test)] mod tests`.
- **Test:** `test_single_emit_site_marker_appears_exactly_once()` — **relocated, separate-file
  source-scan regression test** in the new integration-test file
  `crates/factory-dispatcher/tests/fuel_headroom_single_emit_site.rs` (NOT inside `invoke.rs`'s
  own test module — see redesign rationale above): `include_str!("../src/invoke.rs")` the built
  `invoke.rs` source file from that separate file, construct the needle via
  `concat!("// SINGLE", "-EMIT-SITE")` (so the literal marker substring never appears written out
  in this test file's own source), count occurrences of the constructed needle in the included
  source, assert the count is exactly 1. RED before Task 9 (count 0), GREEN after Task 9 (count
  1). Structural regression guard against a future edit accidentally duplicating the checked call
  site into `classify_trap` or the `Ok(())` arm.

### AC-007: `headroom_ratio` formula — remaining-budget fraction, clamped (traces to BC-1.03.019 PC7)

The extracted pure fn `fuel_headroom_ratio(fuel_consumed: u64, fuel_cap: u64) -> f64` computes
`1.0 - (fuel_consumed as f64 / fuel_cap as f64)`, clamped to `[0.0, 1.0]` via `.clamp(0.0, 1.0)`.
This is the fraction of budget STILL UNCONSUMED, not the fraction consumed — a deliberate choice
(BC-1.03.019 PC7 rationale: "headroom" conventionally denotes remaining margin; the consumed
fraction is already fully recoverable from the co-emitted `fuel_consumed`/`fuel_cap` fields, so a
consumed-fraction `headroom_ratio` would be redundant). Being a pure, directly-callable fn, both
tests below call `fuel_headroom_ratio` straight, no `HostContext`/event plumbing required.

- **Test:** `test_fuel_headroom_ratio_formula_worked_example()` — call
  `fuel_headroom_ratio(18_500_000, 20_000_000)`; assert the result `== 0.075` (within float
  epsilon)
- **Test:** `test_fuel_headroom_ratio_clamped_non_negative_near_full_consumption()` — call
  `fuel_headroom_ratio(fuel_cap - 1, fuel_cap)` (a near-100% but still-`Ok` reading); assert
  `0.0 <= result < 1.0` and the clamp does not produce a negative value

### AC-008: WARN-level classification and exact, non-interpolated message text (traces to BC-1.03.019 PC8, v1.3)

ADR-039 §Decision 5's WARN message was corrected from an earlier `≥90%` draft wording to strict
`>90%` to match the strict-greater-than trigger predicate this BC's PC1/PC2 (and this story's
AC-001/AC-002) already specify (ADR-039 v1.15, 2026-08-20). The v1.0 draft of this AC reproduced
the stale `≥90%` wording; it is corrected below to match ADR-039 v1.15 / BC-1.03.019 v1.3 PC8
byte-for-byte (PC8's content is unchanged since v1.1 — v1.2 only renamed the emitter cited in
§Architecture Anchors, F-S2125-P2-002).

The event's `level` field MUST be the literal string `"warn"` (carried as an explicit `fields`

`"fuel-headroom-warning: plugin consumed >90% of budget; next larger input may trap — recalibrate fuel_cap"`.

structured field (AC-006).

- **Test:** `test_fuel_headroom_warn_level_field_is_warn()` — assert

### AC-009: Independence from `on_error`/`failure_policy`/block-decision (traces to BC-1.03.019 PC9)

Emitting this event MUST NOT read any `on_error`/`failure_policy`-shaped input (the
`emit_plugin_fuel_headroom_warning`/`check_and_emit_fuel_headroom_warning`/`fuel_headroom_exceeded`/
`fuel_headroom_ratio` signatures MUST NOT accept such a parameter at all — `invoke_plugin` itself
has no `RegistryEntry` parameter today; this story MUST NOT add one) and
MUST NOT produce or influence any block-decision value. The event fires identically regardless of
what enforcement configuration a caller conceptually associates with the plugin.

- **Test:** `test_fuel_headroom_warn_fires_identically_regardless_of_simulated_downstream_policy()`
  — call `emit_plugin_fuel_headroom_warning` twice with identical `fuel_consumed`/`fuel_cap` while two
  distinct, purely-local `on_error`/`failure_policy`-shaped test fixtures (constructed but never
  passed as arguments) are held in scope; assert both emitted events are field-identical except
  `plugin_name`/`trace_id`/`ts` — the test's own construction demonstrates by inspection that the
  emission path has no parameter through which such config could flow
- **Test:** `test_fuel_headroom_warn_emission_has_no_side_effect_beyond_event_queue()` — snapshot
  the `HostContext`'s non-event-queue fields before and after calling
  `emit_plugin_fuel_headroom_warning`; assert they are unchanged (the only observable mutation is the
  `drain_events()` length delta of exactly 1) — proving the call cannot possibly influence any
  block-decision state, since it mutates nothing a decision function could read

### AC-010: Exactly-once-per-invocation; independent across repeated invocations (traces to BC-1.03.019 PC10, EC-004, EC-007)

The check runs exactly once per `invoke_plugin` call, evaluated against the single terminal
`fuel_consumed` reading captured after the guest's `_start` export returns or traps. There is no
intra-invocation threshold-crossing-then-recovery to dedup (fuel consumption is monotonic
non-decreasing within a single invocation — Invariant 1). Repeated invocations of the same plugin
each independently evaluate and may each emit their own event; there is no cross-invocation
suppression or rate-limiting (ADR-039 §Decision 5 specifies none).

- **Test:** `test_fuel_headroom_warn_exactly_once_per_invocation()` — call

- **Test:** `test_fuel_headroom_warn_repeated_invocations_each_emit_independently()` — call

  name, each crossing 90% (simulating three dispatcher invocations of the same plugin); assert
  three independent `plugin.fuel_headroom_warning` events are present, none suppressed

## Architecture Mapping

**Extracted named pure helpers (F-S2125-P1-002 fix):** the v1.0 draft specified the predicate,
`headroom_ratio` formula, and check inline inside `invoke_plugin` — a function only reachable via
a real WASM invocation, making it impossible to force `fuel_consumed`/`fuel_cap` to the exact
synthetic values several ACs assert (AC-001 test 2's `fuel_consumed=1, fuel_cap=0`; AC-004's
synthetic `PluginResult::Timeout{fuel_consumed:100, fuel_cap:100}`; AC-007's exact
`18_500_000/20_000_000 → 0.075`). This story now specifies three extracted, directly-callable
functions instead, with `invoke_plugin` reduced to a single call site into the third:

|-----------|--------|---------------|

| Module | Classification | Justification |
|--------|---------------|----------------|
| `fuel_headroom_exceeded` + `fuel_headroom_ratio` | Pure-core | Deterministic `u64`/`f64` arithmetic; no I/O, no shared mutable state read; directly callable with synthetic vectors from any test |
