# S-21.25: Fuel-headroom WARN event (ADR-039 §Decision 5 Mitigation 1 — >90% fuel-consumption early-warning signal)

## Narrative

- **As a** factory pipeline operator running `.factory/` writes and other WASM-validated hook
  plugins under a finite `fuel_cap`
- **I want** the dispatcher to emit a WARN-level structured event whenever a plugin's invocation
  completes successfully (`PluginResult::Ok`) having consumed more than 90% of its configured
  `fuel_cap`
- **So that** I get advance, actionable notice — "this plugin is close to trapping; recalibrate
  `fuel_cap`" — before an actual `Timeout { cause: Fuel }` exhaustion hits me on a larger future
  input, without waiting for the ADR-039 Phase 4 fail-closed enforcement flip (S-21.19–S-21.24)
  to land first

## Context / Finding Summary

ADR-039 §Decision 5 ("Near-term mitigations: fuel-headroom warning and production-scale
fixture") specifies two mitigations, both scoped independently of the `failure_policy`
fail-closed enforcement machinery §Decisions 1–4 govern. **Mitigation 2** (the ≥574 KB
production-scale fixture) shipped in S-21.07 (commit `e94767bc`). **Mitigation 1** (this story)
remained pending at S-21.07's merge and, until now, had zero owning story and zero landed code —
a repo-wide grep for `headroom`/`fuel_headroom` inside `crates/` found no prior occurrence
(confirmed in BC-1.03.019's changelog); the only prior artifact was an abandoned branch
(`fix/fuel-exhaustion-fail-loud`) that never merged.

This story delivers Mitigation 1 only, governed by the newly-authored `BC-1.03.019` (v1.0,
product-owner, 2026-08-20; 10 postconditions, 4 invariants, 7 edge cases). Per the
`S-21.11-decomposition-plan.md` §S-21.25 operator directive, this story is **fully independent**
of the six `S-21.19`–`S-21.24` `failure_policy` split seams: it does not touch `failure_policy`,
`on_error`, `execute_tiers`'s block-decision loop, or `legacy-bash-adapter` at all. It requires
only the pre-existing `fuel_cap` registry field (which predates the `failure_policy` axis
entirely, per ADR-042) and the already-correct fuel-exhaustion detection path
(`Trap::OutOfFuel` → `fuel_consumed_from_store`, both already live in
`crates/factory-dispatcher/src/invoke.rs`). It can be implemented, tested, and merged in any
order relative to S-21.19–S-21.24 (Wave 6, parallel track, zero DAG edges to any of them).

**Residual risk this story does NOT close** (BC-1.03.019 Traceability §Security, verbatim from
ADR-039 §Decision 5): "the warning is logged but the write is approved... the structural defect
(CWE-636) persists until the Phase 4 enforcement flip" — that flip is S-21.19/S-21.24's scope,
not this story's. This story is Phase-2 **observability only**.

## Acceptance Criteria

### AC-001: Threshold predicate fires WARN on `Ok`, integer-exact comparison, no panic at degenerate `fuel_cap=0` (traces to BC-1.03.019 PC1, Invariant 3, EC-002)

When `invoke_plugin` returns `PluginResult::Ok { fuel_consumed, .. }` and
`fuel_consumed.saturating_mul(FUEL_HEADROOM_WARNING_DEN) > fuel_cap.saturating_mul(FUEL_HEADROOM_WARNING_NUM)`
(the integer-exact equivalent of `fuel_consumed > 0.9 × fuel_cap`, using named constants
`FUEL_HEADROOM_WARNING_NUM = 9` / `FUEL_HEADROOM_WARNING_DEN = 10` per Invariant 3), the
dispatcher MUST emit exactly one WARN-level structured event before `invoke_plugin` returns. The
predicate MUST NOT panic at the degenerate `fuel_cap = 0` input (theoretically unreachable via
`Ok` per EC-002, but the arithmetic MUST be defensively safe regardless).

- **Test:** `test_fuel_headroom_warn_fires_above_90_percent()` — `fuel_consumed=18_500_000`,
  `fuel_cap=20_000_000` (92.5%); assert exactly one `plugin.fuel_headroom_warning` event present
  in `ctx.drain_events()` after the check runs
- **Test:** `test_fuel_headroom_warn_predicate_no_panic_at_zero_fuel_cap()` — call the predicate
  directly with `fuel_consumed=1`, `fuel_cap=0`; assert it returns `true` (conservative) without
  panicking (defensive `saturating_mul` guard, EC-002)

### AC-002: Exact-90% boundary does NOT fire (traces to BC-1.03.019 PC2, EC-001)

When `fuel_consumed == fuel_cap × 0.9` exactly (e.g., `fuel_consumed = 18_000_000`,
`fuel_cap = 20_000_000`), the predicate MUST evaluate false and no event MUST be emitted. This is
a dedicated negative-control test, not incidental float-rounding behavior — ADR-039 §Decision 5's
own wording (`fuel_consumed > 0.9 × cap`) is strict-greater-than.

- **Test:** `test_fuel_headroom_warn_exact_90_percent_does_not_fire()` — `fuel_consumed=18_000_000`,
  `fuel_cap=20_000_000`; assert zero `plugin.fuel_headroom_warning` events emitted

### AC-003: Below-threshold negative control (traces to BC-1.03.019 PC3)

When `fuel_consumed <= 0.9 × fuel_cap` by any margin (e.g., 50%), no event MUST be emitted.

- **Test:** `test_fuel_headroom_warn_below_threshold_does_not_fire()` — `fuel_consumed=10_000_000`,
  `fuel_cap=20_000_000`; assert zero `plugin.fuel_headroom_warning` events emitted

### AC-004: Non-`Ok` outcomes never fire this event, including genuine 100%-fuel `Timeout` (traces to BC-1.03.019 PC4, EC-006)

`PluginResult::Timeout { .. }` (either `TimeoutCause::Fuel` or `TimeoutCause::Epoch`) and
`PluginResult::Crashed { .. }` MUST NEVER trigger this event, regardless of the `fuel_consumed`
value those variants carry — including the genuine exhaustion case where
`fuel_consumed == fuel_cap` (100%, trivially `> 0.9 × cap`), which is the actual near-miss's
"came true" outcome and is governed exclusively by sibling BC-1.03.002/BC-1.03.017, not this BC.

- **Test:** `test_fuel_headroom_warn_timeout_fuel_100_percent_does_not_fire()` —
  `PluginResult::Timeout { cause: TimeoutCause::Fuel, fuel_consumed: 100, fuel_cap: 100, .. }`;
  assert zero `plugin.fuel_headroom_warning` events emitted (the check point is gated on the
  `PluginResult::Ok` variant, not merely on a fuel-ratio computed from any variant)
- **Test:** `test_fuel_headroom_warn_crashed_does_not_fire()` — `PluginResult::Crashed { .. }`
  from a non-fuel, non-epoch trap; assert zero `plugin.fuel_headroom_warning` events emitted

### AC-005: Uniform coverage of both `Ok` sub-shapes via a single centralized check point (traces to BC-1.03.019 PC5, EC-005)

The check MUST fire identically for `PluginResult::Ok { exit_code: 0, .. }` (the WASI
clean-exit path) and `PluginResult::Ok { exit_code != 0, .. }` (the `I32Exit` non-zero-exit path
inside `classify_trap`). The check MUST be performed exactly once, at a single centralized point
in `invoke_plugin` after its internal `match call_result { .. }` has produced the final
`PluginResult` — **not** duplicated inline inside each of the two `Ok`-constructing branches.

- **Test:** `test_fuel_headroom_warn_ok_exit_code_zero_fires()` — WASI clean-exit fixture crossing
  90%; assert event fires with `exit_code` context unaffected
- **Test:** `test_fuel_headroom_warn_ok_exit_code_nonzero_fires()` — `I32Exit` non-zero-exit
  fixture crossing 90% (e.g., 95%); assert event fires identically to the `exit_code:0` case
- **Test:** `test_fuel_headroom_warn_single_call_site_in_invoke_rs()` — source-scan regression
  test: `include_str!` the built `invoke.rs` source file, count occurrences of the literal
  substring `"emit_fuel_headroom_warning("`; assert the count is exactly 1 (the single
  centralized call site — the function's own `fn emit_fuel_headroom_warning` definition lives in
  `emit_event.rs`, not `invoke.rs`, so this substring appears in `invoke.rs` only at the call
  site). This is a structural regression guard against a future edit accidentally duplicating the
  check into `classify_trap` or the `Ok(())` arm.

### AC-006: Required event fields (traces to BC-1.03.019 PC6)

The emitted event MUST carry exactly: `plugin_name: String`, `fuel_consumed: u64`,
`fuel_cap: u64`, `headroom_ratio: f64` (clamped `[0.0, 1.0]`), plus the standard `InternalEvent`
envelope fields (`type`, `trace_id`, `session_id`, `ts`, `schema_version`) and a `level` field
(assessed separately by AC-008).

- **Test:** `test_fuel_headroom_warn_event_carries_required_fields()` — trigger a WARN; assert
  the drained event has `type == "plugin.fuel_headroom_warning"` and non-empty/correctly-typed
  `plugin_name`, `fuel_consumed`, `fuel_cap`, `headroom_ratio`, `trace_id`, `session_id`, `ts`
  fields (mirrors the field-presence assertion pattern already used for `plugin.timeout` in
  `emit_event.rs`'s existing test suite)

### AC-007: `headroom_ratio` formula — remaining-budget fraction, clamped (traces to BC-1.03.019 PC7)

`headroom_ratio = 1.0 - (fuel_consumed as f64 / fuel_cap as f64)`, clamped to `[0.0, 1.0]` via
`.clamp(0.0, 1.0)`. This is the fraction of budget STILL UNCONSUMED, not the fraction consumed —
a deliberate choice (BC-1.03.019 PC7 rationale: "headroom" conventionally denotes remaining
margin; the consumed fraction is already fully recoverable from the co-emitted
`fuel_consumed`/`fuel_cap` fields, so a consumed-fraction `headroom_ratio` would be redundant).

- **Test:** `test_fuel_headroom_ratio_formula_worked_example()` — `fuel_consumed=18_500_000`,
  `fuel_cap=20_000_000`; assert `headroom_ratio == 0.075` (within float epsilon)
- **Test:** `test_fuel_headroom_ratio_clamped_non_negative_near_full_consumption()` —
  `fuel_consumed = fuel_cap - 1` (a near-100% but still-`Ok` reading); assert
  `0.0 <= headroom_ratio < 1.0` and the clamp does not produce a negative value

### AC-008: WARN-level classification and exact, non-interpolated message text (traces to BC-1.03.019 PC8)

The event's `level` field MUST be the literal string `"warn"` (carried as an explicit `fields`
entry via `.with_field("level", ...)`, since `InternalEvent` has no dedicated severity field —
the identical idiom `invoke.rs`/`resolver_loader.rs` already use). The event MUST additionally
carry a `message` field equal, verbatim, to:
`"fuel-headroom-warning: plugin consumed ≥90% of budget; next larger input may trap — recalibrate fuel_cap"`.
The `plugin_name` MUST NOT be string-interpolated into this message — it is carried as its own
structured field (AC-006).

- **Test:** `test_fuel_headroom_warn_level_field_is_warn()` — assert
  `event.fields["level"] == Value::String("warn".into())`
- **Test:** `test_fuel_headroom_warn_message_verbatim_text()` — assert
  `event.fields["message"]` equals the exact ADR-039 §Decision 5 string byte-for-byte, for two
  different `plugin_name` values, proving the message text is invariant and never interpolated

### AC-009: Independence from `on_error`/`failure_policy`/block-decision (traces to BC-1.03.019 PC9)

Emitting this event MUST NOT read any `on_error`/`failure_policy`-shaped input (the
`emit_fuel_headroom_warning`/check-point signatures MUST NOT accept such a parameter at all —
`invoke_plugin` itself has no `RegistryEntry` parameter today; this story MUST NOT add one) and
MUST NOT produce or influence any block-decision value. The event fires identically regardless of
what enforcement configuration a caller conceptually associates with the plugin.

- **Test:** `test_fuel_headroom_warn_fires_identically_regardless_of_simulated_downstream_policy()`
  — call `emit_fuel_headroom_warning` twice with identical `fuel_consumed`/`fuel_cap` while two
  distinct, purely-local `on_error`/`failure_policy`-shaped test fixtures (constructed but never
  passed as arguments) are held in scope; assert both emitted events are field-identical except
  `plugin_name`/`trace_id`/`ts` — the test's own construction demonstrates by inspection that the
  emission path has no parameter through which such config could flow
- **Test:** `test_fuel_headroom_warn_emission_has_no_side_effect_beyond_event_queue()` — snapshot
  the `HostContext`'s non-event-queue fields before and after calling
  `emit_fuel_headroom_warning`; assert they are unchanged (the only observable mutation is the
  `drain_events()` length delta of exactly 1) — proving the call cannot possibly influence any
  block-decision state, since it mutates nothing a decision function could read

### AC-010: Exactly-once-per-invocation; independent across repeated invocations (traces to BC-1.03.019 PC10, EC-004, EC-007)

The check runs exactly once per `invoke_plugin` call, evaluated against the single terminal
`fuel_consumed` reading captured after the guest's `_start` export returns or traps. There is no
intra-invocation threshold-crossing-then-recovery to dedup (fuel consumption is monotonic
non-decreasing within a single invocation — Invariant 1). Repeated invocations of the same plugin
each independently evaluate and may each emit their own event; there is no cross-invocation
suppression or rate-limiting (ADR-039 §Decision 5 specifies none).

- **Test:** `test_fuel_headroom_warn_exactly_once_per_invocation()` — one `Ok` outcome crossing
  90%; assert `ctx.drain_events()` contains exactly one `plugin.fuel_headroom_warning` event, not
  zero and not more than one
- **Test:** `test_fuel_headroom_warn_repeated_invocations_each_emit_independently()` — simulate
  three consecutive invocations of the same plugin, each crossing 90%; assert three independent
  `plugin.fuel_headroom_warning` events are present, none suppressed
