# S-19.08 — verify-state-timestamp-refresh: raise 64 KiB byte cap to 256 KiB + wire extract_frontmatter

**Epic:** E-19 — Post-rc.22 Operator Hardening
**Wave:** 2 (parallel-eligible; S-19.02 already MERGED on develop; no hard predecessor)
**Depends on:** none (S-19.02 shipped `extract_frontmatter` in `crates/factory-lock-parse/` via PR #610; reuse not duplicate)
**Priority:** P2 (same defect class as S-19.02 FINDING-1: guard silently inert when STATE.md > 64 KiB; fails open per ADR-025 Decision 7 — no data-loss risk but enforcement gap confirmed 3× in production logs)
**Subsystem anchor:** SS-04 (Plugin Ecosystem) owns the `verify-state-timestamp-refresh` WASM hook plugin crate.

## Narrative

The `verify-state-timestamp-refresh` PreToolUse WASM guard (S-17.04; ADR-025 §Decision 12; BC-5.40.001 PC4) is the timestamp-freshness enforcement gate for STATE.md writes. It reads `.factory/STATE.md` via `host::read_file` with a 64 KiB cap (`STATE_MD_MAX_BYTES = 65536`), then parses the `timestamp:` and `factory_lock.expires_at` YAML frontmatter fields to enforce mid-burst TTL renewal.

**The defect:** In the vsdd-factory repo at rc.22 and all subsequent builds, STATE.md exceeds 64 KiB. `read_file.rs::read_bounded()` returns `ReadErr::TooLarge` when the file's on-disk size exceeds `max_bytes`, emitting `internal.capability_denied reason=output_too_large` and returning `OUTPUT_TOO_LARGE (-3)` to the plugin. The plugin maps any non-zero `read_file` return as a read error and falls back to `Continue` (fail-open per ADR-025 Decision 7). The timestamp-freshness gate is therefore **silently inert on every PreToolUse Edit/Write/MultiEdit dispatch to STATE.md** in any install where STATE.md has grown beyond 64 KiB.

**Evidence (D-826 tracked items + D-835):** Three production dispatcher-log traces confirm the pattern — each shows `internal.capability_denied reason=output_too_large` on `plugin_name=verify-state-timestamp-refresh`. This is the same defect class as S-19.02 FINDING-1 (`verify-factory-lock` had `STATE_MD_MAX_BYTES = 65536`; S-19.02 raised it to 262144 and wired `extract_frontmatter`). S-19.02 is already MERGED on develop via PR #610 (fe303926); `crates/factory-lock-parse::extract_frontmatter` is available.

**Fix direction (mirrors S-19.02 Phase-A):**

**BC-5.40.001 v1.3 Precondition 6 LANDED (product-owner; D-826/D-835). Spec-first gate satisfied.** Precondition 6 mandates `max_bytes = 262144` for `verify-state-timestamp-refresh` reads; Invariant 7 mandates `extract_frontmatter` exclusive use; Invariant 8 mandates the `state_md_approaching_cap` soft-warn at `bytes_read ∈ (200000, 262144]`. This story implements the code changes to bring the plugin into conformance with BC-5.40.001 v1.3.

1. Raise `STATE_MD_MAX_BYTES` to 262144 (256 KiB) — the same cap established for `verify-factory-lock` by BC-4.13.001 Phase-A Precondition 3 + ADR-025 §Decision 14.
2. Wire `factory_lock_parse::extract_frontmatter` (already in `crates/factory-lock-parse/`) before any YAML parsing — guard must not process post-frontmatter body content (parity with BC-4.13.001 Phase-A Invariant 9 semantics applied to this guard).
3. `factory-lock-parse` is ALREADY a dependency of `verify-state-timestamp-refresh` (the plugin's doc comment states: "No `serde_yaml` / `serde_norway` — manual line-by-line scan via `factory-lock-parse`"). No new Cargo.toml dependencies required.
4. Wire soft-warning when byte count is strictly above 200000 and at or below 262144 (parity with S-19.02 AC-006 / BC-4.13.001 Invariant 10 soft-warn).

**Why AC-001 (cap raise) alone closes the guard-bypass defect:** `read_bounded()` checks `metadata.len()` BEFORE reading any bytes — if the cap is below the file's on-disk size, the read fails immediately before the guard logic is ever reached. The fix is to raise `STATE_MD_MAX_BYTES` to 262144 so the cap is above any realistic STATE.md size (worst-case observed <200 KB under 500-line compaction discipline per ADR-026; 262144-byte cap gives ≥25% headroom over observed range). Cite: ADR-025 §Decision 12 §12.5 parity.
