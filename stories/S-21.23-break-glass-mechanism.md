# S-21.23: Break-glass override mechanism — `VSDD_BREAK_GLASS_GATE_BYPASS` for self-locking `PreToolUse` `^Agent$` gates (ADR-039 Phase 4b; split seam 5 of 6 from S-21.11)

## Narrative

- **As a** factory pipeline operator whose two `PreToolUse` `^Agent$` gates
  (`validate-wave-gate-prerequisite`, `validate-pr-merge-prerequisites`) risk a self-lock if
  flipped to fail-closed without a way to escape a miscalibration — a hard block on either
  gate prevents ANY future `Agent` dispatch, including the dispatch needed to fix the
  miscalibration
- **I want** an authenticated-by-possession, human-operator-only break-glass override for
  these two gates specifically, audited on every activation
- **So that** the two self-locking gates cannot wedge all future `Agent` dispatch without a
  documented recovery path, before S-21.24's flip of these two plugins to
  `failure_policy = "fail-closed"` can safely proceed

## Context / Finding Summary

**Self-lock hazard is live today, on two axes (ADR-039 §Context).** `lessons.md` already
exhausts the 10M fuel budget (D-442(e); ≤3500 soft / ≤4000 hard line-count workaround). The
ADR-039 authoring session itself triggered `fail-closed: plugin timed out` blocks from
`validate-factory-path-root`, `validate-input-hash`, and `validate-template-compliance`. A
naive global flip would immediately hard-block all `.factory/` writes. **A second, distinct
self-lock axis exists for the two `PreToolUse` `^Agent$` gates specifically:** a hard block on
either `validate-wave-gate-prerequisite` or `validate-pr-merge-prerequisites` prevents ANY
future `Agent` dispatch — including the dispatch needed to fix the miscalibration. This is why
this story's break-glass mechanism is mandatory, not optional, for these two gates
specifically (ADR-039 §Decision 3 v1.9/v1.10 amendment).

**Why this seam depends on S-21.19 (integration ordering, not semantics).** BC-1.03.018's own
preconditions do not cite S-21.19's decision-function internals — this seam is logically
independent of the exhaustion-calibration Nodes' internals. But the operator's baseline
explicitly sequences this seam AFTER S-21.19 because both land edits inside the SAME
`execute_tiers` block-decision loop body — landing after S-21.19 avoids a signature-mismatch
merge conflict against the 2-arg→3-arg `plugin_fail_closed` call site. This is a source-level
integration ordering choice, preserved as directed from the original DAG's own "(D) and (E)
are independent of each other" statement.

**This story does NOT flip the two Agent gates to `failure_policy = "fail-closed"`** — it
delivers the break-glass mechanism and its own AC-022 mechanical ordering gate that S-21.24's
flip of those two plugins is gated on.

## Acceptance Criteria

### AC-014: Override unset/absent → no behavioral change (baseline regression control) (traces to BC-1.03.018 PC1)

When `VSDD_BREAK_GLASS_GATE_BYPASS` is unset (or set to the empty string), both named gates'
block decisions are computed exactly as if the break-glass mechanism did not exist —
BC-1.03.017's `failure_policy`/`on_error` semantics apply unmodified. Introducing the
break-glass check MUST NOT alter any existing BC-1.03.017 postcondition's observed outcome
when the override is inactive.

- **Test:** `test_break_glass_unset_no_behavior_change()` — real dispatch:
  `VSDD_BREAK_GLASS_GATE_BYPASS` unset; `validate-wave-gate-prerequisite` returns
  `PluginResult::Timeout{Epoch}` + `failure_policy=FailClosed` → `block_intent=true`; exit 2
  (BC-1.03.017 PC6 semantics unmodified)
- **Test:** `test_break_glass_non_utf8_value_treated_as_unset()` (F-S2123-P1-002, EC-015) —
  set `VSDD_BREAK_GLASS_GATE_BYPASS` to a non-UTF-8 byte sequence (e.g. via `std::env::set_var`
  with an `OsString` built from invalid-UTF-8 bytes on a Unix target); the implementation reads
  the variable via `std::env::var_os` (not `std::env::var`) and treats a value that fails
  UTF-8 conversion (`VarError::NotUnicode`'s underlying condition) as equivalent to unset (this
  AC's baseline) — `block_intent=true`; exit 2 (unmodified); the dispatcher MUST NOT panic

### AC-015: Override set to an exact gate name → that gate's block suppressed for that invocation, regardless of block cause (traces to BC-1.03.018 PC2)

When `VSDD_BREAK_GLASS_GATE_BYPASS` contains the plugin `name` of
`validate-wave-gate-prerequisite` or `validate-pr-merge-prerequisites` (exact match;
comma-separated list; each token trimmed of leading/trailing whitespace before comparison),
that specific gate's contribution to `block_intent` for that invocation is forced to `false`
— REGARDLESS of which decision path would otherwise have produced the block
(`plugin_requests_block`'s `HookResult::Block` path, OR `plugin_fail_closed`'s exhaustion path
under `failure_policy = FailClosed`), and regardless of the plugin's own `PluginResult`
variant (`Crashed`, `Timeout{Fuel}`, `Timeout{Epoch}`).

- **Test:** `test_break_glass_exact_name_suppresses_block()` — real dispatch:
  `VSDD_BREAK_GLASS_GATE_BYPASS=validate-wave-gate-prerequisite`; same plugin returns
  `PluginResult::Timeout{Epoch}` + `failure_policy=FailClosed` → this gate's contribution to
  `block_intent` suppressed → exit 0 for this gate's contribution; `break_glass.activated`
  event emitted with gate name, timestamp, trace UUID (see AC-018)
- **Test:** `test_break_glass_suppresses_crash_block_too()` — real dispatch: override names
  the gate; the plugin CRASHES (`PluginResult::Crashed`, `on_error=Block`) rather than
  exhausting a resource budget → the crash-caused block is ALSO suppressed (PC2's "regardless
  of which decision path... and regardless of the plugin's own `PluginResult` variant" — the
  override is outcome-level, not exhaustion-specific; covers BC-1.03.018 EC-006 — BC-1.03.018's
  own internal edge-case numbering, distinct from this story's origin's (S-21.11 v2.11)
  unrelated EC-006 row in its own Edge Cases table — F-S2123-P1-005 wording correction)

### AC-016: Override set to the literal `all` → both named gates bypassed (traces to BC-1.03.018 PC3)

`VSDD_BREAK_GLASS_GATE_BYPASS=all` suppresses both `validate-wave-gate-prerequisite`'s and
`validate-pr-merge-prerequisites`' block contributions for that invocation, equivalent to
naming both explicitly. Both gates are dispatched in separate `execute_tiers` tiers (priority
130 vs 120 — `routing.rs::group_by_priority` starts a new tier on every distinct priority
value), evaluated unconditionally within the same dispatch via `execute_tiers`'s no-early-return
tier loop. If both would have blocked, TWO separate `break_glass.activated` events MUST be
emitted (one per gate name, per BC-1.03.018 EC-005 — BC-1.03.018's own internal edge-case
numbering), not a single combined event — this conclusion does not depend on, and is not
evidenced by, the two gates sharing a tier; it follows from `execute_tiers` looping over every
tier unconditionally (no early return on a block-producing tier), so both gates are always
invoked and both outcomes always folded into `block_intent` within one dispatch, regardless of
tier membership.

- **Test:** `test_break_glass_all_bypasses_both_gates()` — real dispatch:
  `VSDD_BREAK_GLASS_GATE_BYPASS=all`; both gates return blocking outcomes → both suppressed;
  two `break_glass.activated` events emitted, one per gate name, sharing the dispatch trace
  UUID
- **Test:** `test_break_glass_all_as_trimmed_token_in_list()` (F-S2123-P1-006) — `all` matches
  as a trimmed COMMA-SEPARATED TOKEN, not only when it is the entire env-var value verbatim:
  `VSDD_BREAK_GLASS_GATE_BYPASS=<junk>,all` (where `<junk>` is a non-matching token, e.g. a
  typo or an unrelated plugin name) → both named gates are STILL bypassed, because `all` is
  present as one of the comma-separated, whitespace-trimmed tokens (Task 3's parsing already
  treats the value as a token list per AC-015; this test proves `all`-as-wildcard participates
  in that same tokenization rather than requiring an exact whole-value match)

### AC-017: Override set to a non-matching value → no suppression (negative control) (traces to BC-1.03.018 PC4)

When `VSDD_BREAK_GLASS_GATE_BYPASS` is set to a value that does not exact-match either named
gate's `name` and is not `all` (e.g., a typo, or the name of an unrelated plugin such as
`validate-factory-path-root`), neither named gate's normal block behavior is suppressed. This
proves the matcher is name-scoped and not a blanket kill-switch that fires on any non-empty
value.

- **Test:** `test_break_glass_non_matching_value_no_suppression()` — real dispatch:
  `VSDD_BREAK_GLASS_GATE_BYPASS=validate-factory-path-root` (non-matching name);
  `validate-wave-gate-prerequisite` returns a blocking outcome → block NOT suppressed;
  `block_intent=true`; exit 2; NO `break_glass.activated` event for
  `validate-wave-gate-prerequisite`

### AC-018: Mandatory audit on every activation — no silent bypass (traces to BC-1.03.018 PC5)

Every time AC-015 or AC-016 suppresses a gate's block contribution for a given invocation,
the dispatcher MUST emit a structured `break_glass.activated` event to
`.factory/logs/dispatcher-internal-YYYY-MM-DD.jsonl` (the same event-sink family documented
for `VSDD_SINK_FILE` diagnostics, via the existing `InternalLog`/`InternalEvent` mechanism in
`crates/factory-dispatcher/src/internal_log.rs`) carrying at minimum: the bypassed gate
name(s), an ISO-8601 timestamp, and the dispatch's trace UUID (`dispatcher_trace_id`). A test
asserting AC-015/AC-016's suppression behavior fires with NO corresponding
`break_glass.activated` record in the captured log output MUST fail — silent bypass is a
defect, not an acceptable implementation.

- **Test:** `test_break_glass_activation_emits_audit_event()` — integration test asserting
  captured dispatcher-internal JSONL output contains a `break_glass.activated` record with
  the bypassed gate name, an ISO-8601 timestamp field, and the invocation's
  `dispatcher_trace_id`, for a real dispatch that triggers AC-015's suppression path

**Note (PC11/AC-042 cross-reference):** as of PC11, the break-glass call site emits this
record via the new `InternalLog::write_checked` tri-state method (Task 3), not the pre-existing
best-effort `InternalLog::write`. This AC tests the EMISSION obligation (a record is present in
the captured JSONL output) for the healthy-sink case, independent of whether suppression is
ultimately granted — see AC-042 for the audit-write-DURABILITY-gates-suppression behavior when
the write is unhealthy (`Failed`/`SkippedMountGate`).

### AC-019: Audit fires on every matched invocation, independent of whether the plugin's own outcome would have blocked (traces to BC-1.03.018 PC6; BC-1.03.018 EC-004 — BC-1.03.018's own internal edge-case numbering, distinct from this story's origin's unrelated EC-004 row [`PRACTICAL_FUEL_CEILING` calibration overflow])

The `break_glass.activated` event MUST be emitted whenever the override names a gate that is
dispatched in that invocation's tier set, REGARDLESS of whether that gate's own
`PluginResult` would have produced a block absent the override — "active" is defined as "the
override names this gate AND this gate is invoked," not "the override suppressed an outcome
that would otherwise have blocked." An operator who leaves `VSDD_BREAK_GLASS_GATE_BYPASS` set
after the emergency has passed is an auditable fact regardless of whether any individual
invocation would have blocked.

- **Test:** `test_break_glass_audit_fires_even_on_clean_pass()` — real dispatch:
  `VSDD_BREAK_GLASS_GATE_BYPASS=validate-wave-gate-prerequisite`; plugin returns a CLEAN PASS
  (no block) → `break_glass.activated` event STILL emitted (audit fires on matched
  invocation, independent of counterfactual block); observable exit code unchanged (exit 0
  either way)

### AC-020: Non-persistent, validation-preserving override — no registry mutation, plugin still runs (traces to BC-1.03.018 PC7)

The override does NOT write to, or otherwise mutate, `hooks-registry.toml` — it is a
per-invocation runtime decision only, never a persistent configuration change. The named
plugin still executes and its `PluginResult` is still recorded in `per_plugin_results` /
logged via the normal `emit_invoked`/lifecycle event path; only that outcome's contribution
to the aggregate `block_intent` is suppressed.
`TierExecutionSummary.per_plugin_results` for a break-glass-active invocation MUST still
contain an entry for the bypassed plugin showing its actual (would-be-blocking) result, not a
synthesized "skipped" or "not-run" result.

- **Test:** `test_break_glass_does_not_mutate_registry()` — assert
  `hooks-registry.toml`'s on-disk content is byte-identical before and after a
  break-glass-active dispatch
- **Test:** `test_break_glass_plugin_still_executes_and_is_logged()` — assert
  `TierExecutionSummary.per_plugin_results` contains the bypassed plugin's actual
  `PluginResult` (not a synthesized skip marker) after a break-glass-active dispatch

### AC-021: Scope restriction — override has no effect on any plugin other than the two named gates (traces to BC-1.03.018 PC8)

Setting `VSDD_BREAK_GLASS_GATE_BYPASS` to the exact `name` of any registered plugin OTHER
than `validate-wave-gate-prerequisite` or `validate-pr-merge-prerequisites` (e.g.,
`validate-factory-path-root`, or any `on_error="continue"` advisory plugin) has NO effect on
that other plugin's block decision — the mechanism is hard-scoped to the two named gates at
the implementation level, not a generic "bypass any plugin by name" facility.

- **Test:** `test_break_glass_scoped_to_two_named_gates_only()` — real dispatch:
  `VSDD_BREAK_GLASS_GATE_BYPASS=validate-factory-path-root` (a real, valid plugin name, but
  not one of the two named gates); that plugin returns a blocking outcome → block is NOT
  suppressed (scope restriction proven against a real plugin name, not only a typo per
  AC-017)
- **Test:** `test_break_glass_named_gate_does_not_bypass_the_other_gate()` — real dispatch:
  `VSDD_BREAK_GLASS_GATE_BYPASS=validate-wave-gate-prerequisite`; `validate-pr-merge-prerequisites`
  (a different named gate, not the one set) returns a blocking outcome → NOT suppressed
  (per-name scope, not global)

### AC-022: Mechanical intra-story ordering gate — no `failure_policy="fail-closed"` on either `PreToolUse` `^Agent$` gate without the break-glass consultation code already present in the same commit tree (traces to BC-1.03.018 PC9; ADR-039 §Decision 3 v1.10 sequencing rule; mirrors S-21.19's AC-012 pattern for BC-1.03.017 PC11)

A Cargo integration test MUST assert: if `hooks-registry.toml` carries
`failure_policy = "fail-closed"` for `validate-wave-gate-prerequisite` OR
`validate-pr-merge-prerequisites` on a given commit tree, then that SAME commit tree's
`crates/factory-dispatcher/src/executor.rs` MUST already contain the break-glass
consultation code (a `VSDD_BREAK_GLASS_GATE_BYPASS`-reading check in the `execute_tiers`
block-decision path, name-independent detection analogous to S-21.19's AC-012
`.failure_policy`-reference detection). Absence of the break-glass code while either gate
carries `failure_policy = "fail-closed"` MUST cause the test to FAIL (CI blocks merge). This
is the mechanical enforcement of the hard edge: this story's break-glass mechanism MUST
precede, or be atomic with, S-21.24's Phase 4c flip commit for these two specific plugins.

**This gate is a strict superset, for these two plugins only, of S-21.19's AC-012.** AC-012
alone would allow `validate-wave-gate-prerequisite`/`validate-pr-merge-prerequisites` to flip
to fail-closed as soon as the executor's `failure_policy` consultation exists and the plugin
is annotated — it does not know about break-glass. This AC closes that gap specifically for
these two self-locking gates.

The gate MUST include four controls, mirroring AC-012's structure:
- **POSITIVE-CONTROL:** synthetic registry with `validate-wave-gate-prerequisite` at
  `failure_policy="fail-closed"` + synthetic executor-source snippet WITHOUT the break-glass
  check → assert the gate fires RED.
- **NEGATIVE-CONTROL:** the same synthetic registry + synthetic executor-source snippet WITH
  the break-glass check present → assert the gate PASSES.
- **VACUITY-CONTROL:** synthetic registry with BOTH named gates still at `failure_policy`
  absent/fail-open (pre-flip state) + any executor-source state → assert the gate returns
  GREEN vacuously (the ordering rule is not yet triggered because no flip has occurred).
- **LIVE-TREE-CONTROL:** at S-21.24 completion, the detector MUST be run against the actual
  `crates/factory-dispatcher/src/executor.rs` and the actual `hooks-registry.toml`, and MUST
  report the correct ordering state for whichever gates are flipped at that point — this
  final live-tree confirmation is performed by S-21.24, which owns the flip that makes it
  meaningful; this story authors the test and its three pure-function controls.

- **Test:** `test_no_agent_gate_fail_closed_flip_without_break_glass()` — parses
  `hooks-registry.toml` for `failure_policy="fail-closed"` on either named `^Agent$` gate;
  if present, detects break-glass-consultation-active state in `executor.rs` using the
  name-independent signal (a `VSDD_BREAK_GLASS_GATE_BYPASS`-reading check in the
  `execute_tiers` block-decision path); MUST FAIL if either gate is flipped and the
  break-glass code is absent; includes all four controls above (three authored here; the
  fourth, LIVE-TREE-CONTROL, confirmed by S-21.24 post-flip); GREEN vacuously pre-flip
  (this story's own completion state); GREEN at S-21.24-complete state (both gates flipped,
  break-glass code present)

### AC-023: Break-glass negative control — an `Agent`-tool-invoked path CANNOT arm `VSDD_BREAK_GLASS_GATE_BYPASS` for the dispatcher's own process environment (traces to BC-1.03.018 v1.1 PC10; F-006, S-21.11 v2.0 adversarial pass-1 threat-boundary directive)

`VSDD_BREAK_GLASS_GATE_BYPASS` is armed if and only if it is present in the OS process
environment of the process that ultimately launches the `factory-dispatcher` binary for a
given dispatch — i.e., the human operator's shell session (or an ancestor process the operator
directly controls). This is a structural property of the OS process model, not an
application-level access check: a child process's environment is a COPY taken at
`fork`/`exec` time, and a child mutating its own environment can NEVER write back into its
parent's environment. Consequently, none of the following can arm the override for the
dispatcher's own process: (a) a Bash-tool subprocess spawned by an `Agent`-tool-invoked Claude
session (a DESCENDANT of the dispatcher's own process tree, never an ancestor); (b) an MCP
tool invocation (runs entirely outside the harness's own environment-inheritance chain); (c) a
hook-wrapper subprocess (e.g. `legacy-bash-adapter`'s own `exec_subprocess` calls) — itself a
CHILD of the dispatcher process for that single invocation.

**Explicit threat-boundary note (out of this AC's enforcement scope, per F-006):** this AC does
NOT claim the dispatcher validates WHO set the variable in its inherited environment. If the
human operator's own shell session is itself compromised, that compromised process COULD set
the variable before launching Claude Code, and the dispatcher would inherit it exactly as it
would inherit a legitimate operator's setting (Invariant 1's "authentication-by-possession, not
identity" scope). What this AC closes is narrower: the `Agent` tool dispatch path ITSELF
provides no route to arm the override, by construction of the OS process model, regardless of
what any `Agent`-invoked tool call attempts.

- **Test:** `test_break_glass_env_not_settable_by_child_process()` — an integration test MUST
  spawn a child process that attempts to set `VSDD_BREAK_GLASS_GATE_BYPASS` in its own
  environment (via `std::env::set_var`, or an equivalent shell `export`, executed inside the
  spawned child) and then assert that the PARENT test process's own
  `std::env::var("VSDD_BREAK_GLASS_GATE_BYPASS")` remains unset/unchanged after the child
  process exits — proving the OS-level parent-environment isolation this AC relies on, in the
  actual runtime the dispatcher executes in, not merely asserted as documentation

### AC-042: Audit fail-closed-on-failure — suppression is granted ONLY IF the `break_glass.activated` audit write DURABLY completes (sibling to AC-018; traces to BC-1.03.018 PC11/Invariant 7; F-S2123-P1-001, HIGH, Q3, ADR-039 §AMD-004)

When AC-015 or AC-016 would otherwise suppress a gate's block contribution for a given
invocation, that suppression is granted ONLY IF the corresponding `break_glass.activated`
audit write (AC-018/AC-019) is CONFIRMED DURABLY WRITTEN — i.e., `InternalLog::write_checked`
(the new, additive, tri-state method Task 3 implements ALONGSIDE the existing best-effort
`InternalLog::write`, which remains UNCHANGED for its other hot-path telemetry callers)
returns `Written`. If the audit write FAILS (`write_checked` returns `Failed(io::Error)`) OR
is SKIPPED (`write_checked` returns `SkippedMountGate` — the `.factory/` mount-gate skip path,
which the pre-existing best-effort `write()` conflates with a successful write, since both
return `Ok(())`), the override MUST NOT be applied for that gate on that invocation — the
underlying gate's block decision stands, computed EXACTLY as if the override were unset
(AC-014 baseline semantics), even though the override was set and named this gate. This is the
fail-closed-on-audit-failure posture: an audit write that cannot be confirmed durable MUST NOT
silently grant a bypass, because a break-glass activation whose audit trail is dropped —
precisely during a live self-lock, the scenario this mechanism exists to recover from —
reproduces exactly the CWE-636 silent-approval failure mode AC-018/AC-019's own mandatory-audit
requirement exists to prevent, one layer down (BC-1.03.018 EC-007).

- **Test:** `test_break_glass_denied_on_unwritable_audit_sink()` — real dispatch:
  `VSDD_BREAK_GLASS_GATE_BYPASS=validate-wave-gate-prerequisite`; that gate returns a blocking
  outcome; `InternalLog::write_checked` simulated to return `Failed(io::Error)` (unwritable
  audit sink) → suppression DENIED — `block_intent=true`; exit 2 (gate's block decision stands,
  unchanged from the no-override baseline); NO durable `break_glass.activated` record confirmed
- **Test:** same test, second sub-case — `InternalLog::write_checked` simulated to return
  `SkippedMountGate` (`.factory/` mount not yet ready) → suppression DENIED; `block_intent=true`;
  exit 2 (identical outcome to the `Failed` sub-case — a skip is NOT treated as equivalent to a
  durable write)
- **Test:** `test_break_glass_granted_on_written_audit_sink()` (NEGATIVE control) — real
  dispatch: `VSDD_BREAK_GLASS_GATE_BYPASS=validate-wave-gate-prerequisite`; that gate returns a
  blocking outcome; `InternalLog::write_checked` returns `Written` (audit sink healthy) →
  suppression GRANTED — `block_intent` contribution suppressed → exit 0 for this gate's
  contribution (restores AC-015's baseline behavior once the audit write is confirmed durable;
  proves PC11 does not over-block a healthy audit path)

### AC-043: Break-glass negative control — the override is NOT derivable from any Agent-writable source; env-only sourcing (traces to BC-1.03.018 PC10/Invariant 1's full claim; F-S2123-P1-003, MED)

Invariant 1's "authentication-by-possession, human-operator-only" claim requires that
`VSDD_BREAK_GLASS_GATE_BYPASS` be read EXCLUSIVELY from the OS process environment — AC-023
proves no `Agent`-tool-invoked path can arm the environment variable itself; this AC closes the
complementary gap: no OTHER channel available to an `Agent`-tool-invoked call (a JSON tool-call
payload field, a `plugin_config` value, a `hooks-registry.toml` field, or an on-disk file) may
be consulted as an alternate source for the same suppression decision, even if such a channel
happens to carry a value that matches a gate name or `all`.

- **Test:** `test_break_glass_not_derivable_from_non_env_sources()` — real dispatch: construct
  a scenario where a synthetic JSON tool-call payload field, a `plugin_config` entry, an
  alternate `hooks-registry.toml` field (e.g. a hypothetical `break_glass_bypass` key on the
  plugin entry itself), and an on-disk file all carry the literal value
  `validate-wave-gate-prerequisite` (or `all`) under some non-`VSDD_BREAK_GLASS_GATE_BYPASS`
  key, while the actual OS process environment variable `VSDD_BREAK_GLASS_GATE_BYPASS` remains
  UNSET — assert suppression does NOT occur for any of the four alternate-channel sub-cases
  (`block_intent=true`; exit 2 unchanged from the no-override baseline) and NO
  `break_glass.activated` event is emitted, proving the ONLY channel ever consulted for this
  decision is `std::env::var_os("VSDD_BREAK_GLASS_GATE_BYPASS")`
