# S-18.04b-prereq — Dispatcher git_context payload injection on PostToolUse Bash git-commit events (ADR-029)

## Narrative

As a WASM chain-detection plugin author requiring exec-free operation,
I want the factory-dispatcher to detect PostToolUse Bash `git commit` events
targeting the factory-artifacts worktree and inject a `git_context` JSON object
into `payload.extra` (with four fields: `head_subject`, `head_sha`,
`head_parent_subject`, `head_parent_sha`) before routing to registered plugins,
so that `validate-burst-log` and `validate-dispatch-advance` can evaluate commit
chains without calling `host::exec_subprocess` (ADR-029 §Decision 3),
and so that chain detection fires on the actual commit event rather than a stale
Edit/Write file-write event (ADR-029 §Decision 1 decoupling defect fix).

This story contains NO WASM plugin code changes. It is a BLOCKING prerequisite
that must merge to `develop` before S-18.04b branches.

**Why this is a separate story (ADR-029 §Decision 7):** The dispatcher git_context
injection is analogous in scope to the `write_file.rs` path-resolution fix that
warranted S-18.04a-prereq. Keeping dispatcher changes separate from WASM changes
preserves Red Gate discipline: S-18.04b's WASM tests (that read `git_context` from
payload.extra) will fail until this prereq delivers the dispatcher injection.

## Behavioral Contracts

| BC ID | Title | Version | PCs/INVs Exercised |
|-------|-------|---------|-------------------|
| BC-1.16.001 | Dispatcher injects git_context (HEAD/HEAD^ subject+SHA) into payload.extra on PostToolUse Bash git-commit events targeting factory-artifacts worktree — exec-free WASM boundary; fail-open on git error | v1.0 | PC1–PC6 (all postconditions), INV1–INV5 (all invariants), EC-001–EC-009 (all edge cases) |

## Acceptance Criteria

### AC-001 (traces to BC-1.16.001 postcondition 1 — git_context injection on qualifying events)
For any PostToolUse Bash event where `tool = "Bash"` and `tool_input.command`
contains a `git commit` invocation with a factory-artifacts worktree indicator
(`-C .factory`, `-C <CLAUDE_PROJECT_DIR>/.factory`, or equivalent `.factory`
path reference), the dispatcher MUST inject `git_context` into `payload.extra`
with all four string fields populated before routing to registered plugins:
- `head_subject`: result of `git -C <factory_dir> log --format=%s -1 HEAD`
- `head_sha`: result of `git -C <factory_dir> rev-parse HEAD` (full 40-char hex)
- `head_parent_subject`: result of `git -C <factory_dir> log --format=%s -1 HEAD^`
  (empty string if HEAD^ does not exist, i.e., initial commit)
- `head_parent_sha`: result of `git -C <factory_dir> rev-parse HEAD^` (empty
  string if HEAD^ does not exist)

The `git_context` object rides in the `extra` HashMap of `HookPayload`
(`crates/factory-dispatcher/src/payload.rs`); it does NOT add a new named field
to `HookPayload` (ADR-029 §Decision 4).

### AC-002 (traces to BC-1.16.001 postcondition 2 — fail-open on git error)
If any git command in AC-001 fails (non-zero exit code, git not found, not a git
repo, permission denied, or any other error), the dispatcher MUST:
1. Log a `warn`-level tracing event (`tracing::warn!`) describing the failure.
2. Inject `git_context` into `payload.extra` with all four fields set to `""`.
3. Route the enriched payload to registered plugins as normal.

The dispatcher MUST NOT block, abort, or fail-close the hook dispatch on a git
error. The all-empty `git_context` signals to WASM plugins that no chain context
is available — they treat it as "skip check" (consistent with BC-5.41.003 INV5).

### AC-003 (traces to BC-1.16.001 postcondition 3 — no injection on non-qualifying Bash)
For PostToolUse Bash events whose `tool_input.command` does NOT contain a `git commit`
targeting the factory-artifacts worktree, the dispatcher MUST NOT inject `git_context`
into `payload.extra`. Non-qualifying Bash events are routed without `git_context`.

### AC-004 (traces to BC-1.16.001 postcondition 4 — no injection on non-Bash PostToolUse)
For PostToolUse events where `tool = "Edit"`, `tool = "Write"`, `tool = "Agent"`,
or any other non-Bash tool, the dispatcher MUST NOT inspect `tool_input.command`
for `git commit` content. No `git_context` injection occurs for these events.
This invariant corrects the decoupling defect described in ADR-029 §Context: the
prior `check_factory_artifacts_chain()` implementation in `validate-burst-log` and
`validate-dispatch-advance` ran on Edit/Write PostToolUse events against a stale
HEAD. That call is removed in S-18.04b; this story establishes the correct trigger.

### AC-005 (traces to BC-1.16.001 postcondition 5 — HOST_ABI_VERSION unchanged)
`git_context` rides in the existing `extra` map field of `HookPayload` (the
`#[serde(flatten)]` field in `crates/factory-dispatcher/src/payload.rs`). No new
named field is added to `HookPayload`. No new host function is added to the SDK's
`host` module. `HOST_ABI_VERSION` MUST remain 1. Existing plugins that do not read
`git_context` from `extra` are unaffected.

### AC-006 (traces to BC-1.16.001 postcondition 6 — four-field schema always complete)
Whenever `git_context` IS injected into `payload.extra` (including fail-open cases),
all four fields (`head_subject`, `head_sha`, `head_parent_subject`, `head_parent_sha`)
MUST be present as string-typed JSON properties. No field may be omitted. No field
may be `null` — on initial commit (no HEAD^), `head_parent_subject` and
`head_parent_sha` MUST be `""` (empty string, not null, not absent).

### AC-007 (traces to BC-1.16.001 invariant 1 — exec-free WASM boundary preserved)
The `git_context` injection is EXCLUSIVELY the responsibility of the dispatcher host
layer (`crates/factory-dispatcher/src/invoke.rs`). After this story is delivered,
no WASM plugin (`validate-burst-log`, `validate-dispatch-advance`, or any other)
may call `host::exec_subprocess` to obtain commit subjects or SHAs — that path is
removed in S-18.04b. The bats proof harness for VP-093 MUST exercise the injection
via the factory-dispatcher binary (NOT by calling individual functions directly), to
validate the end-to-end host-layer path.

**Operator-release caveat (analogous to S-18.04a-prereq):** This story changes
dispatcher binary behavior. CI tests on `develop` exercise the binary built from
source in this PR. Operator-level pickup requires a subsequent dispatcher release
(new binary bundle). This is expected and consistent with the engine-discipline
release model (RELEASING.md).

### AC-008 (traces to BC-1.16.001 invariant 2 — trigger correctness: commit event not file-write)
The chain-detection evaluation MUST occur on the PostToolUse Bash git-commit event.
The dispatcher MUST NOT inject `git_context` on PostToolUse Edit/Write events.
A Red Gate test MUST confirm that a synthetic PostToolUse Edit event does NOT receive
`git_context` injection.

### AC-009 (traces to BC-1.16.001 invariant 3 — fail-open preserves pipeline availability)
A git-context-acquisition failure (any non-zero git exit code, network error,
missing git binary) MUST result in fail-open (all-empty `git_context` fields
injected, dispatch proceeds). The dispatcher MUST NOT treat git context acquisition
as a blocking operation. A Red Gate bats test MUST verify that when the factory-dir
path is invalid (no git repo), the dispatcher exits 0 and injects all-empty
`git_context` (not blocking).

### AC-010 (traces to BC-1.16.001 invariant 4 — heuristic command detection is acceptable)
The dispatcher detects `git commit` by inspecting `tool_input.command` for the
presence of "git commit" as a substring along with a factory-artifacts worktree
indicator (`-C .factory` or a path reference containing `.factory`). False injection
of valid `git_context` (e.g., a Bash command containing "git commit" as a substring
but not actually committing) is acceptable — the resulting `git_context` values are
authoritative (obtained from the actual HEAD of factory-artifacts post-execution),
and the WASM plugin logic is robust to valid-but-irrelevant `git_context`. The
implementation SHOULD scope the heuristic to commands that also reference `.factory`
to minimize spurious injection (ADR-029 §Decision 3 Negative consequence note).

### AC-011 (traces to BC-1.16.001 invariant 5 — four-field completeness always present)
On initial commit (no HEAD^): `head_parent_subject = ""` and `head_parent_sha = ""`.
These fields MUST be `""` (empty string), NOT `null`, NOT absent from the JSON object.
A Red Gate test MUST verify the initial-commit case via bats (construct a temporary
git repo with a single commit, route a qualifying PostToolUse Bash event, assert
`head_parent_subject` and `head_parent_sha` are `""` not null).

### AC-012 (traces to BC-1.16.001 edge case EC-004 — git push is not a qualifying event)
A PostToolUse Bash event whose command is `git -C .factory push origin factory-artifacts`
(git push, not git commit) MUST NOT trigger `git_context` injection. The dispatcher
must NOT inject `git_context` for push, fetch, status, log, or any other git
subcommand besides `commit`.

### AC-013 (traces to VP-093 — bats proof harness for end-to-end dispatcher injection)
A bats integration test file `plugins/vsdd-factory/tests/vp093-git-context-injection.bats`
MUST be created with the following test cases (modeled on VP-093 Proof Harness Skeleton):
- **VP-093-A:** Four-field injection on qualifying PostToolUse Bash git-commit event
  (two-commit synthetic repo; verify `head_subject`, `head_sha`, `head_parent_subject`,
  `head_parent_sha` in dispatcher JSONL log).
- **VP-093-B:** All-empty injection on git error (non-git dir; verify all four fields
  are `""` and dispatcher exits 0).
- **VP-093-C:** No injection on non-qualifying Bash event (`git push`; verify
  `git_context` key is absent from `payload.extra`).
- **VP-093-D:** No injection on PostToolUse Edit event (verify `git_context` key absent).
- **VP-093-E:** Initial-commit edge case (`head_parent_subject=""`, `head_parent_sha=""`
  not null; single-commit repo).

The bats tests MUST invoke the factory-dispatcher binary via its stdin/IPC path
(same as vp084-proof.bats pattern) — NOT by calling `git_context`-extraction
functions directly. This validates the end-to-end host-layer wiring (AC-007).

## Forbidden Dependencies

`crates/factory-dispatcher/src/invoke.rs` modifications for this story MUST NOT:
- Add a new named field to `HookPayload` in `payload.rs` — `git_context` rides in `extra` only
- Bump `HOST_ABI_VERSION` beyond 1 — no new host function is introduced
- Add a new public host function for git_context (the injection is internal to the dispatcher invoke path; WASM plugins access `git_context` via `payload.extra.get("git_context")`, not via a host function call)
- Remove or modify the existing `exec_subprocess` calls in `validate-burst-log` or `validate-dispatch-advance` WASM source — those removals are S-18.04b's responsibility
- Introduce a hard failure (process exit, panic, or block) when git commands fail — fail-open is mandatory

## Architecture Compliance Rules

- `invoke.rs` git_context injection MUST be in the PostToolUse event branch, AFTER confirming the event is `tool = "Bash"` and the command matches the heuristic, BEFORE routing to registered plugins — not as a side-channel or separate hook
- `git_context` MUST ride in `payload.extra` (`HashMap<String, serde_json::Value>`) — no new named struct field on `HookPayload`
- `HOST_ABI_VERSION` MUST remain 1 — no new host function, no new SDK symbol
- The existing `exec_subprocess` in `crates/factory-dispatcher/src/host/exec_subprocess.rs` is the correct facility — do not re-implement git subprocess execution
- On any git failure: MUST emit `tracing::warn!` (not `tracing::error!`, not panic); MUST inject all-empty git_context; MUST not block
- `hooks-registry.toml` trigger entries for `validate-burst-log` and `validate-dispatch-advance` MUST NOT be changed in this story — the Edit/Write → Bash trigger flip is coupled (ADR-029 §Decision 1 + §Decision 5) to the exec_subprocess removal and git_context consumption rewiring in S-18.04b; changing the trigger before S-18.04b lands would disable structural validation on Edit/Write events while those plugins still exec_subprocess (broken intermediate state); do NOT touch WASM source or registry trigger entries in this story
- `set -euo pipefail` in all new bash scripts (none expected in this story, but the rule applies if any are created)
- No `--no-verify` git flags in any test fixture
