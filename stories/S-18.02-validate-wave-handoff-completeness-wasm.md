# S-18.02 — validate-wave-handoff-completeness WASM Gate Crate

## Narrative

As a factory-dispatcher hook runtime,
I want a WASM PostToolUse gate that validates HANDOFF.md completeness whenever
the file is written or edited,
so that malformed or incomplete wave-handoff artifacts are caught immediately
at write-time rather than discovered later during wave-open.

| BC ID | Title | Version | PCs Exercised |

| BC-4.14.001 | validate-wave-handoff-completeness WASM gate blocks HandoffIncomplete on PostToolUse HANDOFF.md writes | v1.16 | PC1, PC2, PC2a, PC3, PC4, PC5, PC6, PC7, PC8, INV1, INV2, INV3, INV4, INV5 |

## Acceptance Criteria

### AC-001 (traces to BC-4.14.001 postcondition 4 — non-HANDOFF.md no-op)
The WASM gate is triggered on `PostToolUse` events for `Write` and `Edit` tools.
File paths that do NOT match `**/HANDOFF.md` result in immediate no-op (exit 0).

### AC-002 (traces to BC-4.14.001 postcondition 2a — EPIC-COMPLETE detection)
When the written HANDOFF.md contains `next_wave_stories: []`, the gate detects
EPIC-COMPLETE. In EPIC-COMPLETE, the gate first validates that `epic_status:
complete` is present (if absent, emits `HandoffIncomplete: epic_status must be
'complete' when next_wave_stories is empty list` and exits non-zero). If
`epic_status` is valid, the gate then performs full 9-base-field validation. A
malformed base field (e.g., `last_verified_develop_sha: ""`) detected in this
validation pass causes the gate to block with `HandoffIncomplete` naming the
failing field(s). The EPIC-COMPLETE branch augments validation — it adds the
`epic_status` check and then continues to full base-field validation; it does
NOT short-circuit after `epic_status` alone.

### AC-003 (traces to BC-4.14.001 postcondition 3 — wave_id=1 no-op)
When `wave_id: 1` is present AND the file is NOT in EPIC-COMPLETE state, the
gate exits 0 (no-op). Wave-1 handoffs are not subject to completeness gating.

### AC-004 (traces to BC-4.14.001 postcondition 7 + invariant 3 step 4 — wave_id > 1 full validation)
When `wave_id > 1` (and not EPIC-COMPLETE), the gate validates all 9 base
required fields are present and non-empty (for scalar fields) or present (for
list fields which may be empty lists):
- Scalar fields (must be non-empty/non-null where noted):
  `wave_id`, `last_verified_develop_sha`, `precompact_flush_sha` (may be null),
  `factory_lock_holder` (may be null)
- List fields (empty list is valid):
  `active_bcs`, `next_wave_stories`, `open_decisions`, `pending_fixes`, `process_gaps`

### AC-005 (traces to BC-4.14.001 postcondition 3 + postcondition 8 + invariant 3 step 5 — wave_id absent fail-closed)
When `wave_id` field is absent from the HANDOFF.md, the gate fails closed:
emits `HandoffIncomplete: wave_id field is required` and exits non-zero.

### AC-006 (traces to BC-4.14.001 invariant 2 — fail-all-at-once)
When multiple fields are missing or malformed, the gate emits a single
`HandoffIncomplete` message listing ALL failing field names in one output,
not one message per field. (BC-4.14.001 INV2: completeness error names all
failing fields.)

### AC-007 (traces to BC-4.14.001 postcondition 7 — scalar vs list distinction)
List fields (`active_bcs`, `next_wave_stories`, `open_decisions`, `pending_fixes`,
`process_gaps`) accept an empty YAML list `[]` as valid. A missing list field
(field absent from YAML) is invalid. A scalar field with value `""` (empty string)
is invalid.

### AC-008 (traces to BC-4.14.001 invariant 1)
The WASM gate is pure-parse: it reads only the written file content. It does NOT
shell out, does NOT read other files, does NOT query git. All validation is
performed on the in-memory YAML parse result.

### AC-009 (traces to BC-4.14.001 invariant 2)
`HandoffMissing` is NEVER emitted by the WASM gate. HandoffMissing is a shell-side
error emitted when HANDOFF.md is absent. The WASM gate is only triggered when
the file IS present (PostToolUse Write/Edit). These are disjoint error classes.

### AC-010 (traces to BC-4.14.001 invariant 3 — 5-step evaluation order)
The gate evaluates in strict order:
1. Non-HANDOFF.md path → no-op (exit 0)
2. `next_wave_stories: []` present → EPIC-COMPLETE check (AC-002)
3. `wave_id == 1` AND NOT EPIC-COMPLETE → no-op (exit 0)
4. `wave_id > 1` → full validation (AC-004)
5. `wave_id` absent → fail-closed (AC-005)
No step is skipped; step 2 must be evaluated before step 3.

### AC-011 (traces to BC-4.14.001 invariant 3 — VP-083 discriminating fixture)
A HANDOFF.md with `wave_id: 1` AND `epic_status: complete` AND malformed
`last_verified_develop_sha: ""` (empty string) MUST be blocked by the gate
(EPIC-COMPLETE path validates epic_status but malformed base scalar is still
an error — wave_id=1 no-op only applies when NOT EPIC-COMPLETE).
This is the F-P32-002 discriminating fixture from VP-083, proving the Block result.

### AC-012 (traces to BC-4.14.001 postcondition 5 — fuel budget / 200-line advisory)
The gate completes within `timeout_ms = 5000` on any HANDOFF.md body up to 200 lines.
When the body exceeds 200 lines, the gate emits a `plugin.log` advisory record with
`level: warn` and `message: "HANDOFF.md body exceeds 200-line advisory cap"` — but
it continues to parse and validate all fields normally. The advisory does NOT cause
the gate to return a block. (BC-4.14.001 INV5 documents this as advisory: the 200-line
cap is a soft cap; the gate never hard-fails on length alone.)

### AC-013 (traces to BC-4.14.001 postcondition 6 + invariant 1 — on_error=continue; fail-open on crash)
When the WASM gate crashes (WASM panic, fuel exhaustion, ABI violation), the dispatcher
`on_error = "continue"` setting causes the gate to fail open (Continue). The tool call
is NOT blocked. The dispatcher internal log records a `plugin.crashed` event. This
behavior is independent of the gate's own logic — it is enforced by the dispatcher
per the registry `on_error = "continue"` field.

### AC-014 (traces to BC-4.14.001 registered config)
The gate is registered in `hooks-registry.toml` as:
- `event = "PostToolUse"`
- `tool = "Write|Edit"`
- `on_error = "continue"`
- `async = false`
- `timeout_ms = 5000`

## Previous Story Intelligence

S-18.01 defines the HANDOFF.md schema. This story implements the gate that validates
it. Key architecture lesson from existing hook-plugin crates (e.g.,
`validate-burst-log.wasm`): the WASM main entrypoint reads a JSON dispatch packet
from stdin and writes a JSON response to stdout. The dispatcher passes the tool
call context (including file path and written content) in the dispatch packet.
Implementer must read the dispatcher protocol schema from
`crates/factory-dispatcher/src/invoke.rs` before implementing `src/main.rs`.

## Architecture Compliance Rules

- Pure WASM: no filesystem access, no process spawning (BC-4.14.001 INV1)
- `wasm32-wasip1` target: the crate uses WASI command (`[[bin]]` entry); build with `--target wasm32-wasip1` (`wasm32-wasi` is deprecated in current toolchain)
- Crate must be added to `Cargo.toml` workspace members
- All WASM hook-plugin crates follow the pattern in `crates/hook-plugins/` — examine
  existing crates for the exact dispatcher JSON protocol before implementing
- `#[deny(warnings)]` in lib.rs (CI enforces `-D warnings`)
