# S-19.05 — Observability gaps: async plugin completion telemetry + VSDD_SINK_FILE release-mode opt-in

**Epic:** E-19 — Post-rc.22 Operator Hardening
**Wave:** 2 (no hard dependencies on S-19.01..S-19.04; can run in parallel with other E-19 stories)
**Depends on:** none
**Priority:** P2 (observability gaps; no blocking behavioral defect but make async hangs and diagnostics invisible in production)
**Subsystem anchor:** SS-01 (Hook Dispatcher Core) owns `main.rs` async dispatch and VSDD_SINK_FILE. SS-03 (Event Emission) owns the event catalog for new completion events.

## Narrative

Two observability gaps were discovered during the rc.22 smoke test:

**Finding (c) — Async plugin completion telemetry absent:** When async plugins are dispatched, the dispatcher emits `plugin.invoked` at spawn time. However, no `plugin.completed` event is emitted for async plugins that complete successfully within the drain window. For async plugins that are still in-flight when the `ASYNC_DRAIN_WINDOW_MS` timer fires (abandoned), there is NO event at all — they are silently dropped. An operator watching the dispatcher internal log cannot distinguish between an async plugin that finished cleanly, one that was abandoned (still running at drain time), or one that was never spawned.

The current code (main.rs lines 549–581) only emits:
- `plugin.async_block_discarded` for async plugins that returned block intent within the drain window
- `plugin.timeout` for async plugins that timed out (via `PluginResult::Timeout`)

Missing: `plugin.completed` for async plugins that completed cleanly within the drain window, and `plugin.abandoned` for async plugins still in-flight when the timer fires.

**Finding (d) — VSDD_SINK_FILE compile-gated out of release builds:** `VSDD_SINK_FILE` is the structured-event sink used by the bats integration test harness to capture dispatcher events as JSONL. It is gated `#[cfg(debug_assertions)]` (main.rs lines 36, 70, 78, 219, 393, 478–484). In release builds (which is what operators use via the marketplace tarball), the `VSDD_SINK_FILE` env var is entirely ignored — the dispatcher emits no sink JSONL even if the operator sets `VSDD_SINK_FILE`.

This means:
1. Operators cannot use the standard diagnostic workflow (set `VSDD_SINK_FILE`, reproduce issue, inspect JSONL) with the production binary
2. The Factory Hook Diagnostics section of CLAUDE.md does not document this limitation, leaving operators confused when `VSDD_SINK_FILE` produces no output
3. The original rationale (SEC-003: prevent path traversal via env var) applies equally to release builds and can be addressed with the same sanitization in a release-safe way (env-var-gated at runtime, not compile-time)

**Fix direction for finding (c):** Emit `plugin.completed` for async plugins that complete within the drain window (exit code 0, non-block). Emit `plugin.abandoned` for async plugins still in-flight at drain-timer-fire time (requires tracking spawned-but-uncollected count). Both events are observability-only and MUST NOT change the dispatcher exit code.

**Fix direction for finding (d) — two options; story spec chooses Option A as production-grade:**
- **Option A (chosen):** Make `VSDD_SINK_FILE` runtime-gated instead of compile-gated: check `std::env::var("VSDD_SINK_FILE")` at runtime in release builds, subject to the same SEC-003 path sanitization (no `..` components, no null bytes). Remove the `#[cfg(debug_assertions)]` gates. Update CLAUDE.md Factory Hook Diagnostics to document the env var as available in both debug and release builds.
- Option B (rejected): Add CLAUDE.md documentation only, keeping the compile gate. This leaves operators without a diagnostic mechanism and is not production-grade.

Option A rationale: SEC-003 sanitization already provides the security guarantee; the compile-time gate is defense-in-depth that eliminates the feature entirely for operators. The production-grade stance is to ship the capability with sanitization, not to remove it. The bats test suite already exercises SEC-003 path-traversal rejection — that coverage is preserved and now applies to release binaries as well.

## Acceptance Criteria

| ID | Criterion | Gate |

Event type is `plugin.completed` (same schema as sync plugin completion events). | Unit/integration test: spawn async plugin fixture that exits 0 within the drain window; assert `plugin.completed` event present in event stream with correct fields. | AC-002 | When the drain timer fires with one or more async plugins still in-flight (not yet returned to the channel), the dispatcher emits one `plugin.abandoned` event per in-flight plugin with fields: `plugin_name` and `drain_window_ms`. Event type is `plugin.abandoned`. These events are observability-only and do not affect the dispatcher exit code. | Integration test: configure a slow async plugin fixture that exceeds the drain window; assert `plugin.abandoned` event emitted; assert dispatcher exit code unchanged (0 if no sync blockers). | AC-003 | `plugin.completed` and `plugin.abandoned` events for async plugins are emitted to the internal log (`.factory/logs/dispatcher-internal-YYYY-MM-DD.jsonl`) and, if `VSDD_SINK_FILE` is set, to the sink file. They MUST NOT be relayed to dispatcher stderr (parity with BC-1.14.001 Invariant 4: async plugin stderr not relayed). | Assert zero stderr output for async plugin events in the integration test harness. Exit non-zero if SEC-003 test fails in either profile. |
| AC-006 | CLAUDE.md Factory Hook Diagnostics section is updated to document: (1) `VSDD_SINK_FILE` works in both debug and release builds as of this story; (2) how to set it for diagnostic capture (`VSDD_SINK_FILE=/tmp/disp-events.jsonl claude ...`); (3) SEC-003 path constraint (no `..`). | `grep -q "VSDD_SINK_FILE.*release\|release.*VSDD_SINK_FILE" CLAUDE.md` exits 0. |

## Exceptional Cases

| ID | Scenario | Expected Behavior |
|----|----------|-------------------|
| EC-001 | Async plugin exits with non-zero code (non-block) within drain window | `plugin.completed` emitted with the actual `exit_code` field; no block propagation (Invariant 4 preserved). |
| EC-002 | All async plugins complete before the drain timer fires | No `plugin.abandoned` events emitted (correct: zero in-flight at timer time). |
| EC-003 | `VSDD_SINK_FILE` points to a path with `..` component | SEC-003 sanitization rejects it; logs warning "VSDD_SINK_FILE rejected: path traversal"; no file written. |
| EC-004 | `VSDD_SINK_FILE` is not set | Sink flush path is skipped entirely; no performance penalty (same as current debug-build behavior). |

## Architecture Mapping

**SS-01/SS-03 changes (crates/factory-dispatcher/src/main.rs):**
- In the async drain loop (lines 549–581): emit `plugin.completed` for `PluginResult::Ok { exit_code: 0, .. }` outcomes that are not block verdicts
- After the drain timer fires: compute count of still-in-flight plugins (spawned count minus collected count); emit one `plugin.abandoned` per in-flight plugin
- Remove `#[cfg(debug_assertions)]` gates around `ENV_SINK_FILE` constant, `flush_sink_file` call, and related mutex; keep SEC-003 sanitization in `flush_sink_file` function body
- Emit new `emit_plugin_completed_async` and `emit_plugin_abandoned` functions (parity with existing `emit_plugin_async_block_discarded` / `emit_plugin_timeout_async`)

**SS-03 changes (event catalog):**
- `plugin.completed` already exists in the sync path; confirm async variant uses same schema
- `plugin.abandoned` is a new event type; add to event catalog in BC-3.08.001 (requires product-owner amendment — flag for routing)

**Documentation (CLAUDE.md):**
- Factory Hook Diagnostics: add `VSDD_SINK_FILE` documentation per AC-006

**BC amendment flag:** BC-3.08.001 documents the async plugin event catalog. Adding `plugin.abandoned` as a new event type requires a BC amendment. This story does NOT author the BC amendment — flagged for product-owner routing.
