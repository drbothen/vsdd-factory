# S-19.05 — Observability gaps: async plugin completion telemetry + VSDD_SINK_FILE release-mode opt-in

**Epic:** E-19 — Post-rc.22 Operator Hardening
**Wave:** 2 (no hard dependencies on S-19.01..S-19.04; can run in parallel with other E-19 stories)
**Depends on:** none
**Priority:** P2 (observability gaps; no blocking behavioral defect but make async hangs and diagnostics invisible in production)
**Subsystem anchor:** SS-01 (Hook Dispatcher Core) owns `main.rs` async dispatch and VSDD_SINK_FILE. SS-03 (Event Emission) owns the event catalog for new completion events.

## Narrative

Two observability gaps were discovered during the rc.22 smoke test:

**Finding (c) — Async plugin completion telemetry absent:** When async plugins are dispatched, the dispatcher emits `plugin.invoked` at spawn time. However, no `plugin.completed` event is emitted for async plugins that complete successfully within the drain window. For async plugins that are still in-flight when the drain timer fires (abandoned), there is NO event at all — they are silently dropped. An operator watching the dispatcher internal log cannot distinguish between an async plugin that finished cleanly, one that was abandoned (still running at drain time), or one that was never spawned.

The current code in the async drain `tokio::select!` loop in `crates/factory-dispatcher/src/main.rs` only emits:
- `plugin.async_block_discarded` for async plugins that returned block intent within the drain window
- `plugin.timeout` for async plugins that timed out (via `PluginResult::Timeout`)

Missing: `plugin.completed` for async plugins that completed cleanly within the drain window, and `plugin.abandoned` for async plugins still in-flight when the drain timer fires.

**Finding (d) — VSDD_SINK_FILE compile-gated out of release builds:** `VSDD_SINK_FILE` is the structured-event sink used by the bats integration test harness to capture dispatcher events as JSONL. It is gated `#[cfg(debug_assertions)]` — the `ENV_SINK_FILE` constant declaration, the `flush_sink_file` call, and the sink-related mutex initialization in `crates/factory-dispatcher/src/main.rs` are all wrapped in this cfg gate. In release builds (which is what operators use via the marketplace tarball), the `VSDD_SINK_FILE` env var is entirely ignored.

**Important scope boundary:** A separate `#[cfg(debug_assertions)]` gate exists around `VSDD_ASYNC_DRAIN_WINDOW_MS` — the debug-override for the async drain window timeout (SEC-003). This gate is OUT OF SCOPE for this story and MUST remain debug-only. Only the gates specifically protecting `ENV_SINK_FILE`, `flush_sink_file`, and the sink mutex are in scope. The implementer MUST NOT remove the `VSDD_ASYNC_DRAIN_WINDOW_MS` cfg gate.

This means:
1. Operators cannot use the standard diagnostic workflow (set `VSDD_SINK_FILE`, reproduce issue, inspect JSONL) with the production binary
2. The Factory Hook Diagnostics section of CLAUDE.md does not document this limitation
3. The original rationale (SEC-003: prevent path traversal via env var) applies equally to release builds and can be addressed with the same sanitization in a release-safe way (env-var-gated at runtime, not compile-time)

**Fix direction for finding (c):** Emit `plugin.completed` for async plugins that complete within the drain window (exit code 0, non-block). Emit `plugin.abandoned` for async plugins still in-flight at drain-timer-fire time. Both events are observability-only and MUST NOT change the dispatcher exit code. BC-3.08.001 v1.18 (E-19 pass-2 fix burst added Event 5 `plugin.abandoned`; E-19 pass-5 fix burst adds Event 6 `plugin.completed` async path) defines the `plugin.abandoned` event catalog including the `entry_index: u32` field and Invariant 6 terminal semantics with the extended key `trace_id+plugin_name+entry_index`.

**Fix direction for finding (d) — Option A (chosen):** Make `VSDD_SINK_FILE` runtime-gated instead of compile-gated: check `std::env::var("VSDD_SINK_FILE")` at runtime in release builds, subject to the same SEC-003 path sanitization (no `..` components, no null bytes). Remove only the `#[cfg(debug_assertions)]` gates around `ENV_SINK_FILE`, `flush_sink_file`, and the sink mutex. Update CLAUDE.md Factory Hook Diagnostics to document the env var as available in both debug and release builds.

## Architecture Mapping

**SS-01/SS-03 changes (crates/factory-dispatcher/src/main.rs):**
- In the async drain `tokio::select!` loop: emit `plugin.completed` for `PluginResult::Ok { exit_code: 0, .. }` outcomes that are not block verdicts; emit `plugin.abandoned` (with `entry_index: u32` field per BC-3.08.001 v1.18 Event 5) for in-flight plugins at drain-timer expiry
- Remove `#[cfg(debug_assertions)]` gates around the `ENV_SINK_FILE` constant, the `flush_sink_file` call, and the sink mutex. Keep SEC-003 sanitization in `flush_sink_file` unchanged. **Scope boundary:** the `VSDD_ASYNC_DRAIN_WINDOW_MS` cfg gate (SEC-003 drain-window override) MUST remain debug-only and is out of scope for this story — do NOT remove that gate
- **O-P2-003:** when removing the `#[cfg(debug_assertions)]` gate from the sink block, the `use std::sync::Mutex;` import that was colocated inside the cfg block must be moved to the top-level imports section (unconditional). Failure to do this causes a compilation error in release mode where `Mutex` would be referenced without being imported.
- Emit new `emit_plugin_completed_async` and `emit_plugin_abandoned` functions (parity with existing `emit_plugin_async_block_discarded` / `emit_plugin_timeout_async`)

**O-P1-001 Advisory (architect):** Recommended implementation mechanism is additive channel augmentation: take a pre-spawn plugin-name snapshot, emit `plugin.completed` inline per collected outcome in the drain loop, emit `plugin.abandoned` via post-loop set-difference (spawned names minus collected names). A `JoinSet` refactor is an optional follow-on and out of scope for this story; the additive approach avoids restructuring the existing drain loop.

**SS-03 changes (event catalog):**
- `plugin.completed` (sync path) is owned by BC-1.14.001 and the sync executor path in `crates/factory-dispatcher/src/executor.rs`. The async-path variant is governed by BC-3.08.001 v1.18 Event 6 and includes `plugin_version` and `entry_index` in addition to the base fields — implementer follows BC-3.08.001 v1.18 Event 6 wire format (mandatory fields: `type`, `trace_id`, `session_id`, `plugin_name`, `plugin_version`, `entry_index`, `exit_code`, `elapsed_ms`, `fuel_consumed`).
- `plugin.abandoned` per BC-3.08.001 v1.18 Event 5: `{"type":"plugin.abandoned","trace_id":"<uuid>","session_id":"<uuid>","plugin_name":"<string>","entry_index":<u32>,"drain_window_ms":<integer>,"timestamp":"<ISO-8601>"}` — implementer follows this wire format exactly

**Documentation (CLAUDE.md):**
- Factory Hook Diagnostics: add `VSDD_SINK_FILE` documentation per AC-006
