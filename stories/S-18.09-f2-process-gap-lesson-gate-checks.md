## Narrative

- **As a** factory consistency-validator running at the wave-7 terminal gate boundary for E-18

  (a) The machine-stable lesson count (L-F2-machine-stable-count-assertion) is upheld in new bats tests — specifically that test harnesses assert against structured signals, not presentation-coupled regex;
  (b) Fixes are applied at the correct layer (L-F2-fix-at-correct-layer) — no VP body contains assertions that belong in the BC body;
  (c) No bypass on edit failure (L-F2-no-bypass-on-edit-failure) — no hook script uses `|| true` to suppress errors on load-bearing writes;
  (d) The exhaustive-sweep enumerate-and-count pattern (L-F2-exhaustive-sweep-enumerate-and-count) is present in the BC-discovery scan from S-18.08;

  (f) Stale-term detector — no BC or VP file in the E-18 spec set uses the retired term `current_wave:` in a normative behavioral claim;
  (g) BC-precondition registry-block-shape validator — every BC in the E-18 set whose `§Preconditions` section contains a `[[hooks]]` TOML block has BOTH `name = "..."` AND `plugin = "hook-plugins/....wasm"` fields present (canonical native-WASM shape per D-576)
- **So that** the F2 process-gap lessons are machine-enforced at the E-18 wave-7 gate boundary, not just prose-recorded in lessons.md

## Acceptance Criteria

### AC-001 (gate assertion — L-F2-machine-stable-count-assertion: bats tests use plugin.log structured signals, not presentation-coupled regex)

A grep scan of the E-18 bats test files (specifically `validate-heavy-op-delegation.bats` and other E-18-authored bats files) MUST confirm that test harnesses asserting presence/absence of advisory records use the `plugin.log` structured `code:` field, not a `grep -c "^  - "` pattern or similar presentation-coupled regex over human-readable output.

**Machine-checkable assertion:**
```bash
# Scan E-18 bats files for presentation-coupled assertion anti-pattern
ANTI_PATTERN_HITS=$(grep -rE "grep -c '\^\s*-'" \
  plugins/vsdd-factory/tests/validate-heavy-op-delegation.bats \
  plugins/vsdd-factory/tests/pure-parse-invariant-gate.bats \
  2>/dev/null | wc -l)
[ "$ANTI_PATTERN_HITS" -eq 0 ] || echo "FAIL: presentation-coupled assertion pattern found"

# Scan for machine-stable assertion pattern: plugin.log structured record presence
STABLE_ASSERTIONS=$(grep -rE '"code":"?DelegationRecommended"?' \
  plugins/vsdd-factory/tests/validate-heavy-op-delegation.bats \
  2>/dev/null | wc -l)
[ "$STABLE_ASSERTIONS" -gt 0 ] || echo "FAIL: no machine-stable DelegationRecommended assertions found in bats"
```

**Test (bats):** `test_e18_bats_tests_use_machine_stable_assertions_not_presentation_regex()`

### AC-002 (gate assertion — L-F2-fix-at-correct-layer: VP bodies do not assert behavior beyond their source BC guarantors)

A grep scan of the E-18 VP set (VP-088, VP-089, VP-090, VP-091) MUST confirm that no VP body section asserts a behavioral property that is not guaranteed by the VP's `source_bc:` BC file. Specifically:

The VP MUST NOT use language like "the implementation MUST [do X]" where X is not a postcondition or invariant in the source BC. The VP may assert "the gate MUST [do X]" only where the source BC has a corresponding postcondition or invariant clause.

**Machine-checkable assertion (title-cite parity proxy):**
```bash
# For each E-18 VP, verify source_bc frontmatter field matches an existing BC file
for VP_FILE in \
  .factory/specs/verification-properties/VP-088.md \
  .factory/specs/verification-properties/VP-089.md \
  .factory/specs/verification-properties/VP-090.md \
  .factory/specs/verification-properties/VP-091.md; do
  SOURCE_BC=$(grep "^source_bc:" "$VP_FILE" | cut -d'"' -f2 | cut -d' ' -f1)
  BC_ID=$(echo "$SOURCE_BC" | grep -oE "BC-[0-9]+\.[0-9]+\.[0-9]+")
  BC_SS=$(echo "$BC_ID" | grep -oE "[0-9]+" | head -1)
  BC_FILE=".factory/specs/behavioral-contracts/ss-0${BC_SS}/${BC_ID}.md"
  [ -f "$BC_FILE" ] || echo "FAIL: $VP_FILE source_bc $BC_ID not found at $BC_FILE"
done
```

**Test (bats):** `test_e18_vp_source_bc_files_exist_and_are_reachable()`

### AC-003 (gate assertion — L-F2-no-bypass-on-edit-failure: no `|| true` on load-bearing writes in E-18 hook scripts)

A grep scan of E-18 hook bash scripts MUST confirm that no load-bearing write operation uses `|| true` to suppress errors. "Load-bearing write" = any command that writes to `factory-artifacts`, commits to git, or appends to a JSONL log file.

The E-18 hook scripts in scope:
- `plugins/vsdd-factory/hooks/postcompact-reanchor.sh` (S-18.05 deliverable)

**Machine-checkable assertion:**
```bash
# Scan for || true on git commit / git push / tee / >> patterns (load-bearing writes)
BYPASS_HITS=$(grep -En "(git commit|git push|git add|>> .+\.jsonl|tee .+\.jsonl).*\|\| true" \
  plugins/vsdd-factory/hooks/postcompact-reanchor.sh \
  2>/dev/null | wc -l)
[ "$BYPASS_HITS" -eq 0 ] || echo "FAIL: load-bearing write with || true bypass found in E-18 hook scripts"
```

Note: `|| true` is acceptable on non-load-bearing reads (e.g., `git show ... 2>/dev/null || { warn; exit 0; }` is the correct fail-open pattern for read failures in `postcompact-reanchor.sh`). The gate only flags `|| true` on WRITE operations.

**Test (bats):** `test_e18_hook_scripts_no_bypass_on_load_bearing_writes()`

### AC-005 (gate assertion — cross-reference title-cite parity: story frontmatter BC IDs match actual BC H1 titles)

For each story in the E-18 set (S-18.00 through S-18.09) that has a non-empty `behavioral_contracts:` frontmatter array, verify that each BC ID in the array corresponds to a BC file whose H1 heading is cited correctly in the story's `## Behavioral Contracts` table row.

The gate cannot verify the exact prose match programmatically, but it CAN verify:
1. Each BC ID in `behavioral_contracts:` matches the pattern `BC-\d+\.\d{2}\.\d{3}`.
2. A BC file for that ID exists in the spec tree.
3. The BC file's H1 heading (line starting with `# BC-`) is present in the file.

**Machine-checkable assertion:**
```bash
# For each E-18 story, extract behavioral_contracts IDs and verify BC files exist
for STORY_FILE in .factory/stories/S-18.*.md; do
  BC_IDS=$(grep -A 20 "^behavioral_contracts:" "$STORY_FILE" \
    | grep -oE "BC-[0-9]+\.[0-9]+\.[0-9]+" || true)
  for BC_ID in $BC_IDS; do
    BC_SS=$(echo "$BC_ID" | grep -oE "^BC-([0-9]+)" | grep -oE "[0-9]+")
    BC_FILE=".factory/specs/behavioral-contracts/ss-0${BC_SS}/${BC_ID}.md"
    [ -f "$BC_FILE" ] || echo "FAIL: $STORY_FILE references $BC_ID but $BC_FILE not found"
    # Verify H1 heading is present in BC file
    grep -q "^# ${BC_ID}:" "$BC_FILE" \
      || echo "WARN: $BC_ID file exists but H1 does not start with '# BC-NNN:'"
  done
done
```

**Test (bats):** `test_e18_story_behavioral_contracts_bc_ids_resolve_to_existing_bc_files()`

### AC-007 (gate assertion — BC-precondition registry-block-shape validator: every `§Preconditions` TOML hook block has both `name` and `plugin` fields per D-576)

For every BC in the E-18 SS-04 set (BC-4.14.001, BC-4.15.001) whose `§Preconditions` section contains a `[[hooks]]` TOML block, the gate MUST verify that the TOML block contains BOTH:
- `name = "..."` field
- `plugin = "hook-plugins/....wasm"` field

A TOML block with `plugin =` but without `name =` (or vice versa) is the canonical native-WASM shape violation per D-576 (originally found in BC-4.14.001 v1.8 → fixed in v1.9 F-P14-002). This gate ensures regressions cannot silently reintroduce the violation.

**Machine-checkable assertion:**
```bash
for BC_FILE in \
  .factory/specs/behavioral-contracts/ss-04/BC-4.14.001.md \
  .factory/specs/behavioral-contracts/ss-04/BC-4.15.001.md; do
  # Find the [[hooks]] block in the §Preconditions section
  TOML_BLOCK=$(awk '/^## Preconditions/,/^## Postconditions/' "$BC_FILE" \
    | grep -A 10 '\[\[hooks\]\]')
  # Assert both name and plugin fields present
  echo "$TOML_BLOCK" | grep -q 'name = "' \
    || echo "FAIL: $BC_FILE §Preconditions [[hooks]] block missing name field (D-576)"
  echo "$TOML_BLOCK" | grep -q 'plugin = "hook-plugins/' \
    || echo "FAIL: $BC_FILE §Preconditions [[hooks]] block missing plugin field (D-576)"
done
```

**Test (bats):** `test_e18_bc_preconditions_toml_blocks_have_canonical_name_and_plugin_fields()`

## Architecture Compliance Rules

1. **Gate scan scope is specified exactly (no over-scanning):** Each AC's grep scan targets specific files, not the entire repository. Over-scanning produces false positives from unrelated content (e.g., historical lesson prose that describes the violation class while not committing the violation itself).
2. **Exclusion filters are required where specified:** AC-003 and AC-006 require exclusion filters. Omitting them causes false positives. The exclusion patterns are load-bearing parts of the gate specification.
3. **Empty discovery is a gate failure (L-F2-exhaustive-sweep-enumerate-and-count):** AC-004 validates that the S-18.08 discovery scan fails explicitly when the discovered BC set is empty. A vacuously-passing loop over an empty set is a specification violation.
4. **No write side effects:** The gate scans are read-only. If a gate assertion fails, the correct action is to route the finding to the owning specialist (product-owner for BC issues, test-writer for bats issues) — NOT to auto-fix in place.
5. **Forbidden dependencies:** The gate bats file MUST NOT import or depend on any E-18 WASM crate. These are the artifacts being scanned.
