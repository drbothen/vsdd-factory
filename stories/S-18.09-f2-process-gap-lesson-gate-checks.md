### AC-003 (gate assertion — L-F2-no-bypass-on-edit-failure: no `|| true` on load-bearing writes in E-18 hook scripts)

A grep scan of E-18 hook bash scripts MUST confirm that no load-bearing write operation uses `|| true` to suppress errors. "Load-bearing write" = any command that writes to `factory-artifacts`, commits to git, or appends to a JSONL log file.

The E-18 hook scripts in scope:
- `plugins/vsdd-factory/hooks/postcompact-reanchor.sh` (S-18.05 deliverable)

**Machine-checkable assertion:**
```bash
# Positive-coverage pre-assertion (F-P3-001 / F-P4-002 class — absence-only vacuity guard):
# Assert the scan target exists and is non-empty BEFORE the BYPASS_HITS check.
# If the file were renamed or deleted, BYPASS_HITS=0 would vacuously pass (zero items scanned).
# This guard closes that absence-only vacuity in the same class pass-5 escalated for AC-004.
SCAN_TARGET="plugins/vsdd-factory/hooks/postcompact-reanchor.sh"
[ -s "$SCAN_TARGET" ] \
  || echo "FAIL: AC-003 scan target $SCAN_TARGET absent or empty — gate cannot verify no-bypass (positive-coverage guard)"

# Scan for || true on git commit / git push / tee / >> patterns (load-bearing writes)
BYPASS_HITS=$(grep -En "(git commit|git push|git add|>> .+\.jsonl|tee .+\.jsonl).*\|\| true" \
  "$SCAN_TARGET" \
  2>/dev/null | wc -l)
[ "$BYPASS_HITS" -eq 0 ] || echo "FAIL: load-bearing write with || true bypass found in E-18 hook scripts"
```

Note: `|| true` is acceptable on non-load-bearing reads (e.g., `git show ... 2>/dev/null || { warn; exit 0; }` is the correct fail-open pattern for read failures in `postcompact-reanchor.sh`). The gate only flags `|| true` on WRITE operations.

**Positive-coverage guard semantics:** The `[ -s "$SCAN_TARGET" ]` pre-assertion ensures that a zero-hit result from the BYPASS_HITS scan is backed by actual file content. If the scan target is absent or empty, the gate FAILS loud (`FAIL: AC-003 scan target ... absent or empty`) instead of silently passing (BYPASS_HITS=0 with zero items validated). This is the same absence-only weak-positive pattern that LOCAL adv pass-5 escalated to MEDIUM for AC-004's discover_count guard. Validation: with `postcompact-reanchor.sh` present and non-empty the gate PASSES (both pre-assertion satisfied and BYPASS_HITS=0); if the file were absent `[ -s "$SCAN_TARGET" ]` exits non-zero and emits the FAIL loud, causing the wrapping bats `refute_output --partial "FAIL"` assertion to RED.

**Gate scope — advisory-log variable-path append (F-P1-002):** The postcompact-reanchor.sh hook contains the line `printf '%s\n' "$json_line" >> "$log_file" 2>/dev/null || true` (line 112). This append is intentionally fail-open: the log is an advisory diagnostic channel (BC-7.07.002 Inv1 / PC5 / EC-005) — the hook NEVER commits or pushes based on its result, and a log-write failure must not abort the hook. This is NOT a load-bearing write. The gate's regex `>> .+\.jsonl` targets a LITERAL jsonl path token and does NOT match the variable-form `>> "$log_file"` — so this line is correctly excluded from gate scope by regex shape, not by the exclusion rationale alone. Variable-path advisory appends are out of gate scope by design. Adding a broader regex to catch `>> "$log_file"` would create a false-positive on a legitimately fail-open write. A GENUINE load-bearing write would use a literal or well-known path (e.g., `>> .factory/logs/dispatcher.jsonl`), not an advisory-log variable.

**Test (bats):** `test_e18_hook_scripts_no_bypass_on_load_bearing_writes()`

### AC-005 (gate assertion — cross-reference title-cite parity: story frontmatter BC IDs match actual BC H1 titles)

For each story in the E-18 set (S-18.00 through S-18.09) that has a non-empty `behavioral_contracts:` frontmatter array, verify that each BC ID in the array corresponds to a BC file whose H1 heading is cited correctly in the story's `## Behavioral Contracts` table row.

The gate cannot verify the exact prose match programmatically, but it CAN verify:
1. Each BC ID in `behavioral_contracts:` matches the pattern `BC-\d+\.\d{2}\.\d{3}`.
2. A BC file for that ID exists in the spec tree.
3. The BC file's H1 heading contains the BC ID (either `# BC-NNN: Title` or `# Behavioral Contract BC-NNN: Title` form).

**Gate scope — extraction design (frontmatter-array-scoped; both YAML forms handled):**
The extraction MUST capture ONLY the `behavioral_contracts:` frontmatter array members and NEVER body prose. Two frontmatter forms exist in the corpus:
- **Multi-line YAML:** `behavioral_contracts:\n  - BC-X.XX.XXX\n  - BC-Y.YY.YYY`
- **Inline list:** `behavioral_contracts: [BC-1.13.001]` or `behavioral_contracts: ["BC-X"]`

An awk with print-key-line-then-flag-continuation handles both forms. The `[]` empty-array guard (`if (/\[\]/) { next }`) prevents a `# BC status:` comment line (which does not match `/^[a-z_]+:/`) from being scanned as a continuation. ### AC-008 (gate assertion — O-P4-004 process gap: mandatory pre-`status:ready` AC↔PC parity gate — every AC trace in an E-18 story resolves to a real BC clause heading)

**Context:** The AC↔PC mis-numbering defect recurred across S-18.02 (pass-3 fix), S-18.04a (earlier fix), S-18.04b (pass-4 finding). This is a POLICY 5 v1.3.3 sibling-sweep failure. The root cause is the absence of a machine-checkable gate that verifies every `(traces to BC-X.XX.XXX PC-N / INV-N)` parenthetical in an E-18 story body resolves to an actual numbered clause in the cited BC file. This gate closes the process gap permanently.

For every E-18 story that has a non-empty `behavioral_contracts:` frontmatter array, the gate MUST:
1. Extract every `(traces to BC-X.XX.XXX PC-N ...)` and `(traces to BC-X.XX.XXX INV-N ...)` parenthetical from the story's body.
2. For each cite, locate the BC file, grep the `## Postconditions` or `## Invariants` section, and verify that the cited clause number `PC-N` / `INV-N` has a corresponding numbered item in that section.
3. Fail (exit non-zero) if any AC cites a PC or INV number that does not exist in the BC's numbered clause list.

**Definition of "resolves":** A clause cite resolves when the corresponding clause heading is present in the BC file's relevant section. Four label forms are supported:

1. **Numeric:** `postcondition 1`, `postcondition 2a`, `invariant 3`. Resolves if `## Postconditions` (or `## Invariants`) section contains a line beginning `^N\. ` or `^Na\. ` (1-based integer, optional lowercase letter suffix).

2. **PC-letter (BC-4.15.001 scheme):** `postcondition PC-A`, `postcondition PC-B-B1`, `postcondition PC-D`. Resolves if `## Postconditions` section contains a line matching `(^\*\*PC-A\*\*|^### PC-A|^PC-A[ :])` — i.e., the BC uses bold (`**PC-A**`) or heading (`### PC-A`) or bare (`PC-A:`) label form. Do NOT renumber these to integers; the BC uses letter labels.

3. **PC-numeric (stripped):** `postcondition PC1`, `postcondition PC2`. The gate strips the `PC` prefix and resolves as numeric form 1. This covers BCs where the story mistakenly wrote `PC1` instead of `1` but the BC actually uses numeric clause numbering.

4. **Keyword-less (F-P1-001):** `(traces to BC-X.XX.XXX PC-N ...)` or `(traces to BC-X.XX.XXX INV-N ...)` — the citation uses a `PC-N` or `INV-N` token directly after the BC-ID with NO `precondition`/`postcondition`/`invariant` keyword. Real merged stories use this form: `S-18.13` lines 144/147/158/164 use `(traces to BC-5.41.001 PC10 ...)` and `(traces to BC-5.41.002 PC6 ...)`; `S-18.04a-precompact-flush-sh-core.md:343` uses `(traces to BC-7.07.001 PC4; ...)`. The gate infers CLAUSE_TYPE from the token prefix: `PC...` → postconditions section; `INV...` → invariants section. The RAW_LABEL is the token itself (e.g., `PC10`, `INV-1`) and is processed by the existing `_resolve_clause` normalization (PC-letter / PC-numeric / numeric forms). Without this form the gate passes vacuously for S-18.13 because none of its AC headers use the `postcondition`/`invariant` keyword.

A cite for `postcondition PC-A` when the BC has no `PC-A` heading MUST fail. A cite for `postcondition 4` when the BC has only 3 postconditions MUST fail. A cite for "postcondition 2a" resolves if `## Postconditions` contains a line beginning `^2a\. `. A keyword-less cite `PC10` where BC-5.41.001 `## Postconditions` has no line beginning `^10\. ` MUST fail.

**Gate scope (F-P8-004; fenced-code-block exclusion F-P10-003; keyword-less form F-P1-001):** This gate covers `(precondition|postcondition|invariant)` cite forms AND keyword-less `PC-N`/`INV-N` cite forms (CLAUSE_TYPE inferred from token prefix). AC traces of the form `(traces to BC-X edge case EC-NNN)` and `(traces to VP-090 section N)` are NOT in scope for this gate — they are not gated by this check. Future gate axis for EC cites is desirable but out of scope for E-18.

**Fenced-code-block exclusion (F-P10-003):** Before extracting `(traces to ...)` parentheticals from the AC section, the gate strips all fenced code block content (lines between ` ``` ` delimiters inclusive) via an awk fence-toggle pass. This prevents worked-example cite strings that appear in the gate's own documentation code block (e.g. the `#   Single:` / `#   Compound:` comment lines in AC-008's bash fence) from being extracted as real AC traces. Only real AC body prose outside code fences is scanned. S-18.09 is NOT excluded from the scan set — the fence-stripping fix is general and applies to any story whose AC section contains fenced code blocks with illustrative cites.

**Machine-checkable assertion (compound-cite-aware — F-P9-002; AC-section-scoped — F-P9-003; fenced-code-block-stripped — F-P10-003; awk flag form — F-P8-001; printf path — F-P8-005; multi-separator split `+;,` — O-P12-001; keyword-less PC-N/INV-N form — F-P1-001):**
```bash
# For each E-18 story with behavioral_contracts, resolve EVERY clause cite in every
# (traces to ...) parenthetical, including compound cites on a single AC line.
#
# Compound cite forms handled (F-P9-002; O-P12-001):
#   Single:   "(traces to BC-4.15.001 postcondition PC-B-B1)"
#   Compound: "(traces to BC-4.15.001 postcondition PC-B-B1 + postcondition PC-B-B2)"
#             "(traces to BC-5.41.001 invariant 2 + BC-5.41.002 postcondition 5)"
#             "(traces to BC-7.07.001 postcondition 6b — push failure exit 2; postcondition 5 — push success exit 0)"
#             "(traces to BC-X.XX.XXX postcondition N, postcondition M)"
#
# Keyword-less cite forms handled (F-P1-001):
#   "(traces to BC-5.41.001 PC10 — four-step agent-orchestrated flow)"
#   "(traces to BC-5.41.002 PC6 — ONE atomic git commit)"
#   "(traces to BC-7.07.001 PC4; ADR-028 §Decision 13)"
#   "(traces to BC-5.41.001 PC10 EPIC-COMPLETE arm + BC-5.41.002 PC6 — ...)"
#   CLAUSE_TYPE inferred from token prefix: PC... → postconditions; INV... → invariants.
#   The RAW_LABEL is the full PCN/INV-N token; _resolve_clause normalizes it.
#
# Approach: extract the full (traces to ...) parenthetical content, split on '+', ';', and ',',
# carry forward the most-recently-seen BC-ID so bare clause segments resolve
# against the correct BC.
# All three delimiters (+, ;, ,) are treated as equivalent segment separators (O-P12-001).
#
# Scan scope (F-P9-003 + F-P10-003): Acceptance Criteria section ONLY, with
# fenced code blocks stripped before extraction.
# Flag-form awk scopes extraction to the ## Acceptance Criteria section body,
# preventing EC-008 worked-example cites in ## Edge Cases from being extracted
# as real AC traces (F-P9-003).
# A second awk fence-toggle pass strips content between ``` delimiters,
# preventing worked-example cites inside the gate's own bash code block
# (e.g. the "# Single: (traces to ...)" comment lines in AC-008) from being
# extracted as real AC traces (F-P10-003).
#
# Clause label forms supported:
#   - Numeric:           "postcondition 1", "postcondition 2a", "invariant 3"
#   - PC-prefix numeric: "postcondition PC1", "postcondition PC2"  (strip "PC")
#   - PC-letter:         "postcondition PC-A", "postcondition PC-B-B1" (BC-4.15.001)
#   - INV-prefix:        "invariant INV-1", "invariant INV2"
#   - Keyword-less:      "PC10", "PC6", "PC4", "INV-1" (F-P1-001 — no keyword before label)
#
_resolve_clause() {
  # Args: BC_ID CLAUSE_TYPE RAW_LABEL STORY_FILE
  local BC_ID="$1" CLAUSE_TYPE="$2" RAW_LABEL="$3" STORY_FILE="$4"
  # Normalize label
  local NORM_LABEL LABEL_FORM
  if echo "$RAW_LABEL" | grep -qiE "^PC-[A-Z]"; then
    NORM_LABEL="$RAW_LABEL"; LABEL_FORM="letter"
  elif echo "$RAW_LABEL" | grep -qiE "^PC[0-9]"; then
    NORM_LABEL=$(echo "$RAW_LABEL" | sed 's/^[Pp][Cc]//'); LABEL_FORM="numeric"
  elif echo "$RAW_LABEL" | grep -qiE "^INV-?[0-9]"; then
    NORM_LABEL=$(echo "$RAW_LABEL" | sed 's/^[Ii][Nn][Vv]-\{0,1\}//'); LABEL_FORM="numeric"
  else
    NORM_LABEL="$RAW_LABEL"; LABEL_FORM="numeric"
  fi
  # Build BC file path (F-P8-005)
  local BC_SS BC_SS_DIR BC_FILE
  BC_SS=$(echo "$BC_ID" | grep -oE "^BC-([0-9]+)" | grep -oE "[0-9]+")
  BC_SS_DIR=$(printf "ss-%02d" "$BC_SS")
  BC_FILE=".factory/specs/behavioral-contracts/${BC_SS_DIR}/${BC_ID}.md"
  [ -f "$BC_FILE" ] \
    || { echo "FAIL: $STORY_FILE cites $BC_ID but file not found at $BC_FILE"; return; }
  # Determine section heading
  local SECTION_HEAD="## Postconditions"
  [ "$CLAUSE_TYPE" = "invariant" ] && SECTION_HEAD="## Invariants"
  [ "$CLAUSE_TYPE" = "precondition" ] && SECTION_HEAD="## Preconditions"
  # Clause existence check — flag form (F-P8-001)
  # BC section is fence-stripped before the clause-heading grep (O-P2-003): the
  # fence-toggle awk removes content between ``` delimiters so that an N.-prefixed
  # line inside a BC code fence cannot false-positive-match a clause heading. This
  # is false-positive-only hardening — it cannot break a currently-resolving cite.
  local FOUND
  if [ "$LABEL_FORM" = "letter" ]; then
    FOUND=$(awk "/^${SECTION_HEAD}/{f=1; next} /^## /{f=0} f" "$BC_FILE" \
      | awk '/^```/{fence=!fence;next}!fence' \
      | grep -cE "(^|\*\*)${NORM_LABEL}(\*\*|[: ])")
  else
    FOUND=$(awk "/^${SECTION_HEAD}/{f=1; next} /^## /{f=0} f" "$BC_FILE" \
      | awk '/^```/{fence=!fence;next}!fence' \
      | grep -cE "^${NORM_LABEL}\. ")
  fi
  [ "$FOUND" -gt 0 ] \
    || echo "FAIL: $STORY_FILE cites $BC_ID ${CLAUSE_TYPE} ${RAW_LABEL} (normalized: ${NORM_LABEL}) but clause not found in BC ${SECTION_HEAD} section"
}

for STORY_FILE in .factory/stories/S-18.*.md; do
  # --- Non-vacuity check (POLICY 11 / TD-VSDD-059 anti-silent-inert) ---
  # BC_ARRAY extraction is unquoted-frontmatter-tolerant (F-P1-001): mirrors AC-005 awk,
  # handles quoted, unquoted, inline [...], and multiline YAML forms.
  HAS_BC=$(grep -oE "^behavioral_contracts:" "$STORY_FILE" | head -1 || true)
  if [ -n "$HAS_BC" ]; then
    BC_ARRAY=$(awk '
      /^behavioral_contracts:/{
        if (/\[\]/) { next }
        print; f=1; next
      }
      /^[a-z_]+:/{if(f) exit}
      f{print}
    ' "$STORY_FILE" | grep -oE 'BC-[0-9]+\.[0-9]+\.[0-9]+' || true)
    if [ -n "$BC_ARRAY" ]; then
      # Scope to AC section only (F-P9-003), then strip fenced code blocks (F-P10-003)
      AC_SECTION=$(awk '/^## Acceptance Criteria/{f=1; next} /^## /{f=0} f' "$STORY_FILE" \
        | awk '/^```/{fence=!fence;next}!fence')
      RAW_PARENS=$(printf '%s' "$AC_SECTION" \
        | grep -oiE '\(traces to [^)]+\)' 2>/dev/null || true)
      # Count parentheticals with a recognized clause reference — BOTH forms:
      #   (a) keyword form: contains precondition/postcondition/invariant
      #   (b) keyword-less form (F-P1-001): contains a PC-N or INV-N token after a BC-ID
      TRACES_KEYWORD=$(printf '%s' "$RAW_PARENS" \
        | grep -ciE '(precondition|postcondition|invariant)' || true)
      TRACES_KEYLESS=$(printf '%s' "$RAW_PARENS" \
        | grep -ciE 'BC-[0-9]+\.[0-9]+\.[0-9]+[[:space:]]+(PC|INV)-?[0-9]' || true)
      TRACES_CHECKED=$(( TRACES_KEYWORD + TRACES_KEYLESS ))
      [ "$TRACES_CHECKED" -gt 0 ] \
        || { echo "FAIL: $STORY_FILE has non-empty behavioral_contracts but TRACES_CHECKED=0 — gate is vacuously passing (notation not recognized)"; exit 1; }
    fi
  fi

  # --- Per-parenthetical compound-cite resolution (F-P9-002) ---
  # Scope to AC section only (F-P9-003), then strip fenced code blocks (F-P10-003)
  AC_SECTION=$(awk '/^## Acceptance Criteria/{f=1; next} /^## /{f=0} f' "$STORY_FILE" \
    | awk '/^```/{fence=!fence;next}!fence')
  # Extract each full (traces to ...) parenthetical
  while IFS= read -r PAREN; do
    [ -z "$PAREN" ] && continue
    # Strip outer parens and "traces to " prefix (case-insensitive)
    CONTENT=$(echo "$PAREN" | sed 's/^(//;s/)$//;s/^[Tt][Rr][Aa][Cc][Ee][Ss] [Tt][Oo] //')
    # Carry-forward BC-ID: the first segment always carries a BC-ID;
    # subsequent +/;/, segments may omit the BC-ID and inherit the prior one.
    CARRY_BC=""
    # Split on '+', ';', or ',' (O-P12-001: all three are valid segment separators)
    # Each segment may or may not carry a BC-ID
    while IFS= read -r SEG; do
      SEG=$(echo "$SEG" | sed 's/^ *//;s/ *$//')
      [ -z "$SEG" ] && continue
      # Check if this segment introduces a new BC-ID
      NEW_BC=$(echo "$SEG" | grep -oiE "BC-[0-9]+\.[0-9]+\.[0-9]+" | head -1)
      [ -n "$NEW_BC" ] && CARRY_BC="$NEW_BC"
      [ -z "$CARRY_BC" ] && continue
      # Extract clause type (precondition|postcondition|invariant) from this segment (keyword form)
      CLAUSE_TYPE=$(echo "$SEG" | grep -oiE "(precondition|postcondition|invariant)" \
        | head -1 | tr '[:upper:]' '[:lower:]')
      if [ -z "$CLAUSE_TYPE" ]; then
        # Keyword-less form (F-P1-001): infer CLAUSE_TYPE from PC-N / INV-N token after BC-ID.
        # Match a PCN / PC-N / INVN / INV-N token that appears directly in the segment
        # (possibly after the BC-ID or a space). PC... maps to postconditions; INV... to invariants.
        KEYLESS_TOKEN=$(echo "$SEG" | grep -oiE "(PC|INV)-?[0-9][0-9A-Za-z-]*" | head -1)
        if [ -n "$KEYLESS_TOKEN" ]; then
          case "$(echo "$KEYLESS_TOKEN" | tr '[:lower:]' '[:upper:]' | cut -c1-2)" in
            PC) CLAUSE_TYPE="postcondition" ;;
            IN) CLAUSE_TYPE="invariant" ;;
            *)  CLAUSE_TYPE="" ;;
          esac
          RAW_LABEL="$KEYLESS_TOKEN"
        fi
        [ -z "$CLAUSE_TYPE" ] && continue
      else
        # Keyword form: extract raw label as token immediately after the clause type keyword
        RAW_LABEL=$(echo "$SEG" | grep -oiE \
          "(precondition|postcondition|invariant) [^ )]+" \
          | grep -oE " [^ )]+$" | tr -d ' ')
      fi
      [ -z "$RAW_LABEL" ] && continue
      _resolve_clause "$CARRY_BC" "$CLAUSE_TYPE" "$RAW_LABEL" "$STORY_FILE"
    done <<< "$(echo "$CONTENT" | tr '+;,' '\n')"
  done <<< "$(printf '%s' "$AC_SECTION" | grep -oiE '\(traces to [^)]+\)' 2>/dev/null || true)"
done

## Architecture Compliance Rules

1. **Gate scan scope is specified exactly (no over-scanning):** Each AC's grep scan targets specific files, not the entire repository. Over-scanning produces false positives from unrelated content (e.g., historical lesson prose that describes the violation class while not committing the violation itself).
2. **Exclusion filters are required where specified:** AC-003 and AC-006 require exclusion filters. Omitting them causes false positives. The exclusion patterns are load-bearing parts of the gate specification.
3. **Empty discovery is a gate failure (L-F2-exhaustive-sweep-enumerate-and-count):** AC-004 validates that the S-18.08 discovery scan fails explicitly when the discovered BC set is empty. A vacuously-passing loop over an empty set is a specification violation.
4. **No write side effects:** The gate scans are read-only. If a gate assertion fails, the correct action is to route the finding to the owning specialist (product-owner for BC issues, test-writer for bats issues) — NOT to auto-fix in place.
5. **Forbidden dependencies:** The gate bats file MUST NOT import or depend on any E-18 WASM crate. These are the artifacts being scanned.
