# S-21.21: AMD-002 `legacy-bash-adapter` runtime-timeout wiring fix + bifurcated bash-adapter calibration (ADR-039 Phase 3b+3c; split seam 3 of 6 from S-21.11)

## Narrative

- **As a** factory pipeline operator whose registry-config `timeout_ms` calibration for the
  five `legacy-bash-adapter.wasm`-hosted validator plugins currently has **zero effect** on
  the bash subprocess's actual kill deadline
- **I want** `legacy-bash-adapter/src/lib.rs` to honor the registry's calibrated `timeout_ms`
  instead of the hardcoded `BASH_TIMEOUT_MS = 60_000` constant, and per-plugin
  `fuel_cap`/`timeout_ms` calibration for the five bash-adapter plugins measured against that
  wiring-fixed code path
- **So that** calibrating and raising the registry's `timeout_ms` is not a no-op — the
  necessary-but-not-sufficient gap ADR-039 §AMD-002 identifies is closed at the actual
  enforcement point, and S-21.24's flip of these five plugins rests on real, wiring-verified
  calibration evidence rather than a number that reaches nothing

## Context / Finding Summary

**The AMD-002 runtime-wiring gap (RATIFIED v1.10).** Calibrating and raising the registry's
`timeout_ms` for the five `legacy-bash-adapter.wasm`-hosted plugins has, as currently coded,
**zero effect** on the bash subprocess's actual kill deadline: `legacy-bash-adapter/src/lib.rs`
hardcodes `BASH_TIMEOUT_MS = 60_000` and passes that constant — not the registry's calibrated
`timeout_ms` — into `exec_subprocess.rs::run()`. Registry-config calibration (`timeout_ms`
set in `hooks-registry.toml`) is therefore **necessary but not sufficient**: the value must
also reach the real enforcement point. This is a distinct engineering task from calibration
itself (measuring the right number vs. wiring the right number through) — this story delivers
both, in the correct order (wiring first, calibration second), because pre-wiring calibration
measures the wrong mechanism.

**Safe ordering within this story (from S-21.11 v2.11's original DAG, nodes (B) and (C)):**

```
(B) AMD-002 RUNTIME WIRING                        — MUST precede (C)'s meaningful calibration
    wire registry timeout_ms through executor.rs → hook-sdk payload →
    legacy-bash-adapter (AC-013 / PC12)
        │  "meaningful calibration" edge: (C)'s time_consumed_ms measurements are only
        │  evidence of the REAL enforcement point once (B) has landed — pre-wiring,
        │  measuring against the hardcoded 60s backstop calibrates the wrong mechanism.
        ▼
(C) PER-PLUGIN timeout_ms CALIBRATION (5 bash-adapter plugins) — depends on (B)
    measure time_consumed_ms + fuel_consumed over corpus for the five
    bash-adapter plugins; set fuel_cap + timeout_ms (AC-007 / PC2,3,4 / Inv 8)
```

**Targeted `legacy-bash-adapter.wasm`-hosted plugins (fuel-axis necessary but NOT sufficient —
`timeout_ms` additionally required, AND the AMD-002 wiring fix must land for that `timeout_ms`
to mean anything at the real enforcement point):**
- `validate-factory-path-root` (PostToolUse, `on_error="block"`)
- `validate-input-hash` (PostToolUse, `on_error="block"`)
- `validate-template-compliance` (PostToolUse, `on_error="block"`)
- `validate-wave-gate-prerequisite` (**PreToolUse `^Agent$`**, `on_error="block"` — self-lock
  hazard; requires S-21.23's break-glass before/atomic-with its S-21.24-delivered fail-closed
  flip)
- `validate-pr-merge-prerequisites` (**PreToolUse `^Agent$`**, `on_error="block"` — self-lock
  hazard; same as above)

**This story does NOT flip any of these five plugins to `failure_policy = "fail-closed"`** —
it wires the enforcement point and produces the calibration evidence (`fuel_cap`/`timeout_ms`
values, recorded in the PR description) that S-21.24 uses to perform the actual flip
(three non-Agent plugins) once S-21.23's break-glass code is also merged (two Agent-gate
plugins).

bifurcated by adapter class (ADR-039 §Decision 1/2/3/4 v1.8 amendment, §AMD-001). BOTH of the

- `fuel_cap` set to `max(observed_max × 1.5, 50_000_000)` for the adapter's own marshaling

WRITTEN TO THE REGISTRY has no effect on the actual kill deadline until AC-013 lands
(BC-1.03.017 v1.18 Precondition 5) — so calibration performed pre-wiring is not evidence that
the resulting `hooks-registry.toml` state is protective. Devops-engineer MUST run (or re-run)

### AC-013: AMD-002 runtime-wiring fix — `legacy-bash-adapter` honors the registry's calibrated `timeout_ms` instead of the hardcoded `BASH_TIMEOUT_MS` constant (traces to BC-1.03.017 v1.18 PC12; ADR-039 §AMD-002, RATIFIED v1.10)

For any `[[hook]]` entry with `plugin = "hook-plugins/legacy-bash-adapter.wasm"` and
registry field `timeout_ms = X` (resolved via `RegistryEntry::timeout_ms(&defaults)`, which
already exists in `crates/factory-dispatcher/src/registry.rs`), a real dispatch that invokes
that plugin against a bash subprocess whose runtime exceeds `X` MUST have its subprocess
killed at approximately `X` — observed kill time within `X` plus the
`exec_subprocess.rs::run()` poll interval (~5 ms) — NOT at the current hardcoded 60,000 ms
(`legacy_bash_adapter::BASH_TIMEOUT_MS`). This is a distinct enforcement point from
wasmtime's `EPOCH_TICK_MS` (10 ms, `crates/factory-dispatcher/src/engine.rs`) — that ticker
governs guest-WASM epoch interruption and is unrelated to this host-level subprocess-kill
deadline; do not conflate the two.

**This is a GENERIC, adapter-level fix, not a per-plugin one.** The defect affects all 37
`legacy-bash-adapter.wasm`-routed `hooks-registry.toml` entries (ADR-039 §AMD-002 blast-radius
finding, v1.10), not only the five §Decision 2 plugins. `test_legacy_bash_adapter_honors_registry_timeout_ms`
MUST therefore be written generically against the adapter's wiring behavior (any
`legacy-bash-adapter.wasm`-hosted entry, exercised via a synthetic test registry entry), not
hardcoded to only the five targeted plugins — the fix is adapter-level. This story's
calibration scope (AC-007) remains the five named plugins only; AC-013 does not expand that set.

**Host-to-guest plumbing gap (this is what makes the defect possible).** The dispatcher-side
`RegistryEntry.timeout_ms(&defaults)` value is resolved and used to set the WASM store's
epoch deadline (`crates/factory-dispatcher/src/invoke.rs`), but it is NOT currently included
in the per-plugin JSON envelope (`payload_value` / `per_plugin_value`) that
`crates/factory-dispatcher/src/executor.rs`'s `execute_tier` and `spawn_async_plugin`
functions splice `plugin_config` onto before serializing to bytes and piping to the guest via
WASI stdin (confirmed: both functions currently insert only `"plugin_config"` into that JSON
map). The guest-facing `HookPayload` in `crates/hook-sdk/src/payload.rs` has no `timeout_ms`
field to receive it even if the host did send it. `legacy-bash-adapter/src/lib.rs::run_bash_via_host`
therefore has no host-known value to read and falls back to its own hardcoded constant.

**Implementer design choice (not prescribed by this story):** the exact host-to-guest channel
is an implementer decision — a new typed field on `HookPayload` (host-populated from the
dispatched `RegistryEntry`'s resolved `timeout_ms` at the same point `execute_tier`/
`spawn_async_plugin` already splice in `plugin_config`) is the natural mechanism, consistent
with the existing `plugin_config` precedent; an equivalent channel (e.g. injected into
`plugin_config` itself) is also acceptable. AC-013's assertion is BEHAVIORAL (observed kill
time), not mechanism-specific — do not write the test to assert a specific field name or code
path.

**POSITIVE control (the wiring fix's target behavior):** a `hooks-registry.toml`-equivalent
test entry hosted by `legacy-bash-adapter.wasm` with `timeout_ms = 2_000` (deliberately
short), invoked against a bash script that sleeps 10 s. The subprocess MUST be observed killed
at ≈2 s plus the `exec_subprocess.rs::run()` poll interval (~5 ms) — well under the hardcoded
60 s — proving the wiring fix reads and applies the registry's calibrated value rather than the
hardcoded constant. The dispatcher MUST report `PluginResult::Ok { exit_code: 1, .. }` (via
`adapter_logic`'s `HookResult::Error` mapping) for that invocation, **NEVER**
`PluginResult::Timeout { cause: TimeoutCause::Epoch }` — that variant is constructed only by
`classify_trap` on a genuine guest `Trap::Interrupt` and cannot fire while the guest is blocked
inside the synchronous `exec_subprocess` host call (BC-1.03.017 v1.18 PC12 correction, F-002).
PC12 owns the timing/wiring guarantee asserted here — that the kill fires at the registry's
calibrated `timeout_ms`, not the hardcoded constant; PC13 (this story's AC-013b below) owns the
complementary, non-redundant guarantee that for `on_error = Block` entries this resulting
`Ok { exit_code != 0 }` outcome is treated as a fail-closed block regardless of
`failure_policy`.

**NEGATIVE reference (the AMD-002 defect state — documented as the current/pre-fix baseline,
not a standing test that must continue passing):** under the CURRENT (pre-wiring-fix)
implementation, the same `timeout_ms = 2_000` entry invoked against the same 10 s-sleeping
script is NOT killed until ≈60 s, because `run_bash_via_host` passes its own hardcoded
`BASH_TIMEOUT_MS` constant to the host call, never the registry's `timeout_ms`. The wiring
fix's test MUST assert the POSITIVE behavior, and MUST fail against the pre-fix code path
(red-first against the current implementation, green only after this task's wiring fix
lands) — this is the Envoy #38801 discipline (Invariant 6) applied to the wiring fix itself:
the test drives the actual dispatch/subprocess path with a real short `timeout_ms` and a real
long-running script, not merely a unit-level assertion that adapter code reads a config
field.

**EC-011 (highest-risk defect window, CORRECTED per F-002):** a script running LONGER than the
calibrated `timeout_ms` but SHORTER than the hardcoded 60,000 ms constant (e.g.
`timeout_ms=30_000`, script runs 45 s) is, pre-fix, NOT killed at 30 s — but the outcome is
NONDETERMINISTIC, not a deterministic clean pass. Because `run_bash_via_host` passes the
hardcoded `BASH_TIMEOUT_MS=60_000` constant regardless of the registry's calibrated
`timeout_ms=30_000`, the dispatch surfaces as EITHER (a) `PluginResult::Ok { exit_code: 1, .. }`
via `adapter_logic`'s `HookResult::Error` mapping (if the bash script, `exec_subprocess`, or
the adapter's own marshaling encounters any error condition), OR (b) a guest-epoch
`PluginResult::Timeout { cause: TimeoutCause::Epoch }` race on control-return (if wasmtime's
independent `EPOCH_TICK_MS` guest-interruption ticker fires against the adapter's own WASM
execution once control returns from the blocking host call). In BOTH sub-cases the calibrated
30 s budget is silently violated with no fail-closed enforcement reaching `on_error=Block`
under PC1-PC12's pre-§AMD-003 rules. AC-013's test suite MUST include a case covering this
window (asserting the pre-fix nondeterministic-defect behavior as documentation, and the
post-fix kill-at-≈timeout_ms behavior — which blocks every sub-case, but by DIFFERENT
governing axes per outcome: the `Ok{exit_code != 0}` sub-case via this story's own AC-013b/PC13
under `on_error=Block` (`failure_policy`-independent); the `Timeout` sub-case via S-21.19's
AC-011(b)/PC1/PC6/PC10(b) under `failure_policy=FailClosed` (`on_error`-independent for the
exhaustion decision, assuming the plugin's steady-state `failure_policy=FailClosed`
annotation per PC9/AC-008 has landed via S-21.24) — NOT by `on_error=Block` alone in either
case — as the required green state) — see Edge Cases below.

- **Test:** `test_legacy_bash_adapter_honors_registry_timeout_ms()` — Cargo integration test
  driving the real dispatcher/`invoke_plugin` path against the actual
  `hook-plugins/legacy-bash-adapter.wasm` binary with a synthetic test registry entry
  (`timeout_ms = 2_000`) and a bash fixture script that sleeps 10 s; asserts observed kill
  time ≈2_000 ms (± the ~5 ms poll tolerance) and `PluginResult::Ok { exit_code: 1, .. }`
  reported (via `HookResult::Error`) — NEVER `Timeout{cause: Epoch}` (guest-trap-only variant,
  cannot fire inside the blocking `exec_subprocess` host call); MUST be written generically
  (parameterizable `timeout_ms`, not hardcoded to the five targeted plugins); documents the
  pre-fix NEGATIVE reference (≈60_000 ms kill regardless of `timeout_ms`) as a code comment or
  a `#[ignore]`d historical-baseline test, not a standing assertion; includes an EC-011 case
  (`timeout_ms=30_000`, script runs 45 s → pre-fix: NONDETERMINISTIC — `Ok{exit_code:1}` OR a
  guest-epoch `Timeout{Epoch}` race, never a deterministic clean pass / post-fix: killed ≈30 s)

### AC-013b (end-to-end leg): PC13 enforcement — `on_error = Block` fails closed on ANY plugin-reported error exit, not only a crash/timeout outcome (traces to BC-1.03.017 v1.18 PC13; ADR-039 §AMD-003, RATIFIED v1.11; closes S-21.11 v2.0 adversarial pass-1 BLOCKER F-S2111V2-P1-001)

**Leg-scope note (per `.factory/planning/S-21.11-decomposition-plan.md` §3):** AC-013b has two
legs. The UNIT-level leg (the `plugin_fail_closed`/decision-function predicate extension) is
owned by **S-21.19**, calibration-axis-agnostic, and MAY land before or concurrently with this
story's AC-013 wiring fix. This story owns the END-TO-END fixture leg only, which MUST land
AFTER this story's own AC-013 wiring fix is merged (a real `timeout_ms` overrun must actually
be enforced before its downstream block decision can be exercised realistically) AND after
S-21.19's unit predicate is available.

For any plugin dispatched with `on_error = OnError::Block`, if the plugin's outcome is
`PluginResult::Ok { exit_code, .. }` where `exit_code != 0`, the executor's block-decision
function (S-21.19's extended predicate) MUST return `true` (`block_intent = true`, dispatcher
exit code 2), REGARDLESS of `failure_policy`. This rule closes F-001 — a
`legacy-bash-adapter.wasm`-hosted plugin's bash-subprocess host-wall-clock timeout (this
story's AC-013 `exec_subprocess.rs::run()` poll-loop kill) does NOT produce
`PluginResult::Timeout { .. }` — it propagates as `PluginResult::Ok { exit_code: 1, .. }`
(see AC-013's own body for the full propagation chain).

- **Test (end-to-end fixture, owned here, gated on this story's own AC-013):** a real dispatch

## Edge Cases

| ID | Scenario | Expected Behavior |
|----|----------|-------------------|
| EC-005 | `lessons.md` validator post-flip exhausts on a >4000-line `lessons.md` (above D-442(e) hard limit) | This MUST NOT happen if calibration was run against ≥4000-line corpus; if it does, the calibration was insufficient and AC-007 was not met — surfaced to orchestrator |

| EC-011 | `legacy-bash-adapter.wasm`-hosted plugin's script runs LONGER than the calibrated `timeout_ms` but SHORTER than the hardcoded 60,000 ms constant (e.g. `timeout_ms=30_000`, script runs 45 s) — the highest-risk AMD-002/AMD-003 defect window | **Pre-wiring-fix (current implementation):** NOT killed at 30 s, but the outcome is NONDETERMINISTIC, not a deterministic clean pass — surfaces as EITHER (a) `PluginResult::Ok { exit_code: 1, .. }` via `HookResult::Error`, OR (b) a guest-epoch `Timeout{cause: Epoch}` race on control-return; in both sub-cases the calibrated 30 s budget is silently violated with no fail-closed enforcement under PC1-PC12's pre-§AMD-003 rules. **Post-wiring-fix + PC12 + PC13 (this story's AC-013 + AC-013b; assumes the plugin's steady-state annotation `failure_policy=FailClosed` per PC9/AC-008, delivered by S-21.24, in addition to its pre-existing `on_error=Block`):** PC12/AC-013 fixes the kill timing (killed at ≈30 s); whichever outcome results is blocked, but by DIFFERENT governing axes, NOT by `on_error=Block` alone: `PluginResult::Ok { exit_code: 1, .. }` (via `HookResult::Error`) is blocked by PC13/AC-013b under `on_error=Block` (`failure_policy`-independent); `PluginResult::Timeout { .. }` is blocked by PC1/PC6/PC10(b)/AC-011(b) (S-21.19) under `failure_policy=FailClosed` (`on_error`-independent for the exhaustion decision) — a `Timeout` does NOT block merely because `on_error=Block`; that requires `failure_policy=FailClosed`. The nondeterminism in WHICH outcome surfaces no longer has a safety impact under this `FailClosed` steady state (reached at S-21.24) — every sub-case now blocks, each via its own axis |

Edge cases EC-001–EC-004, EC-006–EC-009, EC-012–EC-014 are not cited by this story's owned
ACs; they are owned by S-21.19/S-21.22/S-21.23 respectively. The full 14-row table lives in
