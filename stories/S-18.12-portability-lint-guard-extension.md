## Acceptance Criteria

### AC-001: bash 4+ feature detection — `local -A` / `declare -A` / `typeset -A` associative arrays
The portability-lint guard (bats test in `wave-handoff.bats` or a new dedicated `portability-lint.bats`) scans all `plugins/vsdd-factory/skills/wave-handoff/*.sh` scripts for unguarded use of `local -A`, `declare -A`, or `typeset -A` (`typeset` is a bash synonym for `declare` and equally creates bash-4+ associative arrays with `-A`). Hook scripts (`plugins/vsdd-factory/hooks/*.sh`) are OUT OF SCOPE for this guard — they are SS-07 (Hook Bash Layer) artifacts, not SS-06 skill scripts, and are not scanned by this guard. The detector catches all combined/prefixed flag forms: `-Ax` (associative+export), `-gA` (global+associative), and a lone `-A` at end-of-line, across all three keyword forms (`local`, `declare`, `typeset`). It does NOT flag `-a` (lower-case) — indexed arrays are bash-3-safe.

The detector comment-strips each scanned line (removes lines matching `^[[:space:]]*#`) before matching — a `declare -A`, `local -A`, or `typeset -A` token appearing only inside a comment is NOT flagged. This is parity with the guard-detection loop's existing comment-strip behavior; without it, a comment merely mentioning a removed array declaration (e.g., a refactor note reading `# declare -A my_map (refactored to indexed array below)`) would incorrectly trip the detector on benign code (adversary MAJOR-1 fix).

"Guarded" means a bash-4 version check of the form:
```
if [[ ${BASH_VERSINFO[0]} -lt 4 ]]; then ... fi
```
or equivalent (e.g., `if (( BASH_VERSINFO[0] < 4 ))`) is present in the **entrypoint** (`wave-handoff.sh`) that sources the lib, causing the script to exit before any array-using code path runs. The guard need not be in the same file as the declaration — it must be in the sourcing entrypoint, ahead of execution. A `local -A`, `declare -A`, or `typeset -A` in a `lib/*.sh` sourced by a guarded entrypoint is therefore safe and correctly PASSes; the entrypoint-level guard is sufficient and no per-lib guard is required.

"Unguarded" means the declaration is reachable via an execution path through an entrypoint that carries no such bash version check.

The test FAILS if any unguarded `local -A`, `declare -A`, or `typeset -A` is found. It PASSES when the entrypoint-level guard is confirmed present (covering all sourced libs), or when no associative arrays exist in the scanned scripts.

### AC-002: bash 4+ feature detection — `${var^^}`, `${var,,}`, `${var^}`, `${var,}` case modifiers, and `${var@U}` / `${var@L}` / `${var@u}` bash-4.4 `@`-operator transforms
The portability-lint guard scans for bash 4+ parameter expansion case modifiers: `${...^^}` (all-chars uppercase), `${...,,}` (all-chars lowercase), `${...^}` (first-char uppercase), and `${...,}` (first-char lowercase). All four forms require bash 4+. Coverage includes simple-variable forms (`${var^^}`, `${var,}`), array-element forms (`${arr[0]^^}`, `${map[k],,}`), and positional/special parameter forms (`${1^^}`, `${@^^}`, `${*^^}`, `${#^^}`). Additionally, the bash-4.4 `@`-operator transforms `${var@U}` (uppercase), `${var@L}` (lowercase), and `${var@u}` (first-char uppercase) are flagged — these require bash 4.4+ and are equally non-portable on macOS bash 3.2. The step-1 regex used by the detector is:
```
\$\{([a-zA-Z_][a-zA-Z0-9_]*|[0-9]+|[@*#])(\[[^]]*\])?(\^\^?|,,?|@[ULu])
```
These MUST either be absent or guarded by a bash version check. The test FAILS if any unguarded instance is found.

### AC-003: global IFS mutation detection
The portability-lint guard scans for `IFS=` assignments in all of the following forms (all are flagged as global mutations). The step-1 anchor regex used by the detector is:
```
(^|;|&&|&|[|][|]|(then|do|else|elif)[[:space:]]|\{[[:space:]]+|[)][[:space:]]+)[[:space:]]*(export[[:space:]]+|readonly[[:space:]]+|declare[[:space:]]+-g[[:space:]]+)?IFS=
```

Covered leading-anchor positions (all matched by the regex above):
- Bare `IFS=` at script scope (anchored by `^`)
- Second-statement form: `cmd; IFS=` (anchored by `;`) — includes `IFS='|'; read x` (global mutation followed by read, distinct from the exempt command-prefix form `IFS=... read`)
- Conditional-operator form: `cmd && IFS=` (anchored by `&&`) or `cmd || IFS=` (anchored by `||`)
- Single-ampersand background form: `cmd & IFS='|'` (anchored by `&` — the background operator runs the left-hand command asynchronously but does not create a subshell for the right-hand side; IFS set after `&` on the same logical line mutates the parent shell)
- Keyword-prefixed form: `then IFS=` / `do IFS=` / `else IFS=` / `elif IFS=` (anchored by the respective shell keyword followed by whitespace — these keyword positions are current-shell continuations; an IFS assignment here is a global mutation visible to subsequent commands in the same shell)
- Brace-group form: `{ IFS=$'\n'; read x; }` (anchored by `{` followed by whitespace — brace group runs in current shell, so IFS assignment is a global mutation)
- Case-pattern-action form: `case $x in p) IFS='|' ;; esac` (anchored by `)` followed by whitespace — pattern-action body runs in current shell, so IFS assignment is a global mutation)

Prefixed modifier forms detected within any of the above anchor positions:
- `export IFS=`
- `readonly IFS=`
- `declare -g IFS=`

The following forms are explicitly exempt:
- `local IFS=` (locally scoped within a function)
- `while IFS= read` or `IFS=... read` command-prefix patterns (IFS scoped to a single command)
- Subshell `(IFS=...; command)` (subshell-scoped — IFS set inside `(...)` does NOT leak to the parent shell; this is why the `(` subshell position is intentionally excluded from the IFS anchor set. By contrast, AC-005 DOES anchor on `(` for jq detection because jq executing inside a subshell is still a forbidden jq invocation regardless of scoping — the hazard is the binary being called, not its environment mutations)

AC-003 anchors on current-shell command positions where an IFS assignment mutates the parent shell's IFS: line-start, `;`, `&&`/`||`/`&`, then/do/else/elif keywords, brace-group `{ `, and case-pattern-action `) `. A subshell `( ` is intentionally EXCLUDED because IFS set in a subshell does not leak to the parent. Each of these anchor choices is justified by the IFS scoping semantics alone — not by cross-reference to any other AC's anchor set.

The test FAILS if any flagged form is found. PASSES after confirming all IFS uses are locally scoped, command-prefix scoped, or subshell-scoped.

### AC-004: forbidden python/pip shell-out detection
Python (in any version-suffixed form: `python`, `python2`, `python3`, `python3.11`, `python3.12`, etc.) and pip (`pip`, `pip2`, `pip3`, `pipx`, and version-dotted forms like `pip3.11`, symmetric with python's dotted-version coverage) are forbidden in ANY execution position. Rationale (self-contained): SKILL.md 'Forbidden Dependencies' section explicitly forbids any language runtime beyond bash in wave-handoff scripts; PEP 668 makes a preflight check unable to install third-party packages on macOS GitHub Actions runners anyway; and macOS does not guarantee `python3` is present on all runner images. The correct fix for any detection is REMOVAL — replace with a POSIX-portable alternative (e.g., awk-based YAML/JSON parsing). There is NO preflight-acceptance path and NO stdlib exemption: even `python3 -c 'import json'` is a forbidden shell-out and must be removed.

The portability-lint guard scans for python/pip invocations in wave-handoff scripts across all syntactic contexts. The step-1 detector regex (`python_re`) is:
```
(^[[:space:]]*(python[0-9.]*|pip[0-9x.]*)([[:space:]]|$)|[|;&][[:space:]]*(python[0-9.]*|pip[0-9x.]*)([[:space:]]|$)|\$[(](python[0-9.]*|pip[0-9x.]*)([[:space:]]|$)|`(python[0-9.]*|pip[0-9x.]*)([[:space:]]|$)|(xargs|if|then|do|else|elif|while|until|time|env|command|sudo)[[:space:]]+(python[0-9.]*|pip[0-9x.]*)([[:space:]]|$)|xargs([[:space:]]+-[^[:space:]]+)+[[:space:]]+(python[0-9.]*|pip[0-9x.]*)([[:space:]]|$)|\{[[:space:]]*(python[0-9.]*|pip[0-9x.]*)([[:space:]]|$)|\)[[:space:]]*(python[0-9.]*|pip[0-9x.]*)([[:space:]]|$)|\([[:space:]]*(python[0-9.]*|pip[0-9x.]*)([[:space:]]|$))
```

This covers line-start, pipe/semicolon/ampersand separators, command substitution (`$(...)` and backtick), shell keywords (`if`/`then`/`do`/`else`/`elif`/`while`/`until`), command wrappers (`xargs`, `time`, `env`, `command`, `sudo`), brace-group (`{ `), case-pattern-action (`) `), and subshell (`( `) positions — mirroring the AC-005 jq coverage model.

If any python/pip invocation is found in any of these contexts, the test FAILS. The fix is REMOVAL — replace with a POSIX-portable alternative. There is no preflight-acceptance path. The canonical fix from S-18.01 (`--break-system-packages` workaround) is not accepted in new scripts.

### AC-005: undeclared jq runtime dependency detection
jq is a hazard in ANY execution position (including subshell) because jq is forbidden by the wave-handoff SKILL.md contract and must never appear; the correct fix for any detection is removal.

The portability-lint guard scans for `jq` invocations in wave-handoff scripts across all of the following syntactic contexts. The step-1 detector regex is:
```
(^[[:space:]]*jq([[:space:]]|$)|[|;&][[:space:]]*jq([[:space:]]|$)|\$[(]jq([[:space:]]|$)|`jq([[:space:]]|$)|(xargs|if|then|do|else|elif|while|until|time|env|command|sudo)[[:space:]]+jq([[:space:]]|$)|xargs([[:space:]]+-[^[:space:]]+)+[[:space:]]+jq([[:space:]]|$)|\{[[:space:]]*jq([[:space:]]|$)|\)[[:space:]]*jq([[:space:]]|$)|\([[:space:]]*jq([[:space:]]|$))
```

Covered execution positions (all matched by the regex above):
- Line-start position: `jq ...` (anchored by `^` with optional leading whitespace)
- After a pipe, semicolon, or single-ampersand: `... | jq ...` / `...; jq ...` / `... & jq ...` (anchored by `|`, `;`, or `&`)
- Command substitution: `$(jq ...)` (anchored by `$(`) or backtick form `` `jq ` `` (anchored by `` ` ``)
- After `&&` or `||` (conditional execution — covered by `[|;&]` alternation)
- Via `xargs`: `xargs jq ...` or with intervening options (`xargs -n1 jq`, `xargs -I{} jq ...`) (anchored by `xargs` keyword, with and without intervening option flags)
- Shell-keyword-prefixed: `if jq ...` / `then jq ...` / `do jq ...` / `else jq ...` / `elif jq ...` / `while jq ...` / `until jq ...` (anchored by the respective shell keyword)
- Command-wrapper-prefixed: `time jq ...` / `env jq ...` / `command jq ...` / `sudo jq ...` (anchored by the respective command wrapper)
- Brace-group position: `{ jq ...` (anchored by `{` followed by whitespace — jq executes in the current shell inside a brace group)
- Case-pattern-action position: `) jq ...` (anchored by `)` followed by whitespace — pattern-action body executes in the current shell)
- Subshell position: `( jq ...` (anchored by `(` followed by whitespace — jq executes in a subshell; the binary invocation is still a forbidden jq call regardless of the subshell boundary)

If any jq invocation is found in any of these contexts, the test FAILS. jq is forbidden in any execution position; the correct fix is REMOVAL — replace with a POSIX-portable alternative (e.g., pure-bash parsing, `awk`, or `sed`). There is no preflight-acceptance path. This mirrors AC-004's python forbidden-removal model: both Python and jq are forbidden by SKILL.md 'Forbidden Dependencies' section ("Python, jq, or any language runtime beyond bash"), and neither is acceptable with a preflight guard.

## Architecture Compliance Rules

1. **Static-analysis only, no script execution (preserves Pure classification):** The guard tests grep the script source files. They MUST NOT execute the wave-handoff scripts. Executing untested scripts in bats context creates test-isolation violations.
2. **Non-vacuity assertion (EC-005):** The guard must verify at least one `.sh` file was scanned. A grep that finds nothing because the scope is empty is a false-pass. Add an explicit `[[ $found_scripts -gt 0 ]]` check after the file discovery step.

5. **Additive, not replacing:** The new tests are added to `wave-handoff.bats` or a new `portability-lint.bats`. The existing PCRE guard test is NOT modified.
