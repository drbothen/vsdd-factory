## Narrative

As a CI maintainer or factory implementer writing bash scripts for wave-handoff or any hook,
I want the portability-lint bats guard to detect bash 4+-gated syntax, global IFS mutations, and undeclared runtime dependencies (Python/PyYAML, jq),
so that macOS CI failures caused by these issues are caught statically before code is merged — eliminating the class of runtime portability failures that required four emergency CI fixes in S-18.01's merge.

## Acceptance Criteria

### AC-001: bash 4+ feature detection — `local -A` / `declare -A` associative arrays
The portability-lint guard (bats test in `wave-handoff.bats` or a new dedicated `portability-lint.bats`) scans all `plugins/vsdd-factory/skills/wave-handoff/*.sh` scripts (and optionally all `plugins/vsdd-factory/hooks/*.sh` scripts) for unguarded use of `local -A` or `declare -A`. The detector catches all combined/prefixed flag forms: `-Ax` (associative+export), `-gA` (global+associative), and a lone `-A` at end-of-line. It does NOT flag `-a` (lower-case) — indexed arrays are bash-3-safe.

"Guarded" means a bash-4 version check of the form:
```
if [[ ${BASH_VERSINFO[0]} -lt 4 ]]; then ... fi
```
or equivalent (e.g., `if (( BASH_VERSINFO[0] < 4 ))`) is present in the **entrypoint** (`wave-handoff.sh`) that sources the lib, causing the script to exit before any array-using code path runs. The guard need not be in the same file as the declaration — it must be in the sourcing entrypoint, ahead of execution. A `local -A` or `declare -A` in a `lib/*.sh` sourced by a guarded entrypoint is therefore safe and correctly PASSes; the entrypoint-level guard is sufficient and no per-lib guard is required.

"Unguarded" means the declaration is reachable via an execution path through an entrypoint that carries no such bash version check.

The test FAILS if any unguarded `local -A` or `declare -A` is found. It PASSES when the entrypoint-level guard is confirmed present (covering all sourced libs), or when no associative arrays exist in the scanned scripts.

### AC-002: bash 4+ feature detection — `${var^^}`, `${var,,}`, `${var^}`, and `${var,}` case modifiers
The portability-lint guard scans for bash 4+ parameter expansion case modifiers: `${...^^}` (all-chars uppercase), `${...,,}` (all-chars lowercase), `${...^}` (first-char uppercase), and `${...,}` (first-char lowercase). All four forms require bash 4+. Coverage includes simple-variable forms (`${var^^}`, `${var,}`), array-element forms (`${arr[0]^^}`, `${map[k],,}`), and positional/special parameter forms (`${1^^}`, `${@^^}`, `${*^^}`, `${#^^}`). These MUST either be absent or guarded by a bash version check. The test FAILS if any unguarded instance is found.

### AC-003: global IFS mutation detection
The portability-lint guard scans for `IFS=` assignments in all of the following forms (all are flagged as global mutations):
- Bare `IFS=` at script scope
- `export IFS=`
- `readonly IFS=`
- `declare -g IFS=`
- Second-statement form: `cmd; IFS=` (IFS set immediately after another command on the same logical line) — includes `IFS='|'; read x` (global mutation followed by read, distinct from the exempt command-prefix form `IFS=... read`)
- Conditional-operator form: `cmd && IFS=` or `cmd || IFS=` (IFS assigned as the right-hand side of a short-circuit `&&` / `||` operator)
- Single-ampersand background form: `cmd & IFS='|'` (background the command, then assign IFS globally — the background operator `&` does not scope the IFS mutation; parity with AC-005's `& jq` detection)
- Keyword-prefixed form: `then IFS=` / `do IFS=` / `else IFS=` / `elif IFS=` (IFS assigned immediately after a shell keyword — parity with AC-005's keyword-prefix coverage)

The following forms are explicitly exempt:
- `local IFS=` (locally scoped within a function)
- `while IFS= read` or `IFS=... read` command-prefix patterns (IFS scoped to a single command)
- Subshell `(IFS=...; command)` (subshell-scoped)

The test FAILS if any flagged form is found. PASSES after confirming all IFS uses are locally scoped, command-prefix scoped, or subshell-scoped.

### AC-004: undeclared python/pyyaml runtime dependency detection
The portability-lint guard scans for the following invocation forms in wave-handoff scripts:
- `python`/`python2`/`python3`/`python3.11`/`python3.12` invocations that reference yaml or external packages (see EC-002 — python stdlib-only use such as `import json` is exempt from this AC)
- `pip`/`pip2`/`pip3`/`pipx install` invocations that reference pyyaml / external YAML packages
- Any install invocation referencing `pyyaml` or `PyYAML` (the match is case-insensitive, so the canonical PyPI package name `PyYAML` is detected alongside lowercase `pyyaml`)

If any are found, the script MUST have a corresponding preflight check that either:
- Verifies the interpreter and pyyaml are available before use (e.g., `python3 -c "import yaml" 2>/dev/null || ...` — versioned binaries such as `python3.11 -c "import yaml"` are equally acceptable as preflight forms), OR
- Is replaced with a POSIX-portable alternative (e.g., awk-based YAML key extraction).

The test FAILS if any flagged invocation is found without a preflight guard. The canonical fix from S-18.01 (`--break-system-packages` workaround) is NOT accepted as a long-term resolution in new scripts — proper preflight or removal of the dependency is required.

**EC-002 exemption applies:** `python3 -c "import json; ..."` or any invocation using only Python stdlib modules (no pyyaml or external package install) is PASS for this AC (see EC-002).

### AC-005: undeclared jq runtime dependency detection
The portability-lint guard scans for `jq` invocations in wave-handoff scripts across all of the following syntactic contexts:
- Line-start position: `jq ...`
- After a pipe, semicolon, or single-ampersand: `... | jq ...` / `...; jq ...` / `... & jq ...`
- Command substitution: `$(jq ...)` or backtick form
- After `&&` or `||` (conditional execution)
- Via `xargs`: `xargs jq ...` or with intervening options (`xargs -n1 jq`, `xargs -I{} jq ...`)
- Shell-keyword-prefixed: `if jq ...` / `then jq ...` / `do jq ...` / `else jq ...` / `elif jq ...`
- Command-wrapper-prefixed: `time jq ...` / `env jq ...` / `command jq ...` / `sudo jq ...`

If any are found, the script MUST have a preflight check that verifies `jq` is installed (`command -v jq >/dev/null 2>&1 || { echo "jq required"; exit 1; }`). The test FAILS if a `jq` invocation in any of these contexts is found without a preflight guard.

### AC-006: extended guard is scoped to wave-handoff scripts and is not a false-positive source
The guard scans only `plugins/vsdd-factory/skills/wave-handoff/*.sh` (and optionally `plugins/vsdd-factory/hooks/*.sh`). It does NOT scan test fixtures or bats helper files, which intentionally contain negative test examples. The guard uses the same scope exclusion approach as the existing PCRE guard (scans the source scripts, not the test corpus).

### AC-007: existing PCRE shorthand guard is preserved and still passes
The pre-existing guard `test_BC_5_41_001_F_P11_001_bsd_portability_no_pcre_classes_in_grep_sed` continues to pass after S-18.12 changes. The new tests are additive; they do not modify or remove the existing guard.

## Architecture Compliance Rules

1. **Static-analysis only, no script execution (preserves Pure classification):** The guard tests grep the script source files. They MUST NOT execute the wave-handoff scripts. Executing untested scripts in bats context creates test-isolation violations.
2. **Non-vacuity assertion (EC-005):** The guard must verify at least one `.sh` file was scanned. A grep that finds nothing because the scope is empty is a false-pass. Add an explicit `[[ $found_scripts -gt 0 ]]` check after the file discovery step.
3. **Exclusion of fixture files:** The grep scope MUST NOT include `tests/fixtures/`, `tests/*.bats`, or other test-corpus files. Only production scripts in `plugins/vsdd-factory/skills/wave-handoff/` are in scope.
4. **`set -euo pipefail` in all new bash code** (CLAUDE.md convention; applies to any helper scripts used within the bats tests).
5. **Additive, not replacing:** The new tests are added to `wave-handoff.bats` or a new `portability-lint.bats`. The existing PCRE guard test is NOT modified.

## Library and Framework Requirements

- bash (for bats tests running the grep commands)
- GNU grep or BSD grep with ERE (`grep -E`); only POSIX character classes used
- bats-core: existing version in `plugins/vsdd-factory/tests/`
- No new tool dependencies
