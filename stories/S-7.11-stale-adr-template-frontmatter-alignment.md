# S-7.11 — Stale ADR template frontmatter alignment — document_type and level field correction

**Epic:** E-7 — Process Codification (Self-Improvement)
**Source:** F-ADR032-P1-008, adr-032-cascade-log.md, D-869 item (6)(c)
**Owner:** spec-steward (template alignment is spec governance, not architecture content)
**Priority:** P2 (defect-prevention; small scope; no runtime behavior change — affects only newly created ADRs)
**Subsystem anchor:** SS-08 (Template Catalog)

## Narrative

- **As a** vsdd-factory architect creating a new ADR using `plugins/vsdd-factory/templates/adr-template.md`
- **I want** the template to carry the canonical `document_type: architecture-decision-record` and `level: L3` frontmatter fields
- **So that** every ADR created from the template is immediately compliant with the hook chain's frontmatter validation, and the ADR-032 class of defect cannot recur from a stale template

ADR-032's original draft was authored with `document_type: adr` instead of
`document_type: architecture-decision-record`. The `level: L3` field was absent entirely.
Both defects were caught by the adversary in pass-1 as F-ADR032-P1-008 ("Frontmatter
convention drift"). The root cause is the template itself: `adr-template.md` carries the
stale Bash-style shorthand `document_type: adr` and omits `level: L3`.

Every sibling ADR in `.factory/specs/architecture/` that was NOT authored from the template
uses `document_type: architecture-decision-record` and carries `level: L3`. The template is
the divergent artifact. Aligning it is a 2-field change with no prose content modifications.

Sibling check: a bats test must verify the template's canonical values so future template
editing cannot silently reintroduce the drift.
