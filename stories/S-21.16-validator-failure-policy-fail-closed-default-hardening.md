# S-21.16: Validator-class failure_policy CI lint + fail-closed global-default hardening (ADR-039 §Consequences residual risk — CWE-636 follow-up)

## Narrative

- **As a** factory plugin author and pipeline operator
- **I want** CI to fail if any plugin classified as validator-class in `hooks-registry.toml`
  lacks an explicit `failure_policy` field, and optionally to have the dispatcher global
  default flipped from `fail-open` to `fail-closed` once the Phase 3+4 migration is complete
- **So that** a future plugin author who omits `failure_policy` is caught at PR time rather
  than silently inheriting fail-open behavior, eliminating the CWE-636 "Not Failing Securely"
  residual risk documented in ADR-039 v1.3 §Consequences

## Context / Finding Summary

ADR-039 v1.3 §Consequences (Negative) documents the following residual risk after Phase 1
(schema extension, S-21.10) and Phase 3+4 (per-plugin calibration + enforcement flip,
S-21.11):

> "The Phase-1 default (`absent failure_policy` = `fail-open`) is the safe migration choice
> but creates a footgun: a future validator-class plugin author who omits `failure_policy`
> silently inherits fail-open behavior and reintroduces CWE-636. Secure-by-default would set
> fail-closed as the global default; this ADR preserves fail-open for migration safety. The
> hardening path is tracked as **S-21.16** — a follow-up CI lint requiring explicit
> `failure_policy` on every validator-class plugin entry and/or a global-default flip to
> fail-closed post-migration."

ADR-039 Decision 1 defines the migration-window behavior: `absent failure_policy` = treat
as `fail-open`. Decision 2 specifies the `failure_policy` field semantics. ADR-039 also
states explicitly that the Phase-1 fail-open default **MUST NOT** be changed before Phase
3+4 (S-21.11) completes, because without per-plugin fuel-cap calibration every large-artifact
write by a validator-class plugin would exhaust fuel and fail-closed, causing a hard
unconditional block on every write.

This story is the hardening follow-up. It presupposes S-21.11 has shipped (calibrated fuel
caps + enforced `failure_policy = "fail-closed"` on all existing validator-class plugins).
The risk being closed: a future plugin author adds a new validator-class plugin without the
`failure_policy` field, and the pipeline silently approves writes the new plugin should block.

**CWE reference:** CWE-636 "Not Failing Securely (Failing Open)".

**Hard ordering constraint:** `depends_on: [S-21.11]`. S-21.16 MUST NOT merge before
S-21.11. Specifically, the CI lint must not be introduced before all existing validator-class
plugins carry explicit `failure_policy` annotations — otherwise the lint would immediately
fail on the existing entries and block CI.

## Ordering Constraint

This story carries `depends_on: [S-21.11]`. This is a HARD sequencing gate, not a soft
preference:

1. S-21.11 (Phase 3+4) adds explicit `failure_policy = "fail-closed"` annotations to all
   existing validator-class plugins in `hooks-registry.toml`.
2. Only after S-21.11 merges do all existing validator-class entries carry explicit
   `failure_policy` — at which point the CI lint can be introduced without immediately
   failing on pre-existing entries.
3. The global default flip (Mechanism B below) similarly requires Phase 3+4 to complete
   so that advisory-class plugins (which legitimately remain fail-open) are not
   inadvertently broken.

Do NOT collapse this story into S-21.11 scope. S-21.11 is already authoring the
per-plugin calibration and enforcement flip; adding an opt-in-annotation lint and/or
global-default flip to that story would expand its scope and risk destabilizing the
Phase 3+4 migration.

## Scope

**Mechanism A (CI lint gate — REQUIRED):**

Add a CI check (GitHub Actions job or cargo/bats test) that:
1. Reads `plugins/vsdd-factory/hooks-registry.toml`
2. Identifies all plugin entries with a `tier = "validator"` (or equivalent validator-class
   designation — confirm exact field name in hooks-registry.toml at implementation time)
3. Asserts every such entry carries an explicit `failure_policy` field
4. Fails CI (non-zero exit) if any validator-class entry lacks the field

This lint fires on every PR, ensuring no future validator-class plugin can be merged
without an explicit `failure_policy` declaration. Absent annotation = CI failure, not
silent fail-open.

**Mechanism B (global default flip — OPTIONAL, deferred pending human decision):**

After S-21.11 ships and all validator-class plugins carry `failure_policy = "fail-closed"`,
it becomes structurally safe to flip the dispatcher global default from `fail-open` to
`fail-closed`. This would mean `absent failure_policy` = fail-closed (not fail-open),
giving secure-by-default behavior.

However, this flip has broader blast radius: it affects ALL plugins (not just
validator-class), and advisory/observability plugins that currently rely on the
fail-open default would need explicit `failure_policy = "fail-open"` annotations to
preserve their behavior. The flip therefore requires an audit of all non-validator-class
plugins to confirm they carry explicit `failure_policy` annotations before the flip lands.

Per ADR-039 v1.3, the global default flip is tracked here but the decision to proceed is
deferred to human adjudication at S-21.11 close-out.

**Out of scope:**
- Per-plugin fuel-cap calibration (S-21.11 scope)
- Changes to the `failure_policy` serialization or dispatcher runtime logic (S-21.10/S-21.11)
- Backfilling `failure_policy` on existing entries (S-21.11 delivers these annotations)

### AC-001: CI lint job added — validator-class plugin entries require explicit failure_policy (traces to ADR-039 Decision 1 + CWE-636 residual risk)

A CI check (new GitHub Actions job, cargo test, or bats test) MUST exist that reads
`plugins/vsdd-factory/hooks-registry.toml`, identifies all validator-class plugin entries,
and fails (non-zero exit) if any such entry lacks an explicit `failure_policy` field.

The check MUST be triggered on every `pull_request` to `develop` or `main` with no
`paths:` filter on the workflow-level trigger (same pattern as the cargo-deny advisories
gate from S-21.12 AC-007).

### AC-002: All currently-known validator-class plugins carry explicit failure_policy before lint is activated (traces to ordering constraint — S-21.11 precondition)

Before the CI lint is activated, every validator-class plugin entry currently present in
`hooks-registry.toml` MUST carry an explicit `failure_policy` field. This is satisfied by
S-21.11 (Phase 3+4) delivering the annotations before S-21.16 merges. The lint MUST NOT
be merged before S-21.11 merges.

- **Test (structural):** `git log --oneline --ancestry-path S-21.11..HEAD` at merge time
  confirms S-21.11 is an ancestor of the S-21.16 merge commit.

### AC-003: (Conditional on Mechanism B decision) Global default flip documented and audited

IF the human decides to proceed with Mechanism B (global default flip to fail-closed):
- All non-validator-class plugins in `hooks-registry.toml` MUST carry explicit
  `failure_policy` annotations before the flip lands
- An audit report listing every plugin entry and its `failure_policy` classification
  MUST be included in the PR body
- ADR-039 MUST be updated to reflect the new global default and close the §Consequences
  (Negative) residual risk note

IF Mechanism B is deferred: a STORY-INDEX note and STATE.md Drift Items entry MUST be
added to track the open decision.
