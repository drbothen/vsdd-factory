# S-23.05: POLICY 7/8/14/17/19 enforcement wiring (`validate-cross-site-correspondence` INDEX-resolution extension)

## Narrative

- **As a** `validate-cross-site-correspondence` (BC-5.39.010) PostToolUse gate, which today compares an inline `vN.NN` token in a citing document against the target's frontmatter/INDEX version (Arm A1/A2/E1/E2 per its own doc comments)
- **I want** to be extended so its version-leg comparison resolves the citing document's stable ID through S-23.04's `resolve_version` INDEX-resolution mechanism, accepting a stable-anchor-only citation (no inline version) as correct-by-construction, while still detecting a genuinely mismatched *inline* version if one is present during the migration window
- **So that** the amended POLICY 7/8/14/17/19 semantics (stable-anchor citation, mechanically resolved version) have real enforcement machinery underneath them once state-manager applies the corresponding `policies.yaml` amendments at the ratification burst

## Context / Problem Statement

ADR-045 §Policy Amendments Required table describes five policies whose "version-leg" semantics
change under Tier 1: POLICY 7 (BC-table Version cell → stable ID only, parity gate resolves via
BC-INDEX), POLICY 8 (D-1080 TABLE-CELL-AWARE PARITY GATE recast as INDEX-resolution check),
POLICY 14 (5-leg parity gate's version-leg → stable-anchor + INDEX resolution), POLICY 17
(frontmatter parity gate's version fields → stable-anchor form), POLICY 19 (already-stable-anchor
for ADR cites, scope extended to all load-bearing positions). These five policies are currently
enforced primarily via `enforced_by: [adversary-prompt, consistency-validator, ...]` — i.e.,
agent-prompt-driven narrative checking — but POLICY 8's D-1080 TABLE-CELL-AWARE PARITY GATE and
POLICY 14's tripartite parity are also code-adjacent to the mechanical
`validate-cross-site-correspondence` (BC-5.39.010) gate, which today literally extracts and
compares inline version tokens (its own doc comments: "BC `version:` vs BC-INDEX.md row version
cell"; "story body BC-table version citations vs BC frontmatter"). ADR-045 §Migration Plan Phase
A step 3 requires INDEX-resolution to be implemented "wherever version-leg parity is checked —
POLICY 7/8/14/17 gates."

This story extends `validate-cross-site-correspondence`'s Arm A1/A2 (and any sibling code-enforced
parity path this story's implementer discovers touches inline-version comparison) so that: (a) a
citation with NO inline version token (the post-migration, stable-anchor form) is treated as
automatically correct — the parity check becomes "does this stable ID exist and is it the right
one," not "does this version number match" — and (b) a citation that STILL has an inline version
token (pre-migration form, present during the corpus migration window since S-23.06..S-23.13 land
document-class by document-class) continues to be checked against the resolved current version,
so the gate does not silently stop catching genuine staleness in not-yet-migrated files.

This story does **not** edit `.factory/policies.yaml` — POLICY 7/8/14/17/19's declarative text
amendments are state-manager's exclusive write path, applied at the ratification burst per
ADR-045 §Policy Amendments Required ("State-manager applies them to policies.yaml as part of the
ratification burst; no agent may apply them before ratification"). This story builds the code
machinery the amended policy text will describe.

## Acceptance Criteria

### AC-001
Given a story body BC-table cell citing `BC-1.03.017` with no inline version token,
`validate-cross-site-correspondence`'s Arm A2 check passes if `BC-1.03.017` exists in BC-INDEX
(via S-23.04's `resolve_version`), without requiring or checking any version number in the citing
cell. (traces to ADR-045 §Policy Amendments Required, POLICY 7 row, "Version cell contains the
stable BC identifier only... the parity gate resolves the current version from BC-INDEX at lint
time")

### AC-002
Given a story body BC-table cell citing `BC-1.03.017 v1.27` (pre-migration form, still present
during the migration window), Arm A2 continues to check that `v1.27` matches `resolve_version("BC-1.03.017")`'s
current answer and flags a mismatch exactly as it does today — this story does not weaken
detection of genuine staleness in not-yet-migrated files. (traces to ADR-045 §Migration Plan
Phase A, migration is phased per document class — mixed-corpus tolerance requirement)

### AC-003
Arm A1 (BC file `version:` vs BC-INDEX.md row version cell) is extended identically: this arm
already compares two *stable* locations (the BC's own frontmatter and its own INDEX row) rather
than a citing document's inline pin, so this story confirms via test that Arm A1's existing
behavior is unaffected by the Tier-1 migration (it is not a "citation" in ADR-045's sense — it is
the authoritative source, and continues unchanged). (traces to ADR-045 §Decision, Tier 1 — the
INDEX row itself remains the ground-truth version; this arm is explicitly out of scope for
behavior change)

### AC-004
Given a story `behavioral_contracts:` frontmatter entry in canonical stable-anchor-only form
(`BC-1.03.017`, no version suffix), all code paths that previously expected a version-suffixed
frontmatter entry (e.g., `"BC-1.03.017 v1.27"`, per current POLICY 19-adjacent convention observed
in S-21.25's frontmatter) accept the stable-anchor-only form without error. (traces to ADR-045
§Decision, Tier 1, "Permitted forms" bullet)

### AC-005
The extended gate's diagnostic output, when it does flag a mismatch, names the citing location,
the cited version (if any), and the resolved current version — matching S-23.03's AC-006
structured-diagnostic discipline (mechanical report, not narrative attestation). (traces to
ADR-045 §Rationale, "Tier 3 aligns with D-449(a)... the validator is a mechanical gate")

### AC-006
This story adds regression tests proving the extended gate still catches every pre-existing Arm
A1/A2/E1/E2 defect class documented in `validate-cross-site-correspondence`'s own test suite
(e.g., the BC-1.17.001/BC-2.07.001 last-wins hazard, escaped-pipe version chains) — the
INDEX-resolution extension must not regress any of the gate's existing coverage. (traces to
ADR-045 §Consequences, Positive — "Cohort re-anchoring eliminated by construction" must not come
at the cost of losing existing detection power)

### AC-007 (negative control)
Given a citation to a nonexistent stable ID (`BC-9.99.999`, no version token), the extended gate
still flags this as an error (S-23.04 AC-005/AC-008's "not found" case) — INDEX-resolution does
not make the gate permissive toward bad IDs, only toward absent version numbers on good IDs.
(traces to S-23.04 AC-005/AC-008; ADR-045 §Decision, Tier 1 — resolution must fail closed on an
unresolvable ID)
