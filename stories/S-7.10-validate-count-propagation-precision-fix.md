# S-7.10 — validate-count-propagation precision fix — scope regex to count-assertion contexts, WASM port per POLICY 21

**Epic:** E-7 — Process Codification (Self-Improvement)
**Source:** D-762 (pre-existing known false-positive), D-869 item (6)(c) ADR-032 cascade observation
**Priority:** P2 (quality-of-life and noise reduction; not a correctness blocker — false-positive fires after writes succeed, is advisory)
**Subsystem anchor:** SS-04 (WASM Plugin Tier) + SS-07 (Hook Bash/WASM Layer)

## Narrative

- **As a** vsdd-factory state-manager or story-writer editing ARCH-INDEX.md
- **I want** validate-count-propagation to fire only when an index file's canonical count-assertion rows change — not when changelog prose that happens to contain a number followed by "BCs" is edited
- **So that** every ARCH-INDEX changelog amendment (which is routine and frequent) does not produce a spurious count-propagation advisory, and genuine count drift is still caught reliably

`validate-count-propagation.sh` (S-7.02 deliverable) greps index files for patterns like
`\b[0-9]+ BCs\b` to detect count drift across ARCH-INDEX, BC-INDEX, and SS-NN subsystem files.
The known D-762 false-positive fires because ARCH-INDEX.md's `last_amended` and `Changelog`
sections contain prose like "E-18 BCs" or "28 BCs across 4 subsystems" in historical narrative
rows — not in the canonical count-assertion header row that actually matters.

During the ADR-032 cascade, every amendment to ARCH-INDEX (which received 24 version bumps
across the cascade) triggered this false-positive, flooding the session with advisory noise
and degrading the signal-to-noise ratio for genuine findings.

POLICY 21 (operator-level WASM policy) requires new hook plugins to be written in Rust and
compiled to WASM rather than as Bash scripts. Per S-7.02 precedent, validate-count-propagation
was shipped as a Bash hook as a pragmatic first implementation. This story ports it to
Rust/WASM with a precision-matched pattern that restricts detection to count-assertion contexts.

**Scope boundary — ARCH-INDEX WASM fuel exhaustion:** The related issue of
`validate-factory-path-root`, `validate-input-hash`, and `validate-template-compliance` WASM
plugins timing out on the 277 KB ARCH-INDEX file (fuel-budget exhaustion) is a DIFFERENT root
cause (WASM fuel limits, not regex pattern over-matching) and has an existing S-15.03
PRIORITY-A anchor. That issue is out of scope for this story; see TD D-442(e).

## Architecture Mapping

| Component | Module | Pure/Effectful |
|-----------|--------|----------------|
| WASM hook plugin (core logic) | `crates/hook-plugins/validate-count-propagation/src/lib.rs` | pure-core (pattern-match on diff content; no I/O beyond reading the Write payload from stdin) |
| count-assertion pattern matcher | `crates/hook-plugins/validate-count-propagation/src/pattern.rs` | pure-core (regex or structural parse of table rows) |
| Bash hook (superseded) | `plugins/vsdd-factory/hooks/validate-count-propagation.sh` | effectful-shell (replaced by WASM) |
| hooks-registry entry | `plugins/vsdd-factory/hooks-registry.toml` | effectful-shell (config; governs plugin dispatch at runtime) |

## Edge Cases

| ID | Scenario | Expected Behavior |
|----|----------|-------------------|
| EC-001 | ARCH-INDEX Changelog section contains a row like `\| v3.24 \| 2026-07-20 \| ... \| 6 BCs \|` (a table row inside the Changelog, not the canonical subsystem count table) | Plugin must NOT fire — Changelog table rows are historical, not count-assertion contexts; the plugin discriminates by section-header context |
| EC-002 | BC-INDEX.md `bc_count:` frontmatter field changes | Plugin SHOULD fire — frontmatter count-assertion fields are canonical count assertions, not prose |
| EC-003 | ARCH-INDEX.md subsystem table has a row with "5 BCs" in a non-count-assertion column (e.g., a notes column) | Plugin must evaluate context: if the pattern is in the canonical count column, fire; if in a notes column, do not fire |
| EC-004 | ARCH-INDEX WASM fuel exhaustion fires on the same Write that triggers validate-count-propagation | Both plugins run independently; fuel exhaustion in one does not affect the other; validate-count-propagation precision fix is orthogonal to the fuel-budget issue |

## Architecture Compliance Rules (MANDATORY)

| Rule | Source | Enforcement |
|------|--------|-------------|
| New hook plugins MUST be Rust/WASM, not Bash | POLICY 21 (operator-level WASM preference policy) | cargo build --target wasm32-wasip1 succeeds; hooks-registry.toml entry uses `.wasm` extension |
| WASM hooks read Write payload from stdin as JSON; must not make filesystem calls | WASM sandbox contract (host ABI); `crates/hook-sdk/` API | Rust code uses only hook-sdk host functions; no `std::fs` |
| Pure-core/effectful-shell boundary: count-assertion pattern matching is pure; registry update is effectful | VSDD architectural purity discipline | `src/lib.rs` and `src/pattern.rs` contain no `std::io` beyond host-function interface |
| hooks-registry.toml must be updated atomically with the WASM binary | TD-VSDD-053 single-commit-per-burst | Both registry change and compiled binary delivered in same commit |
