# S-25.04: Close validate-factory-path-staging Zero-Enforcement Gap — Real Layer-1 Production Trigger

## Narrative

- **As a** factory pipeline operator who was told (S-25.01) that `validate-factory-path-staging`'s
  fail-closed assignment closes the CWE-754 "cannot-complete-treated-as-PASS" hole for `.factory/`
  path-staging mutations
- **I want** that fail-closed assignment to have an ACTUAL production enforcement effect — a real
  trigger path that reaches `write_indeterminate_marker` and the next-advance gate when this
  validator's WASM execution cannot complete (fuel exhaustion, epoch timeout, or OutputTooLarge)
- **So that** the gap identified in ADR-047 v1.4 / BC-1.18.004 v1.2 (the assignment is safely SET
  but currently ENFORCES NOTHING — identical runtime effect to `failure_policy = "fail-open"`) is
  genuinely closed, not just correctly documented

## Context / Feature Summary

**Follow-up to S-25.01 (Layer 1), anchored per ADR-047 v1.4 §Decision 8a "Known Gap" note
(20bf81dd) and BC-1.18.004 v1.2 postcondition 4 (df3219ea) — both human-directed factual
corrections, routed from pr-reviewer's fresh-eyes MAJOR finding on PR #807, NOT a POLICY 22
design/security-model change.**

**The gap, precisely stated:** `validate-factory-path-staging` is registered in
`hooks-registry.toml` as `failure_policy = "fail-closed"`, PreToolUse `^Bash$`. The Layer-1
durable-marker write path (`write_indeterminate_marker`, invoked from the dispatcher's PostToolUse
handling per BC-1.18.001 invariant 4) fires **ONLY on a PostToolUse dispatch**. Because this
validator is registered PreToolUse, it structurally can never reach that write path — no matter
how many times its WASM execution fuel-exhausts, epoch-times-out, or trips OutputTooLarge, no
marker is ever written and no gate is ever triggered. Combined with `on_error = "continue"`
(which never blocks the *current* dispatch either, present or future) and this validator's
absence from the ADR-039 §Decision 2 six-validator exhaustion-leg roadmap (`validate-cross-site-
correspondence`, `validate-factory-path-root`, `validate-input-hash`, `validate-template-
compliance`, `validate-wave-gate-prerequisite`, `validate-pr-merge-prerequisites` — note this is
`validate-factory-path-**root**`, a DIFFERENT plugin from `validate-factory-path-**staging**`),
an INDETERMINATE outcome on this validator degrades to the identical advisory-only
`plugin.indeterminate` event that a `failure_policy = "fail-open"` plugin would produce. The
fail-closed config bit is real and correctly set; it currently enforces nothing.

**Why this matters:** `validate-factory-path-staging` was the ONE Cohort A validator originally
advertised (S-25.01 v1.1–v1.20, ADR-047 v1.0–v1.3) as immediately, unconditionally effective — no
S-21.24 calibration dependency, unlike the two `^Agent$` Cohort A-deferred validators. Discovering
that it, too, currently delivers zero enforcement means Layer 1's fail-LOUD guarantee has **no
live production trigger at all** as of S-25.01 merge — both effective-enforcement paths (this one
structurally inert, the other two S-21.24-gated) are dormant.

**Technical options for closure (carried forward from ADR-047 §Decision 8a "Known Gap" note;
architect adjudication in that ADR did not select among them — that is this story's F1/F2 scope):**

- **(a) — RECOMMENDED.** A NEW PostToolUse companion validator (e.g.
  `validate-factory-path-staging-write`, or equivalent naming TBD at F2) that mirrors
  `validate-factory-path-staging`'s `.factory/` path-staging check on the artifact-write side —
  i.e., actually registers PostToolUse for the write-completing event and therefore CAN reach
  `write_indeterminate_marker` on a genuine cannot-complete outcome. This activates the EXISTING
  marker + next-advance-gate mechanism (delivered by S-25.01) for real, rather than requiring any
  change to that mechanism. Lowest-risk option: reuses `indeterminate_marker.rs`,
  `validate-unvalidated-mutation-marker` (both gate arms), and the existing `classify_outcome` /
  `should_write_marker` pure-core functions verbatim — only a new WASM plugin crate + a new
  `hooks-registry.toml` entry are needed.
- **(c) — RECOMMENDED companion to (a).** Extend the ADR-039 §Decision 2 six-validator
  exhaustion-leg roadmap to add the new PostToolUse companion validator (from option (a)) as a
  seventh member, so its own resource-exhaustion calibration (fuel_cap / timeout_ms per ADR-039
  §Decision 3/4) is tracked through the same S-21.19→S-21.24 chain as the other six, rather than
  being an uncalibrated one-off. This does NOT require S-21.24 to merge before option (a)/(c) can
  be implemented and shipped in this story — S-21.24 is what eventually wires ADR-039 Phase 4
  CURRENT-DISPATCH-blocking enforcement for the six (now seven) named validators; the new
  companion validator's Layer-1 marker-write trigger (option (a)) is independent of that and
  activates immediately on this story's merge.
- **(b) — REJECTED as primary.** Changing `validate-factory-path-staging`'s own `on_error` from
  `"continue"` to a blocking variant. Rejected because it reopens the deliberate self-lock-
  avoidance design established in ADR-047 §Decision 8a's "Why the partition?" analysis (S-25.01):
  `on_error = "continue"` is precisely why this validator was judged "no self-lock risk" and safe
  to set fail-closed unconditionally, without an S-21.24 calibration dependency. Making it
  blocking would require its own fresh self-lock-risk re-analysis and its own POLICY 22
  human-ratified design-change justification — out of scope for a gap-CLOSURE story whose purpose
  is to activate the EXISTING mechanism, not redesign the crash-safety model. Evaluate only if F1
  delta analysis at activation finds option (a) infeasible.

**Subsystem anchor justifications:**
- SS-01 owns this story's primary scope because SS-01 is the Hook Dispatcher Core
  (executor.rs, indeterminate_marker.rs) per ARCH-INDEX Subsystem Registry; wiring a new
  PostToolUse callsite into the existing marker-write path is a dispatcher core responsibility,
  identical to the SS-01 anchor S-25.01 already established for the same `write_indeterminate_
  marker` / `classify_outcome` machinery this story reuses.
- SS-04 owns the new PostToolUse companion WASM plugin crate per ARCH-INDEX Subsystem Registry
  (SS-04 = Hook Plugin SDK and WASM plugin development) — option (a)'s companion validator is a
  new `crates/hook-plugins/` crate, the same subsystem anchor S-25.01 used for
  `validate-unvalidated-mutation-marker`.
- SS-07 owns `hooks-registry.toml` configuration per ARCH-INDEX Subsystem Registry (SS-07 = Hook
  Registry Configuration); the new companion validator's registry entry and the ADR-039
  §Decision 2 roadmap extension (option (c)) are both registry-config-adjacent changes.

**Dependency anchor justification:**
- S-25.04 depends_on [S-25.01] because S-25.01 delivers the entire mechanism this story activates:
  `write_indeterminate_marker`, `should_write_marker`, `classify_outcome`, the
  `validate-unvalidated-mutation-marker` two-arm gate plugin, and the Cohort A
  `failure_policy = "fail-closed"` registry assignment for `validate-factory-path-staging` itself
  (whose zero-enforcement gap this story closes). Without S-25.01 merged, there is no marker-write
  path for the new PostToolUse companion validator (option (a)) to trigger, and no gate for it to
  activate. S-25.04 does NOT depend on S-25.02/S-25.03 (Layers 2/3, different artifact-sharding and
  bounded-window concerns) or on S-21.24 for its own F1/F2/implementation scope — only option (c)'s
  eventual CURRENT-DISPATCH-blocking activation (via ADR-039 Phase 4 executor wiring) depends on
  S-21.24; the roadmap-registration act itself and option (a)'s marker-write trigger do not.

### AC-001: New PostToolUse companion validator reaches the existing marker-write path (traces to ADR-047 §D8a "Known Gap" note, option (a) — BC-TBD)

A new PostToolUse WASM validator (naming TBD at F2; e.g. `validate-factory-path-staging-write`)
MUST be registered in `hooks-registry.toml` for the event/tool pattern that corresponds to
completed `.factory/` path-staging writes, with `failure_policy = "fail-closed"`. On a genuine
cannot-complete outcome (fuel exhaustion, epoch timeout, or OutputTooLarge) for this validator,
the dispatcher MUST classify the outcome as `DispatchOutcome::Indeterminate` and MUST reach
`write_indeterminate_marker` — i.e., this is the first Layer-1 validator whose fail-closed
assignment has a structurally-reachable PostToolUse trigger.

### AC-002: Existing marker + gate mechanism is reused, not re-implemented (traces to ADR-047 §D8a "Known Gap" note — BC-TBD)

The new companion validator MUST NOT introduce a second marker file, a second gate mechanism, or
duplicate `classify_outcome` / `should_write_marker` logic. It reuses
`.factory/unvalidated-mutation.marker`, `write_indeterminate_marker`,
`validate-unvalidated-mutation-marker` (both existing gate arms), and the existing pure-core
classification functions from S-25.01 verbatim.

### AC-003: No behavioral change to `validate-factory-path-staging` itself (traces to ADR-047 §D8a "Known Gap" note — BC-TBD)

`validate-factory-path-staging`'s own registration (PreToolUse `^Bash$`, `on_error = "continue"`,
`failure_policy = "fail-closed"`) is UNCHANGED by this story. This story adds a companion
validator; it does not modify or replace the existing one. Option (b) (changing `on_error`) is
explicitly OUT OF SCOPE for the primary delivery (see Context §Technical options).

### AC-004: ADR-039 §Decision 2 roadmap extension (traces to ADR-047 §D8a "Known Gap" note, option (c) — BC-TBD)

ADR-039 §Decision 2's six-validator exhaustion-leg roadmap MUST be extended to name the new
PostToolUse companion validator (from AC-001) as a seventh member, with its own fuel_cap /
timeout_ms calibration tracked through the same ADR-039 §Decision 3/4 mechanism as the existing
six. This registration act does NOT require S-21.24 to have merged; it is independent of the
ADR-039 Phase 4 CURRENT-DISPATCH-blocking executor wiring that S-21.24 delivers for the full
seven-validator set.

### AC-005: Layer-1 effective fail-closed count increases from ZERO (traces to ADR-047 §D8a "Known Gap" note; BC-1.18.004 postcondition 4 amendment — BC-TBD)

After this story merges, S-25.01's Traceability documentation ("Layer-1 effective fail-closed
count at S-25.01 merge: ZERO") MUST be superseded by an updated statement reflecting the new
companion validator's live enforcement — this is the concrete, measurable closure criterion for
the gap ADR-047 v1.4 / BC-1.18.004 v1.2 identified. Product-owner amends BC-1.18.004 postcondition
4 accordingly at F2.

### AC-006: Full regression suite stays green (traces to ADR-047 §D7 backward-compat — BC-TBD)

`cargo test --workspace --all-targets` and `plugins/vsdd-factory/tests/run-all.sh` MUST stay
green after this story lands. `test_BC_1_18_004_fail_open_default_preserves_advisory_behavior`
(the DO-NOT-DELETE backward-compat guard test from S-25.01) MUST NOT be deleted or modified.
