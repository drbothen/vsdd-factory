# S-7.13 — Human merge gate for GitHub publish actions — replace AUTHORIZE_MERGE=yes protocol

**Epic:** E-7 — Process Codification (Self-Improvement)
**Source:** S-21.02 delivery process-gap (2026-07-24), cycle-closing checklist (S-7.02 / lessons-codification rule)
**Owner:** story-writer (playbook amendments) / spec-steward (pr-manager behavioral guidance)
**Priority:** P1 (process-gap; caused ~7h wall-clock delay during active S-21.02 delivery; same severity class as S-7.06–S-7.09)
**Subsystem anchor:** SS-05 (Pipeline Orchestration) + SS-06 (Skill Catalog)

## Narrative

- **As a** vsdd-factory orchestrator running the per-story delivery cycle
- **I want** the playbook to contain an explicit human-merge-gate step (instead of an AUTHORIZE_MERGE=yes flag) for the final `gh pr review --approve` and `gh pr merge` publish actions
- **So that** pr-manager never idle-loops or hard-blocks waiting for a permission grant that the Claude Code auto-mode classifier cannot deliver via teammate relay, and the human always receives a clear, actionable informed-consent prompt before any GitHub publish action executes

During S-21.02 delivery (2026-07-24), the per-story-delivery.md step 2f dispatched pr-manager
with `AUTHORIZE_MERGE=yes`. The Claude Code auto-mode permission classifier does not treat
teammate-relayed authorization as consent for GitHub publish actions (`gh pr review --approve`,
`gh pr merge`). Observed consequences:

- **pr-manager #1** wedged in an idle loop holding an open convergence gate, waiting for
  a permission grant that was never forthcoming.
- **pr-manager #2** hard-blocked twice against the same classifier wall.
- The orchestrator's own retry attempt was refused as a self-approval bypass.
- Resolution required the human to execute both commands directly after receiving an
  AskUserQuestion naming the two-party-review concern.
- Total wall-clock cost: approximately 7 hours.

The root cause is architectural: `AUTHORIZE_MERGE=yes` was designed to signal intra-agent
consent within the orchestrator's call graph, but the Claude Code harness enforces a
separate, outward-facing permission tier for GitHub publish actions that cannot be bypassed
by any agent dispatch instruction. The correct protocol is to:

1. Have pr-manager reach the merge-ready state (all gates passed: security + review + CI +
   deps + stale-verdict check) and then **surface a human-gate prompt** naming the exact
   GitHub publish actions pending and requesting explicit human consent.
2. Document an alternative settings allow-rule path for projects where the human prefers
   fully-automated merge (with informed-consent prerequisite documented in RELEASING.md).
3. Require pr-manager, when a publish action is blocked mid-execution, to **surface the
   verbatim block reason and hold** — never idle-loop or silently retry.
