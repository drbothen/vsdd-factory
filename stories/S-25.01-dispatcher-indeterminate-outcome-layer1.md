# S-25.01: Dispatcher INDETERMINATE Outcome Layer 1 — Fail-Loud on Cannot-Complete: Durable Marker + Next-Advance Gate

## Narrative

- **As a** factory pipeline operator whose validators run in fuel-bounded and epoch-bounded WASM
  sandboxes
- **I want** the dispatcher to make "couldn't validate" a FIRST-CLASS, fail-LOUD outcome that
  writes a durable `.factory/unvalidated-mutation.marker` file and blocks the next state-advancing
  Agent dispatch and `git commit`/`git push` Bash dispatch until the affected artifact is
  re-validated or an operator explicitly clears the marker
- **So that** the silent CWE-754 hole (treating INDETERMINATE as PASS) is permanently closed for
  `validate-factory-path-staging` (Cohort A-immediate; EFFECTIVE-NOW at S-25.01 merge) and
  pre-configured for `validate-pr-merge-prerequisites` and `validate-wave-gate-prerequisite`
  (Cohort A-deferred; SET-BUT-LATENT — set in registry with comment, enforcement conditional on
  S-21.24); existing ~76 fail-open plugins are completely unchanged (advisory
  `plugin.indeterminate` event only)

## Context / Feature Summary

**Layer 1 of the three-layer validation-integrity architecture (ADR-047 v1.3, human-ratified
2026-08-30). Delivered independently of S-21.19–S-21.24 (enforcement seams).**

Operational forensics driving this story (F1-delta-analysis.md §3):
- ~11,262 `plugin.timeout { cause: Fuel }` events in the event log
- ~480 `plugin.timeout { cause: Epoch }` events
- 167 `host_fn_returned_output_too_large` events (read path OutputTooLarge returning −3 to WASM)
- ~455 events where the entire validator suite wiped out on a single artifact edit

Current behavior: all three root causes (fuel exhaustion, epoch timeout, OutputTooLarge) are
treated as PASS by the dispatcher because the plugin "returned" (via the trap mechanism) without
setting a non-zero exit code. This is a PASS misclassification — the correct outcome is
INDETERMINATE ("could not determine"). CWE-754: Improper Check for Exceptional Conditions.

Layer 1 fix:
1. New INDETERMINATE outcome class in the dispatcher (distinct from PASS and FAIL)
2. For fail-closed plugins: write durable `.factory/unvalidated-mutation.marker` + emit
   `plugin.indeterminate` event
3. New `validate-unvalidated-mutation-marker` WASM plugin: TWO hooks-registry entries — Arm 1
   blocks `^Agent$` PreToolUse dispatches while marker exists; Arm 2 blocks `git commit`/
   `git push` Bash PreToolUse dispatches while marker exists
4. Marker clear: PASS re-validation by the named plugin deletes the marker (unblocks both arms)
5. Cohort A fail-closed assignments: all three human-confirmed validators SET to
   `failure_policy = "fail-closed"` in hooks-registry.toml (ADR-047 §D8a v1.3):
   - **Cohort A-immediate — `validate-factory-path-staging`** (EFFECTIVE-NOW): set
     unconditionally; PreToolUse `^Bash$`; `on_error = "continue"`; bounded input (file path
     from tool params); no self-lock risk; no S-21.24 calibration dependency.
   - **Cohort A-deferred — `validate-pr-merge-prerequisites` and
     `validate-wave-gate-prerequisite`** (SET-BUT-LATENT): field SET in registry with comment
     `# ACTIVATION CONDITIONAL on S-21.24 calibration per ADR-047 §D8a Cohort A-deferred`.
     Field is inert (S-21.10 schema-only; ADR-039 Phase 4 enforcement not wired until S-21.24).
     Enforcement activates when S-21.24 merges (confirming S-21.21 calibration + S-21.23
     break-glass). PreToolUse `^Agent$`; `on_error = "block"` means self-lock risk if
     activated without calibration.
   - **Layer-1 effective fail-closed count at S-25.01 merge: 1**
     (`validate-factory-path-staging`). The two deferred validators are present in registry
     but their enforcement is latent until S-21.24.
6. For fail-open plugins (~76 existing): advisory `plugin.indeterminate` event only; no marker;
   no gate; backward-compat guard test MUST NOT be deleted

## Acceptance Criteria

### BC-1.18.001 — INDETERMINATE Outcome Classification, plugin.indeterminate Event, Durable Marker

**AC-001** (traces to BC-1.18.001 postcondition 1 — fuel cause)

When a fail-closed plugin's WASM execution traps and `trap.downcast_ref::<Trap>()` yields
`Some(Trap::OutOfFuel)`, the dispatcher classifies the outcome as `DispatchOutcome::Indeterminate`
with `cause = "fuel"`. `get_fuel()` is NOT the authoritative check — only the Trap downcast is.

**AC-002** (traces to BC-1.18.001 postcondition 1 — epoch timeout cause)

When a fail-closed plugin's WASM execution traps and `trap.downcast_ref::<Trap>()` yields
`Some(Trap::Interrupt)`, the dispatcher classifies the outcome as `DispatchOutcome::Indeterminate`
with `cause = "epoch"`.

**AC-003** (traces to BC-1.18.001 postcondition 1 + invariant 1 — OutputTooLarge cause with
per-invocation Store flag reset)

When any host function returns `OutputTooLarge(-3)` to the plugin WASM during execution (setting
`StoreData::host_output_too_large_seen = true`), AND the plugin subsequently completes with
`exit_code = 0`, AND `failure_policy = fail-closed`, the outcome MUST be
`DispatchOutcome::Indeterminate` with `cause = "output-too-large"`. The `host_output_too_large_seen`
flag MUST be reset to `false` immediately before each WASM module invocation (not only at `Store`
creation) — this is a correctness invariant (per-invocation reset, not per-Store creation reset).

**AC-004** (traces to BC-1.18.001 postcondition 2 + postcondition 5 + invariant 2 — outcome trichotomy; non-exhaustive Trap wildcard)

`DispatchOutcome::Indeterminate` is a distinct variant from `DispatchOutcome::Pass` and
`DispatchOutcome::Fail`. PASS requires `exit_code = 0` AND `host_output_too_large_seen = false`.
FAIL requires non-zero `exit_code`. INDETERMINATE covers the remaining gap. Existing PASS/FAIL
semantics for `PluginResult::Ok`, `PluginResult::Crash`, and normal `PluginResult::Timeout`
variants are UNCHANGED (backward-compat anchor). The Trap match arm in `classify_outcome`
MUST include a wildcard arm `_ => { /* not INDETERMINATE; route to existing on_error handling */ }`
— `Trap` is `#[non_exhaustive]`; a future unrecognized Trap variant MUST NOT be silently bucketed
as INDETERMINATE (BC-1.18.001 invariant 2).

**AC-005** (traces to BC-1.18.001 postcondition 4 + invariant 3 + invariant 4 — atomic marker write; single-marker policy; PostToolUse-only)

When `failure_policy = fail-closed` AND hook type is `PostToolUse` AND outcome is `Indeterminate`,
the dispatcher atomically writes `.factory/unvalidated-mutation.marker` via write-to-temp + rename
(`O_CREAT | O_WRONLY | O_TRUNC` then `rename`). The marker file MUST contain all five required
TOML fields: `timestamp` (RFC 3339), `plugin_name` (string), `artifact_path` (string, empty
string when no artifact context — never omit the field), `cause` (one of `"fuel"`, `"epoch"`,
`"output-too-large"`), `trace_id` (string). Single-marker policy: a second INDETERMINATE event
overwrites (last-writer-wins). The marker write is PostToolUse only.

**AC-006** (traces to BC-1.18.001 postcondition 3; BC-3.08.001 Event 8 — plugin.indeterminate
event)

The dispatcher emits a `plugin.indeterminate` event to the OTel-aligned FileSink (`events-*.jsonl`)
for EVERY INDETERMINATE outcome (both fail-closed and fail-open). The event wire format MUST
include all mandatory fields per BC-3.08.001 Event 8: `type` ("plugin.indeterminate"),
`trace_id`, `session_id`, `plugin_name`, `artifact_path` (empty string when no artifact context),
`cause` (`"fuel"` | `"epoch"` | `"output-too-large"`), `failure_policy` (`"fail-closed"` or
`"fail-open"`), `timestamp`. BC-3.08.001 is the wire-format authority; BC-1.18.001 is the
triggering-condition authority.

### BC-1.18.002 — Next-Advance Gate: Two-Arm Quarantine

**AC-007** (traces to BC-1.18.002 postcondition 1 + invariant 4 — Agent arm block; block message completeness)

When `.factory/unvalidated-mutation.marker` exists AND a `PreToolUse` hook fires for an `^Agent$`
dispatch, the `validate-unvalidated-mutation-marker` WASM plugin returns `exit_code = 2`
(block). The block message MUST contain: the `plugin_name` from the marker, the `artifact_path`
from the marker, the `cause` from the marker, a re-validation command (e.g., re-invoke the named
plugin by running the relevant dispatcher command), and the manual escape hatch instruction
(`rm .factory/unvalidated-mutation.marker`). The message MUST be machine-parseable (structured
fields, not freeform prose).

**AC-008** (traces to BC-1.18.002 postcondition 2 + invariant 4 — Bash arm block: git commit/push Phase 1/1b/2/3/4 security filter algorithm (v1.3); quoting-in-scope; block message completeness)

When `.factory/unvalidated-mutation.marker` exists AND a `PreToolUse` hook fires for a `^Bash$`
dispatch for which `is_git_commit_or_push(command)` returns `true`, the
`validate-unvalidated-mutation-marker-git` WASM plugin returns `exit_code = 2` (block). The
block message format is identical to AC-007.

`is_git_commit_or_push(command) → bool` is the authoritative production-grade security filter
(BC-1.18.002 PC2 v1.3; ADR-047 §Decision 9). Under-blocking is the dangerous failure mode;
the algorithm is fail-safe on ambiguity:

- **Phase 1 — Compound command splitting.** Split `command` on `&&`, `||`, `;`, `|`, `&`, and
  newline. Trim each segment. Apply Phases 1b–4 to each segment independently; return `true` if
  ANY segment returns `true`.
- **Phase 1b — POSIX quote-aware tokenization.** Before applying Phases 2–4, tokenize each
  segment from Phase 1 using POSIX word-splitting rules via the `shell-words` crate. Quote
  removal and token concatenation occur at this phase — Phases 2–4 operate on the resulting
  token list, not on the raw whitespace-split string. Examples: `git "commit"` → tokens
  `["git", "commit"]`; `git 'push' origin` → tokens `["git", "push", "origin"]`; `g'i't commit`
  → tokens `["git", "commit"]` (POSIX concatenates unquoted `g`, single-quoted `i`, and unquoted
  `t` into the token `git`). Do NOT implement ad-hoc quote-stripping (e.g., `s/["']//g` regex)
  — the `shell-words` crate provides POSIX parser-equivalence, eliminating the parser-differential
  bypass class where ad-hoc stripping could produce different tokenization than the actual shell.
- **Phase 2 — Executable identification by basename.** Strip leading env-var assignment tokens
  (matching `^[A-Za-z_][A-Za-z0-9_]*=`) and the literal `env` token if it is the first token.
  Compute `basename` of the first remaining token (strip all characters up to and including the
  last `/`). If `basename ≠ "git"` (case-sensitive), return `false` for that segment.
- **Phase 3 — Skip global options.** Scan tokens after `git`: `--` ends Phase 3 (next token is
  subcommand); `--flag=value` skips one token; tokens in the **complete recognized arg-taking set**
  (`-C`, `-c`, `--namespace`, `--git-dir`, `--work-tree`, `--super-prefix`, `--config-env`) skip
  that token AND the immediately following token; tokens in the recognized no-arg set are skipped;
  an unrecognized token starting with `-` triggers **fail-safe → return `true` (block)** — arity
  is unknown from the closed recognized set, and under-blocking is the dangerous failure mode.
- **Phase 4 — Subcommand match.** Return `true` iff the candidate subcommand is exactly `commit`
  or `push` (case-sensitive, full-token match). `commit-graph`, `commit-tree`, `push-pack`, and
  any other token that merely contains `commit` or `push` as a substring do NOT match.

The illustrative regex `\bgit\b.*\b(commit|push)\b` approximates this rule but is NOT
authoritative — it false-positives on `git commit-graph write` because the hyphen in `commit-graph`
is a word boundary making `\bcommit\b` match inside a different subcommand token (EC-011); it
cannot detect the gated subcommand in compound commands (EC-015/EC-016); and it does not enforce
basename matching (EC-017/EC-018). The Phase 1/1b/2/3/4 algorithm above is the sole authoritative
specification.

Commands that MUST be blocked (non-exhaustive): `git commit --amend` (EC-006), `git push
--force-with-lease` (EC-007), `git --git-dir .git commit -m "state"` (EC-013), `git --work-tree
/tmp push` (EC-014), `git status && git commit -m "x"` (EC-015), `git diff ; git push` (EC-016),
`/usr/bin/git commit -m "init"` (EC-017), `./git push origin main` (EC-018), `env GIT_DIR=.git
git commit -m "x"` (EC-021), `git --unknown-flag commit` (EC-022, fail-safe), `git --config-env
FOO=BAR commit` (EC-023), `git "commit"` (EC-024, Phase 1b quoting), `git 'push' origin`
(EC-025, Phase 1b quoting), `g'i't commit` (EC-026, Phase 1b POSIX token concatenation).

The following are OUT OF SCOPE by design — blocking these forms is UNDECIDABLE for static string
analysis (Rice's theorem). They are ALLOWED under the fail-open posture; the durable marker
written at PostToolUse time, the `^Agent$` next-advance arm, and GitHub server-side branch
protection provide defense-in-depth. See BC-1.18.002 Threat Model & Scope for the canonical
actor model (cooperating AI agent, NOT adversary-resistant boundary): `$(git commit -m "x")`
(EC-027, command substitution), `echo x | xargs git commit` (EC-028, xargs indirection),
`eval "git push origin main"` (EC-029, dynamic evaluation), and variable/alias/function
indirection forms.

**AC-009** (traces to BC-1.18.002 postcondition 3 — non-advancing not gated; out-of-scope forms documented)

Bash dispatches for which `is_git_commit_or_push(command)` returns `false` are NOT gated even
when the marker exists. Read, Edit, Write, MultiEdit tool dispatches are NOT gated.

The v1.3 algorithm (authoritative per BC-1.18.002 PC2 v1.3; ADR-047 §Decision 9; full
definition in AC-008) is the load-bearing pure filter. Key NOT-gated behaviors:

- **Phase 1 (compound splitting):** A compound command is only NOT gated if ALL segments return
  `false`; if any segment resolves to `commit` or `push`, the function returns `true` (blocked).
- **Phase 1b (POSIX quote-aware tokenization):** The `shell-words` crate tokenizes each segment.
  Quoted forms that resolve to `commit` or `push` after quote removal ARE blocked (e.g.,
  `git "commit"` → BLOCKED per EC-024; `git 'push' origin` → BLOCKED per EC-025; `g'i't commit`
  → BLOCKED per EC-026). This phase is what differentiates v1.3 from v1.2.
- **Phase 2 (basename):** A command is NOT gated if `basename(executable) ≠ "git"` (e.g.,
  `cat gitfile` — `basename("cat") = "cat" ≠ "git"`, returns `false`).
- **Phase 3–4 (option skip + subcommand match):** The recognized arg-taking global-option set
  (`-C`, `-c`, `--namespace`, `--git-dir`, `--work-tree`, `--super-prefix`, `--config-env`) each
  consume the following token as their argument before subcommand identification. Recognized no-arg
  flags are skipped without consuming a following token. An unrecognized `-`-prefixed token
  triggers fail-safe → `true` (blocked). Only exact tokens `commit` or `push` are gated.

The illustrative regex `\bgit\b.*\b(commit|push)\b` is NOT the authoritative rule — see AC-008.

BC-1.18.002 EC-001 through EC-005 MUST pass (non-advancing commands — `git status`, `git log`,
`git diff`, `git fetch`, non-git commands — `is_git_commit_or_push` returns `false`).
Additionally:
- `git commit-graph write` → NOT blocked: Phase 4 full-token match; subcommand is `commit-graph`,
  not `commit` (EC-011).
- `git -C .factory commit -m "state"` → BLOCKED: Phase 3 recognizes `-C` as arg-taking; `.factory`
  consumed as argument; Phase 4 subcommand is `commit` (EC-012).
- `git --git-dir .git commit -m "state"` → BLOCKED: Phase 3 `--git-dir` arg-taking; `.git`
  consumed; Phase 4 subcommand is `commit` (EC-013).
- `git --work-tree /tmp push` → BLOCKED: Phase 3 `--work-tree` arg-taking; `/tmp` consumed;
  Phase 4 subcommand is `push` (EC-014).
- `git status && git commit -m "x"` → BLOCKED: Phase 1 splits on `&&`; segment 2 subcommand is
  `commit`; any-segment `true` → function returns `true` (EC-015).
- `git diff ; git push` → BLOCKED: Phase 1 splits on `;`; segment 2 subcommand is `push` (EC-016).
- `/usr/bin/git commit -m "init"` → BLOCKED: Phase 2 `basename("/usr/bin/git") = "git"`;
  Phase 4 subcommand `commit` (EC-017).
- `./git push origin main` → BLOCKED: Phase 2 `basename("./git") = "git"`; Phase 4 subcommand
  `push` (EC-018).
- `git status && git log --oneline` → NOT blocked: Phase 1 splits; segment 1 subcommand `status`,
  segment 2 subcommand `log`; no segment matches `commit` or `push`; returns `false` (EC-019).
- `env GIT_DIR=.git git commit -m "x"` → BLOCKED: Phase 2 strips `env` + `GIT_DIR=.git`;
  executable is `git`; Phase 4 subcommand `commit` (EC-021).
- `git --unknown-flag commit` → BLOCKED (fail-safe): Phase 3 unrecognized option, no `=`,
  subcommand position uncertain; returns `true` (EC-022).
- `git --config-env FOO=BAR commit` → BLOCKED: Phase 3 `--config-env` arg-taking; `FOO=BAR`
  consumed; Phase 4 subcommand `commit` (EC-023).

**Phase 1b quoting (v1.3 additions — IN SCOPE):**
- `git "commit"` → BLOCKED: Phase 1b POSIX tokenization; `"commit"` → token `commit`; Phase 4
  match (EC-024).
- `git 'push' origin` → BLOCKED: Phase 1b POSIX tokenization; `'push'` → token `push`; Phase 4
  match (EC-025).
- `g'i't commit` → BLOCKED: Phase 1b POSIX token concatenation; `g'i't` → token `git`; Phase 2
  basename `git`; Phase 4 match (EC-026).

**Out-of-scope forms (NOT blocked by design — BC-1.18.002 Threat Model & Scope; defense-in-depth):**
- `$(git commit -m "x")` → NOT blocked: outer command is a command substitution, not a
  statically-literal `git` invocation; undecidable for static analysis; caught by other controls
  (EC-027).
- `echo x | xargs git commit` → NOT blocked: Phase 1 splits on `|`; segment 2 executable is
  `xargs` (basename `xargs` ≠ `git`); `git commit` is a string argument to `xargs`, not the
  top-level executable; returns `false` (EC-028).
- `eval "git push origin main"` → NOT blocked: Phase 2 executable is `eval` (basename `eval` ≠
  `git`); `git push` is a string argument subject to dynamic evaluation; undecidable for static
  analysis; caught by other controls (EC-029).

**AC-010** (traces to BC-1.18.002 postcondition 4 — absent marker: both arms pass)

When `.factory/unvalidated-mutation.marker` is absent, both Arm 1 (`^Agent$`) and Arm 2
(`^Bash$` git commit/push) return `exit_code = 0` (allow).

**AC-011** (traces to BC-1.18.002 precondition 1 + invariant 2 — gate registers on_error="continue" (fail-open-on-crash); cannot self-lock; two-axis model)

Both `validate-unvalidated-mutation-marker` hook entries in `hooks-registry.toml` MUST have
`on_error = "continue"` (NOT `"block"`) AND `failure_policy = "fail-open"`. If the gate plugin
itself cannot complete at the dispatcher layer (fuel exhaustion, epoch timeout, crash), the
dispatcher ALLOWS the triggering dispatch. The gate CANNOT self-lock. Setting `on_error = "block"`
would produce an unconditional self-lock on gate crash — the opposite of the intended behavior.

**Two-axis model (ADR-039; ADR-047 §Decision 9):** Two orthogonal failure-mode axes govern the
gate and MUST NOT be conflated:
- **(i) Dispatcher-level fail-open-on-crash** (`on_error = "continue"`): when the WASM plugin
  itself fails at the dispatcher layer — crash, fuel exhaustion, epoch timeout — the dispatcher
  ALLOWS the triggering dispatch. This is what satisfies INV-2 / EC-003 / this AC. The correction
  from `on_error = "block"` to `on_error = "continue"` was made at BC v1.3 (HIGH-1 finding
  reconciliation).
- **(ii) Filter-internal fail-SAFE posture** (Phase 3 of `is_git_commit_or_push`): when the
  filter encounters an UNRECOGNIZED git global option, it returns BLOCK (subcommand position is
  uncertain; under-blocking is the dangerous failure mode). This is a conservative within-filter
  design choice, orthogonal to axis (i): the filter's internal posture has no bearing on what the
  dispatcher does when the WASM plugin itself crashes.

### BC-1.18.003 — Marker Clear Protocol

**AC-012** (traces to BC-1.18.003 postcondition 1 + invariant 2 — re-validation clear; scoped to named plugin; PostToolUse hook only)

When the plugin whose `plugin_name` matches the marker's `plugin_name` field subsequently
produces `DispatchOutcome::Pass` (i.e., exit_code = 0 AND `host_output_too_large_seen = false`)
**in a PostToolUse hook invocation**, the dispatcher calls `delete_marker_if_pass()` which deletes
`.factory/unvalidated-mutation.marker`. The clear is scoped: only a PostToolUse PASS result from
the NAMED plugin clears the marker. A PreToolUse PASS result from the named plugin (e.g., a
PreToolUse registration of the same plugin passing on a new dispatch) MUST NOT clear the marker.
Other plugins' PASS results do not clear the marker regardless of hook type.

**AC-013** (traces to BC-1.18.003 postcondition 2 — idempotent delete)

`delete_marker_if_pass()` is idempotent: if `.factory/unvalidated-mutation.marker` is absent at
delete time, the function returns `Ok(())` (no-op). `io::ErrorKind::NotFound` is silently
swallowed. All other `io::Error` variants are propagated as `Err`.

**AC-014** (traces to BC-1.18.002 invariant 3 + BC-1.18.003 postcondition 3 + BC-1.18.003 invariant 3 — operator rm escape hatch; both arms unblocked simultaneously)

`rm .factory/unvalidated-mutation.marker` is the fully supported operator escape hatch. No
special command is required. After the rm, both Arm 1 and Arm 2 unblock simultaneously (both
check for the marker's presence at runtime; absent marker → pass).

### BC-1.18.004 — Fail-Open Advisory-Only Backward Compatibility

**AC-015** (traces to BC-1.18.004 postcondition 1 + postcondition 2 + postcondition 3 — fail-open
advisory only; no marker; no gate)

For any plugin with `failure_policy` absent (default) or `failure_policy = "fail-open"`, an
INDETERMINATE outcome produces: (a) an advisory `plugin.indeterminate` event emitted to FileSink;
(b) NO `.factory/unvalidated-mutation.marker` written; (c) NO gate triggered. The predicate
`should_write_marker(Indeterminate, FailOpen) == false` is the load-bearing implementation gate.
`FailurePolicy::default() == FailOpen` (S-21.10 canonical; ADR-039 §Decision 1).

**AC-016** (traces to BC-1.18.004 postcondition 4 — Cohort A exactly three validators;
consistent with ADR-047 §D8a v1.3)

`plugins/vsdd-factory/hooks-registry.toml` MUST have `failure_policy = "fail-closed"` for
exactly these three Cohort A validators; no other validator receives `fail-closed` in this story.
The three validators are split into two operational sub-groups:

**Cohort A-immediate (EFFECTIVE-NOW — 1 validator):**
- `validate-factory-path-staging`: set unconditionally. PreToolUse `^Bash$`; `on_error =
  "continue"`; bounded input; calibration confirmed; no S-21.24 dependency. No registry comment
  required. This is the ONE validator that is fully, unconditionally fail-closed at S-25.01 merge.

**Cohort A-deferred (SET-BUT-LATENT — 2 validators):**
- `validate-pr-merge-prerequisites`: field SET with registry comment:
  `# ACTIVATION CONDITIONAL on S-21.24 calibration per ADR-047 §D8a Cohort A-deferred`
- `validate-wave-gate-prerequisite`: field SET with the same registry comment.

Both deferred validators are PreToolUse `^Agent$` with `on_error = "block"`. Setting the
`failure_policy = "fail-closed"` field in this story is safe because the field is INERT
(S-21.10 is schema-only; ADR-039 Phase 4 enforcement not wired until S-21.24). Their
enforcement activates when S-21.24 wires the executor — at which point S-21.24's own
dependency chain (S-21.19 → S-21.21 calibration values → S-21.23 break-glass code) has already
resolved the self-lock risk.

**Layer-1 effective fail-closed count at S-25.01 merge: 1** (`validate-factory-path-staging`).
The "3-validator Cohort A" reflects the complete membership; the immediate enforcement is 1.

**AC-017** (traces to BC-1.18.004 postcondition 5 — DO-NOT-DELETE backward-compat guard test)

The implementation MUST include the test
`test_BC_1_18_004_fail_open_default_preserves_advisory_behavior` in the executor.rs test module
(or equivalently `test_BC_1_18_004_fail_open_indeterminate_writes_no_marker` with a code comment
cross-referencing the canonical name per BC-1.18.004 PC5 allowance). This test MUST NOT be
deleted per ADR-047 §Decision 7. It is the canonical regression guard for ~76 existing fail-open
plugins.

### BC-1.18.001 Invariant 5 — OutputTooLarge Flag Is Dispatcher-Internal StoreData

**AC-018** (traces to BC-1.18.001 invariant 5 — host_output_too_large_seen is dispatcher-internal StoreData; no ABI exposure)

`StoreData::host_output_too_large_seen` MUST reside in `crates/factory-dispatcher/src/invoke.rs`
exclusively, as dispatcher-internal state. It MUST NOT be exposed in `crates/hook-sdk/` or any
public hook-sdk ABI type. Plugin WASM binaries do not read or write this flag directly — they
observe the `OutputTooLarge (-3)` return code from host functions and may return a non-zero
`exit_code` in response, but the flag is invisible to the plugin. No HOST_ABI_VERSION bump is
required for this story's changes. If any PR review reveals that `crates/hook-sdk` has gained a
dependency on this flag, the PR MUST be blocked and the dependency removed.

### BC-1.18.002 Invariant 1 — Single WASM Binary for Both Gate Arms

**AC-019** (traces to BC-1.18.002 invariant 1 — Arm 1 and Arm 2 use the same WASM binary)

The TWO `[[hook]]` entries for the gate plugin in `hooks-registry.toml` — `validate-unvalidated-mutation-marker`
(`tool = "^Agent$"`) and `validate-unvalidated-mutation-marker-git` (`tool = "^Bash$"`) — MUST
both reference the IDENTICAL compiled binary via `plugin = "hook-plugins/validate-unvalidated-mutation-marker.wasm"`.
There is exactly ONE `.wasm` file on disk; the dispatch routing between Arm 1 (Agent check) and
Arm 2 (Bash command-content filter) is implemented by plugin-internal logic reading the tool event
payload (`command` parameter for Bash dispatches). Confirming this invariant: the `crates/hook-plugins/validate-unvalidated-mutation-marker/`
crate produces a single `validate-unvalidated-mutation-marker.wasm` binary from `T-4`; `T-5`
registers it under two names pointing to the same `plugin` path.
