# S-17.05: stamp-state-timestamp PostToolUse Hook — Hook-Authored Timestamp + Identity-Gated Lock Keep-Alive

**Epic:** E-17 — Factory State Durability and Concurrency (brownfield-backfill #170 lineage)
**Wave:** 5
**Depends on:** S-17.06 (`factory_lock::renew_lock_if_holder`, `factory_lock::classify_identity_resolution`,
`factory_lock::trim_git_email` — all created by S-17.06 and called from `stamp-state-timestamp/src/main.rs`;
`crates/factory-lock-parse/` exists and is merged — S-17.04 PR #184 3b2a378c)
**Blocks:** none
**Priority:** P1 (engine-hardening; targets rc.25 per operator directive; ships as one atomic
release per ADR-046 Decision 3 — see Delivery Constraint below)
**BC gate:** BC-4.17.001 v1.0 (draft; POL-14 auto-promotes to active on this story's PR merge)
+ BC-5.40.001 v1.4 (active; PC4 actor already reassigned to this hook by product-owner
amendment — this story is the "story anchor" BC-5.40.001 v1.4's own Traceability table
currently lists as "[pending]")

## Narrative

- **As a** `state-manager` agent (or any agent) writing `.factory/STATE.md` via `Edit`,
  `Write`, or `MultiEdit`
- **I want** a `PostToolUse` WASM hook that unconditionally re-stamps `timestamp:` to the
  current wall-clock UTC instant after every qualifying write, and — only when I am the
  recorded `factory_lock.holder` — automatically renews `factory_lock.expires_at` to
  `now + 2700s`
- **So that** I (and every other agent) can never author a stale `timestamp:` or a stale
  `expires_at` again, the mid-burst TTL keep-alive obligation (BC-5.40.001 PC4) becomes a
  mechanically-guaranteed property instead of a documentary "state-manager MUST remember to
  run `factory-lock-write.sh renew`" instruction, and a non-holder writer legitimately admitted
  through an expired-lock window (BC-4.13.001 PC2 `LockExpired`) can never silently resurrect
  a foreign holder's dead lock

## Acceptance Criteria

### AC-001 (traces to BC-4.17.001 postcondition PC1)

On any qualifying `PostToolUse` invocation (an `Edit`, `Write`, or `MultiEdit` that landed a
write to `.factory/STATE.md`) where **no** `factory_lock` block is present in the post-write
frontmatter, the hook MUST re-stamp the top-level `timestamp:` field to `chrono::Utc::now()`
formatted as `YYYY-MM-DDTHH:MM:SSZ`, regardless of what value (if any) the agent's own write
proposed. No `factory_lock` block is created as a side effect of this stamp.

**Test (Rust unit):** `test_timestamp_always_restamped_no_lock_present()`

### AC-002 (traces to BC-4.17.001 postcondition PC1 + Invariant 1)

On any qualifying invocation where a `factory_lock` block **is** present, `timestamp:` MUST
still be unconditionally re-stamped — including in the identity-mismatch case where PC2's
gate will separately decline to renew `expires_at` (AC-006). `timestamp:` re-stamping has no
identity gate of any kind; the only paths that skip it are the PC3 fail-open error paths
(AC-008/AC-009).

**Test (Rust unit):** `test_timestamp_restamped_when_lock_held_regardless_of_identity_match()`

### AC-003 (traces to BC-4.17.001 postcondition PC2 — identity-gate truth-table row 1: full match → renew)

When the post-write frontmatter has a `factory_lock` block with a non-empty `holder`, AND
the hook's own resolved caller identity (`git config user.email` via `host::exec_subprocess`)
is byte-equal to that `holder`, the hook MUST renew `factory_lock.expires_at = now +
TTL_SECONDS` (2700s). `holder` and `locked_at` MUST remain byte-identical to their pre-write
values — only `expires_at` changes.

**Test (Rust unit):** `test_identity_match_renews_expires_at()`

### AC-004 (traces to BC-4.17.001 postcondition PC2 — identity-gate truth-table row 2: lock absent → no renewal attempted)

When no `factory_lock` block is present in the post-write frontmatter, the hook MUST NOT
attempt any renewal and MUST NOT create a `factory_lock` block. This is not a "gate failure"
in the safety sense — there is simply nothing to keep alive.

**Test (Rust unit):** `test_no_lock_block_skips_renewal_entirely()`

### AC-005 (traces to BC-4.17.001 postcondition PC2 — identity-gate truth-table row 3: holder present but empty → no renewal)

When a `factory_lock` block is present but its `holder` field is present and extracted as the
empty string, the hook MUST treat this identically to "no lock held" for renewal purposes:
`expires_at` MUST be left byte-identical to its pre-write value. (`timestamp:` is still
re-stamped per AC-002.)

**Test (Rust unit):** `test_empty_holder_skips_renewal()`

### AC-006 (traces to BC-4.17.001 postcondition PC2 + Invariant 2 — identity-gate truth-table row 4: identity MISMATCH → no renewal — SAFETY-CRITICAL)

When a `factory_lock` block is present with a non-empty `holder`, AND the hook's resolved
caller identity is **NOT** byte-equal to `holder` — including the specific hazard case where
the writer was legitimately admitted through BC-4.13.001 PC2 (`LockExpired`, i.e. a foreign,
expired lock let a new caller's tool call through) — the hook MUST leave `expires_at`
byte-identical to its pre-write value. A foreign or expired holder's lock is NEVER silently
resurrected by this hook. This is the load-bearing safety property distinguishing this
design from a naive "renew whenever a `holder` is present" hook (ADR-046 Rationale §"Why the
identity gate on `expires_at`").

**Test (Rust unit):** `test_identity_mismatch_never_renews_expires_at()` and
`test_lock_expired_admitted_non_holder_writer_never_renews()` (the specific
BC-4.13.001-PC2-admission scenario)
**Test (bats):** `test_stamp_state_timestamp_foreign_holder_write_never_renews_e2e()`

### AC-007 (traces to BC-4.17.001 postcondition PC2 + PC3 — identity-gate truth-table row 5: identity-resolution failure → fail-closed on renewal, unaffected on timestamp)

When `host::exec_subprocess(["git", "config", "user.email"])` fails, times out, or returns
empty/unparseable output, the hook MUST treat the PC2 gate as failed (no renewal — same
outcome as AC-006) while `timestamp:` re-stamping (PC1) proceeds unaffected, since it never
depends on identity resolution.

**Test (Rust unit):** `test_identity_resolution_failure_skips_renewal_but_timestamp_still_restamped()`

### AC-008 (traces to BC-4.17.001 postcondition PC3 — fail-open on read/parse errors: zero bytes written)

When `host::read_file` fails, or the on-disk content has malformed/missing frontmatter
delimiters, or the content is non-UTF-8, or there is no `timestamp:` anchor line to replace,
the hook MUST write **nothing** for that invocation (neither `timestamp:` nor `expires_at`
changes) and MUST NOT surface this as a block or otherwise alter the `PostToolUse` result.
The agent's own STATE.md write is never reverted, corrupted, or partially rewritten.

**Test (Rust unit):** `test_malformed_frontmatter_writes_nothing()`,
`test_read_file_error_writes_nothing()`, `test_non_utf8_content_writes_nothing()`,
`test_missing_timestamp_anchor_writes_nothing()`

### AC-009 (traces to BC-4.17.001 postcondition PC3 — no accumulated failure state across invocations)

Following a PC3 fail-open invocation (AC-008), the next qualifying write to STATE.md MUST be
treated as an independent attempt — the hook MUST NOT remember or be influenced by the prior
failure. A subsequent well-formed write MUST stamp `timestamp:` normally.

**Test (Rust unit):** `test_failure_then_success_is_independent_per_invocation()`

### AC-010 (traces to BC-4.17.001 postcondition PC4 — idempotent, frontmatter-only rewrite)

The hook's rewrite MUST touch at most two single lines within the YAML frontmatter region
(bounded by the opening and closing `---` delimiters): the `timestamp:` line and, only when
PC2's gate is satisfied, the `factory_lock.expires_at` line. The hook MUST NOT modify, read
for decision purposes, or depend on any content after the closing `---` delimiter (mirrors
BC-4.13.001 Invariant 9 / BC-5.40.001 Invariant 7 frontmatter-only mandate; uses
`factory_lock_parse::extract_frontmatter` to scope parsing). Re-running the hook against its
own just-written output is idempotent in the sense defined by BC-4.17.001 PC4: `timestamp:`
always advances to a new "now" (never a no-op — it is a live wall clock), while PC2's
renewal outcome is deterministic given the same frontmatter + identity inputs.

**Test (Rust unit):** `test_rewrite_touches_only_two_frontmatter_lines()` and
`test_body_content_after_closing_delimiter_never_modified()`

### AC-011 (traces to BC-4.17.001 postcondition PC5 — no acquire/release/CAS-push involvement)

The hook's registered `tool` matcher (`^(Edit|Write|MultiEdit)$`) MUST NOT include `Bash` or
`Agent`. This is a structural, registry-level guarantee that the hook never intercepts
`factory-lock-write.sh acquire`/`clear` (both invoked via the Bash tool, mutating STATE.md
via direct file I/O — `mv "$tmpfile" "$file"` — never via `Edit`/`Write`/`MultiEdit`) or
`state-burst`'s fetch-then-`--force-with-lease` CAS push (a `Bash` git-push invocation).

**Test (bats):** `test_stamp_state_timestamp_registry_tool_matcher_excludes_bash_and_agent()`

### AC-012 (traces to BC-4.17.001 precondition 3 + Invariant 3 — TTL_SECONDS single canonical constant)

The plugin MUST import `TTL_SECONDS` from a single canonical source shared with
`plugins/vsdd-factory/bin/factory-lock-write.sh`'s own `TTL_SECONDS=2700` — a
`pub const TTL_SECONDS: u32 = 2700` added to `crates/factory-lock-parse/src/lib.rs` (already
a dependency of every guard in this family) and re-exported for `stamp-state-timestamp` to
import. Independently declaring a second `2700`-valued literal inside
`stamp-state-timestamp`'s own source is a production blocker. A cross-reference comment MUST
be added on both the new Rust constant and the existing bash literal.

**Test (Rust unit):** `test_ttl_seconds_constant_equals_2700()` and
`test_ttl_seconds_is_imported_not_redeclared()` (source-scan assertion: no second
`2700`-valued `const`/literal declaration for TTL purposes exists in
`stamp-state-timestamp/src/lib.rs`)

### AC-013 (traces to BC-4.17.001 preconditions 1–2 + BC-5.40.001 PC4 — registry: stamper added AND verify-state-timestamp-refresh deregistered in the same commit — DELIVERY-ATOMICITY)

`plugins/vsdd-factory/hooks-registry.toml` MUST, in the same commit:
1. Contain a new `[[hooks]]` entry `name = "stamp-state-timestamp"`, `event =
   "PostToolUse"`, `tool = "^(Edit|Write|MultiEdit)$"`, capability-scoped
   `path_allow = [".factory/STATE.md"]` for both `[hooks.capabilities.read_file]` and
   `[hooks.capabilities.write_file]`, and `[hooks.capabilities.exec_subprocess]` with
   `binary_allow = ["git"]` / `env_allow = ["HOME", "GIT_CONFIG_GLOBAL",
   "XDG_CONFIG_HOME"]` (identical to `verify-factory-lock`'s block — Precondition 2).
2. NOT contain a `verify-state-timestamp-refresh` `[[hooks]]` entry (deregistered).

Both conditions MUST hold in the same commit — never a commit with (1) but not (2), or (2)
but not (1). See **Delivery Constraint** below for the rationale (ADR-046 Decision 3).

**Test (bats):** `test_hooks_registry_stamper_present_and_old_guard_absent_atomically()`

### AC-014 (traces to BC-5.40.001 postcondition PC4 — end-to-end: hook mechanically performs mid-burst renewal)

Through the real WASM dispatcher: an `Edit` to `.factory/STATE.md` while a `factory_lock`
block is held by the same git identity as the caller MUST result, after the write, in
`expires_at` advanced to `write_instant + 2700s` with `locked_at` unchanged — demonstrating
end-to-end that this hook mechanically discharges BC-5.40.001 PC4 on `state-manager`'s
behalf without `state-manager` invoking `factory-lock-write.sh renew` itself.

**Test (bats):** `test_stamp_state_timestamp_mid_burst_renewal_e2e()`

## Delivery Constraint (ADR-046 Decision 3 — single-release atomicity)

The new `stamp-state-timestamp` registry entry going live and the
`verify-state-timestamp-refresh` registry entry being deregistered MUST ship in the same
release (never split across two rc cuts). ADR-046's Rollout/Migration Note is explicit: a
window where the old guard is removed but the new stamper is not yet deployed would silently
reintroduce agent-authored, error-prone wall-clock fields with **no detector at all**; a
window where the stamper is live but the old guard still blocks on staleness it no longer
needs to block on is merely redundant (not unsafe) but wastes a registry priority slot and a
dispatcher PreToolUse cycle on every STATE.md write for no purpose. AC-013 is the mechanical
enforcement point for this constraint (both registry conditions verified in one bats
assertion against one `hooks-registry.toml` state). This is a same-PR requirement, not
merely a same-epic one — the implementer MUST NOT split T-4/T-5 below (registry add + old
entry removal) into separate PRs.

## Out of Scope (explicit — do not implement in this story)

- **Deleting the `verify-state-timestamp-refresh` crate source or its Rust unit test module**
  (`crates/hook-plugins/verify-state-timestamp-refresh/src/lib.rs`). Per ADR-046 Decision
  point 2, the crate source and its ~28 existing Rust unit tests are LEFT IN PLACE as
  historical/reference material at this release — they are pure function tests of
  `guard_logic()` via injectable callbacks and do not depend on registry state, so they
  continue to compile and pass unmodified after deregistration. Actual crate deletion is an
  explicit, human-approved future deferral (ADR-046: "pending a follow-up cleanup story that
  deletes the crate outright once the human has confirmed the new mechanism is stable in
  production") — this satisfies the CANONICAL PRINCIPLE Rule 3 deferral bar (human-directed
  in the ratified ADR; concrete future dependency = production-stability observation window;
  attach to a specific future story once state-manager allocates its ID — flagged in the
  Report below, not invented here).
- **`plugins/vsdd-factory/tests/verify-state-timestamp-refresh.bats` is NOT left in place.**
  Unlike the crate's unit tests, this bats suite drives the real dispatcher through the
  now-deregistered registry entry — once deregistered, its "expect exit 2 Block" assertions
  would start failing as false regressions (the guard structurally cannot fire; the
  dispatcher has no entry to invoke). This file MUST be retired (deleted) in this story's
  scope (T-6 below) — retiring it is required for CI to stay green, not merely tidy.
- **`verify-state-timestamp-advisory`** (`crates/hook-plugins/verify-state-timestamp-advisory/`,
  registry priority 159, `event = "PostToolUse"`, `tool = "^Bash$"`, BC-5.41.003) is a
  wholly separate, already-shipped advisory mechanism (git-commit-diff-scoped, exec-free,
  never writes) unrelated to ADR-046. It is NOT touched by this story.
- **ADR-045 / E-23 / S-23.\* / ARCH-INDEX / STATE.md / `.factory/policies.yaml`** — strictly
  out of scope per this story's isolation mandate.

## Architecture Compliance Rules

Extracted from ADR-046 and BC-4.17.001; enforced by both implementer and adversarial review:

1. **`event = "PostToolUse"`, `tool = "^(Edit|Write|MultiEdit)$"` — no `Bash`, no `Agent`
   (BC-4.17.001 PC5 / AC-011):** This is the structural guarantee that the hook never
   observes `factory-lock-write.sh acquire`/`clear` (Bash-invoked) or the CAS push
   (Bash-invoked).
2. **`async = false` is a correctness requirement (ADR-019 / ADR-025 precedent):** Only
   sync-group plugins participate in the dispatcher's result aggregation at the correct
   phase; this hook has no `block_intent` need (PC3/Invariant 4: it never blocks), but
   `async = false` MUST still be explicit for consistent ordering semantics with sibling
   entries.
3. **`on_error = "continue"` (BC-4.17.001 PC3 / Invariant 4):** Fail-open on crash — this
   hook has no `block_intent` capability by design; a crash MUST NOT be surfaced as a block
   of the agent's own already-completed write.
4. **`[hooks.capabilities.read_file]` AND `[hooks.capabilities.write_file]` are both
   mandatory, both `path_allow = [".factory/STATE.md"]` and nothing else** (BC-4.17.001
   Precondition 1). Omitting either capability block causes `CapabilityDenied` on the
   corresponding host call → silent inertness on that half of the hook (timestamp stamps
   but lock renewal silently never fires, or vice versa, depending on which capability is
   missing) — this is the sixth instance of the deny-by-default silent-no-op footgun class
   documented across this hook family (ADR-025/BC-4.13.001/BC-5.40.001 precedent).
5. **`[hooks.capabilities.exec_subprocess]` with `binary_allow = ["git"]`,
   `env_allow = ["HOME", "GIT_CONFIG_GLOBAL", "XDG_CONFIG_HOME"]` — required ONLY for PC2's
   gate check** (BC-4.17.001 Precondition 2). Omitting `env_allow` produces the same
   `IdentityResolutionFailed`-class silent inertness documented in BC-4.13.001 EC-016 — the
   gate would always fail closed (never renew), which is the *safe* direction but still a
   functional defect (PC4 mid-burst keep-alive would never actually happen for any writer).
6. **No `serde_yaml`/`serde_norway`, no `regex` crate (established Architecture Compliance
   Rule across this crate family):** Manual line-by-line scan only, via
   `factory_lock_parse::extract_frontmatter` + the crate's existing scanning helpers.
7. **No independent TTL literal (BC-4.17.001 Precondition 3 / Invariant 3):** `TTL_SECONDS`
   MUST be imported from `crates/factory-lock-parse`, never redeclared.
8. **Frontmatter-only; body never read, parsed, or depended upon (BC-4.17.001 Invariant 5):**
   Mirrors BC-4.13.001 Invariant 9 / BC-5.40.001 Invariant 7. Full-file read is necessary
   (to reconstruct and write back the complete file), but all *decision* logic and all
   *substitution targets* are confined to the region bounded by the frontmatter delimiters.
9. **String/byte-equality identity comparison via `factory_lock::trim_git_email` (canonical
   home established by S-17.06; BC-4.17.001 Precondition 2, mirrors BC-4.13.001's
   `trim_git_email` precedent):** `stamp-state-timestamp` MUST NOT reimplement email-string
   normalization. `trim_git_email` is promoted to `factory_lock::trim_git_email` by S-17.06;
   it is consumed transitively through `factory_lock::classify_identity_resolution` →
   `factory_lock::renew_lock_if_holder` — no direct call to `trim_git_email` is required in
   this crate.

## Edge Cases

Reused directly from BC-4.17.001 (no new edge cases invented — per story-writer discipline,
ACs and edge cases trace to the BC, not the reverse):

| ID | Description | Expected Behavior | AC Reference |

| EC-001 | Write while unlocked (no `factory_lock` block) | `timestamp:` re-stamped; no block created | AC-001, AC-004 |

## Demo Plan

1. **AC-001/AC-004 (unlocked write):** Fixture STATE.md with no `factory_lock` block. Run an
   `Edit` through the real dispatcher. Assert post-write `timestamp:` differs from pre-write
   value; assert no `factory_lock` block was created.
2. **AC-003 (identity match — renews):** Fixture with `factory_lock.holder` equal to the
   test harness's configured `git config user.email`. Run a `Write`. Assert
   `expires_at` = write-instant + 2700s; assert `locked_at` unchanged.
3. **AC-006 (identity mismatch — SAFETY-CRITICAL, never renews):** Fixture with
   `factory_lock.holder` set to a foreign email, `expires_at` in the past (simulating a
   `LockExpired`-admitted writer). Run a `MultiEdit`. Assert `expires_at` is byte-identical
   pre- and post-write; assert `timestamp:` still advanced.
4. **AC-013 (registry atomicity):** `grep -c 'name = "stamp-state-timestamp"'
   hooks-registry.toml` → 1; `grep -c 'name = "verify-state-timestamp-refresh"'
   hooks-registry.toml` → 0. Both assertions in the same test run against the same commit.
5. **AC-014 (mid-burst renewal e2e):** Simulate a `state-manager` burst: acquire a lock via
   `factory-lock-write.sh acquire`, then perform an `Edit` to STATE.md as the same identity
   without calling `renew`. Assert the hook alone advanced `expires_at` by 2700s from the
   write instant — no manual `renew` invocation required.
6. **AC-012 (TTL sourcing):** `cargo test -p factory-lock-parse
   test_ttl_seconds_constant_equals_2700` and the `stamp-state-timestamp` crate's mirror test
   both pass; grep confirms no second `2700` literal exists in
   `stamp-state-timestamp/src/lib.rs`.
