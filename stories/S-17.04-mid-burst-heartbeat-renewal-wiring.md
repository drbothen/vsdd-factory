# S-17.04: Mid-Burst Heartbeat Renewal Wiring — SKILL Renew Step + Rust WASM State-Timestamp-Refresh Guard

**Epic:** E-17 — Factory State Durability and Concurrency (brownfield-backfill #170)
**Wave:** 4 (no product dependencies — `factory-lock-write.sh renew` is merged in S-17.01)
**Depends on:** none (S-17.01 delivered `factory-lock-write.sh renew` subcommand; already on develop; S-17.02 delivered `verify-factory-lock` WASM crate — its `lib.rs` parse functions are the extraction source for D15)
**Blocks:** none
**Priority:** P1 (closes prose/executable gap for BC-5.40.001 PC4 enforcement; co-deployed with rc.21 per ADR-025 v1.6 §R5)
**BC gate:** BC-5.40.001 v1.1 (active; PC4 is the unimplemented enforcement target)

## Narrative

- **As a** factory `state-manager` agent running a burst while a factory lock is held
- **I want** the `state-burst` SKILL to unconditionally call
  `factory-lock-write.sh renew .factory/STATE.md` immediately before staging the commit,
  AND a Rust WASM PreToolUse guard `verify-state-timestamp-refresh` to block any
  Edit, Write, or MultiEdit to `.factory/STATE.md` whose proposed content does not advance the
  `timestamp:` frontmatter field (and, when a lock is held, the `factory_lock.expires_at` field)
- **So that** BC-5.40.001 PC4 (mid-burst TTL renewal) is enforced at write-time by a
  structurally bypass-proof WASM guard rather than at push-time by a brittle bash
  command-string regex — closing all four bypass vectors identified in ADR-025 v1.6
  Decision 11 Mechanism 2 (inert-match, over-match, newline-injection, env-injection),
  and ensuring every STATE.md write advances its timestamp regardless of lock state

## Acceptance Criteria

### AC-001 (traces to BC-5.40.001 postcondition PC4 — mid-burst renewal: skill step invoked)

The `state-burst` SKILL (`plugins/vsdd-factory/skills/state-burst/SKILL.md`) MUST
contain a mandatory numbered step immediately before the `git -C .factory add -A` /
`git -C .factory commit` block with the exact invocation:

```
bash plugins/vsdd-factory/bin/factory-lock-write.sh renew .factory/STATE.md
```

The step MUST be annotated: "No-op when factory is unlocked (absent `factory_lock:`
key) — exits 0 with 'no factory_lock block present — renew is a no-op'. Safe to
call unconditionally."

An anti-pattern row MUST be added to the SKILL's "Anti-patterns this skill blocks"
table:

| Anti-pattern | Detection | Recovery |
|---|---|---|
| Skipping renew before `git add` while lock is held | `verify-state-timestamp-refresh` WASM guard blocks the subsequent STATE.md write (LockExpiryStale) | Run `bash plugins/vsdd-factory/bin/factory-lock-write.sh renew .factory/STATE.md`; then retry the Edit/Write/MultiEdit to STATE.md |

**Test (bats):** `test_state_burst_skill_contains_renew_step()`
— Asserts: `grep -c 'factory-lock-write.sh renew' plugins/vsdd-factory/skills/state-burst/SKILL.md` outputs `>= 1`

### AC-003 (traces to BC-5.40.001 postcondition PC4 + ADR-025 v1.6 Decision 12 — WASM guard: allows write when timestamps advanced)

When the proposed STATE.md content advances `timestamp:` vs the on-disk value AND
(if a lock is held in the proposed content) `factory_lock.expires_at` is also advanced,
the `verify-state-timestamp-refresh` WASM guard MUST return `Continue` (exit 0).

This is the success path for every correctly-executed state-manager burst: the SKILL's
renew step (AC-001 / D10) has run, both time fields are fresh, the guard passes
transparently.

**Test (bats):** `test_verify_state_timestamp_refresh_continues_when_timestamps_advanced()`

### AC-004 (traces to BC-5.40.001 postcondition PC4 + ADR-025 v1.6 Decision 12 §12.4 — shared crate: factory-lock-parse extracted)

The `parse_factory_lock`, `LockState`, `extract_yaml_string_value`, and `parse_iso8601`
functions/types from `crates/hook-plugins/verify-factory-lock/src/lib.rs` MUST be
promoted to a new workspace-internal crate `crates/factory-lock-parse/`.

`verify-factory-lock/src/lib.rs` MUST import these from `factory_lock_parse::` rather
than `crate::`. All existing `verify-factory-lock` tests MUST continue to pass unmodified
(only import paths change, not logic or test assertions).

`verify-state-timestamp-refresh` MUST also declare `factory-lock-parse` as a dependency
and use `parse_factory_lock` for all lock-block parsing — no independent reimplementation
of the frontmatter scanner.

**Test:** all existing `verify-factory-lock` unit tests pass after the extraction (`cargo test -p verify-factory-lock`).

### AC-005 (traces to BC-5.40.001 postcondition PC4 + ADR-025 v1.6 Decision 12 §12.2 — WASM guard: blocks stale timestamp)

When the proposed STATE.md content has `timestamp:` byte-identical to the on-disk
STATE.md `timestamp:` value (the timestamp was not advanced in this write), the
`verify-state-timestamp-refresh` WASM guard MUST return `Block` (exit 2) with the
canonical `HookResult::block_with_fix` message:

```
BLOCKED by verify-state-timestamp-refresh: STATE.md timestamp not advanced in this write. Fix: Update 'timestamp:' to the current UTC time before writing STATE.md. Code: TimestampStale.
```

This check applies regardless of whether a lock is held — every STATE.md write must
advance `timestamp:`.

**Test (Rust unit):** `test_timestamp_stale_no_lock_blocks()` and
`test_timestamp_stale_lock_held_blocks()`

### AC-006 (traces to BC-5.40.001 postcondition PC4 + ADR-025 v1.6 Decision 12 §12.2 — WASM guard: blocks stale, absent, or empty lock expiry when lock held)

When a lock is held in the proposed STATE.md content (`factory_lock.holder` is present
and non-empty) AND `factory_lock.expires_at` in the proposed content is byte-identical
to `factory_lock.expires_at` in the on-disk STATE.md, the guard MUST return `Block`
(exit 2) with:

```
BLOCKED by verify-state-timestamp-refresh: factory_lock.expires_at not refreshed in this write while lock is held. Fix: Run: factory-lock-write.sh renew .factory/STATE.md before writing STATE.md. Code: LockExpiryStale.
```

**Scope note (v1.4, ADR-025 §12.3 Gemini pass):** The `LockExpiryStale` block applies
to three conditions when a lock is held in the proposed content:
1. **Byte-identical** — proposed `expires_at` equals on-disk `expires_at` (renewal was skipped).
2. **Absent** — `factory_lock.expires_at` field is not present in proposed frontmatter
   (see AC-016 for the dedicated test case).
3. **Empty** — `factory_lock.expires_at` field is present but its value is empty string
   after extraction (see AC-017 for the dedicated test case).

All three conditions use the same canonical block message above.

When no lock is held in the proposed content (`factory_lock` absent or `factory_lock.holder`
absent/empty), the `LockExpiryStale` check MUST NOT fire regardless of `expires_at`
values — the `TimestampStale` check still applies.

**Test (Rust unit):** `test_lock_expiry_stale_blocks()` and
`test_no_lock_held_skips_expiry_check()`

### AC-007 (traces to BC-5.40.001 postcondition PC6 + ADR-025 v1.6 Decision 12 §12.1 — WASM guard: non-STATE.md files pass immediately)

When the Edit, Write, or MultiEdit tool payload `file_path` does NOT resolve to
`.factory/STATE.md` (after canonical-path normalization per EC-006),
the guard MUST return `Continue` (exit 0) immediately without invoking `host::read_file`.
The guard adds zero overhead to all edits of files other than STATE.md.

**Test (Rust unit):** `test_non_state_md_file_continues_without_read()`
**Test (bats):** `test_verify_state_timestamp_refresh_continues_for_non_state_md()`

### AC-008 (traces to BC-5.40.001 postcondition PC4 + ADR-025 v1.6 Decision 12 §12.3 — WASM guard: fail-open on all error paths)

All error/edge paths MUST result in `Continue` (fail-open), consistent with ADR-025
Decision 7 and the `verify-factory-lock` precedent:

1. Proposed content is unparseable (malformed frontmatter) → `Continue`
2. On-disk STATE.md read fails (`host::read_file` returns `HostError`) → `Continue`
3. `timestamp:` absent in on-disk file (first write ever) → `Continue`
4. `timestamp:` absent **or empty string** in proposed content → `Block: TimestampStale` (absence or empty is itself a stale/missing-field violation; see AC-019 for the dedicated empty-string test case)

**Tests (Rust unit):** `test_proposed_unparseable_continues()`,
`test_on_disk_read_fails_continues()`,
`test_timestamp_absent_on_disk_continues()`,
`test_timestamp_absent_in_proposed_blocks()`

`plugins/vsdd-factory/agents/state-manager.md` §"factory_lock Write/Renewal/Clear
Obligation" → §Sequencing invariants Invariant 2 MUST have a cross-reference sentence

> The `state-burst` SKILL enforces this invariant mechanically: the mandatory

> enforces freshness at write-time: any Edit, Write, or MultiEdit to `.factory/STATE.md`

**Test:** `grep -c 'verify-state-timestamp-refresh' plugins/vsdd-factory/agents/state-manager.md` outputs `>= 1`

### AC-010 (traces to BC-5.40.001 postcondition PC4 + ADR-025 v1.6 Decision 12 §12.6 — registry entry: capability block complete; priorities correct; MultiEdit covered)

The `hooks-registry.toml` entry for `verify-state-timestamp-refresh` MUST be present
and MUST include the capability block per ADR-025 Decision 12 §12.6. `ReadFileCaps` is
`#[serde(deny_unknown_fields)]` with ONLY `path_allow: Vec<String>` — any unrecognized
field (including `max_bytes` or `timeout_ms`) breaks registry load. Omitting `path_allow`
causes `CapabilityDenied` → silent fail-open → guard is a no-op.

The entry MUST specify:

```toml
[hooks.capabilities.read_file]
path_allow = [".factory/STATE.md"]
```

No other fields in `[hooks.capabilities.read_file]`. No `[hooks.capabilities.exec_subprocess]`
is needed (the guard never shells out).

Additionally:
- The plugin entry MUST include `priority = 143` (ensures `verify-state-timestamp-refresh`
  runs after `verify-factory-lock` which carries `priority = 142` — lock-identity check fires first).
- The `tool` matcher MUST be `"Edit|Write|MultiEdit"` (not `"Edit|Write"` alone — MultiEdit
  is a distinct Claude Code tool that mutates file content and must be subject to the same guard).
- The existing `verify-factory-lock` registry entry MUST be amended to add `priority = 142`
  so the ordering relationship is explicit.
- **Sibling-sweep (ADR-025 §12.9 R1, Gemini cross-family pass):** The existing
  `verify-factory-lock` registry entry currently has `tool = "Edit|Write|Agent"` and omits
  `MultiEdit`. A MultiEdit to `.factory/STATE.md` therefore bypasses the lock-identity check
  while being subject to the timestamp-refresh guard — a parity gap. As an in-scope D16
  registry edit (ADR-025 Decision 1/2 scope), the implementer MUST change the
  `verify-factory-lock` entry `tool` matcher from `"Edit|Write|Agent"` to
  `"Edit|Write|MultiEdit|Agent"` in the same hooks-registry.toml commit that adds the new
  `verify-state-timestamp-refresh` entry. This is a one-line change; it does not require a
  new story.

**Test (bats):** `test_verify_state_timestamp_refresh_registry_entry_has_capability_block()`

### AC-011 (traces to BC-5.40.001 postcondition PC4 + ADR-025 v1.6 Decision 12 §12.2 — Write payload: stale timestamp blocks)

When the guard receives a `Write` tool payload for `.factory/STATE.md` where
`tool_input.content` (the full new file body) contains a `timestamp:` value byte-identical
to the on-disk STATE.md `timestamp:` value, the guard MUST return `Block: TimestampStale`.

`tool_input.content` is the correct payload field for the Write tool — it is the complete
proposed file body. The guard reads this directly without any reconstruction step.

**Test (Rust unit):** `test_write_payload_stale_timestamp_blocks()`

### AC-012 (traces to BC-5.40.001 postcondition PC4 + ADR-025 v1.6 Decision 12 §12.2 — Edit payload: reconstructed stale timestamp blocks)

When the guard receives an `Edit` tool payload for `.factory/STATE.md` with
`tool_input.old_string` + `tool_input.new_string` (and optional `tool_input.replace_all`),
the guard MUST:

1. Read on-disk STATE.md via `host::read_file`.
2. Replace the first occurrence of `old_string` with `new_string` in the on-disk content
   (or all occurrences if `replace_all` is `true`) to produce the proposed full content.
3. Compare the `timestamp:` field in the proposed full content against the on-disk value.
4. Return `Block: TimestampStale` if the `timestamp:` field is byte-identical after
   reconstruction.

The proposed full content MUST be reconstructed from the on-disk content + edit fragment —
the guard MUST NOT assume `tool_input.new_string` alone contains the entire file. Using
the fragment directly would compare a fragment to a full file, producing false positives
on every Edit that does not touch the `timestamp:` line.

**Test (Rust unit):** `test_edit_payload_reconstruct_stale_timestamp_blocks()` and
`test_edit_payload_reconstruct_advanced_timestamp_continues()`

### AC-013 (traces to BC-5.40.001 postcondition PC4 + ADR-025 v1.6 Decision 12 §12.2 — MultiEdit payload: reconstructed stale timestamp blocks)

When the guard receives a `MultiEdit` tool payload for `.factory/STATE.md` with
`tool_input.edits[]` (an array of `{old_string, new_string, replace_all?}` elements),
the guard MUST:

1. Read on-disk STATE.md via `host::read_file`.
2. Apply each element of `edits[]` sequentially in array order, same substitution logic
   as Edit (first occurrence, or all if `replace_all`), to produce the proposed full content.
3. Compare the `timestamp:` field in the proposed full content against the on-disk value.
4. Return `Block: TimestampStale` if `timestamp:` is byte-identical after all edits applied.

**Test (Rust unit):** `test_multiedit_payload_reconstruct_stale_timestamp_blocks()` and
`test_multiedit_payload_reconstruct_advanced_timestamp_continues()`

### AC-014 (traces to BC-5.40.001 postcondition PC6 + ADR-025 v1.6 Decision 12 §12.3 — Edit/MultiEdit: old_string not found → Continue)

When the guard attempts reconstruction for an `Edit` or `MultiEdit` payload and
`old_string` is not found in the on-disk content (for any element of `edits[]`),
the guard MUST return `Continue` (fail-open, exit 0).

Rationale: the Edit/MultiEdit tool itself will reject the payload with an error; the
guard's responsibility is timestamp enforcement, not edit-applicability validation.
Blocking here would add no safety and would prevent the tool's own error message from
reaching the user.

**Test (Rust unit):** `test_edit_old_string_not_found_continues()` and
`test_multiedit_first_old_string_not_found_continues()`

### AC-015 (traces to BC-5.40.001 postcondition PC6 + ADR-025 v1.6 Decision 12 §12.3 — host::read_file NotFound → Continue)

When `host::read_file` returns `NotFound` (the first-ever write to `.factory/STATE.md`
— the file does not yet exist on disk), the guard MUST return `Continue` (fail-open,
exit 0).

There is no on-disk value to compare against, so any write is valid. This is the same
semantics as "timestamp: absent in on-disk content" (AC-008 item 3) but triggered by
file absence rather than a parseable file with no `timestamp:` field.

**Test (Rust unit):** `test_read_file_not_found_continues()`

### AC-016 (traces to BC-5.40.001 postcondition PC4 + ADR-025 v1.6 Decision 12 §12.3 — WASM guard: blocks when lock held and expires_at absent from proposed content)

When a lock is held in the proposed STATE.md content (`factory_lock.holder` is present
and non-empty) AND the `factory_lock.expires_at` field is **absent** (not present in the
proposed frontmatter at all), the guard MUST return `Block: LockExpiryStale` (exit 2)
with the canonical message:

```
BLOCKED by verify-state-timestamp-refresh: factory_lock.expires_at not refreshed in this write while lock is held. Fix: Run: factory-lock-write.sh renew .factory/STATE.md before writing STATE.md. Code: LockExpiryStale.
```

Rationale: a held lock with no `expires_at` field is not a valid renewal, regardless of
the on-disk value. Absent is semantically equivalent to stale. This prevents a bypass
where the write simply omits the `expires_at` key entirely instead of reusing the old
value (ADR-025 §12.3 Gemini cross-family pass).

**Test (Rust unit):** `test_lock_held_expires_at_absent_blocks()` (ADR-025 D17 case t)
**Test (bats):** `test_verify_state_timestamp_refresh_lock_held_absent_expires_blocks()`

### AC-017 (traces to BC-5.40.001 postcondition PC4 + ADR-025 v1.6 Decision 12 §12.3 — WASM guard: blocks when lock held and expires_at is empty string)

When a lock is held in the proposed STATE.md content (`factory_lock.holder` is present
and non-empty) AND the `factory_lock.expires_at` field is **present but its extracted
value is the empty string** (e.g., `expires_at: ""` or `expires_at:` with no value), the
guard MUST return `Block: LockExpiryStale` (exit 2) with the same canonical message as
AC-016.

Rationale: a held lock with an empty `expires_at` is not a valid renewal. Empty string
is as wrong as absent or stale. The guard MUST treat the empty-string case as a block,
not a Continue (ADR-025 §12.3 Gemini cross-family pass, row "Lock held AND proposed
`expires_at` is **empty**").

**Test (Rust unit):** `test_lock_held_expires_at_empty_blocks()` (ADR-025 D17 case u)

### AC-018 (traces to BC-5.40.001 postcondition PC4 + ADR-025 v1.6 Decision 12 §12.1 / §12.7 R6 — WASM guard: absolute-path file_path triggers guard end-to-end)

When the Edit, Write, or MultiEdit tool payload `file_path` is an **absolute path** ending
in `/.factory/STATE.md` (e.g., `/Users/zious/proj/.factory/STATE.md` — the path Claude
Code actually emits in practice), the `verify-state-timestamp-refresh` WASM guard MUST
recognize this as `.factory/STATE.md` and enforce the timestamp-freshness check.

**Why this AC exists (adversary deep-pass 7 P0 finding):** Prior EC-006 specified stripping
a `$CLAUDE_PROJECT_DIR/` environment variable prefix as step 1 of canonical-path normalization.
The WASI sandbox provides NO environment variables — `std::env::var("CLAUDE_PROJECT_DIR")`
always fails in the WASM runtime. Any path that Claude Code emits as an absolute path
(which is the REAL form emitted for all project files) will not match the literal string
`.factory/STATE.md` after the relative-path-only normalizations. This was the root cause:
the guard was structurally inert on the absolute paths Claude Code actually emits. Unit
tests running in the native environment (where env vars ARE available) would not detect
this because the native test harness is not the WASM runtime.

**New trigger rule (ADR-025 §12.7 R6 revised):** After the four relative-path normalizations
(strip leading `./`; collapse `//`; collapse `/./`; `..` segment-stack), the guard fires when:
- The normalized path **equals** `.factory/STATE.md` (relative paths — canonical match), OR
- The normalized path **ends with** `/.factory/STATE.md` (absolute paths and any
  project-root-relative path with a prefix — e.g., `/Users/x/proj/.factory/STATE.md`,
  `proj/.factory/STATE.md`).

**Non-matching examples (no guard activation):**
- `.factory/STATE.md.bak` — equals check fails, ends_with check fails (suffix is `.bak`)
- `other/STATE.md` — neither equals `.factory/STATE.md` nor ends with `/.factory/STATE.md`
- `/tmp/STATE.md` — ends with `/tmp/STATE.md`, not `/.factory/STATE.md`

**Critical test requirement:** This AC MUST be validated by a **bats end-to-end test through
the actual WASM runtime** — not a Rust native-env unit test. Env-var-based or native-harness
unit tests exercise a different execution environment than the deployed WASM binary. The bats
e2e test is the only test that actually loads `verify-state-timestamp-refresh.wasm` via the
dispatcher and exercises the real code path. This is why the absolute-path bypass survived
6 prior adversary passes: unit tests ran in the native env, not in the WASM sandbox.

**Test (bats — MANDATORY):** `test_verify_state_timestamp_refresh_absolute_path_stale_blocks()`
— sends a Write payload with `file_path = "/abs/path/to/project/.factory/STATE.md"` (absolute)
and stale `content` (timestamp not advanced) through the real WASM dispatcher;
asserts exit 2 with canonical `TimestampStale` block message.

### AC-019 (traces to BC-5.40.001 postcondition PC4 + ADR-025 v1.6 Decision 12 §12.2 — WASM guard: proposed timestamp present-but-empty → Block TimestampStale)

When the proposed STATE.md content has `timestamp:` present but its extracted value is
the **empty string** (e.g., `timestamp:` with no value, or `timestamp: ""`), the guard
MUST return `Block: TimestampStale` (exit 2) with the canonical message:

```
BLOCKED by verify-state-timestamp-refresh: STATE.md timestamp not advanced in this write. Fix: Update 'timestamp:' to the current UTC time before writing STATE.md. Code: TimestampStale.
```

Rationale: an empty timestamp is not a valid advancement of the timestamp field. It is
semantically equivalent to absent (AC-008 item 4). Consistent with the v1.4 pattern:
empty `factory_lock.expires_at` blocks (AC-017), so empty `timestamp:` must also block.
Without this rule, a single write with `timestamp:` left empty would slip through one
cycle — the on-disk value after that write would differ from the empty string, making
the next write appear to "advance" even if the implementer forgot to set a real value.

**Test (Rust unit):** `test_timestamp_empty_string_in_proposed_blocks()` (new case for v1.6)

## Architecture Compliance Rules

The following rules are extracted from ADR-025 v1.6 Decision 12 and must be enforced
by both implementer and adversarial review:

1. **PreToolUse on Edit|Write|MultiEdit, trigger on file_path (ADR-025 Decision 12 §12.1 / §12.7 R6 revised):** The
   guard MUST be registered as `event = "PreToolUse"` with `tool = "Edit|Write|MultiEdit"`.
   MultiEdit is a distinct Claude Code tool that delivers `tool_input.edits[]` (an array
   of `{old_string, new_string, replace_all?}` elements) and MUST be covered alongside
   Edit and Write. The trigger condition (per EC-006 revised) is: after four relative-path
   normalizations (strip leading `./`; collapse `//`; collapse `/./`; `..` segment-stack),
   the guard fires when the result **equals** `".factory/STATE.md"` OR **ends with**
   `"/.factory/STATE.md"`. The `ends_with` branch is mandatory — Claude Code emits absolute
   paths in practice, and the WASI sandbox provides NO environment variables, making any
   `$CLAUDE_PROJECT_DIR` env-var-strip approach dead code. DO NOT implement env-var stripping;
   DO NOT check for `$CLAUDE_PROJECT_DIR` in the Rust source. Any payload whose normalized
   `file_path` matches neither branch returns `Continue` without reading any file.
   `tool_input.file_path` is always the correct field name — the field `new_content`
   does not exist in Claude Code payloads (confirmed 0 occurrences in 5,235+ real events).

2. **`async = false` is a correctness requirement (ADR-025 Decision 12 / ADR-019):**
   Only sync-group plugins participate in `block_intent` aggregation at
   `executor.rs:100–117`. An `async = true` plugin's block signal is advisory-only.
   `async = false` MUST be explicit in the registry entry.

3. **`on_error = "continue"` (ADR-025 Decision 12 §12.3 / Decision 7):** Fail-open on
   crash. Consistent with `verify-factory-lock` precedent and Kleppmann efficiency-class
   lock model. Do NOT change to `on_error = "block"`.

4. **No `exec_subprocess` capability (ADR-025 Decision 12 §12.5):** The guard reads
   the on-disk STATE.md via `host::read_file` only. It never shells out to `git` or
   any other process. This eliminates the `env_allow` footgun class entirely. No
   `[hooks.capabilities.exec_subprocess]` block.

5. **`[hooks.capabilities.read_file]` block is mandatory (ADR-025 Decision 12 §12.6):**
   Omitting the block causes `CapabilityDenied` → guard fails open → silent no-op.
   The block MUST specify `path_allow = [".factory/STATE.md"]` and NOTHING ELSE.
   `ReadFileCaps` is `#[serde(deny_unknown_fields)]` with only `path_allow: Vec<String>`.
   Adding any other field (e.g., `max_bytes`, `timeout_ms`) breaks registry load entirely —
   the registry will fail to parse and the guard will never run. `max_bytes` and
   `timeout_ms` are arguments passed at the `host::read_file` call site in the WASM source
   code, NOT TOML fields. This is the fifth instance of the deny-by-default silent-no-op
   footgun class documented in ADR-025.

6. **No `serde_yaml` / `serde_norway` (Architecture Compliance Rule 4 — established in
   `verify-factory-lock`):** Parse using the same manual line-by-line scan as
   `verify-factory-lock`. `factory-lock-parse` crate MUST NOT add a YAML-parser
   dependency. `chrono` is a workspace dep.

7. **Shared crate is mandatory — no duplication (ADR-025 Decision 12 §12.4):** Two
   independent implementations of the same frontmatter scanner violate the no-duplication
   principle. `verify-state-timestamp-refresh` MUST import from `factory-lock-parse`, not
   copy-paste from `verify-factory-lock`. `verify-factory-lock` MUST also be migrated to
   import from `factory-lock-parse` in the same story scope.

8. **String inequality, not datetime parse (ADR-025 Decision 12 §12.2):** The guard
   detects "value did not change" by byte-level string comparison, not by parsing ISO-8601
   and comparing instants. This avoids datetime-parse edge cases being misused as a bypass.
   Full datetime semantics are enforced by `factory-lock-write.sh renew` (Mechanism 1).

### Registry Entry Spec (D16 — canonical TOML)

The registry entry for `verify-state-timestamp-refresh` MUST exactly match:

```toml
# ---------- verify-state-timestamp-refresh (PreToolUse, Edit|Write|MultiEdit) ----------
# S-17.04: PreToolUse guard — blocks Edit/Write/MultiEdit to .factory/STATE.md when
# proposed content (reconstructed for Edit/MultiEdit) does not advance timestamp:
# frontmatter (every write) or factory_lock.expires_at (when lock held).
# Decision 12 / BC-5.40.001 PC4.
# Trigger: file_path == ".factory/STATE.md" after canonical-path normalization.
# async = false REQUIRED — see ADR-019 + ADR-025 Decision 12

[[hooks]]
name = "verify-state-timestamp-refresh"
event = "PreToolUse"
tool = "Edit|Write|MultiEdit"
plugin = "hook-plugins/verify-state-timestamp-refresh.wasm"
priority = 143
timeout_ms = 5000
on_error = "continue"
async = false

[hooks.capabilities.read_file]
path_allow = [".factory/STATE.md"]
```

**Critical: `path_allow` only in capabilities block.** `ReadFileCaps` is
`#[serde(deny_unknown_fields)]`. Do NOT add `max_bytes` or `timeout_ms` to this block —
they are not struct fields and will break registry load. These values are arguments to
`host::read_file` in the Rust source code, not TOML configuration.

**Priority = 143:** Placed after `verify-factory-lock` entries (priority = 142). The
lock-identity check runs first (verify-factory-lock blocks if the lock is held by another
developer), then the timestamp-freshness check runs for the same writer. The existing
`verify-factory-lock` entry MUST be amended to add `priority = 142` so the ordering
relationship is explicit.

**tool = "Edit|Write|MultiEdit":** All three Claude Code tools that mutate file content
must be covered. MultiEdit is a distinct tool from Edit and must be listed explicitly.

**`async = false` annotation:** MUST be present explicitly (it does not default correctly
for all dispatcher versions — explicit is correct, per S-17.02 precedent).

## Edge Cases

| ID | Description | Expected Behavior |
|----|-------------|-------------------|
| EC-001 | `timestamp:` present in both on-disk and proposed but values are identical | Block: `TimestampStale`. This is the primary enforcement case — state-manager forgot to advance the timestamp. |
| EC-002 | `factory_lock` block present in on-disk STATE.md but absent from proposed content (unlock write) | No `LockExpiryStale` check — lock absent in proposed content means lock is being cleared. `TimestampStale` check still applies. |
| EC-003 | Both `timestamp:` and `factory_lock.expires_at` are stale simultaneously (lock held, neither field advanced) | Guard fires on `TimestampStale` first (checked before `LockExpiryStale`). One block signal is returned; both conditions are addressed by advancing both fields via `factory-lock-write.sh renew`. |
| EC-004 | On-disk STATE.md has no `timestamp:` key (brand-new file, first write to repo) | `Continue` — no prior value to compare against (ADR-025 §12.3 table row: "`timestamp:` absent in on-disk (first write ever) → Continue"). |
| EC-005 | Proposed STATE.md content is well-formed frontmatter but `timestamp:` is absent | `Block: TimestampStale` — absence of `timestamp:` in proposed content is itself a stale/missing-field violation per ADR-025 §12.3. |
| EC-006 | `file_path` in the Edit/Write/MultiEdit payload is a non-canonical form of `.factory/STATE.md`: leading `./`, double slashes, `/./` segments, absolute path (e.g., `/Users/x/proj/.factory/STATE.md` — the form Claude Code actually emits), or `..` traversal segments | The guard applies four relative-path normalizations followed by an ends_with trigger check (ADR-025 §12.7 R6 revised; `$CLAUDE_PROJECT_DIR` env-strip removed — WASI sandbox provides no env vars, making env-var-based stripping dead code): **(1)** strip a single leading `./`; **(2)** collapse `//` to `/`; **(3)** collapse `/./` to `/`; **(4)** **resolve `..` segments via segment-stack algorithm** — split on `/`, iterate left-to-right: push non-empty non-`.` segments onto a stack; on `..` pop the top if stack non-empty (above-root `..` pops an empty stack and is silently discarded); rebuild by joining stack with `/`. **Trigger condition (step 5 — match rule):** after steps 1–4, the guard fires when the result **equals** `.factory/STATE.md` (relative form) OR **ends with** `/.factory/STATE.md` (absolute or prefixed form). **Trigger examples:** `"./. factory/STATE.md"` (strip `./`) → `.factory/STATE.md` → equals → triggers; `"/Users/x/proj/.factory/STATE.md"` → no relative normalizations apply → ends_with `/.factory/STATE.md` → triggers; `"foo/../.factory/STATE.md"` → segment-stack → `.factory/STATE.md` → equals → triggers; `"../../.factory/STATE.md"` → above-root `..` discarded → `.factory/STATE.md` → equals → triggers. **Non-triggering examples:** `.factory/STATE.md.bak` — equals check fails, does not end with `/.factory/STATE.md` → Continue; `other/STATE.md` — neither check matches → Continue; `/tmp/STATE.md` — ends with `/tmp/STATE.md` not `/.factory/STATE.md` → Continue. Fail-open (Continue) applies to paths that cannot be normalized: non-UTF-8, paths that reduce to the empty string, or paths containing NUL bytes. |
| EC-007 | `host::read_file` returns a truncated file (partial read due to `max_bytes` limit) | The guard attempts to parse the truncated content. If the frontmatter is parseable (the `---` block is within the first 64 KiB, which it always is for STATE.md), the check proceeds normally. If unparseable, fail-open per EC-008. |
| EC-008 | On-disk STATE.md content is malformed YAML frontmatter (e.g., unclosed `---`, stray colons) | `Continue` (fail-open) — consistent with `verify-factory-lock` `MalformedLockBlock` → `log_warn` + Continue precedent. |
