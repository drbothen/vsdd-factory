# S-19.06 — host::read_prefix bounded partial read: head-c semantics, NEVER OUTPUT_TOO_LARGE, additive FFI entry point

**Epic:** E-19 — Post-rc.22 Operator Hardening
**Wave:** 2 (depends on S-19.03 — `path_util::resolve_path_for_allowlist` and `codes::NOT_FOUND` must be available; depends on S-19.04 — `hooks-registry.toml` preamble section must be in place before adding `capabilities.read_prefix` schema documentation)
**Depends on:** S-19.03 (creates `crates/factory-dispatcher/src/host/path_util.rs` and `codes::NOT_FOUND = -5`); S-19.04 (creates preamble comment block in `hooks-registry.toml`; `capabilities.read_prefix` schema doc extends that section)
**Priority:** P2 (new capability; no blocking behavioral defect; unlocks plugins that need bounded prefix reads without OUTPUT_TOO_LARGE risk)
**Subsystem anchor:** SS-01 (Hook Dispatcher Core) owns the host function implementation. The hook-sdk wrapper (SS-02 boundary) enables WASM plugins to call the new entry point.

## Narrative

`host::read_file` is an all-or-nothing read: it returns OUTPUT_TOO_LARGE (-3) when the file exceeds `max_bytes`. This is correct for plugins that parse TOML or YAML and require a complete, untruncated document. However, plugins that only need the first N bytes of a file — for example, reading YAML frontmatter from a large markdown artifact, or scanning a log file for a pattern in its header — cannot use `read_file` without risking OUTPUT_TOO_LARGE on any file that grows beyond the cap.

**The gap:** No `head -c`-style partial-read host function exists. Plugins that want bounded prefix reads must either set an aggressively large `max_bytes` cap (risking OUTPUT_TOO_LARGE on even larger files) or implement workarounds.

**The fix (BC-1.17.001 v1.1, ADR-025 Decision 15):** Add `read_prefix(path: &str, max_bytes: u32, timeout_ms: u32) -> i32` as an additive FFI entry point in the `vsdd` WASM import namespace. The function returns at most `max_bytes` bytes from the start of the file (equivalent to `head -c max_bytes`). It is **guaranteed never to return OUTPUT_TOO_LARGE (-3)** — by construction, `max_bytes` IS the output cap, so the response always fits within the requested bound.

**Critical invariants (BC-1.17.001):**
- `read_file` all-or-nothing semantics are **IMMUTABLE** (Invariant 2). Plugins relying on `read_file` for complete TOML/YAML parsing are unaffected. Silent truncation-as-success would corrupt those plugins' parse (D-d rationale). `read_prefix` is the alternative for plugins that explicitly want a bounded prefix.
- **Separate `capabilities.read_prefix` block** is required in the registry entry (Invariant 3). A plugin granted `capabilities.read_file` does NOT automatically receive `capabilities.read_prefix`. The two capabilities are independently declared, enabling defense-in-depth.
- **Traversal defense is identical to `read_file`** (Invariant 4). `read_prefix` imports `resolve_path_for_allowlist` from `crates/factory-dispatcher/src/host/path_util.rs` (created by S-19.03), using the same rejoin algorithm and `starts_with` allowlist check.
- **NOT_FOUND semantics are consistent with BC-2.07.001** (Invariant 5). Absent-file paths within the allowlist return NOT_FOUND (-5) and emit `internal.file_not_found` — same as `read_file` after S-19.03.

**ABI treatment:** `read_prefix` is additive. HOST_ABI_VERSION remains 1. Plugins that do not import `read_prefix` are unaffected; the new import is visible only to plugins that declare it in their FFI binding.

**Signature authority:** BC-1.17.001 is authoritative. The signature is `read_prefix(path: &str, max_bytes: u32, timeout_ms: u32) -> i32`. ADR-025 Decision 15 and BC-1.17.001 agree on the signature (reconciled at the ADR's pass-3 amendment); BC-1.17.001 remains the normative contract.

## Architecture Mapping

**SS-01 changes (`crates/factory-dispatcher/src/host/read_prefix.rs` — new file):**
- Implement `read_prefix(path: &str, max_bytes: u32, timeout_ms: u32) -> i32`:
  1. Capability check: require `capabilities.read_prefix` block in registry; return CAPABILITY_DENIED (-1) if absent (does NOT fall back to `capabilities.read_file`)
  2. Path resolution: call `resolve_path_for_allowlist` from `path_util.rs` (created by S-19.03); check `starts_with` against the `capabilities.read_prefix` `path_allow` list; return CAPABILITY_DENIED (-1) for out-of-allowlist paths
  3. Existence check: if path is allowlisted but file absent, return NOT_FOUND (-5) and emit `internal.file_not_found` (same semantics as `read_file` post S-19.03)
  4. Bounded read: open file, read at most `max_bytes` bytes from start (head-c semantics); if `max_bytes = 0`, return empty payload immediately without opening; return exit code 0 on success
  5. Timeout: respect `timeout_ms`; return TIMEOUT (-2) on expiry
  6. Directory/OS error: return INTERNAL_ERROR (-99)
  7. **NEVER emit or return OUTPUT_TOO_LARGE (-3)** — `max_bytes` IS the cap; data beyond the cap is not read
- Unit tests for AC-001..AC-006 (T-001..T-007) inline in `read_prefix.rs`

**SS-01 changes (`crates/factory-dispatcher/src/host/mod.rs`):**
- Register `read_prefix` in the host dispatch table (additive, parallel to `read_file`)

**`read_file.rs` is NOT modified** — `read_file` semantics are immutable per BC-1.17.001 Invariant 2. No changes to `read_file.rs` in this story.

**`path_util.rs` is NOT modified** — created by S-19.03; `resolve_path_for_allowlist` is imported as-is. If S-19.03 is not yet merged, this story cannot proceed (enforced by `depends_on: [S-19.03]`).

**`codes::NOT_FOUND = -5` is NOT re-declared** — defined by S-19.03 in the codes module; `read_prefix.rs` imports from there.

**hook-sdk changes (`crates/hook-sdk/src/host.rs`):**
- Add `read_prefix(path: &str, max_bytes: u32, timeout_ms: u32) -> i32` as an FFI extern function in the `vsdd` import namespace (parallel to existing `read_file` wrapper)
- Return value uses same `codes::*` vocabulary; OUTPUT_TOO_LARGE is mechanically excluded from this fn's return paths (by construction in the dispatcher implementation)

**Registry changes (`plugins/vsdd-factory/hooks-registry.toml`):**
- Document `capabilities.read_prefix` capability block schema in the preamble comment section (added by S-19.04, which also anchors `tool =` patterns). No live `[[hooks]]` entries in this story declare `capabilities.read_prefix` — the capability is available for operators to use in their own plugins. The preamble schema comment makes the capability discoverable.

## Edge Cases

| ID | Scenario | Expected Behavior |
|----|----------|-------------------|
| EC-001 | `max_bytes = 0` | Returns empty byte sequence (0 bytes), exit code 0. File is not opened. |
| EC-002 | `max_bytes` greater than file size | Returns full file content (no padding, no OUTPUT_TOO_LARGE). Response length = file_size. |
| EC-003 | File is absent, path is within `capabilities.read_prefix` allowlist | Returns NOT_FOUND (-5); emits `internal.file_not_found`. Same semantics as BC-2.07.001 part c. |
| EC-004 | Path is outside all allowed prefixes in `capabilities.read_prefix` | Returns CAPABILITY_DENIED (-1); emits `internal.capability_denied reason=path_not_allowed`. Check is against `capabilities.read_prefix` path_allow, not `capabilities.read_file`. |
| EC-005 | Plugin has `capabilities.read_file` but no `capabilities.read_prefix` block | Returns CAPABILITY_DENIED (-1). `read_file` capability does not extend to `read_prefix` (Invariant 3 defense-in-depth). |
| EC-006 | Read times out before `max_bytes` bytes are returned | Returns TIMEOUT (-2); emits `internal.timeout`. Same timeout semantics as `read_file`. |
| EC-007 | Target path is a directory, not a regular file | Returns INTERNAL_ERROR (-99); does not return partial content. |
| EC-008 | Plugin compiled without importing `read_prefix` from hook-sdk | Plugin cannot call `read_prefix` (absent from its import table). No runtime error; the capability is opt-in by declaration. |
