# S-21.12 — wasmtime major-version move ≥ 46.0.2: clear RUSTSEC-2026-0188/CVE-2026-58494 + RUSTSEC-2026-0222, add cargo-deny advisories CI job

## Narrative

- **As a** factory pipeline operator and future SEC-001 preopen hardening implementer
- **I want** the workspace to move from `wasmtime = "44.0"` to `wasmtime = "46.0.2"`, closing
  the FilePerms bypass advisory that survives on the entire 44.x line, and to have a
  `cargo deny check advisories` CI job that surfaces any future advisory before human-directed
  triage catches it
- **So that** (a) the WASM sandbox's FilePerms enforcement is not bypassable via `path_link` /
  `path_rename` destination paths, (b) the type-index confusion advisory is also cleared, and
  (c) SEC-001 preopen hardening can land knowing both integrity holes are closed

## Context / Finding Summary

PR #770 bumped `wasmtime-wasi` from `44.0.0` to `44.0.3`, clearing RUSTSEC-2026-0149 and
RUSTSEC-2026-0182. The fresh-eyes review of PR #770 (pr-review.md, PR-001) found that the
PR body's central claim — "this unblocks SEC-001 preopen hardening" — was false: a second
FilePerms bypass advisory (RUSTSEC-2026-0188, CVE-2026-58494) survives on every version of
the 44.x line and has no 44.x backport fix. The review mandated that PR-001 be resolved by
scheduling a concrete story anchor for the `>=46.0.2` move before SEC-001 is dispatched.
This story is that anchor.

**RUSTSEC-2026-0188 (CVE-2026-58494) — severity: see CVSS note below**

WASI hard links and renames bypass `wasmtime-wasi`'s `FilePerms` for the destination
path. A WASM plugin holding a read-only preopen (e.g., `FilePerms::READ`) can still create
a hard link or rename file to that directory's contents, bypassing the intended write
restriction at the filesystem level. The vulnerable configuration is `DirPerms::all() +
FilePerms::READ` — exactly the configuration SEC-001 preopen hardening plans to set in
the `invoke.rs` host-function registration path.

Patched: `>= 46.0.1`, `>= 45.0.3 < 46.0.0`, `>= 36.0.12`, `>= 24.0.11`. No 44.x fix.

> **CVSS confirmation required (security-reviewer):** The initial triage cited CVSS 7.5 HIGH
> for RUSTSEC-2026-0188. The advisory page may reflect 6.5 MEDIUM. The security-reviewer MUST
> confirm the correct score before it is cited in the PR body — do not forward this score
> from the spec to the PR description without verification.

**RUSTSEC-2026-0222 — LOW (no CVE assigned)**

Stores can mix up type indices between Engine instances in wasmtime 44.x and 45.x.
Patched: `>= 46.0.2 < 47.0.0`, `>= 47.0.3`. No 45.x fix.

**PR-007: cargo-deny CI gap**

`deny.toml` exists at repo root with `[advisories] ignore = []` (deny-all posture), but no
GitHub Actions workflow invokes it. RUSTSEC-2026-0188 was not surfaced by project tooling;
it required human-directed manual triage. The gap must be closed so future advisories are
caught automatically before they sit silently on `develop`.

**SEC-001 sequencing constraint**

SEC-001 preopen hardening (the plan to configure `DirPerms::all() + FilePerms::READ` in the
`setup_host_on_store_data` host-function registration path in `invoke.rs`) is verbatim the
vulnerable configuration for RUSTSEC-2026-0188. SEC-001 MUST NOT be dispatched until
S-21.12 is merged and the wasmtime floor is confirmed at `>=46.0.2`. When the SEC-001 story
is authored, it MUST carry `depends_on: [S-21.12]` to encode this gate structurally.

## Judgment Calls Documented

### Version target: 46.0.2 (not 45.0.3)

45.0.3 clears RUSTSEC-2026-0188 but does NOT clear RUSTSEC-2026-0222 (no 45.x fix
exists; patched range starts at `>=46.0.2,<47.0.0`). Landing at 45.0.3 would mean the
`cargo deny check advisories` CI job (PR-007 deliverable) ships permanently red on
RUSTSEC-2026-0222. That is not production-grade: we would be shipping an active advisory
gate with a known-red state from day one.

Decision: target `wasmtime = "46.0.2"` / `wasmtime-wasi = "46.0.2"` (Cargo interprets
`"46.0.2"` as `>=46.0.2,<47.0.0`), clearing both advisories and shipping a green CI gate.

### BC determination: BC-free

This story delivers: a Cargo manifest edit, a lockfile update, a GitHub Actions CI job, and
a Rust version-gate unit test. None of these items introduce a new behavioral API surface
observable by other components or behavioral contracts. The wasmtime version move fixes a
security defect in the underlying sandbox — the hook plugin dispatch semantics are
unchanged. The CI job is an infrastructure gate with no runtime behavioral contract.
BC-free is the correct determination.

### Mechanical SEC-001 gate: AC-008 Rust unit test

AC-008 requires a Rust unit test (`test_wasmtime_version_satisfies_rustsec_2026_0188_patched_range`)
that reads the resolved wasmtime-wasi version from `Cargo.lock` and asserts `>=46.0.2`. This
test fails if wasmtime-wasi is inadvertently downgraded in a future `cargo update`. It encodes
the SEC-001 precondition mechanically rather than relying on human memory or documentation.

**Confirmed mechanism:** The wasmtime crate does not expose a public `VERSION` constant
(verified: `grep -rn 'pub const VERSION\|pub static VERSION'` against the 44.0.3 source
tree returns no results; the version string is only used internally via `env!("CARGO_PKG_VERSION")`
in wasmtime's own code, which resolves to wasmtime's own package version but is not exported).
The correct mechanism is to parse `Cargo.lock` at test time. `Cargo.lock` is a TOML file with
`[[package]]` array entries; the wasmtime-wasi entry has `name = "wasmtime-wasi"` and
`version = "44.0.3"` (current). The test locates this entry, extracts the version string, and
performs a semver comparison against `46.0.2`. This is the production-grade gate per Canonical
Principle Rule 1 — not a doc comment, not a README note.

### AC-008: Rust unit test asserts wasmtime-wasi Cargo.lock resolved version ≥ 46.0.2 — mechanical SEC-001 sequencing gate (traces to RUSTSEC-2026-0188 patched range; SEC-001 precondition)

A Rust unit test named `test_wasmtime_version_satisfies_rustsec_2026_0188_patched_range`
MUST be present in `crates/factory-dispatcher/` (in `src/` or `tests/`). The test MUST:

1. Locate `Cargo.lock` from the workspace root at test time using
   `Path::new(env!("CARGO_MANIFEST_DIR")).join("../../Cargo.lock")` (or equivalent
   workspace-root resolution)
2. Read and parse the TOML content to find the `[[package]]` entry where `name = "wasmtime-wasi"`
3. Extract the `version` field string from that entry
4. Parse the extracted string as a semver triple
5. Assert the parsed version `>= 46.0.2`

**Confirmed mechanism:** `Cargo.lock` is a TOML file with `[[package]]` array entries. At
wasmtime 44.0.3 (current), the relevant entry reads:
```

version = "44.0.3"
```
Parsing this file is straightforward via the `toml` crate (already a workspace transitive
dep) or a targeted line-scan. The wasmtime crate does NOT export a public version constant;
`env!("CARGO_PKG_VERSION")` written in our code expands to our own crate's version, not
wasmtime's.

**RED-before / GREEN-after state table:**

| State | wasmtime-wasi in Cargo.lock | Test outcome |
|-------|---------------------------|--------------|
| Before story merges (current) | 44.0.3 (< 46.0.2) | FAIL — confirms the test is a valid Red Gate |
| After story merges | >= 46.0.2 | PASS |
| Future inadvertent downgrade | < 46.0.2 | FAIL — SEC-001 gate fires correctly |

If wasmtime-wasi is ever inadvertently downgraded (e.g., by a misapplied `cargo update
--precise` to a version below the floor), this test fails, blocking dispatch of SEC-001
preopen hardening via the SEC-001 story's `depends_on: [S-21.12]` pipeline gate.

The test MUST run unconditionally under `cargo test -p factory-dispatcher` — it must not
be guarded by a `#[cfg(...)]` attribute that excludes it from standard CI runs.

- **Test:** `cargo test -p factory-dispatcher test_wasmtime_version_satisfies_rustsec_2026_0188_patched_range`
  exits non-zero at wasmtime-wasi 44.0.3 (confirming Red Gate discipline); exits 0 at
