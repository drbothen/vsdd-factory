# S-19.04 — Registry/bundle hygiene: orphan WASM removal + tool-filter regex anchoring convention + lint check

**Epic:** E-19 — Post-rc.22 Operator Hardening
**Wave:** 2 (no hard dependencies on S-19.01..S-19.03; can run in parallel with wave 1)
**Depends on:** none
**Priority:** P2 (hygiene defects; no blocking behavioral gap but increase bundle size and create latent mismatch bugs)
**Subsystem anchor:** SS-07 (Hook Bash Layer) owns `hooks-registry.toml`. SS-09 (Configuration and Activation) owns the bundle and release pipeline.

## Narrative

Post-rc.22 operator install inspection found two registry/bundle hygiene gaps:

**Finding (a) — Orphan WASMs in bundle:** The rc.22 release bundle at `~/.claude/plugins/cache/claude-mp/vsdd-factory/1.0.0-rc.22/hook-plugins/` contains three WASM files that are unreferenced by any entry in EITHER `hooks-registry.toml` OR `resolvers-registry.toml`:
- `hello-hook.wasm` — a development sample; never intended for production distribution
- `vsdd_context_resolvers.wasm` — context resolver library (underscore variant); the live resolver is the hyphen variant `vsdd-context-resolvers.wasm` (referenced by `resolvers-registry.toml`); this underscore variant is a stale build artifact
- `wasm_resolver_export.wasm` — resolver export artifact; not referenced by any registry entry

**Note — `vsdd-context-resolvers.wasm` (hyphen) is NOT an orphan:** It is the live WaveContextResolver registered in `resolvers-registry.toml` as `plugin = "hook-plugins/vsdd-context-resolvers.wasm"`. The dispatcher printed "Compiled 1 resolver modules from .../resolvers-registry.toml" at every smoke-gate dispatch, confirming it was loaded. Orphan-status determination requires checking BOTH `hooks-registry.toml` (hook plugins) AND `resolvers-registry.toml` (context resolvers); checking only `hooks-registry.toml` produces a false-positive orphan classification for this file (root cause of v1.0 story defect, corrected in v1.1).

These three unreferenced files add ~0.5 MB to every operator install bundle and create noise in operator directory listings. The release pipeline's WASM-whitelist sweep (PR #431) does not explicitly exclude them.

**Decision for hello-hook.wasm:** This is a development sample created during initial plugin scaffolding. It has no production value and MUST be excluded from release bundles. Rationale: shipping development samples in production distributions is a packaging anti-pattern; the sample serves its purpose in the dev repo but should not be installed by operators. Decision recorded here (D-NNN TBD at codification).

**Finding (b) — Tool-filter regex semantics undocumented:** The `tool` field in `[[hooks]]` entries (e.g., `tool = "Edit|Write"`) is matched as a regex SEARCH (substring match), not as a fullmatch. This means `tool = "Edit|Write"` also fires on `MultiEdit` (because "Edit" is a substring of "MultiEdit"). This is semantically incorrect for hooks that are meant only for `Edit` and `Write`.

The fix requires:
1. A documented anchoring convention: hooks targeting specific tools should use anchored patterns (`^(Edit|Write)$`) to prevent substring matches
2. A hooks-registry.toml preamble comment explaining the regex-search semantics
3. A lint check (bats test) that scans all `tool =` entries and warns when an unanchored pattern could match unintended tool names (specifically: `Edit` without `^` would match `MultiEdit`; `Write` without `^` would match `MultiWrite` if introduced in future; `Bash` without anchoring would match future `BashAsync`)
4. Existing unanchored entries that fire on wrong tools to be corrected with `^(...)$` anchors

Post-release verification: `hello-hook.wasm` absent from a freshly-built bundle. Exit non-zero if present. |
| AC-002 | `vsdd_context_resolvers.wasm` (underscore, stale artifact) and `wasm_resolver_export.wasm` are excluded from the hook-plugins/ directory in the release bundle. `vsdd-context-resolvers.wasm` (hyphen) MUST remain — it is the live WaveContextResolver registered in `resolvers-registry.toml` as `plugin = "hook-plugins/vsdd-context-resolvers.wasm"`. A keep-assertion in the bundle verification step confirms `hook-plugins/vsdd-context-resolvers.wasm` is present after the bundle is assembled. | Exclusion gate: zero occurrences of `vsdd_context_resolvers.wasm` and `wasm_resolver_export.wasm` under `hook-plugins/` in the bundle (exit non-zero if present). Keep-assertion gate: `test -f hook-plugins/vsdd-context-resolvers.wasm` exits 0 (exit non-zero if absent — L-F2-silent-inert-validator-class: assertion must be load-bearing, not advisory). |
| AC-003 | `plugins/vsdd-factory/hooks-registry.toml` contains a preamble comment section (placed before the first `[[hooks]]` entry) that documents: (1) the `tool` field uses regex SEARCH semantics (not fullmatch); (2) the anchoring convention (`^(ToolA\|ToolB)$`) for hooks targeting specific tool sets; (3) why anchoring matters (e.g., `Edit` without anchoring matches `MultiEdit`). | `grep -q "regex SEARCH\|fullmatch\|anchoring" plugins/vsdd-factory/hooks-registry.toml` exits 0. |
| AC-004 | All existing `tool =` entries in `hooks-registry.toml` that target specific tools (not wildcard) use anchored patterns: `^(Tool1\|Tool2)$` form. Entries that intentionally match tool prefixes must carry an inline comment explaining the intent. | Extract tool values and check anchoring: `grep -E '^tool = ' plugins/vsdd-factory/hooks-registry.toml \| grep -v 'tool = "^' \| grep -v '# intent:'` produces zero lines (no unanchored entries without intent comments). Exit non-zero if any unanchored lines remain. Positive fixture: entry `tool = "^(Edit\|Write)$"` → value starts with `^` → filtered out (passes, zero output). Negative fixture: entry `tool = "Edit\|Write"` (no leading `^`) → value does not start with `^` → appears in output (exits non-zero). |
| AC-005 | A bats lint test (`plugins/vsdd-factory/tests/registry-tool-filter-anchoring.bats`) verifies that every `tool =` line in `hooks-registry.toml` either (a) uses an anchored pattern beginning with `^` or (b) carries an `# intent:` inline comment. The test exits non-zero if any unanchored, uncommented `tool =` entry is found. | `bats plugins/vsdd-factory/tests/registry-tool-filter-anchoring.bats` exits 0 after all registry entries are fixed. The test itself must exit non-zero on a fixture registry with an unanchored entry. |
| AC-006 | The bundle orphan-detection script determines WASM orphan status by querying BOTH `hooks-registry.toml` AND `resolvers-registry.toml`. A WASM present under `hook-plugins/` but referenced only by `resolvers-registry.toml` is classified as non-orphan and must NOT be excluded. A bats test (`plugins/vsdd-factory/tests/bundle-orphan-detection.bats`) verifies: (a) a fixture WASM referenced only by `resolvers-registry.toml` is classified non-orphan; (b) a fixture WASM referenced only by `hooks-registry.toml` is classified non-orphan; (c) a fixture WASM referenced by neither registry is classified as orphan. | `bats plugins/vsdd-factory/tests/bundle-orphan-detection.bats` exits 0. The test must exit non-zero on a fixture where the `resolvers-registry.toml` check is skipped (regression gate for the v1.0 defect: false-positive orphan on `vsdd-context-resolvers.wasm`). |

## Architecture Mapping

- `.github/workflows/release.yml` — add explicit exclusion list for 3 orphan artifacts (`hello-hook.wasm`, `vsdd_context_resolvers.wasm`, `wasm_resolver_export.wasm`) in the bundle assembly step; add keep-assertion confirming `hook-plugins/vsdd-context-resolvers.wasm` IS present post-assembly (live WaveContextResolver per `resolvers-registry.toml`; exit non-zero if absent)
- `plugins/vsdd-factory/hooks-registry.toml` — add preamble comment block; update all `tool =` entries to use anchored patterns
- `plugins/vsdd-factory/tests/registry-tool-filter-anchoring.bats` — new bats lint test for AC-005

## Edge Cases

| ID | Scenario | Expected Behavior |
|----|----------|-------------------|
| EC-001 | An existing hook intentionally uses an unanchored pattern (e.g., for future tool name extensions) | Must carry `# intent: unanchored — matches future Tool*` inline comment. Lint test accepts entries with `# intent:` comment. |
| EC-002 | A new hook is added without an anchored pattern | Lint test (AC-005) blocks the addition in CI. |
| EC-003 | A WASM file is present under `hook-plugins/` but referenced only by `resolvers-registry.toml`, not `hooks-registry.toml` | Orphan-status determination MUST check BOTH registries. A file referenced by either registry is non-orphan and must not be excluded from the bundle. `vsdd-context-resolvers.wasm` (hyphen) is the canonical example: it is the live WaveContextResolver registered in `resolvers-registry.toml` and must remain in `hook-plugins/`. Root cause of v1.0 story defect: checking only `hooks-registry.toml` produced a false-positive orphan classification for this file (corrected v1.1). |
