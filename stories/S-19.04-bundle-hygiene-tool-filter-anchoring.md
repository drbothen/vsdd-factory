# S-19.04 — Registry/bundle hygiene: orphan WASM removal + tool-filter regex anchoring convention + lint check

**Epic:** E-19 — Post-rc.22 Operator Hardening
**Wave:** 2 (no hard dependencies on S-19.01..S-19.03; can run in parallel with wave 1)
**Depends on:** none
**Priority:** P2 (hygiene defects; no blocking behavioral gap but increase bundle size and create latent mismatch bugs)
**Subsystem anchor:** SS-07 (Hook Bash Layer) owns `hooks-registry.toml`. SS-09 (Configuration and Activation) owns the bundle and release pipeline.

## Narrative

Post-rc.22 operator install inspection found two registry/bundle hygiene gaps:

**Finding (a) — Orphan WASMs in bundle:** The rc.22 release bundle at `~/.claude/plugins/cache/claude-mp/vsdd-factory/1.0.0-rc.22/hook-plugins/` contains three WASM files that are unreferenced by any entry in EITHER `hooks-registry.toml` OR `resolvers-registry.toml`:
- `hello-hook.wasm` — a development sample; never intended for production distribution
- `vsdd_context_resolvers.wasm` — context resolver library (underscore variant); the live resolver is the hyphen variant `vsdd-context-resolvers.wasm` (referenced by `resolvers-registry.toml`); this underscore variant is a stale build artifact
- `wasm_resolver_export.wasm` — resolver export artifact; not referenced by any registry entry

**Note — `vsdd-context-resolvers.wasm` (hyphen) is NOT an orphan:** It is the live WaveContextResolver registered in `resolvers-registry.toml` as `plugin = "hook-plugins/vsdd-context-resolvers.wasm"`. The dispatcher printed "Compiled 1 resolver modules from .../resolvers-registry.toml" at every smoke-gate dispatch, confirming it was loaded. Orphan-status determination requires checking BOTH `hooks-registry.toml` (hook plugins) AND `resolvers-registry.toml` (context resolvers); checking only `hooks-registry.toml` produces a false-positive orphan classification for this file (root cause of v1.0 story defect, corrected in v1.1).

These three unreferenced files add ~0.5 MB to every operator install bundle and create noise in operator directory listings.

**Ground truth for release.yml (verified at rc.22):** `vsdd_context_resolvers.wasm` and `wasm_resolver_export.wasm` are currently PASSED THROUGH into the bundle — the `vsdd_context_resolvers.wasm|wasm_resolver_export.wasm) ;;` arm exits the inner case WITHOUT `continue`, so control falls through to `cp "$wasm" artifact/`; the comment "pass through the two legitimate underscore binaries" confirms their inclusion. They are NOT currently excluded. `hello-hook.wasm` is ACTIVELY built via the `--example hello-hook` build step and explicitly copied via the `cp …examples/hello-hook.wasm artifact/` staging step. The fix requires TWO changes: (1) REMOVE the hello-hook build step and copy step; (2) MOVE the `vsdd_context_resolvers.wasm|wasm_resolver_export.wasm` pair from the pass-through arm into the skip path (joining `*) echo "skip..."; continue` behavior) at the inner case-arm `vsdd_context_resolvers.wasm|wasm_resolver_export.wasm) ;;` at both artifact-staging sites. Nothing is "preserved as exclusion" because no exclusion of the pair currently exists. **O-P6-002 (orchestrator adjudication):** both underscore (`vsdd_context_resolvers.wasm`) AND hyphen (`vsdd-context-resolvers.wasm`) resolver files exist as distinct artifacts in the rc.22 bundle — byte-verified in the post-install smoke: 341,975 B vs 342,292 B — confirming the two-file premise and the keep-assertion for the hyphen file stand.

**Decision for hello-hook.wasm:** This is a development sample created during initial plugin scaffolding. It has no production value and MUST NOT be included in release bundles. The corrective action requires two changes: (1) remove the explicit `cargo build --example hello-hook` step and the `cp ...hello-hook.wasm artifact/` staging step from `.github/workflows/release.yml`; (2) move `vsdd_context_resolvers.wasm|wasm_resolver_export.wasm` from the current pass-through arm into the skip path at the inner case-arm `vsdd_context_resolvers.wasm|wasm_resolver_export.wasm) ;;` at both artifact-staging sites — these two underscore artifacts are orphans that must not ship. Decision recorded here (D-NNN TBD at codification); policy change registered as POLICY 20 (release_bundle_no_dev_samples). **Secondary rationale for BUILD-OMISSION approach:** `hello-hook.wasm` contains no underscore character — the `*_*.wasm` outer-glob arm in the release.yml staging step would copy it if present in build output. However, it additionally cannot reach staging input through a secondary mechanism: `--example hello-hook` outputs land at `target/wasm32-wasip1/release/examples/hello-hook.wasm`; the release.yml staging glob `target/wasm32-wasip1/release/*.wasm` is non-recursive and never descends into the `examples/` subdirectory, so even if the build step existed, the `.wasm` would not reach the staging copy loop. The primary exclusion mechanism (BUILD-OMISSION: remove the build step) is still the correct fix because the secondary mechanism is a filesystem accident rather than an explicit guard.

**Finding (b) — Tool-filter regex semantics undocumented:** The `tool` field in `[[hooks]]` entries (e.g., `tool = "Edit|Write"`) is matched as a regex SEARCH (substring match), not as a fullmatch. This means `tool = "Edit|Write"` also fires on `MultiEdit` (because "Edit" is a substring of "MultiEdit"). This is semantically incorrect for hooks that are meant only for `Edit` and `Write`.

The fix requires:
1. A documented anchoring convention: hooks targeting specific tools should use anchored patterns (`^(Edit|Write|MultiEdit)$` for multi-tool Edit/Write/MultiEdit guards; `^Bash$`/`^Read$`/`^Agent$` for single-tool singletons) to prevent substring matches and ensure all first-class mutating vectors are covered
2. A hooks-registry.toml preamble comment explaining the regex-search semantics
3. A lint check (bats test) that scans all `tool =` entries and warns when an unanchored pattern could match unintended tool names (specifically: `Edit` without `^` would match `MultiEdit`; `Write` without `^` would match `MultiWrite` if introduced in future; `Bash` without anchoring would match future `BashAsync`)
4. Existing unanchored entries that fire on wrong tools to be corrected with `^(...)$` anchors
