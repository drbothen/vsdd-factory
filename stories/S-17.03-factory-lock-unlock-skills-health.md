# S-17.03: /factory-lock + /factory-unlock Skills + Health Status Surfacing

**Epic:** E-17 — Factory State Durability and Concurrency (brownfield-backfill #170)
**Wave:** 3 (depends on S-17.01 schema + S-17.02 guard)
**Depends on:** S-17.01 (schema); S-17.02 (guard active before skills delivered)
**Blocks:** none
**Priority:** P1 (user-facing entry points for CAP-031 lock management)
**BC gate:** BC-6.23.001 v1.0 (draft; POL-14 auto-promotion on PR merge)

## Narrative

- **As a** developer managing concurrent factory sessions
- **I want** explicit `/factory-lock` and `/factory-unlock` skills that acquire and
  release the cross-session factory lock with CAS-protected pushes, plus three-state
  lock status surfacing in `/factory-health` and `/factory-worktree-health`
- **So that** I can deliberately take ownership of the factory-artifacts branch before
  beginning pipeline work, release it cleanly when done, break-glass force-release a
  stale lock with an audit trail, and always know who holds the lock and when it expires
  from any health check

## Acceptance Criteria

### AC-001 (traces to BC-6.23.001 postcondition PC1 — /factory-lock success)

When `/factory-lock` is run and the factory is unlocked (or the lock is expired), the
acquire succeeds:
1. `state-manager` writes `factory_lock = { holder: <current_email>, locked_at: <now_iso8601>, expires_at: <now_iso8601 + 2700s> }` into STATE.md frontmatter.
2. `state-manager` commits and pushes using the CAS primitive from S-17.01 (D6):
   `git -C .factory fetch origin factory-artifacts && EXPECTED_SHA=... && git -C .factory push --force-with-lease=factory-artifacts:"${EXPECTED_SHA}" origin factory-artifacts`
3. A `factory.lock.acquired` event is emitted to the SS-03 event pipeline with fields:
   `holder` (email), `locked_at` (ISO-8601), `expires_at` (ISO-8601).
4. User sees: `Factory lock acquired by <email>. Expires at <expires_at>.`

**Error variant:** `AcquireRaceRejected` (on CAS push rejection)
**Test:** `test_BC_6_23_001_factory_lock_acquire_success_schema_event_message()`

### AC-002 (traces to BC-6.23.001 postcondition PC2 — /factory-lock CAS rejection)

When the CAS push is rejected (non-zero exit from `git push --force-with-lease`), the
acquire MUST fail with:
```
Acquire failed — concurrent lock write detected. Fetch and retry.
(TOCTOU acquire-race CWE-367: another session wrote the lock between your fetch and your push.)
```
STATE.md MUST NOT be in a partial written state (the push rejection means the write was
rejected by git — no local STATE.md commit should be present). No audit event emitted
for a rejected acquire.

**Error variant:** `AcquireRaceRejected`
**Test:** `test_BC_6_23_001_factory_lock_cas_rejection_error_message()`

### AC-003 (traces to BC-6.23.001 postcondition PC3 — /factory-lock foreign lock held: refuse)

When the fetch reveals `factory_lock.holder` is set, `now ≤ expires_at`, and
`holder != current_git_email`, the `/factory-lock` skill MUST exit without attempting
the CAS push and MUST display the refusal message containing ALL FIVE fields (matching
BC-4.13.001 PC1 format):
- Holder email
- `locked_at` timestamp
- `expires_at` timestamp
- `time_remaining` (human-readable)
- `/factory-unlock --force` command

**Error variant:** `ForeignLockHeld`
**Test:** `test_BC_6_23_001_factory_lock_foreign_lock_refusal_message_all_five_fields()`

### AC-004 (traces to BC-6.23.001 postcondition PC4 — /factory-unlock self-release)

When `factory_lock.holder == current_git_email` and the user runs `/factory-unlock`:
1. `state-manager` removes the `factory_lock` key entirely from STATE.md frontmatter
   (BC-5.40.001 PC2: not null — key must be absent).
2. `state-manager` commits and pushes (CAS push per S-17.01 D6).
3. A `factory.lock.released` event emitted with: `holder` (email), `locked_at`,
   `released_at` (ISO-8601 of the release instant).
4. User sees: `Factory lock released.`

**Error variant:** `UnlockCASRejected` (if CAS push rejected)
**Test:** `test_BC_6_23_001_factory_unlock_self_release_clears_key_emits_event()`

### AC-005 (traces to BC-6.23.001 postcondition PC5 — /factory-unlock non-holder rejection)

When `factory_lock.holder != current_git_email` and the user runs plain `/factory-unlock`
(no `--force`):
1. Skill exits non-zero.
2. Error displayed: `Cannot unlock — factory is held by <holder_email>. Use /factory-unlock --force to force-release.`
3. STATE.md MUST NOT be modified.
4. No event emitted.

**Error variant:** `NotLockHolder`
**Test:** `test_BC_6_23_001_factory_unlock_non_holder_rejected_no_state_change()`

### AC-006 (traces to BC-6.23.001 postcondition PC6 — /factory-unlock --force break-glass)

When the user runs `/factory-unlock --force` (regardless of current holder):
1. `state-manager` removes the `factory_lock` key entirely from STATE.md.
2. `state-manager` commits and pushes (CAS push per S-17.01 D6).
3. A `factory.lock.stolen` audit event MUST be emitted with ALL FOUR required fields:
   - `stolen_by`: `current_git_email`
   - `stolen_from`: `factory_lock.holder` at force-release time
   - `holder_locked_at`: original `locked_at` from the lock block
   - `stolen_at`: ISO-8601 of the force-release instant
4. The event is PERMANENT — if SS-03 sink is unavailable, proceed with the lock clear
   but log the emission failure as `log_warn` (BC-6.23.001 Invariant 2 + EC-008).
5. User sees: `Factory lock force-released. Audit event 'factory.lock.stolen' emitted.`

Special case (EC-010): If `/factory-unlock --force` is run against a self-held lock,
emit `factory.lock.released` (NOT `factory.lock.stolen` — `stolen_by == stolen_from`
is not a meaningful audit event).

**Error variant:** `ForceStealAudited`
**Test:** `test_BC_6_23_001_factory_unlock_force_emits_stolen_event_all_four_fields()`

### AC-007 (traces to BC-6.23.001 postcondition PC7 — /factory-health three-state display)

The `/factory-health` skill MUST display one of three lock status lines based on the
local STATE.md `factory_lock` block:
- `Factory lock: FREE` — `factory_lock` absent or expired
- `Factory lock: HELD by this session (expires <expires_at>)` — holder is current email AND unexpired
- `Factory lock: HELD by <holder_email> since <locked_at> (expires <expires_at>)` — holder is another email AND unexpired

Malformed block renders as: `Factory lock: FREE (malformed block — treated as unlocked)`.

The status is read from the LOCAL STATE.md (no fetch required — local view is what matters
for informational display).

**Test:** `test_BC_6_23_001_factory_health_three_state_display()`
(three variants of STATE.md → assert three display strings)

### AC-008 (traces to BC-6.23.001 postcondition PC8 — /factory-worktree-health three-state display)

The `/factory-worktree-health` skill MUST display the same three-state lock status as
AC-007, using the same display strings and the same local STATE.md read logic. The
implementation MUST use a shared helper (not duplicated inline logic) so that the two
skills cannot diverge on display format.

**Test:** `test_BC_6_23_001_factory_worktree_health_same_display_as_factory_health()`

### AC-009 (traces to BC-6.23.001 precondition 2 — fetch-before-check mandatory on acquire)

The `/factory-lock` acquire MUST perform `git fetch origin factory-artifacts` BEFORE
reading STATE.md for the lock check. The fetch completes before any lock state is read
or written. If the fetch fails (non-zero exit), the skill exits non-zero:
`"Fetch failed before lock check. Cannot acquire safely."` No lock is written.

**Error variant (from EC-006):** `FetchFailed`
**Test:** `test_BC_6_23_001_factory_lock_fetch_failure_aborts_acquire()`

### AC-010 (traces to BC-6.23.001 precondition 3 — git user.email required for acquire)

If `git config user.email` returns empty output during `/factory-lock`, the skill exits
non-zero: `"git user.email not configured — cannot acquire factory lock."` No lock is
written with an empty holder.

**Test:** `test_BC_6_23_001_factory_lock_empty_email_rejected()`

### AC-011 (traces to BC-6.23.001 invariant 5 — state-manager delegation on all writes)

Neither `/factory-lock` nor `/factory-unlock` writes STATE.md directly. Both MUST
delegate to `state-manager` for the write and push. This preserves TD-VSDD-053
single-writer discipline. The skill SPEC documents this delegation obligation
explicitly.

**Test:** (structural assertion in skill SPEC; verified by code review — no direct
`Write` calls in skill SPEC except via state-manager delegation)

### AC-012 (traces to BC-6.23.001 edge case EC-001 — re-lock by self is no-op)

When `/factory-lock` is run and the factory is already locked BY THE SAME developer
(self-held, unexpired), the skill MUST treat this as already acquired:
- Display: `Factory lock already held by this session.`
- No STATE.md write.
- No new event emitted.
- Exit 0.

**Test:** `test_BC_6_23_001_factory_lock_self_relock_is_noop()`

### AC-013 (traces to BC-6.23.001 canonical test vector T-4 — concurrent acquire CAS race)

When two concurrent `/factory-lock` invocations (from `dev-a@x.com` and `dev-b@x.com`)
both see an unlocked STATE.md and both attempt acquire simultaneously, the CAS push
is the tiebreaker. One CAS push succeeds; the other receives a non-fast-forward
rejection. The loser MUST receive `AcquireRaceRejected` error and may retry. The winner
holds the lock. This is the D9 T-10 bats scenario (BC-4.13.001 canonical test vectors).

**Test:** `test_BC_6_23_001_concurrent_acquire_cas_race_one_wins_one_rejected()` (bats T-10)

### AC-014 (traces to BC-6.23.001 edge case EC-005 — force-release of absent lock is no-op)

When `/factory-unlock --force` is run and no `factory_lock` block is present (factory
already unlocked), the skill succeeds silently. Exit 0. No event emitted (there is no
holder to name in `stolen_from`).

**Test:** `test_BC_6_23_001_factory_unlock_force_on_absent_lock_noop()`

## Edge Cases

| ID | Description | Expected Behavior |
|----|-------------|-------------------|
| EC-001 | `/factory-lock` when already locked by self (re-lock) | "Already held by this session"; no write; exit 0 |
| EC-002 | `/factory-lock` when lock is expired (held by other but expired) | Treat as unlocked; proceed with acquire (CAS push safety net) |
| EC-003 | `/factory-unlock` when factory already unlocked | Exit 0 silently; no error; no event |
| EC-004 | `/factory-lock` CAS push rejected (concurrent acquire race) | `AcquireRaceRejected`; user retries; no partial STATE.md write |
| EC-005 | `/factory-unlock --force` when no lock held | No-op; exit 0; no event |
| EC-006 | `git fetch origin factory-artifacts` fails during `/factory-lock` | Non-zero exit: "Fetch failed before lock check. Cannot acquire safely." No lock written |
| EC-007 | `git config user.email` not set during `/factory-lock` | Non-zero exit: "git user.email not configured." No lock written |
| EC-008 | `factory.lock.stolen` event emission fails (SS-03 sink down) | Force-release proceeds (lock cleared); emission failure logged as `log_warn`; no abort |
| EC-009 | Locked STATE.md pushed from `/factory-lock`; concurrent blocked session's guard sees stale local STATE.md | Guard reads local STATE.md; stale view resolved on next fetch (state-burst fetch cycle); cooperative convergence window |
| EC-010 | `/factory-unlock --force` run against a self-held lock | Emit `factory.lock.released` (NOT `stolen` — `stolen_by == stolen_from`); proceed as plain unlock |

## Previous Story Intelligence

**Predecessors:** S-17.01 and S-17.02.

**From S-17.01:** The `factory_lock` schema (3 fields: holder, locked_at, expires_at;
TTL = 2700s; ISO-8601 UTC) is the authoritative format this skill WRITES. The CAS push
primitive from S-17.01 (D6) is the push mechanism this skill USES for acquire and
release. Read `state-burst/SKILL.md` and `agents/state-manager.md` after S-17.01 lands
to see the finalized CAS push form.

**From S-17.02:** The guard (BC-4.13.001) is active before this story ships (Wave 3
comes after Wave 2). This creates a useful invariant: before `/factory-lock` is
available, no `factory_lock` block will be written, so the guard will always see absent
blocks and pass all tools (fail-open path). The skills in this story are the ONLY way to
create and clear `factory_lock` blocks — no other code path should exist after both
stories land.

**Consistency requirement:** The refusal message format in `/factory-lock` (AC-003) MUST
match the guard's block message format (BC-4.13.001 PC1) exactly — same 5 fields, same
display format. Both share the same mental model: the blocked developer sees identical
information whether blocked by the guard (Edit/Write/Agent) or by the skill (attempt to
acquire while locked).

## Architecture Compliance Rules

From ADR-025 v1.2, BC-6.23.001, and BC-5.40.001:

1. **state-manager delegation for ALL writes.** Neither `/factory-lock` nor
   `/factory-unlock` writes STATE.md directly. They delegate to `state-manager`.
   TD-VSDD-053 single-writer discipline applies. Skills call state-manager; state-manager
   commits and pushes.

2. **`factory.lock.stolen` is mandatory on force-release (non-self).** The event MUST be
   emitted. If SS-03 sink is unavailable, the force-release proceeds and the emission
   failure is logged (BC-6.23.001 Invariant 2). The emission failure MUST NOT abort
   the force-release.

3. **`factory_lock` key absent on unlock (not null).** Per BC-5.40.001 PC2, state-manager
   removes the key entirely. Skills MUST specify key removal, not null assignment, in
   their delegation to state-manager.

4. **Fetch-before-check is mandatory for acquire.** The fetch MUST complete before any
   lock state is read or written (BC-6.23.001 Invariant 6). A stale local STATE.md must
   not be the basis for the acquire decision.

5. **Shared helper for health display.** factory-health and factory-worktree-health MUST
   use the same helper function/logic for three-state lock status. Divergence on display
   strings between the two skills is a production-grade defect (BC-6.23.001 PC8 mandates
   "same display strings and same local STATE.md read logic").

6. **No auto-acquire.** The `/factory-lock` skill is the ONLY acquisition path. No
   other code auto-acquires on first write (BC-6.23.001 Invariant 1 + ADR-025 Decision 6).
