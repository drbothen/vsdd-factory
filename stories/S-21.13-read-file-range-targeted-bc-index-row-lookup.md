# S-21.13: `read_file_range` host function + BC-INDEX row-offset sidecar + `validate-cross-site-correspondence` targeted-row lookup (ADR-042 §Decision 5 Option C)

## Narrative

- **As a** factory operator whose `validate-cross-site-correspondence` WASM plugin currently
  performs a linear scan of the entire BC-INDEX prefix to locate BC-5.39.010's row
- **I want** the dispatcher to expose a `read_file_range(path, offset, len)` host function so
  the plugin can locate BC-5.39.010 directly by byte offset, consuming O(1) fuel regardless of
  BC-INDEX corpus size
- **So that** the fuel ceiling introduced by the linear scan is eliminated structurally, the
  20M bridge budget (ADR-042 §Decision 1) is no longer the only guard against exhaustion,
  and future BC-INDEX growth does not threaten validation integrity

## Context / Problem Statement

ADR-042 §Decision 1 raised the global fuel budget from 10M to 20M as a bridge fix, providing
~589 rows of headroom. This is a palliative: fuel consumption for BC-5.39.010 version extraction
scales linearly with BC-INDEX corpus size (`fuel = 2,585,970 + 53.18 × var_bytes`, R²=0.998790
over 24 measured points). The 20M raise buys 12–30 feature waves of growth before the ceiling is
hit again; it does not eliminate the ceiling.

**Measured facts (ADR-042, performance-engineer, 2026-08-08):**

| Metric | Value |
|--------|-------|
| BC-INDEX prefix scanned to reach BC-5.39.010's row | ~415 KB |
| Fuel consumed at current corpus | 9,920,913 of 10,000,000 (99.21%) |
| Rows of runway at 10M cap | 4 rows safe; 5th exhausts |
| Rows of runway at 20M cap | ~589 rows |
| Per-row marginal cost (measured, near-exhaustion boundary) | ~17,114 fuel/row |
| Linear model | `fuel = 2,585,970 + 53.18 × var_bytes`, R²=0.998790 |
| Load-bearing design invariant | `extract_bc_index_version_state` returns early at BC-5.39.010 — early-return is load-bearing for 20M budget |

ADR-042 §Decision 5 defines the structural fix: Option C — targeted row lookup via a new
`read_file_range` host function. Fuel consumption for BC-5.39.010 extraction becomes O(1) in
corpus size once the plugin reads only the row's byte range rather than the linear prefix.

**Why this wave (W7) and not earlier:** Option C requires the ADR-039 Phase 1 registry schema
extension (S-21.10 W5) and per-plugin fuel-cap calibration (S-21.11 W6) to land first:

- S-21.10 adds the `fuel_cap` field to the registry schema (Phase 1 schema extension). Without
  it, setting a per-plugin `fuel_cap` for `validate-cross-site-correspondence` is impossible.
- S-21.11 calibrates and enforces per-plugin fuel caps for the six validator-class plugins
  (Phase 3+4). Once S-21.11 ships, the calibration pattern (p99×1.5, min 50M for fail-closed
  validation) is operational; this story applies it to `validate-cross-site-correspondence`.

Both prerequisites must merge before this story is dispatched.

## Scope — Four Items (ADR-042 §Decision 5, verbatim)

### Item 1: `read_file_range` host function in dispatcher WASM ABI (SS-01)

Implement `read_file_range(path: &str, offset: u64, len: u64) -> Vec<u8>` as a host function
in the dispatcher's WASM ABI.

**Registration:** `crates/factory-dispatcher/src/engine.rs` linker registration, analogous to
the existing `read_file` host function. The new function MUST honor the same path-validation
semantics as `read_file` (no traversal; paths relative to the factory root or absolute paths
within the allowed-reads set). Requesting a range beyond the file's end SHOULD return the
bytes available (not an error), matching POSIX `pread` semantics.

**BC note:** This host function needs a new BC at elaboration (SS-01 anchor documenting the
ABI surface, path-validation contract, and range-clamping behavior). The draft-story policy
allows `behavioral_contracts: []` here; BC authoring is a prerequisite before story status
advances from `draft` to `ready`.

### Item 2: BC-INDEX row-offset sidecar or binary-search index mechanism (SS-05)

The `validate-cross-site-correspondence` plugin needs to know BC-5.39.010's byte offset in
BC-INDEX.md without a linear scan. Implement one of:

**Option 2A (recommended):** A sidecar file `bc-index-offsets.jsonl` (or `.json`) stored in
`.factory/specs/behavioral-contracts/` alongside BC-INDEX.md. Each line maps a BC ID to its
byte offset in BC-INDEX.md. Maintained by the same tooling that regenerates BC-INDEX. Format:

```jsonl
{"bc_id": "BC-5.39.010", "offset": 415278, "length": 683}
```

**Option 2B:** Binary search on a sorted in-memory index derived from the first N bytes of
BC-INDEX (e.g., reading the 5-byte ID prefix of each row using `read_file_range` in a
bisection loop). Higher implementation complexity; suitable if the sidecar maintenance burden
is unacceptable.

The architect's Option C description cites both approaches as equivalent; the implementer
chooses at authoring time. The chosen approach MUST be documented in the story's implementation
notes section and recorded in an ADR amendment or a follow-up ADR if it introduces new
persistence obligations.

**BC note:** The sidecar format and its maintenance obligation (who generates it, when, under
what invariant) requires a BC or BC amendment at elaboration. Pending BC anchoring, the
maintenance rule is: the sidecar MUST be regenerated atomically with any BC-INDEX content
change; the `validate-cross-site-correspondence` plugin MUST fail loudly (not silently skip)
if the sidecar is absent or its offset is inconsistent with BC-INDEX content.

### Item 3: `validate-cross-site-correspondence` Arm A1/Arm A2 extraction via `read_file_range`

Rewrite `extract_bc_index_version_state`'s Arm A1 (BC-5.39.010 version) and Arm A2 (active AC
count) extraction in `crates/hook-plugins/validate-cross-site-correspondence/src/lib.rs` to use
`read_file_range` rather than the linear `read_file` scan.

**Current behavior anchor:** `extract_bc_index_version_state` calls the `read_file` host
function, receives the full BC-INDEX.md content, and scans the ~415KB prefix until
BC-5.39.010's row is found (early-return on first match). This early-return is load-bearing
for the current 20M budget.

**Target behavior:** Use the sidecar (Item 2) to resolve BC-5.39.010's byte offset, then call
`read_file_range(path, offset, len)` to read only the row's bytes directly. Fuel cost becomes
O(1) in corpus size: `read_file_range` invocation cost + row-parse cost, independent of
BC-INDEX total size.

**Test coverage requirement:** The story MUST include a regression test asserting that the
restructured extraction produces the same result as the current linear scan against the
production fixture corpus (BC-INDEX.md at its current size). The 20M budget should still pass
trivially for all fixture sizes; the test is a behavioral-equivalence regression gate, not a
fuel-consumption gate.

### Item 4: Per-plugin `fuel_cap` for `validate-cross-site-correspondence`

Once S-21.10's `fuel_cap` registry schema extension lands (prerequisite), set a per-plugin
`fuel_cap` for `validate-cross-site-correspondence` in `plugins/vsdd-factory/hooks-registry.toml`
calibrated to ADR-039 §Decision 4 Option A: `max(p99 × 1.5, 50M)` where p99 is the 99th
percentile fuel consumption measured against the post-Option-C corpus.

**Minimum 50M:** Per ADR-039 §Decision 4 Option A, the minimum `fuel_cap` for a Phase 3
fail-closed validator is 50M regardless of the p99 measurement. The O(1) restructuring
(Item 3) will reduce p99 dramatically; the 50M floor applies independently.

**ADR-042 §Decision 2 lifted prohibition:** BC-5.39.010 previously contained a normative
prohibition "MUST NOT add a `fuel_cap` entry." ADR-042 §Decision 2 lifts that prohibition
explicitly, replacing it with "SHOULD set per-plugin `fuel_cap` once ADR-039 Phase 1 ships."
No BC amendment is required for Items 1–3; the product-owner amends BC-5.39.010 per the
ADR-042 downstream routing (concurrent with this wave, not a prerequisite for story
dispatch). The implementer MUST NOT set the `fuel_cap` registry entry until S-21.10's schema
extension has merged — that is enforced by the `depends_on: [S-21.10, S-21.11]` constraint.

## Exclusions

- **BC-5.39.010 product-owner amendment:** BC-5.39.010 `fuel_cap` prohibition lift (ADR-042
  §Decision 2 downstream routing) is assigned to product-owner and runs concurrently with this
  wave. This story does NOT touch BC-5.39.010.md or BC-INDEX.md content.

- **Other O(n)-in-input plugins:** `validate-factory-path-root`, `validate-input-hash`,
  `validate-template-compliance` fuel models are unmeasured as of ADR-042. Their optimization
  is out of scope; performance-engineer dispatch is needed to determine whether those three
  still exhaust at 20M (ADR-042 §Consequences, unresolved follow-up).

- **Option A (BC-5.39.010 reposition) or Option B (BC-INDEX compaction):** These are
  palliatives that shift the exhaustion point without eliminating the O(n) ceiling. They are
  not blocked by this story but are not in scope here; the structural fix (Option C) is the
  only target.

- **ADR-039 Phase 1 schema work:** Already delivered by S-21.10 (prerequisite merged before
  dispatch). This story's Item 4 consumes the schema extension; it does not re-implement it.
