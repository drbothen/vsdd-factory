# S-21.11: Validator exhaustion fail-closed calibration and enforcement — unified scope (ADR-039 Phase 3+4 enforcement + §AMD-002 runtime wiring + break-glass override; CWE-636 closure for validator-class WASM and legacy-bash-adapter-hosted plugins)

## Narrative

- **As a** factory pipeline operator whose validator writes are currently approved silently
  when a WASM plugin exhausts its fuel budget, and whose two `PreToolUse` `^Agent$` gates
  (`validate-wave-gate-prerequisite`, `validate-pr-merge-prerequisites`) risk a self-lock if
  flipped to fail-closed without a way to escape a miscalibration
- **I want** (1) each of the six validator-class plugins to have a measured, corpus-calibrated
  resource budget for its actual exhaustion axis and an enforced `failure_policy = "fail-closed"`
  annotation; (2) the `legacy-bash-adapter` runtime to actually honor the registry's calibrated
  `timeout_ms` instead of silently enforcing a hardcoded 60-second constant; and (3) an
  authenticated-by-possession, human-operator-only break-glass override for the two
  self-locking `PreToolUse` `^Agent$` gates, audited on every activation
- **So that** CWE-636 is closed for the authorization-class WASM validator tier AND for the
  runtime-wiring gap AMD-002 identified, the pipeline's write-gating guarantee is semantically
  meaningful at the actual enforcement point (not merely in registry config), the two
  self-locking gates cannot wedge all future `Agent` dispatch without a documented recovery
  path, and D-442(e)'s size-workaround is superseded by a calibrated budget that accommodates
  production-scale `lessons.md` without exhausting

## Context / Finding Summary

ADR-039 §Context establishes:

1. **The detection mechanism is already correct.** `Trap::OutOfFuel` is distinguished from
   clean completion in `invoke.rs` → `PluginResult::Timeout { cause: TimeoutCause::Fuel }`.
   The defect is enforcement, not detection.

2. **The enforcement defect is CWE-636.** `plugin_fail_closed` returns `false` when
   `on_error == OnError::Continue`, regardless of `TimeoutCause`. The existing deliberate
   test `fail_closed_timeout_with_on_error_continue_is_open` encodes this policy. Any change
   requires revising that test **deliberately** (TD-VSDD-059: not deleting it, not renaming
   it; revising it to cover the new semantics for the `fail-open` configuration case).

3. **Self-lock hazard is live today, on two axes.** `lessons.md` already exhausts the 10M fuel
   budget (D-442(e); ≤3500 soft / ≤4000 hard line-count workaround). The ADR-039 authoring
   session itself triggered `fail-closed: plugin timed out` blocks from `validate-factory-path-root`,
   `validate-input-hash`, and `validate-template-compliance`. A naive global flip would
   immediately hard-block all `.factory/` writes. **A second, distinct self-lock axis exists
   for the two `PreToolUse` `^Agent$` gates specifically:** a hard block on either
   `validate-wave-gate-prerequisite` or `validate-pr-merge-prerequisites` prevents ANY future
   `Agent` dispatch — including the dispatch needed to fix the miscalibration. This is why the
   break-glass mechanism (scope element 4 below) is mandatory, not optional, for these two
   gates specifically (ADR-039 §Decision 3 v1.9/v1.10 amendment).

4. **The AMD-002 runtime-wiring gap (RATIFIED v1.10).** Calibrating and raising the registry's
   `timeout_ms` for the five `legacy-bash-adapter.wasm`-hosted plugins has, as currently coded,
   **zero effect** on the bash subprocess's actual kill deadline: `legacy-bash-adapter/src/lib.rs`
   hardcodes `BASH_TIMEOUT_MS = 60_000` and passes that constant — not the registry's calibrated
   `timeout_ms` — into `exec_subprocess.rs::run()`. Registry-config calibration (`timeout_ms`
   set in `hooks-registry.toml`) is therefore **necessary but not sufficient**: the value must
   also reach the real enforcement point. This is a distinct engineering task from calibration
   itself (measuring the right number vs. wiring the right number through).

5. **Safe migration ordering (ADR-039 §Decision 3):** S-21.10 (Phase 1, merged prerequisite)
   added the `failure_policy` TOML field to the registry schema with a `fail-open` default.
   This story delivers Phase 3 (calibration, bifurcated by adapter class) + the AMD-002 wiring
   fix + the break-glass mechanism + Phase 4 (enforcement flip) as **one unified delivery
   unit**. See "Scope Elements and Task Ordering (DAG)" immediately below for the mandatory
   internal sequencing — several of these elements have hard ordering dependencies on each
   other; violating the ordering reopens the exact self-lock and CWE-636 hazards this story
   exists to close.

**Targeted validator-class plugins (ADR-039 §Decision 2), bifurcated by adapter class:**
- **Native-WASM (fuel-axis calibration sufficient):** `validate-cross-site-correspondence`
- **`legacy-bash-adapter.wasm`-hosted (fuel-axis necessary but NOT sufficient — `timeout_ms`
  additionally required, AND the AMD-002 wiring fix must land for that `timeout_ms` to mean
  anything at the real enforcement point):**
  - `validate-factory-path-root` (PostToolUse, `on_error="block"`)
  - `validate-input-hash` (PostToolUse, `on_error="block"`)
  - `validate-template-compliance` (PostToolUse, `on_error="block"`)
  - `validate-wave-gate-prerequisite` (**PreToolUse `^Agent$`**, `on_error="block"` — self-lock
    hazard; requires break-glass before/atomic-with its fail-closed flip)
  - `validate-pr-merge-prerequisites` (**PreToolUse `^Agent$`**, `on_error="block"` — self-lock
    hazard; requires break-glass before/atomic-with its fail-closed flip)

## Acceptance Criteria

### AC-001: No `failure_policy = "fail-closed"` entry may carry `fuel_cap < 50_000_000`, and no `legacy-bash-adapter.wasm`-hosted `failure_policy = "fail-closed"` entry may carry `timeout_ms < 30_000` — standing calibration regression/invariant gate (traces to BC-1.03.017 v1.16 PC8; ADR-039 §Decision 3 atomicity constraint; POLICY 15 gate-outcome discipline; Invariant 7 ordering constraint is mechanically enforced by AC-012/PC11)

A Cargo integration test MUST assert that no `[[hook]]` entry in
`plugins/vsdd-factory/hooks-registry.toml` (the production registry; this is the ONLY scan
target for this gate — test-fixture registries are exempt) carries both
`failure_policy = "fail-closed"` AND `fuel_cap < 50_000_000`. The calibration floor is
50_000_000 (inclusive) per ADR-039 §Decision 4 (`max(observed_max × 1.5, 50M)`); exactly
50_000_000 PASSES the gate (inclusive floor). The factory default of 20_000_000 per
ADR-042 §Decision 2 is below this floor and insufficient for fail-closed annotation.

This gate is a **standing regression/invariant gate** — NOT a red-first TDD gate:
- **GREEN when the live registry contains zero fail-closed entries** (vacuously satisfied
  today; no such entries exist yet in `plugins/vsdd-factory/hooks-registry.toml`)
- **GREEN at final state** after all targeted plugins carry `failure_policy = "fail-closed"`
  with calibrated `fuel_cap >= 50_000_000` (exactly 50_000_000 is the inclusive floor and
  a VALID calibrated value per ADR-039 §Decision 4)
- **RED only if a bad half-state edit** introduces a fail-closed entry with an
  uncalibrated `fuel_cap < 50_000_000`, or (see below) an uncalibrated `timeout_ms < 30_000`
  on a `legacy-bash-adapter.wasm`-hosted entry

The genuine red-first TDD gates for this story are AC-009
(`test_all_six_validator_class_plugins_are_fail_closed`, which is RED before Phase 4
annotations land) and AC-002/003/004/005/010 (all RED because the extended 3-arg
`plugin_fail_closed` signature does not compile yet — their RED state is natural, not forced).

The gate test MUST include an in-test **POSITIVE-CONTROL fixture** to prevent false-green
vacuity: inject a hard-coded fail-closed entry with `fuel_cap = 20_000_000` (the factory
default per ADR-042 §Decision 2, strictly below the 50_000_000 inclusive floor → RED)
directly in the test body (NOT in the live registry) and assert the gate logic returns an
error for that fixture. This proves the gate is non-vacuous and cannot silently pass when
the live registry contains zero fail-closed entries.

The gate test MUST ALSO include a **NEGATIVE-CONTROL fixture** (per BC-1.03.017 v1.16 PC8
symmetric extension + POLICY 15 gate-outcome discipline): inject a hard-coded synthetic
fail-closed entry with `fuel_cap = 75_000_000` (above the 50M floor) directly in the test
body and assert the gate logic ACCEPTS / PASSES that fixture (returns no error). This
proves the gate does not over-fire on legitimately calibrated entries and is symmetric:
positive-control confirms rejection of the bad half-state; negative-control confirms
acceptance of the good state.

The gate test MUST ALSO assert the **boundary-pass case**: a synthetic fail-closed entry
with `fuel_cap = 50_000_000` (exactly at the inclusive floor) MUST PASS the gate (no
error), confirming that exactly 50_000_000 is a valid calibrated value per ADR-039
§Decision 4. This prevents the gate from incorrectly rejecting entries at the minimum
valid cap.

**Parallel host-wall-clock-timeout-axis assertion for `legacy-bash-adapter.wasm`-hosted entries
(ADR-039 §Decision 1/4 v1.8 amendment — fuel-axis calibration is necessary but NOT sufficient
for these entries; BC-1.03.017 v1.16 PC8):** The same test MUST ALSO assert that no `[[hook]]`
entry whose `plugin = "hook-plugins/legacy-bash-adapter.wasm"` carries both
`failure_policy = "fail-closed"` AND `timeout_ms < 30_000` (the host-wall-clock-timeout-axis
calibration floor per ADR-039 §Decision 4 formula: `max(measured_p99_ms × 2.0, 30_000)`;

assertion above, not a replacement — a `legacy-bash-adapter.wasm`-hosted entry satisfying
`fuel_cap >= 50_000_000` alone remains half-state and MUST still fail this gate if
`timeout_ms < 30_000`, because `fuel_cap` gives no protection against that adapter class's
actual exhaustion axis. This axis-parallel assertion requires two more controls:
- **TIMEOUT-POSITIVE-CONTROL fixture:** a hard-coded `legacy-bash-adapter.wasm` entry with
  `failure_policy = "fail-closed"` and `timeout_ms = 10_000` (the current live default for
  four of the five targeted bash-adapter plugins, strictly below the 30_000 floor) injected
  directly in the test body → assert the gate fires RED on that fixture.
- **TIMEOUT-NEGATIVE-CONTROL fixture:** a hard-coded `legacy-bash-adapter.wasm` entry with
  `failure_policy = "fail-closed"` and `timeout_ms = 45_000` (above the 30_000 floor) injected
  directly in the test body → assert the gate does NOT fire (PASS / no error).

### AC-002: Exhaustion + fail-closed → block (exit 2) (traces to BC-1.03.017 PC1; BC-1.01.016 PC1/PC5; ADR-039 §Decision 6 test case 1)

A unit test MUST invoke the dispatcher's `plugin_fail_closed` (or its replacement function)
with `PluginResult::Timeout { cause: TimeoutCause::Fuel, ... }` and
`failure_policy = FailurePolicy::FailClosed`. The function MUST return `true` (block
intent). The unit test reads `RegistryEntry.failure_policy` (traces to BC-1.01.016 PC1:
`failure_policy = "fail-closed"` parses to `FailurePolicy::FailClosed` — the field is
parseable from TOML and accessible on `RegistryEntry`; and BC-1.01.016 PC5:
`failure_policy` is an independent axis in `RegistryEntry` alongside `on_error` —
axes-independence: both fields coexist without structural conflict, enabling the
executor to read `failure_policy` independently of `on_error`).
The test exercises the `Timeout + FailClosed` branch, not configuration intent.

Separately, a bats test MUST verify that a real dispatch with a plugin configured
`failure_policy = "fail-closed"` and a deliberately tiny `fuel_cap = 100` produces
dispatcher exit code 2 (BLOCK). **The `fuel_cap = 100` + `failure_policy = "fail-closed"`
entry MUST live in a dedicated TEST-FIXTURE registry** (NOT
`plugins/vsdd-factory/hooks-registry.toml`), so that AC-001's gate scan does not trip on
this fixture. The `.bats` test MUST be registered in the Bats harness at
`plugins/vsdd-factory/tests/`; no new `.sh` file may be introduced per POLICY 21 (`.bats`
files and `tests/fixtures/` entries are exempt from POLICY 21).

- **Test:** `test_exhaustion_fail_closed_blocks()` — unit: `Timeout { cause: Fuel }` +
  `FailClosed` → `plugin_fail_closed` returns `true` (traces to BC-1.01.016 PC1/PC5)
- **Test:** bats integration test (TEST-FIXTURE registry only, NOT production registry) —
  dispatch with `fuel_cap = 100` + `failure_policy = "fail-closed"` on a
  budget-exhausting payload → observed dispatcher exit code 2 asserted

### AC-003: Exhaustion + fail-open → advisory, not block (exit 0) (traces to BC-1.03.017 PC2; ADR-039 §Decision 6 test case 2)

The same exhaustion scenario (`Timeout { cause: TimeoutCause::Fuel }`) with
`failure_policy = FailurePolicy::FailOpen` MUST produce exit 0 (advisory, not block).
This verifies the `fail-open` path is preserved for plugins that legitimately need it.

- **Test:** `test_exhaustion_fail_open_is_advisory()` — unit: `Timeout { cause: Fuel }` +
  `FailOpen` → `plugin_fail_closed` returns `false`; exit 0 asserted

### AC-004: `on_error = "continue"` + `failure_policy = "fail-closed"` + exhaustion → BLOCK (axes are independent) (traces to BC-1.03.017 PC3; ADR-039 §Decision 6 test case 3)

A plugin with BOTH `on_error = "continue"` AND `failure_policy = "fail-closed"` that
exhausts its fuel budget MUST produce a block (exit 2). The `on_error` field governs crash
outcomes only; it MUST NOT override `failure_policy` for exhaustion outcomes.

This is the primary correctness test of the axes-independence design. It directly validates
the behavior that the prior `fail_closed_timeout_with_on_error_continue_is_open` test
denied.

- **Test:** `test_on_error_continue_with_fail_closed_exhaustion_still_blocks()` — unit:
  `Timeout { cause: Fuel }` + `on_error = Continue` + `failure_policy = FailClosed` →
  `plugin_fail_closed` returns `true`; axes do not interfere

### AC-005: Crash vs exhaustion as distinct paths (traces to BC-1.03.017 PC4+PC5; ADR-039 §Decision 6 test case 4)

Two scenarios MUST be verified as distinct paths:

(a) A crashed plugin (`on_error = "block"`, `failure_policy = "fail-open"`) MUST block
    via the `on_error` path. `PluginResult::Crashed` + `on_error = Block` → block (exit 2).

(b) A fuel-exhausted plugin (`on_error = "block"`, `failure_policy = "fail-open"`) MUST
    NOT block — exhaustion is not a crash. `Timeout { cause: Fuel }` + `on_error = Block`
    + `failure_policy = FailOpen` → exit 0.

This verifies that `on_error = "block"` does not accidentally gate exhaustion outcomes,
preserving the original semantics of `on_error` for crash paths only.

- **Test:** `test_crash_blocks_via_on_error_not_failure_policy()` — `PluginResult::Crashed` +
  `Block` + `FailOpen` → exit 2
- **Test:** `test_exhaustion_with_on_error_block_but_fail_open_is_advisory()` — `Timeout { cause: Fuel }` +
  `Block` + `FailOpen` → exit 0

### AC-006: `fail_closed_timeout_with_on_error_continue_is_open` revised, not deleted (traces to BC-1.03.017 PC7; TD-VSDD-059)

The existing test `fail_closed_timeout_with_on_error_continue_is_open` in `executor.rs`
(or its module) encodes the current deliberate fail-open policy. When Phase 4 enforcement
ships, this test MUST be revised to assert the new invariant for the `fail-open`
configuration case — it is not the unconditional policy it once was, but it still describes
valid behavior when `failure_policy = FailOpen`.

Specifically, the revised test MUST:
- Retain the function name (or a derivative that clearly conveys the same intent)
- Assert: `Timeout { cause: Fuel } + on_error=Continue + failure_policy=FailOpen → NOT block`
- NOT be deleted, as deletion would allow silent regression of the `fail-open` path

Deletion of this test without an equivalent replacement is a TD-VSDD-059 (paper-fix) violation.

- **Test:** revised `fail_closed_timeout_with_on_error_continue_is_open` (or

### AC-013b: PC13 enforcement — `on_error = Block` fails closed on ANY plugin-reported error exit, not only a crash/timeout outcome (traces to BC-1.03.017 v1.16 PC13; ADR-039 §AMD-003, RATIFIED v1.11; closes S-21.11 v2.0 adversarial pass-1 BLOCKER F-S2111V2-P1-001)

`PluginResult::Ok { exit_code, .. }` where `exit_code != 0`, the executor's block-decision
function (`plugin_fail_closed` or its replacement, per Task #19's Node (D) extension) MUST
return `true` (`block_intent = true`, dispatcher exit code 2), REGARDLESS of `failure_policy`.
This is a THIRD axis alongside AC-002/003/004/010's `failure_policy` (resource-exhaustion)
coverage and AC-005/AC-011's `on_error`-vs-`Crashed` coverage — it is the missing
`on_error`-vs-clean-nonzero-exit case: a plugin that ran to completion without crashing or
timing out at the WASM-trap/epoch layer, but returned a nonzero exit via its own reported
`HookResult::Error` (exit code 1 per `crates/hook-sdk/src/result.rs::HookResult::exit_code`).

host-wall-clock timeout (AC-013's `exec_subprocess.rs::run()` poll-loop kill) does NOT produce

genuine `Trap::Interrupt`, which cannot fire while the guest is blocked inside the synchronous
`exec_subprocess` host call. Instead it propagates as `host::exec_subprocess`'s
`Err(codes::TIMEOUT)` → `run_bash_via_host`'s string-erasing `Err` map → `adapter_logic`'s
`HookResult::error(...)` → `exit_code = 1` → `classify_trap`'s `Err(I32Exit(1))` arm →

be enforced before its downstream block decision can be exercised realistically.

`failure_policy = FailurePolicy::FailOpen`, and `result = PluginResult::Timeout { cause: Fuel |

`Ok { exit_code != 0, .. }` and MUST NOT be implemented as a negation of `Ok { exit_code: 0 }`

## Acceptance Criteria — Break-Glass Mechanism (BC-1.03.018)

The following ten ACs (AC-014 through AC-023) deliver the break-glass override mandated by
ADR-039 §Decision 3 v1.10 minimum-viable definition, governed by BC-1.03.018 v1.1 (AC-014
through AC-022 cover PC1–PC9; AC-023 covers PC10, the F-006 threat-boundary control added in
S-21.11 v2.0 adversarial pass-1 remediation). This is scope element (E) in the DAG
above — it must land before, or atomically with, the fail-closed-flip commit for
`validate-wave-gate-prerequisite` and `validate-pr-merge-prerequisites` specifically (AC-022
is the mechanical gate that enforces this).

### AC-014: Override unset/absent → no behavioral change (baseline regression control) (traces to BC-1.03.018 PC1)

When `VSDD_BREAK_GLASS_GATE_BYPASS` is unset (or set to the empty string), both named gates'
block decisions are computed exactly as if the break-glass mechanism did not exist —
BC-1.03.017's `failure_policy`/`on_error` semantics apply unmodified. Introducing the
break-glass check MUST NOT alter any existing BC-1.03.017 postcondition's observed outcome
when the override is inactive.

- **Test:** `test_break_glass_unset_no_behavior_change()` — real dispatch:
  `VSDD_BREAK_GLASS_GATE_BYPASS` unset; `validate-wave-gate-prerequisite` returns

  (BC-1.03.017 PC6 semantics unmodified)

### AC-015: Override set to an exact gate name → that gate's block suppressed for that invocation, regardless of block cause (traces to BC-1.03.018 PC2)

When `VSDD_BREAK_GLASS_GATE_BYPASS` contains the plugin `name` of
`validate-wave-gate-prerequisite` or `validate-pr-merge-prerequisites` (exact match;

(`plugin_requests_block`'s `HookResult::Block` path, OR `plugin_fail_closed`'s exhaustion path
under `failure_policy = FailClosed`), and regardless of the plugin's own `PluginResult`

- **Test:** `test_break_glass_exact_name_suppresses_block()` — real dispatch:

- **Test:** `test_break_glass_suppresses_crash_block_too()` — real dispatch: override names

### AC-016: Override set to the literal `all` → both named gates bypassed (traces to BC-1.03.018 PC3)

`VSDD_BREAK_GLASS_GATE_BYPASS=all` suppresses both `validate-wave-gate-prerequisite`'s and
`validate-pr-merge-prerequisites`' block contributions for that invocation, equivalent to
naming both explicitly. Both gates are dispatched in separate `execute_tiers` tiers (priority
130 vs 120 — `routing.rs::group_by_priority` starts a new tier on every distinct priority
value), evaluated unconditionally within the same dispatch via `execute_tiers`'s no-early-return
tier loop (corrected per F-004, S-21.11 v2.0 adversarial pass-1 — the prior "dispatched in the
SAME tier" premise was false). If both would have blocked, TWO separate `break_glass.activated`
events MUST be emitted (one per gate name, per EC-005), not a single combined event — this
conclusion does not depend on, and is not evidenced by, the two gates sharing a tier; it
follows from `execute_tiers` looping over every tier unconditionally (no early return on a
block-producing tier), so both gates are always invoked and both outcomes always folded into

### AC-023: Break-glass negative control — an `Agent`-tool-invoked path CANNOT arm `VSDD_BREAK_GLASS_GATE_BYPASS` for the dispatcher's own process environment (traces to BC-1.03.018 v1.1 PC10; F-006, S-21.11 v2.0 adversarial pass-1 threat-boundary directive)

`VSDD_BREAK_GLASS_GATE_BYPASS` is armed if and only if it is present in the OS process
environment of the process that ultimately launches the `factory-dispatcher` binary for a
given dispatch — i.e., the human operator's shell session (or an ancestor process the operator
directly controls). This is a structural property of the OS process model, not an
application-level access check: a child process's environment is a COPY taken at
`fork`/`exec` time, and a child mutating its own environment can NEVER write back into its
parent's environment. Consequently, none of the following can arm the override for the
dispatcher's own process: (a) a Bash-tool subprocess spawned by an `Agent`-tool-invoked Claude
session (a DESCENDANT of the dispatcher's own process tree, never an ancestor); (b) an MCP
tool invocation (runs entirely outside the harness's own environment-inheritance chain); (c) a
hook-wrapper subprocess (e.g. `legacy-bash-adapter`'s own `exec_subprocess` calls) — itself a
CHILD of the dispatcher process for that single invocation.

**Explicit threat-boundary note (out of this AC's enforcement scope, per F-006):** this AC does
NOT claim the dispatcher validates WHO set the variable in its inherited environment. If the
human operator's own shell session is itself compromised, that compromised process COULD set
the variable before launching Claude Code, and the dispatcher would inherit it exactly as it
would inherit a legitimate operator's setting (Invariant 1's "authentication-by-possession, not
identity" scope). What this AC closes is narrower: the `Agent` tool dispatch path ITSELF
provides no route to arm the override, by construction of the OS process model, regardless of
what any `Agent`-invoked tool call attempts.

- **Test:** `test_break_glass_env_not_settable_by_child_process()` — an integration test MUST
  spawn a child process that attempts to set `VSDD_BREAK_GLASS_GATE_BYPASS` in its own
  environment (via `std::env::set_var`, or an equivalent shell `export`, executed inside the
  spawned child) and then assert that the PARENT test process's own
  `std::env::var("VSDD_BREAK_GLASS_GATE_BYPASS")` remains unset/unchanged after the child
  process exits — proving the OS-level parent-environment isolation this AC relies on, in the
  actual runtime the dispatcher executes in, not merely asserted as documentation
