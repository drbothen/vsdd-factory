# S-21.11: Per-plugin fuel-cap calibration + fail-closed enforcement flip (ADR-039 Phase 3+4 — CWE-636 closure for validator-class WASM plugins)

## Narrative

- **As a** factory pipeline operator whose validator writes are currently approved silently
  when a WASM plugin exhausts its fuel budget
- **I want** each of the six validator-class plugins to have a measured, corpus-calibrated
  `fuel_cap` and an enforced `failure_policy = "fail-closed"` annotation, so that exhaustion
  blocks the write (exit 2) rather than silently approving it
- **So that** CWE-636 is closed for the authorization-class WASM validator tier, the
  pipeline's write-gating guarantee is semantically meaningful, and D-442(e)'s
  size-workaround is superseded by a calibrated budget that accommodates production-scale
  `lessons.md` without exhausting

## Context / Finding Summary

ADR-039 §Context establishes:

1. **The detection mechanism is already correct.** `Trap::OutOfFuel` is distinguished from
   clean completion in `invoke.rs` → `PluginResult::Timeout { cause: TimeoutCause::Fuel }`.
   The defect is enforcement, not detection.

2. **The enforcement defect is CWE-636.** `plugin_fail_closed` returns `false` when
   `on_error == OnError::Continue`, regardless of `TimeoutCause`. The existing deliberate
   test `fail_closed_timeout_with_on_error_continue_is_open` encodes this policy. Any change
   requires revising that test **deliberately** (TD-VSDD-059: not deleting it, not renaming
   it; revising it to cover the new semantics for the `fail-open` configuration case).

3. **Self-lock hazard is live today.** `lessons.md` already exhausts the 10M fuel budget
   (D-442(e); ≤3500 soft / ≤4000 hard line-count workaround). The ADR-039 authoring session
   itself triggered `fail-closed: plugin timed out` blocks from `validate-factory-path-root`,
   `validate-input-hash`, and `validate-template-compliance`. A naive global flip would
   immediately hard-block all `.factory/` writes.

4. **Safe migration ordering (ADR-039 §Decision 3):** S-21.10 (Phase 1, now merged as
   prerequisite) added the `failure_policy` TOML field to the registry schema with a
   `fail-open` default. This story delivers Phase 3 (calibration) + Phase 4 (enforcement
   flip) as a single delivery unit. Phase 3 and Phase 4 MUST be atomic per-plugin (see
   AC-001 gate).

**Targeted validator-class plugins (ADR-039 §Decision 2):**
- `validate-factory-path-root`
- `validate-input-hash`
- `validate-template-compliance`
- `validate-wave-gate-prerequisite`
- `validate-pr-merge-prerequisites`
- `validate-cross-site-correspondence`

### AC-001: No `failure_policy = "fail-closed"` entry may carry `fuel_cap < 50_000_000`; no on_error="block" targeted plugin may remain at failure_policy=fail-open once the decision function is extended — standing regression/invariant gate (traces to BC-1.03.017 v1.3 PC8 extended + Invariant 7; ADR-039 §Decision 3 atomicity constraint; POLICY 15 gate-outcome discipline)

A Cargo integration test MUST assert that no `[[hook]]` entry in
`plugins/vsdd-factory/hooks-registry.toml` (the production registry; this is the ONLY scan
target for this gate — test-fixture registries are exempt) carries both
`failure_policy = "fail-closed"` AND `fuel_cap < 50_000_000`. The calibration floor is
50_000_000 (inclusive) per ADR-039 §Decision 4 (`max(observed_max × 1.5, 50M)`); exactly
50_000_000 PASSES the gate (inclusive floor). The factory default of 20_000_000 per
ADR-042 §Decision 2 is below this floor and insufficient for fail-closed annotation.

This gate is a **standing regression/invariant gate** — NOT a red-first TDD gate:
- **GREEN when the live registry contains zero fail-closed entries** (vacuously satisfied
  today; no such entries exist yet in `plugins/vsdd-factory/hooks-registry.toml`)
- **GREEN at final state** after all targeted plugins carry `failure_policy = "fail-closed"`
  with calibrated `fuel_cap >= 50_000_000` (exactly 50_000_000 is the inclusive floor and
  a VALID calibrated value per ADR-039 §Decision 4)
- **RED only if a bad half-state edit** introduces a fail-closed entry with an
  uncalibrated `fuel_cap < 50_000_000`

The genuine red-first TDD gates for this story are AC-009
(`test_all_six_validator_class_plugins_are_fail_closed`, which is RED before Phase 4
annotations land) and AC-002/003/004/005/010 (all RED because the extended 3-arg
`plugin_fail_closed` signature does not compile yet — their RED state is natural, not forced).

The gate test MUST include an in-test **POSITIVE-CONTROL fixture** to prevent false-green
vacuity: inject a hard-coded fail-closed entry with `fuel_cap = 20_000_000` (the factory
default per ADR-042 §Decision 2, strictly below the 50_000_000 inclusive floor → RED)
directly in the test body (NOT in the live registry) and assert the gate logic returns an
error for that fixture. This proves the gate is non-vacuous and cannot silently pass when
the live registry contains zero fail-closed entries.

The gate test MUST ALSO include a **NEGATIVE-CONTROL fixture** (per BC-1.03.017 v1.3 PC8
symmetric extension + POLICY 15 gate-outcome discipline): inject a hard-coded synthetic
fail-closed entry with `fuel_cap = 75_000_000` (above the 50M floor) directly in the test
body and assert the gate logic ACCEPTS / PASSES that fixture (returns no error). This
proves the gate does not over-fire on legitimately calibrated entries and is symmetric:
positive-control confirms rejection of the bad half-state; negative-control confirms
acceptance of the good state.

The gate test MUST ALSO assert the **boundary-pass case**: a synthetic fail-closed entry
with `fuel_cap = 50_000_000` (exactly at the inclusive floor) MUST PASS the gate (no
error), confirming that exactly 50_000_000 is a valid calibrated value per ADR-039
§Decision 4. This prevents the gate from incorrectly rejecting entries at the minimum
valid cap.

The gate MUST ALSO assert the **Invariant 7 fail-open-window invariant** (BC-1.03.017 v1.3
Invariant 7): once the extended 3-arg `plugin_fail_closed` decision function is in effect,
no on_error="block" targeted plugin may remain at `failure_policy = fail-open`. This is
enforced at the commit-ordering level (see Task #10 ATOMICITY GATE) rather than as a
post-hoc parse assertion, but the gate test SHOULD warn (not pass silently) if it detects
a live registry entry that has `on_error = "block"` (for the five targeted plugins) but
lacks `failure_policy = "fail-closed"` after Phase 4 completes.

with `PluginResult::Timeout { cause: TimeoutCause::Fuel, ... }` and
`failure_policy = FailurePolicy::FailClosed`. The function MUST return `true` (block
intent). The unit test reads `RegistryEntry.failure_policy` (traces to BC-1.01.016 PC1:
`failure_policy = "fail-closed"` parses to `FailurePolicy::FailClosed` — the field is
parseable from TOML and accessible on `RegistryEntry`; and BC-1.01.016 PC5:
`failure_policy` is an independent axis in `RegistryEntry` alongside `on_error` —
axes-independence: both fields coexist without structural conflict, enabling the
executor to read `failure_policy` independently of `on_error`).
The test exercises the `Timeout + FailClosed` branch, not configuration intent.

Separately, a bats test MUST verify that a real dispatch with a plugin configured
`failure_policy = "fail-closed"` and a deliberately tiny `fuel_cap = 100` produces
dispatcher exit code 2 (BLOCK). **The `fuel_cap = 100` + `failure_policy = "fail-closed"`
entry MUST live in a dedicated TEST-FIXTURE registry** (NOT
`plugins/vsdd-factory/hooks-registry.toml`), so that AC-001's gate scan does not trip on
this fixture. The `.bats` test MUST be registered in the Bats harness at
`plugins/vsdd-factory/tests/`; no new `.sh` file may be introduced per POLICY 21 (`.bats`
files and `tests/fixtures/` entries are exempt from POLICY 21).

- **Test:** `test_exhaustion_fail_closed_blocks()` — unit: `Timeout { cause: Fuel }` +

- **Test:** bats integration test (TEST-FIXTURE registry only, NOT production registry) —

### AC-003: Exhaustion + fail-open → advisory, not block (exit 0) (traces to BC-1.03.017 PC2; ADR-039 §Decision 6 test case 2)

The same exhaustion scenario (`Timeout { cause: TimeoutCause::Fuel }`) with

- **Test:** `test_exhaustion_fail_open_is_advisory()` — unit: `Timeout { cause: Fuel }` +

### AC-004: `on_error = "continue"` + `failure_policy = "fail-closed"` + exhaustion → BLOCK (axes are independent) (traces to BC-1.03.017 PC3; ADR-039 §Decision 6 test case 3)

A plugin with BOTH `on_error = "continue"` AND `failure_policy = "fail-closed"` that
exhausts its fuel budget MUST produce a block (exit 2). The `on_error` field governs crash
outcomes only; it MUST NOT override `failure_policy` for exhaustion outcomes.

This is the primary correctness test of the axes-independence design. It directly validates
the behavior that the prior `fail_closed_timeout_with_on_error_continue_is_open` test
denied.

- **Test:** `test_on_error_continue_with_fail_closed_exhaustion_still_blocks()` — unit:
  `Timeout { cause: Fuel }` + `on_error = Continue` + `failure_policy = FailClosed` →
  `plugin_fail_closed` returns `true`; axes do not interfere

### AC-005: Crash vs exhaustion as distinct paths (traces to BC-1.03.017 PC4+PC5; ADR-039 §Decision 6 test case 4)

Two scenarios MUST be verified as distinct paths:

(a) A crashed plugin (`on_error = "block"`, `failure_policy = "fail-open"`) MUST block
    via the `on_error` path. `PluginResult::Crashed` + `on_error = Block` → block (exit 2).

(b) A fuel-exhausted plugin (`on_error = "block"`, `failure_policy = "fail-open"`) MUST
    NOT block — exhaustion is not a crash. `Timeout { cause: Fuel }` + `on_error = Block`
    + `failure_policy = FailOpen` → exit 0.

This verifies that `on_error = "block"` does not accidentally gate exhaustion outcomes,
preserving the original semantics of `on_error` for crash paths only.

- **Test:** `test_crash_blocks_via_on_error_not_failure_policy()` — `PluginResult::Crashed` +
  `Block` + `FailOpen` → exit 2
- **Test:** `test_exhaustion_with_on_error_block_but_fail_open_is_advisory()` — `Timeout { cause: Fuel }` +
  `Block` + `FailOpen` → exit 0

### AC-007: Per-plugin fuel-cap calibration against production-scale corpus (traces to BC-1.03.017 Preconditions 2–4, enabling PC9; ADR-039 §Decision 4 Option A)

For each of the six targeted validator-class plugins, `fuel_cap` MUST be set to at least
`max(observed_max × 1.5, 50_000_000)` where `observed_max` is the maximum `fuel_consumed`
value observed over the calibration corpus below. For the hard-block/fail-closed boundary
validators in this story, the appropriate percentile basis is the **observed maximum over
the mandated corpus** — with ~4 corpus inputs, "p99" and "observed max" are effectively
identical (p99 ≈ the single largest value; using the observed max eliminates statistical
ambiguity). `fuel_consumed` MUST be read from the `Ok`-path measurement ONLY: on a
`Trap::OutOfFuel` outcome, `fuel_consumed == fuel_cap` (conveys the cap, not actual
demand), so a `Timeout`-path reading is invalid for calibration purposes. The calibration
corpus MUST include:

1. `lessons.md` at ≥3000 lines (above the D-442(e) soft limit)
2. `STATE.md` at current live size
3. `decision-log.md` at current live size
4. The ≥574 KB synthetic fixture committed at `plugins/vsdd-factory/tests/fixtures/validate-cross-site-correspondence/a1-production-scale/` (576,396 bytes; added in S-21.07 merge e94767bc)

A calibration run MUST be executed for each plugin by the devops-engineer role before the
implementer annotates hooks-registry.toml. The measured `fuel_consumed` p99 and the chosen
`fuel_cap` MUST be recorded in the PR description or a calibration log artifact, not merely
asserted in code.

Any plugin whose calibration reveals a required `fuel_cap` that would exceed
`PRACTICAL_FUEL_CEILING` (`PRACTICAL_FUEL_CEILING = 500_000_000`, even at observed_max×1.5
for the largest corpus input) MUST be surfaced to the orchestrator rather than silently
annotated with an insufficient cap. EC-004 governs this case; see also the EC-004 resolution
path under Edge Cases.

- **Test:** AC-001 gate (`test_no_fail_closed_plugin_with_uncalibrated_cap`) enforces the
  structural invariant; the calibration log provides the human-auditable evidence

## Edge Cases

| ID | Scenario | Expected Behavior |
|----|----------|-------------------|
| EC-001 | Plugin with `failure_policy = "fail-closed"` completes successfully (no exhaustion) | Exit 0; `on_error` and `failure_policy` do not affect clean-pass outcomes |
| EC-002 | Plugin with `failure_policy = "fail-closed"` + `PluginResult::Crashed` (`on_error = "continue"`) | Crash governed via `on_error`; exit 0 (crash is advisory per `continue`); `failure_policy` is NOT consulted for crash outcomes |
| EC-003 | Plugin with `failure_policy = "fail-closed"` + `PluginResult::Crashed` (`on_error = "block"`) | Crash governed via `on_error`; exit 2 — crash blocks regardless of `failure_policy` |
| EC-004 | Calibration reveals plugin needs `fuel_cap > PRACTICAL_FUEL_CEILING` (`PRACTICAL_FUEL_CEILING = 500_000_000`) even at observed_max×1.5 for the corpus | MUST surface to orchestrator; do not annotate with an insufficient cap; plugin deferred from the Phase 4 flip. **Resolution to prevent PC9/AC-009 deadlock:** S-21.11 is descoped to the flippable subset via orchestrator-approved spec amendment; AC-009's asserted set reduces to the flippable plugins only; the deferred plugin routes to **S-21.13** (depends_on [S-21.10, S-21.11]; note ordering tension if validate-cross-site-correspondence is the deferred plugin — S-21.13 must not merge before S-21.11). **Non-neutral deferral caveat (BC-1.03.017 v1.3 PC8 + Invariant 7):** Deferring an on_error="block" plugin is NOT behavior-neutral — post-merge, the deferred plugin would carry on_error="block" (incidentally blocking crashes) but failure_policy=fail-open (failing open on exhaustion), reintroducing CWE-636 for exhaustion outcomes on that plugin. A deferred on_error="block" plugin MUST either (a) retain a temporary fallback mechanism preserving block-on-exhaustion until S-21.13 lands (PREFERRED path), OR (b) explicitly record the transient fail-open window and gate S-21.13 as a HARD BLOCKER (no merge of any commit that relies on the deferred plugin's fail-closed enforcement until that plugin's annotation lands in S-21.13). **Carve-out:** validate-cross-site-correspondence has on_error="continue" — it currently does NOT block on exhaustion. Deferring validate-cross-site-correspondence to S-21.13 IS behavior-neutral and does not reintroduce CWE-636 (exhaustion was already advisory for this plugin). |
| EC-005 | `lessons.md` validator post-flip exhausts on a >4000-line `lessons.md` (above D-442(e) hard limit) | This MUST NOT happen if calibration was run against ≥3000-line corpus; if it does, the calibration was insufficient and AC-007 was not met — surfaced to orchestrator |

| EC-007 | `TimeoutCause::Epoch` (epoch deadline) with `failure_policy = "fail-closed"` | MUST block (exit 2); both `TimeoutCause::Fuel` and `TimeoutCause::Epoch` are resource-exhaustion outcomes per ADR-039 §Decision 1 |
