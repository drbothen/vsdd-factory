# S-7.14 — Bats inert-guard lint — CI detection for &&{false;}||true pattern (process-gap, S-21.03 F-P4-002)

**Epic:** E-7 — Process Codification (Self-Improvement)
**Source:** S-21.03 delivery process-gap (2026-07-24), cycle-closing checklist (S-7.02 / lessons-codification rule); human governance ruling "Story + policy"
**Owner:** story-writer (Rust workspace test + agent guidance) / spec-steward (policy extension anchor)
**Priority:** P1 (process-gap; inert guards survived mutation attestation and required fresh-context adversary to catch; same severity class as S-7.06–S-7.09)
**Subsystem anchor:** SS-05 (Pipeline Orchestration) + SS-06 (Skill Catalog)

## Narrative

- **As a** vsdd-factory test-writer delivering bats test suites
- **I want** CI to statically reject the `&&{false;}||true` inert-guard idiom in any `*.bats` file
- **So that** structurally-unable-to-fail guards cannot survive code review or mutation attestation and silently render a test suite toothless

During S-21.03 delivery (2026-07-24), five bats assertion guards shipped with the pattern:

```bash
some_cmd && { echo "FAIL: ..." ; false; } || true
```

This idiom is **structurally unable to fail**. The parse is `(A && B) || C`:

- If `some_cmd` exits 0, `&&{false;}` executes `false` (exit 1), which would propagate as
  failure — but `||true` catches any non-zero and returns 0 (success).
- If `some_cmd` exits non-zero, `&&{false;}` is short-circuited and never runs, but
  `||true` still catches the non-zero from `some_cmd` and returns 0 (success).

In both cases the expression returns 0. The guard **always passes**. It provides zero
detection power for the condition it claims to test.

These five guards were delivered alongside a per-guard mutation attestation. That
attestation only exercised the `overrun` mutant class (verifying the guard fires when the
command succeeds unexpectedly), but the structural inertness means even an `overrun` mutant
will not trigger a real failure — the attestation itself was flawed. A fresh-context
adversary caught all five at pass 4 (finding F-S2103-P4-002, HIGH). The guards were
subsequently fixed in-burst (commit fc08a70a) with correct assertion forms and three-class
mutation verification (overrun / misclassification / mandate-deletion).

The pattern is grep-identifiable and belongs in CI. Two interventions are required:

1. **A static lint check** (Rust workspace test per POLICY 21 — no new `.sh` files) that
   greps all `*.bats` files in the repository for the inert-guard pattern classes and fails
   CI on any match.
2. **A doc note in the test-writer agent guidance** that names the forbidden idiom, explains
   why it is inert, and specifies the correct assertion alternatives.

The companion policy leg — extending POLICY 5 and/or POLICY 15 with a per-guard
mutant-verification discipline requirement — is state-manager's codification task at story
close. This story references it but does not implement it.

## Edge Cases

| ID | Scenario | Expected Behavior |
|----|----------|-------------------|
| EC-001 | A `.bats` file contains `|| true` in a setup/teardown helper where the intent is "run this command; ignore failure" (e.g., `rm -rf "$WORK" \|\| true`) | The lint pattern MUST be scoped to lines where `false` immediately precedes `\|\| true` (directly or inside a compound body); bare `cmd \|\| true` without an adjacent `false` command on the same logical line is NOT flagged |
| EC-002 | A `.bats` file contains the pattern inside a `# comment` line | The lint grep MUST exclude comment lines (lines where the first non-whitespace character is `#`); a comment describing the idiom is not itself an inert guard |
| EC-003 | A `.bats` fixture file in `tests/fixtures/` also contains the pattern | The lint check scope is `plugins/vsdd-factory/tests/**/*.bats`; implementer must decide whether to include fixture `.bats` files or restrict to top-level test files; the decision must be documented in the test body comment |
| EC-004 | A future story adds a new `.bats` file that inadvertently uses the idiom | The lint check catches it at CI time before merge; no additional action required — CI failure is the intended outcome |
| EC-005 | The Rust workspace test is added to a crate that does not currently have integration tests | The implementer must verify the crate compiles and passes clippy before committing; the choice of crate is implementer's, but preference is an existing crate with a tests/ directory whose scope is "tooling lint" or "corpus validation" |
