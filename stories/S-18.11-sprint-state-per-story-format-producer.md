# S-18.11 — sprint-state.yaml producer migration to per-story {id, status} format

**Epic:** E-18 — Factory Context Durability (feature #173)
**Wave:** 9 (depends on S-18.01 merged + S-18.02 WASM gate drafted; placed after both consumers are in-flight)
**Depends on:** S-18.01 (merged), S-18.02
**Priority:** P1 — integration gap between producer and consumers; the WASM wave-gate (S-18.02) and shell wave-handoff (S-18.01) both consume sprint-state.yaml in per-story format that the current production file does not emit
**Subsystem anchor:** SS-05 owns this story's scope because SS-05 (Pipeline Orchestration) governs the sprint-state.yaml lifecycle, the wave-scheduling skill, and the producer-side format obligation. SS-06 is co-listed because the wave-handoff SKILL.md (SS-06) consumes sprint-state.yaml directly.

## NEW BC NEEDED (producer-side sprint-state format)

The existing BCs BC-5.41.001 and BC-5.41.002 govern the CONSUMER side (wave-gate reads per-story `{id, status}` entries from sprint-state.yaml per BC-5.41.002 PC3). No BC currently governs the PRODUCER side — the obligation on the `wave-scheduling` / `decompose-stories` sprint-state generation step to EMIT the per-story format in the first place.

**Flag for product-owner:** Author a new BC (candidate ID BC-5.41.XXX — next available after BC-5.41.003) that specifies:
> "The sprint-state.yaml generation step (wave-scheduling skill or equivalent producer) emits a per-story entries list: each story appears as `- id: <S-NNN> / status: <sprint-status>` under a `stories:` root key. Count-summary and per-epic aggregated schema are NOT emitted in the stories list section (they may co-exist in a separate `epics:` section). Consumers (BC-5.41.002 PC3, BC-5.41.001 PC3) must be able to parse this format directly."

Until this BC is authored and its canonical ID placed in `behavioral_contracts:` above, this story's status MUST remain `draft` per spec-first gate S-7.01.

## Narrative

As a wave-gate operator or wave-handoff skill,
I want sprint-state.yaml to emit a per-story `- id: / status:` list under a `stories:` root key,
so that BC-5.41.001 (wave-gate HANDOFF.md production) and BC-5.41.002 (wave-state.yaml manifest production) can mechanically derive `next_wave_stories`, `wave_id`, and EPIC-COMPLETE status from sprint-state.yaml without a bespoke format adapter.

## Background

The observation O-P9-001 from the S-18.01 cascade (pass-9 adversary) identified that:
- The production `.factory/stories/sprint-state.yaml` is in a legacy count-summary + per-epic schema (fields: `current_cycle`, `current_milestone`, `stories.total/merged/ready/draft`, `epics: {E-NNN: {name, stories, status, ...}}`).
- The consumers BC-5.41.001 PC3 and BC-5.41.002 PC3 both require a flat per-story `{id, status}` list to derive wave_id (leading-contiguous-terminal-run algorithm) and next_wave_stories.
- Without a conformant producer, the wave-handoff and WASM gate either require a bespoke adapter (hidden complexity, drift risk) or silently fail to compute correct wave IDs.

This story scopes:
1. A migration of the existing production sprint-state.yaml to emit per-story `stories:` entries alongside (or replacing) the legacy aggregate counts.
2. An update to the wave-scheduling skill's SKILL.md so that future sprint-state.yaml writes produce the conformant format by default.
3. Round-trip validation: verify wave-handoff (S-18.01) and wave-gate WASM (S-18.02) correctly parse the migrated file.

## Acceptance Criteria

### AC-001 (traces to BC-5.41.002 postcondition 3 — stories derived from sprint-state.yaml status:pending/draft)
The production `.factory/stories/sprint-state.yaml` contains a `stories:` root-level key whose value is a list of per-story objects. Each object has at minimum:
- `id:` — story ID string (e.g., `S-18.02`)
- `status:` — canonical sprint status string (one of: `draft`, `pending`, `merged`, `withdrawn`, `cancelled`, `in-progress`, `partial`, `completed`, `blocked`, `ready`)

No story is omitted from this list that appears in STORY-INDEX.md with a non-retired status. The list covers all 120 active stories (as of sprint-state.yaml v2 authorship).

### AC-002 (traces to BC-5.41.002 postcondition 3 — leading-contiguous-terminal-run algorithm prerequisite)
The `stories:` list is ordered by wave/dependency order (stories in wave N appear before wave N+1 stories in the list). This ordering is required for the P-SPRINT-STATE-WAVE-ORDER precondition in BC-5.41.001 PC2 (wave_id derivation from file order when no per-entry `wave:` field is present).

If per-entry `wave:` fields are present on each entry (as per BC-5.41.001 PC2 algorithm note), the list order is still wave-ascending to remain unambiguous regardless of which algorithm the consumer uses.

### AC-003 (traces to BC-5.41.002 postcondition 3 — mechanically derived, no RAG)
The per-story status values in `stories:` match the authoritative status from STORY-INDEX.md catalog rows (the catalog row `| S-NNN | ... | status |` column). No story status is invented or inferred. A round-trip verification script compares `stories[*].status` against STORY-INDEX.md catalog rows and fails on any mismatch.

### AC-004 (traces to BC-5.41.002 postcondition 3 + BC-5.41.001 postcondition 3 — wave-handoff round-trip)
After the sprint-state.yaml migration, invoking the wave-handoff skill (S-18.01) in a test harness against the migrated file produces correct `next_wave_stories` output — specifically, entries with `status: draft` or `status: pending` appear in wave-state.yaml's `stories:` section, and entries with terminal status (merged/withdrawn/cancelled) are excluded. No `BrokenSprintState` error fires on a well-formed migrated file.

### AC-005 (traces to BC-5.41.002 postcondition 3 — WASM gate round-trip)
After the migration, the validate-wave-handoff-completeness WASM gate (S-18.02) correctly processes a HANDOFF.md whose `next_wave_stories` list was derived from the migrated sprint-state.yaml. The gate does not emit false-positive `HandoffIncomplete` errors due to a mismatched format.

### AC-006 (traces to BC-5.41.001 postcondition 2 — wave_id derivation)
The wave-handoff skill, operating against the migrated sprint-state.yaml, correctly computes `wave_id` using the leading-contiguous-terminal-run algorithm: count the contiguous prefix of `stories:` entries with terminal status; `wave_id = count + 1`. A bats test verifies this with a known fixture (e.g., 10 merged stories followed by drafts → `wave_id: 11`).

### AC-007 (traces to NEW BC NEEDED — producer output obligation; TBD pending PO authorship)
The wave-scheduling skill's SKILL.md behavioral steps include an explicit step mandating that any sprint-state.yaml write operation emits the per-story `stories:` list in the conformant format. Existing per-epic aggregate blocks (under `epics:`) MAY co-exist but are NOT the primary format consumed by wave-gate / wave-handoff. The SKILL.md step cites BC-5.41.002 PC3 as the format authority.

## Architecture Compliance Rules

1. **No phantom `wave:` story frontmatter field (BC-5.41.002 INV3):** The `stories:` list ordering in sprint-state.yaml MUST be derived from STORY-INDEX.md `depends_on:` dependency graph (topological sort), NOT from a `wave:` frontmatter field on story files — that field does not exist on story specs.
2. **No fabricated statuses (BC-5.41.002 PC3):** Each story's `status` value MUST be read directly from STORY-INDEX.md catalog rows. No AI-inferred or context-approximated statuses are permitted. A round-trip verification step is mandatory (T-1 AC-003 test).
3. **set -euo pipefail in all new bash scripts** (CLAUDE.md convention).
4. **POSIX character classes in grep/sed/awk** (lesson from S-18.01 portability fixes): use `[[:space:]]` not `\s`, `[[:digit:]]` not `\d`, `[[:alnum:]_]` not `\w`. No PCRE shorthand classes. Enforced by the existing bats portability guard in `tests/wave-handoff.bats` test `test_BC_5_41_001_F_P11_001_bsd_portability_no_pcre_classes_in_grep_sed`.
5. **No `local -A` (bash 3.2 compatibility guard):** macOS ships bash 3.2 as `/bin/bash`. Associative arrays (`declare -A` / `local -A`) require bash 4+. Any new bash scripts that need associative arrays MUST either: (a) guard with `if [[ ${BASH_VERSINFO[0]} -lt 4 ]]; then echo "requires bash 4+"; exit 1; fi` OR (b) use a bash 4 binary explicitly (e.g., `/usr/local/bin/bash` from homebrew). Lesson from S-18.01 CI failure: `ea7328ac` added this guard.
6. **No global IFS mutation:** Any `IFS=` assignment MUST be local (`local IFS=...`) or scoped within a subshell. Global IFS mutation causes parse failures in callers. Lesson from S-18.01 CI failure: `2b40dfd5` replaced IFS-based parsing with `awk -F'|'`.
7. **No undeclared python/PyYAML runtime dependency:** If YAML parsing requires Python, document the dependency in the SKILL.md step AND add a preflight check. Lesson from S-18.01 CI failure: `aaa8da8a/3fe11ea1` added `--break-system-packages` for PEP 668 environments. Prefer `yq` (if available) or AWK-based YAML key extraction over Python for simple key reads.

## Library and Framework Requirements

- bash >= 4.x for any new scripts using advanced features (CI provides bash 4 on Linux; macOS requires explicit path or guard per Rule 5)
- Standard POSIX tools: `awk`, `grep -E` with POSIX character classes, `sort`, `uniq`
- bats-core: existing version in `plugins/vsdd-factory/tests/`
- No new Python dependencies without preflight check in SKILL.md
- No `jq` unless already present in CI matrix (verify in `ci.yml` first)
