# S-18.11 — sprint-state.yaml producer migration to per-story {id, status} format

**Epic:** E-18 — Factory Context Durability (feature #173)
**Wave:** 9 (depends on S-18.01 merged + S-18.02 WASM gate drafted; placed after both consumers are in-flight)
**Depends on:** S-18.01 (merged), S-18.02
**Priority:** P1 — integration gap between producer and consumers; the WASM wave-gate (S-18.02) and shell wave-handoff (S-18.01) both consume sprint-state.yaml in per-story format that the current production file does not emit
**Subsystem anchor:** SS-05 owns this story's scope because SS-05 (Pipeline Orchestration) governs the sprint-state.yaml lifecycle, the wave-scheduling skill, and the producer-side format obligation. SS-06 is co-listed because the wave-handoff SKILL.md (SS-06) consumes sprint-state.yaml directly.

## Producer BC (BC-5.41.004)

**BC-5.41.004** (v1.4, authored 2026-06-28/2026-06-29 by product-owner) governs the PRODUCER side of sprint-state.yaml — the obligation on the `wave-scheduling` skill (or any equivalent sprint-state.yaml writer) to emit a conformant per-story `{id, status}` list under a `stories:` root key. This BC is the producer-side complement to the consumer-side obligations in BC-5.41.001 (PC2 P-SPRINT-STATE-WAVE-ORDER precondition) and BC-5.41.002 (PC3 stories derivation).

Key obligations from BC-5.41.004:
- **PC1:** `stories:` root key MUST be present; absent key is a hard abort.
- **PC2:** Each entry has `id:` (canonical story ID from STORY-INDEX.md) and `status:` (one of the canonical 8-value enum; read mechanically from STORY-INDEX.md — no RAG).
- **PC3 (full-graph wave-depth ordering, v1.4 def b):** The `stories:` list uses a two-partition ordering rule per ADR-026 §Decision 3a v1.37: **Partition A** — all terminal stories (merged/withdrawn/cancelled) form a contiguous leading block; **Partition B** — all non-terminal stories follow in a contiguous trailing block. **Intra-partition sort key (both partitions):** Within each partition, order by **(full-graph wave-depth ASC, story-ID lexicographic ASC)**. Full-graph wave-depth of story S = 1 if S has no `depends_on` entries (root story); otherwise `1 + max(depth(P) for all P in S.depends_on)` computed over the FULL `depends_on` graph including cross-partition supersession edges (this is a global graph property, independent of partition placement). Cross-partition supersession edges (terminal story in Partition A `depends_on` a non-terminal story in Partition B that carries `superseded_by:` frontmatter) are INCLUDED in the full-graph depth computation; the terminal story still appears in Partition A before its superseded non-terminal dependency in Partition B (partition placement is determined by terminal/non-terminal status, not dependency direction). **EC-010** governs the two sub-cases: (a) supersession edge with `superseded_by:` on the dep-story — TOLERATE, emit normally, edge INCLUDED in depth computation; (b) genuine anomaly without `superseded_by:` on the dep-story — HARD ABORT `TopoViolation: terminal story <ID> depends_on non-terminal story <dep-ID>`. The bats test `test_partitions_sorted_by_full_graph_depth_def_b` independently computes depths from STORY-INDEX, asserts each partition monotonic-by-depth + lex tie-break + done-first contiguity.
- **PC4:** Every non-retired story from STORY-INDEX.md MUST appear; retired stories are omitted.
- **PC5:** Legacy `epics:` section MAY co-exist; producer MUST NOT mutate it.
- **PC6:** YAML MUST remain well-formed.
- **INV-1:** Canonical 8-value status enum: `draft`, `ready`, `in-progress`, `partial`, `blocked`, `merged`, `withdrawn`, `cancelled`. `completed` and `pending` are NOT valid emitted values (`completed` is removed; `pending` is RESERVED in BC-5.41.002 PC3 for forward-compatibility but NOT emitted by STORY-INDEX.md or the producer).
- **EC-007:** Any status outside the 8-value enum triggers `UnknownStatusToken` hard-abort.

## Narrative

As a wave-gate operator or wave-handoff skill,
I want sprint-state.yaml to emit a per-story `- id: / status:` list under a `stories:` root key,
so that BC-5.41.001 (wave-gate HANDOFF.md production) and BC-5.41.002 (wave-state.yaml manifest production) can mechanically derive `next_wave_stories`, `wave_id`, and EPIC-COMPLETE status from sprint-state.yaml without a bespoke format adapter.

## Background

The observation O-P9-001 from the S-18.01 cascade (pass-9 adversary) identified that:
- The production `.factory/stories/sprint-state.yaml` is in a legacy count-summary + per-epic schema (fields: `current_cycle`, `current_milestone`, `stories.total/merged/ready/draft`, `epics: {E-NNN: {name, stories, status, ...}}`).
- The consumers BC-5.41.001 PC3 and BC-5.41.002 PC3 both require a flat per-story `{id, status}` list to derive wave_id (wave-group-ordinal: completed terminal wave groups + 1) and next_wave_stories.
- Without a conformant producer, the wave-handoff and WASM gate either require a bespoke adapter (hidden complexity, drift risk) or silently fail to compute correct wave IDs.

This story scopes:
1. A migration of the existing production sprint-state.yaml to emit per-story `stories:` entries alongside (or replacing) the legacy aggregate counts.
2. An update to the wave-scheduling skill's SKILL.md so that future sprint-state.yaml writes produce the conformant format by default.
3. Round-trip validation: verify wave-handoff (S-18.01) and wave-gate WASM (S-18.02) correctly parse the migrated file.

## Acceptance Criteria

### AC-001 (traces to BC-5.41.004 PC1 + PC2 + INV-1; BC-5.41.002 PC3)
The production `.factory/stories/sprint-state.yaml` contains a `stories:` root-level key whose value is a list of per-story objects. Each object has at minimum:
- `id:` — story ID string (e.g., `S-18.02`)
- `status:` — canonical sprint status string; one of the **8-value** set defined in BC-5.41.004 INV-1: `draft`, `ready`, `in-progress`, `partial`, `blocked`, `merged`, `withdrawn`, `cancelled`. (`completed` and `pending` are NOT valid emitted values: `completed` is removed from the taxonomy; `pending` is RESERVED in BC-5.41.002 PC3 for forward-compatibility but is NOT emitted by STORY-INDEX.md or this producer.)

No story is omitted from this list that appears in STORY-INDEX.md with a non-retired status (BC-5.41.004 PC4). The list covers all 149 active stories (as of sprint-state.yaml v2 authorship). The `stories:` key being absent is a hard abort per BC-5.41.004 PC1.

### AC-002 (traces to BC-5.41.004 PC3 v1.4 + INV-3; BC-5.41.002 PC3; BC-5.41.001 PC2)
The `stories:` list uses the **two-partition ordering rule, definition (b)** (BC-5.41.004 PC3 v1.4 per ADR-026 §Decision 3a v1.37):

- **Partition placement (unchanged from def a):** All terminal stories (merged/withdrawn/cancelled) form a contiguous leading **Partition A**; all non-terminal stories follow in a contiguous trailing **Partition B**. Partition placement is determined by terminal/non-terminal status only — not by dependency direction.
- **Intra-partition sort key — definition (b), both partitions:** Within each partition, stories are ordered by **(full-graph wave-depth ASC, story-ID lexicographic ASC)**. The **full-graph wave-depth** of story S is: `depth(S) = 1` if S has no `depends_on` entries (root story); otherwise `depth(S) = 1 + max(depth(P) for all P in S.depends_on)`, computed recursively over the **FULL** `depends_on` graph — all edges, including cross-partition supersession edges. This is a global graph property independent of partition placement.
- **Cross-partition supersession edges — INCLUDED in depth computation:** When a terminal story (Partition A) has a `depends_on:` entry pointing to a non-terminal story (Partition B) that carries `superseded_by:` frontmatter (e.g., merged S-3.01/02/03/S-4.07/08 → partial S-3.04 with `superseded_by: ADR-015`), this cross-partition edge IS INCLUDED in the full-graph depth computation for the terminal story. The terminal story still appears in Partition A before its superseded non-terminal dependency in Partition B. The EC-010 guard in BC-5.41.004 v1.4 distinguishes this tolerated supersession case (edge included, emit normally) from genuine anomalies (terminal story depends on non-terminal story WITHOUT `superseded_by:` — those trigger `TopoViolation` hard-abort).

**No phantom `wave:` frontmatter field on story files is consulted** — such a field does not exist (BC-5.41.004 INV-3). The two-partition structure structurally satisfies the P-SPRINT-STATE-WAVE-ORDER precondition in BC-5.41.001 PC2 v1.28 (all terminal stories form a contiguous leading prefix; the WaveOrderUnverifiable guard logic is unchanged). The bats test `test_partitions_sorted_by_full_graph_depth_def_b` independently computes full-graph depths from STORY-INDEX, then asserts: each partition is monotonic-non-decreasing by depth, lex tie-break within same-depth stories, and done-first contiguity (no terminal story follows a non-terminal story).

### AC-003 (traces to BC-5.41.004 PC2 + INV-2; BC-5.41.002 PC3)
The per-story status values in `stories:` match the authoritative status from STORY-INDEX.md catalog rows (the catalog row `| S-NNN | ... | status |` column). No story status is invented, inferred, or RAG-approximated (BC-5.41.004 INV-2 — no fabricated statuses; producer-side complement to BC-5.41.002 INV4 no-RAG rule). A round-trip verification script compares `stories[*].status` against STORY-INDEX.md catalog rows and fails on any mismatch. Any status token not in the canonical 8-value enum triggers `UnknownStatusToken` hard-abort (BC-5.41.004 EC-007).

### AC-004 (traces to BC-5.41.002 PC3 v1.20 + BC-5.41.001 PC2 + PC3)
After the sprint-state.yaml migration, invoking the wave-handoff skill (S-18.01) in a test harness against the migrated file produces correct `next_wave_stories` output — specifically, entries with `status: draft` appear in wave-state.yaml's `stories:` section (the `pending` arm in BC-5.41.002 PC3 is a presently-no-op RESERVED arm; per BC-5.41.002 PC3 v1.20 reserved-pending note, only `draft` is the current next-wave selector), and entries with terminal status (merged/withdrawn/cancelled) are excluded. No `BrokenSprintState` error fires on a well-formed migrated file. The anti-fabrication cross-checks in BC-5.41.001 PC3 pass (wave_id and next_wave_stories derive from the conformant sprint-state.yaml per-story list).

### AC-005 (traces to BC-5.41.002 PC3 v1.20 + BC-5.41.001 PC2)
After the migration, the validate-wave-handoff-completeness WASM gate (S-18.02) correctly processes a HANDOFF.md whose `next_wave_stories` list was derived from the migrated sprint-state.yaml. The gate does not emit false-positive `HandoffIncomplete` errors due to a mismatched format. The conformant `stories:` list produced by BC-5.41.004 PC1–PC3 enables BC-5.41.001 PC2 wave_id derivation (P-SPRINT-STATE-WAVE-ORDER precondition met), which is what the WASM gate validates.

### AC-006 (traces to BC-5.41.001 PC2; BC-5.41.004 PC3 + INV-3)
The wave-handoff skill, operating against the migrated sprint-state.yaml, correctly computes `wave_id` as the **wave-group ordinal**: `wave_id = (number of completed terminal WAVE GROUPS) + 1`, where a completed terminal wave group is a contiguous terminal-run (merged/withdrawn/cancelled) in the wave-ascending `stories:` list that is followed by at least one non-terminal entry (a terminal→non-terminal transition). This is the `derive_wave_id` semantics per ADR-026 §Wave-Identity Derivation and BC-5.41.001 PC2: count completed terminal wave groups, add 1. A bats test verifies this with a known fixture: 10 merged stories appearing as one contiguous block followed by draft entries → **one completed terminal wave group → `wave_id: 2`** (not 11; the count is wave-groups, not individual stories). This AC also validates BC-5.41.004 PC3 indirectly: the wave-group-ordinal algorithm can only operate correctly when the `stories:` list is wave-ascending (which PC3 mandates) and uses real terminal statuses from STORY-INDEX.md (which INV-3 mandates via no phantom fields).

### AC-007 (traces to BC-5.41.004 PC1 + PC2 + PC3)
The wave-scheduling skill's SKILL.md behavioral steps include an explicit step mandating that any sprint-state.yaml write operation emits the per-story `stories:` list in the conformant format per BC-5.41.004 PC1 (key present), PC2 (per-entry schema: `id:` + `status:` from STORY-INDEX.md), and PC3 (wave-ascending topo-sort order). Existing per-epic aggregate blocks (under `epics:`) MAY co-exist per BC-5.41.004 PC5 but are NOT the primary format consumed by wave-gate / wave-handoff. The SKILL.md step MUST cite BC-5.41.004 as the producer format authority (not BC-5.41.002 PC3 alone — the latter is the consumer-side obligation; BC-5.41.004 is the producer-side obligation).

## Architecture Compliance Rules

1. **No phantom `wave:` story frontmatter field (BC-5.41.004 INV-3; BC-5.41.002 INV3):** The `stories:` list ordering in sprint-state.yaml MUST be derived from STORY-INDEX.md `depends_on:` dependency graph (topological sort), NOT from a `wave:` frontmatter field on story files — that field does not exist on story specs.
2. **No fabricated statuses (BC-5.41.004 INV-2; BC-5.41.002 PC3):** Each story's `status` value MUST be read directly from STORY-INDEX.md catalog rows. No AI-inferred or context-approximated statuses are permitted. A round-trip verification step is mandatory (T-1 AC-003 test). Status values outside the canonical 8-value enum trigger `UnknownStatusToken` hard-abort per BC-5.41.004 EC-007.
3. **set -euo pipefail in all new bash scripts** (CLAUDE.md convention).
4. **POSIX character classes in grep/sed/awk** (lesson from S-18.01 portability fixes): use `[[:space:]]` not `\s`, `[[:digit:]]` not `\d`, `[[:alnum:]_]` not `\w`. No PCRE shorthand classes. Enforced by the existing bats portability guard in `tests/wave-handoff.bats` test `test_BC_5_41_001_F_P11_001_bsd_portability_no_pcre_classes_in_grep_sed`.
5. **No `local -A` (bash 3.2 compatibility guard):** macOS ships bash 3.2 as `/bin/bash`. Associative arrays (`declare -A` / `local -A`) require bash 4+. Any new bash scripts that need associative arrays MUST either: (a) guard with `if [[ ${BASH_VERSINFO[0]} -lt 4 ]]; then echo "requires bash 4+"; exit 1; fi` OR (b) use a bash 4 binary explicitly (e.g., `/usr/local/bin/bash` from homebrew). Lesson from S-18.01 CI failure: `ea7328ac` added this guard.
6. **No global IFS mutation:** Any `IFS=` assignment MUST be local (`local IFS=...`) or scoped within a subshell. Global IFS mutation causes parse failures in callers. Lesson from S-18.01 CI failure: `2b40dfd5` replaced IFS-based parsing with `awk -F'|'`.
7. **No undeclared python/PyYAML runtime dependency:** If YAML parsing requires Python, document the dependency in the SKILL.md step AND add a preflight check. Lesson from S-18.01 CI failure: `aaa8da8a/3fe11ea1` added `--break-system-packages` for PEP 668 environments. Prefer `yq` (if available) or AWK-based YAML key extraction over Python for simple key reads.
