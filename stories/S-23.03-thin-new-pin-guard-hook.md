# S-23.03: Thin new-pin guard (WASM PreToolUse hook)

## Narrative

- **As a** factory operator writing or editing a `.factory/` markdown artifact
- **I want** a PreToolUse hook that blocks my Edit/Write if it introduces a newly-stale or newly-added load-bearing inline version pin in a live section
- **So that** the corpus migration (S-23.06..S-23.13) cannot silently regress, and no future contributor reintroduces the exact self-regenerating pin-propagation churn ADR-045 eliminates

## Context / Problem Statement

ADR-045 Migration Plan Phase A step 2 requires: "Build the thin new-pin guard (a lightweight check — regex-based codemod-class detector is sufficient at this stage per the cheaper-alternative finding — that rejects newly-introduced load-bearing inline version pins in live sections; this is the only build Phase A requires [besides INDEX-resolution])." The guard operates in "stale-only" mode during the migration window per ADR-045 Decision, Tier 3 item 6 (applied here at the thin-guard tier, not the deferred full Tier-3 validator): a pin that is present and *currently correct* does not block (avoiding blocking untouched historical corpus mid-migration), but any pin that is *stale* (its inline version token no longer matches the ID's current version per S-23.04's `resolve_version`) blocks the write.

This hook is a new PreToolUse WASM plugin under `crates/hook-plugins/`, following the same architecture pattern as the existing `validate-stable-anchors` (TD-VSDD-091 line-cite enforcement) — a sibling concern (volatile line numbers, not version pins) that already established the exemption-zone-classifier + PreToolUse-block pattern this story reuses. It consumes S-23.01's classifier/detector to find candidate pins in the proposed write, and S-23.04's `resolve_version` to determine whether a found pin is stale.

## Acceptance Criteria

### AC-001
Given an Edit/Write payload whose diff introduces a new inline version pin in a live section where the version token is stale (does not match `resolve_version`'s current answer for that ID), the hook blocks with `exit_code=2` and a diagnostic naming the file, line, ID, cited version, and current version. (traces to ADR-045 Migration Plan Phase A step 2; ADR-045 Decision, Tier 3 item 6 "stale-only mode... stale pins block")

### AC-002
Given an Edit/Write payload whose diff introduces a new inline version pin in a live section where the version token happens to be current (matches `resolve_version`), the hook does NOT block — "stale-only" mode explicitly tolerates a correct-at-write-time pin during the migration window (the pin is still discouraged but not yet a hard block; full-mode enforcement, "detect any pin at all," is a Tier-3-gated Phase-C escalation, not this story's scope). (traces to ADR-045 Decision, Tier 3 item 6, "pins present but current do not block")

### AC-003
Given an Edit/Write payload that only touches an exempt zone (per S-23.01's classifier — frontmatter `modified:`, `[Prior:]`, `## Changelog`, cycle logs, decision-log/burst-log narrative), the hook never blocks regardless of the version token's staleness. (traces to ADR-045 Decision, Tier 1, "Permitted exceptions")

### AC-004
Given an Edit/Write payload that does not touch any pin-shaped text at all, the hook is a no-op (passes through with no diagnostic). (traces to ADR-045 Decision preamble item 1 — the guard's scope is limited to newly-introduced/newly-stale pins, not a general content gate)

### AC-005
The hook is wired into `plugins/vsdd-factory/hooks-registry.toml` as a PreToolUse plugin scoped to Edit|Write on `.factory/**/*.md` paths, following the existing `validate-stable-anchors` and `validate-index-cite-refresh` registry-entry conventions (tier, on-error behavior = block). (traces to CLAUDE.md Hook registry semantics section; ADR-045 Migration Plan Phase A step 2)

### AC-006
The hook's blocking diagnostic is a literal, structured message (file/line/ID/cited-version/current-version), not a narrative attestation — consistent with D-449(a) "literal-shell-execution-evidence" (the gate computes and reports; it does not ask an agent to narrate). (traces to ADR-045 Rationale, "Tier 3 aligns with D-449(a)... the validator is a mechanical gate")

### AC-007 (negative control)
The hook does not block a write that only *removes* a pin (a codemod-produced migration edit) — only additions/introductions of a stale pin trigger the block. Removing a pin is always permitted. (traces to ADR-045 Migration Plan Phase A step 5, "mechanical corpus migration" must not be blocked by its own guard)

### AC-008
Given a diff spanning a line-wrapped or anchor-interposed pin (S-23.01 AC-003/AC-004 detection classes), the hook still correctly identifies it as a candidate pin and evaluates staleness — it does not silently miss the pin merely because the detector's tokenization is non-adjacent. (traces to S-23.01 AC-003/AC-004; ADR-045 Context failure modes 1-2)

## Edge Cases

| ID | Description | Expected Behavior |
|----|-------------|--------------------|
| EC-001 | `resolve_version` returns AC-005-class "not found" for the cited ID (per S-23.04) | Hook fails closed: treats an unresolvable ID as stale (cannot prove currency) and blocks, per the project's fail-closed-on-exhaustion precedent (ADR-039) |
| EC-002 | Diff touches a file outside `.factory/**/*.md` (e.g., a `crates/` Rust source file) | Hook does not fire at all (registry scope excludes it) |
| EC-003 | Diff is a pure rename/move with no textual content change | Hook does not block (no new pin content introduced) |
| EC-004 | Multiple pins in one diff, one stale and one current | Hook blocks on the stale one and reports both in its diagnostic (does not silently report only the first) |

## Previous Story Intelligence

**From S-23.01:** the detector already tolerates line-wraps and anchor-interposition (AC-008 here is a direct consequence — do not re-derive tokenization logic in this crate). **From S-23.04:** `resolve_version`'s "not found" error must be treated fail-closed here (EC-001), matching the project's existing fail-closed-on-exhaustion posture (ADR-039, POLICY 11-class discipline) rather than silently passing an unresolvable ID. **From `validate-stable-anchors` (sibling precedent, not part of this epic):** the pure-`hook_logic`-with-injectable-closures pattern is this codebase's established, test-friendly WASM-hook architecture; follow it exactly rather than inventing a new shape.

## Architecture Compliance Rules

- `hook_logic` MUST be pure (all I/O — file reads via the detector's caller, `resolve_version` calls — injected as closures/results, not called directly from inside the pure function).
- No `unwrap()`/`expect()` in the WASM entry point; a resolver failure (EC-001) must route through the fail-closed decision path, not panic.
- Follow `HOST_ABI_VERSION = 1` unless S-23.04 requires a new host function beyond `read_file_range` (it should not — S-23.04 already extends the existing host-function surface).
- Must not duplicate `validate-stable-anchors`'s SOURCE_FILE_EXTENSIONS pattern-matching logic — that crate's scope (source-code line-cites) is deliberately distinct from this crate's scope (version pins); the two hooks coexist as siblings, not as one merged hook.
