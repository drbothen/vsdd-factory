# S-21.09: validate-factory-path-staging.wasm artifact restore + per-name registry parity check

## Narrative

- **As a** factory pipeline operator running any Bash tool call
- **I want** the `validate-factory-path-staging` WASM guard to actually execute (its `.wasm`
  artifact is committed and tracked in git) AND a per-name registry parity CI check that
  detects any future declared-but-missing artifact before it reaches production
- **So that** INV-E21-001 Layer-1 enforcement (BC-4.16.001) is not silently inert, and the
  structural class of failure — registry count 36, git count 36, but different 36 — is
  permanently closed

## Context / Finding Summary

S-21.01 (merged PR #759, 2026-07-23) created the crate source at
`crates/hook-plugins/validate-factory-path-staging/` and registered the plugin in
`hooks-registry.toml` with `event = "PreToolUse"`, `tool = "^Bash$"`, `priority = 140`,
`on_error = "continue"`. However the `.wasm` artifact was never built and committed, so
the plugin has never executed in any production session.

Evidence of non-invocation: the session dispatcher log shows 0 events for the
`validate-factory-path-staging` plugin while sibling `^Bash$` guards at the same priority
(`verify-git-push` prio 140 and `verify-factory-lock-bash` prio 142) each logged 888-889
events. `git ls-files plugins/vsdd-factory/hook-plugins/` confirms the artifact is absent.

The gap was masked by a count-based parity check (POLICY 20) that reported a clean balance
because `validate-factory-path-staging.wasm` is declared-but-missing while
`vsdd-context-resolvers.wasm` is tracked-but-declared-in `resolvers-registry.toml` (not
`hooks-registry.toml`). A 1-for-1 swap is structurally invisible to count-based checking.

## Acceptance Criteria

### AC-001: Artifact is tracked in git (traces to BC-4.16.001 Precondition 3)

The file `plugins/vsdd-factory/hook-plugins/validate-factory-path-staging.wasm` MUST
be present in the git index — i.e., `git ls-files plugins/vsdd-factory/hook-plugins/validate-factory-path-staging.wasm`
returns a non-empty result. File existence on disk alone is insufficient; the artifact must
be committed.

**Note:** `plugins/vsdd-factory/hook-plugins/` is excluded by `.gitignore` (gitignored
directory for WASM binaries not shipped via source control in normal commits). The
established precedent for committing WASM binaries to this path is `git add -f`, which
overrides the gitignore. This same pattern was used to track all 35 existing `.wasm` files
in that directory.

- **Test:** `test_validate_factory_path_staging_wasm_is_git_tracked()` — calls
  `git ls-files` and asserts the file is present

### AC-002: Guard appears in dispatcher session log (traces to BC-4.16.001 Precondition 3)

After the artifact is committed and the session starts fresh, a Bash tool call containing
any `git add` command MUST produce a `plugin.completed` (or `plugin.log`) event for the
plugin named `validate-factory-path-staging` in the dispatcher internal log. Zero log
entries for this plugin while same-tier `^Bash$` siblings are logging normally is direct
evidence of non-invocation and MUST cause this AC to fail.

- **Test:** bats integration test — issue a `git add <non-.factory path>` Bash call in a
  test session; grep the dispatcher log for `validate-factory-path-staging`; assert
  non-empty match

### AC-003: Guard BLOCKS git add of .factory/ path on product branch (traces to BC-4.16.001 Postcondition 1)

When a Bash payload `git add .factory/STATE.md` is dispatched on a product branch (e.g.,
`develop`), the dispatcher MUST return `block_intent = true` (exit code 2) and the log
MUST contain a `FactoryPathOnProductBranch` error emitted by the `validate-factory-path-staging`
plugin. Evidence must be a dispatcher log entry, NOT merely file presence.

- **Test:** `test_guard_blocks_factory_path_on_product_branch()` — bats mock with
  `branch = develop`, payload = `git add .factory/STATE.md`; assert exit 2 and
  `FactoryPathOnProductBranch` in output

### AC-004: Guard PASSES git add of non-.factory/ path (traces to BC-4.16.001 Postcondition 2)

When a Bash payload `git add src/main.rs` is dispatched on any branch, the dispatcher
MUST return `block_intent = false` (exit code 0) and the log MUST contain a
`plugin.completed` event for `validate-factory-path-staging` with no block.

- **Test:** `test_guard_passes_non_factory_path()` — bats mock with any branch, payload =
  `git add src/main.rs`; assert exit 0

### AC-005: Guard PASSES git add of .factory/ path on factory-artifacts branch (traces to BC-4.16.001 Postcondition 3)

When a Bash payload `git add .factory/STATE.md` is dispatched on the `factory-artifacts`
branch, the dispatcher MUST return `block_intent = false` (exit code 0). This is the
state-manager's canonical mounted-worktree workflow and MUST NOT be blocked.

- **Test:** `test_guard_passes_factory_path_on_factory_artifacts_branch()` — bats mock
  with `branch = factory-artifacts`, payload = `git add .factory/STATE.md`; assert exit 0

### AC-006: Exhaustive per-name declared-vs-built set-difference audit (traces to BC-4.16.001 Precondition 3)

A Cargo workspace integration test MUST compute the set difference between:

1. **Declared set:** the union of all unique `plugin` values across `hooks-registry.toml`
   AND `resolvers-registry.toml` (both registries; handles the multi-registry split)
2. **Tracked set:** the set of `.wasm` filenames returned by
   `git ls-files plugins/vsdd-factory/hook-plugins/`

The test MUST assert that `declared_set == tracked_set` (both directions: no
declared-but-missing artifact, no tracked-but-undeclared artifact).

The test MUST handle `vsdd-context-resolvers.wasm` as declared-in-resolvers-registry
(not a false positive) without special-casing it by name — it must be correctly resolved
by aggregating declared sets across both registries before computing the difference.

**Implementation placement decision:** The check is implemented as a Cargo integration
test (not a WASM hook or new `.sh` file), because:
(a) artifact parity is a build-time invariant, not a per-tool-call concern;
(b) POLICY 21 prohibits new `.sh` files;
(c) a Cargo test is platform-agnostic, runs locally via `cargo test --workspace --all-targets`,
    and is enforced by the same CI gate (`ci.yml`) that already runs `cargo test`.

The test should be self-contained and read `hooks-registry.toml` + `resolvers-registry.toml`
from a path relative to the workspace root (determined via `CARGO_MANIFEST_DIR` or env).

- **Test:** `test_registry_parity_declared_set_equals_tracked_set()` — parses both
  registries, reads git-tracked list, asserts set equality; MUST FAIL against pre-fix state
  where `validate-factory-path-staging.wasm` is absent

### AC-007: Pre-fix audit confirms validate-factory-path-staging.wasm is the only gap (traces to BC-4.16.001 Invariant 1)

An exhaustive set-difference audit across both registries (conducted as part of this story's
implementation) MUST confirm that `validate-factory-path-staging.wasm` is the only
declared-but-missing artifact. If any additional declared-but-missing artifacts are found,
they MUST be surfaced as findings and addressed within this story's scope before the story
can be marked ready.

**Pre-story audit result (verified 2026-08-04):**
- Declared in `hooks-registry.toml` (unique): 35 plugins
- Declared in `resolvers-registry.toml`: 1 plugin (`vsdd-context-resolvers.wasm`)
- Total declared: 36 unique plugin artifacts
- Tracked in git (`git ls-files plugins/vsdd-factory/hook-plugins/ | grep \.wasm$`): 35 files
- Declared-but-missing: `{validate-factory-path-staging.wasm}` (1 artifact)
- Tracked-but-undeclared-in-hooks-registry: `{vsdd-context-resolvers.wasm}` (correctly declared in resolvers-registry; 0 true undeclared)
- True gap: exactly 1 artifact missing; no others

This AC is satisfied when AC-006's test passes and the devops build confirms no other
artifacts are absent.

- **Test:** AC-006's test with the audit result asserted explicitly (zero additional gaps
  after `validate-factory-path-staging.wasm` is committed)

## Routing Proposals (surfaced, not authored per instructions)

### POLICY 20 routing

The dispatch references "POLICY 20's count-based parity check." Search of
`.factory/policies.yaml` finds no entry for POLICY 20 by that identifier. Two scenarios:

1. **POLICY 20 is informal/procedural and not yet registered in policies.yaml:** In that
   case, AC-006's Cargo test is the formal enforcement mechanism that replaces the informal
   count-based check. No policy registration is strictly needed.

2. **POLICY 20 needs to be formally registered:** Proposed routing: state-manager via
   `/vsdd-factory:policy-add`. The registration should document: (a) count-based checking is
   prohibited (it cannot detect 1-for-1 swaps), (b) the correct check is per-name
   set-difference across all registries, (c) the Cargo test added by S-21.09 is the
   enforcement mechanism, (d) adding a new hooks-registry.toml entry without also adding a
   corresponding `.wasm` artifact tracked in git is a POLICY 20 violation.

**Decision needed from human:** Which scenario applies? If POLICY 20 needs formal
registration, the story-writer will not author it — route to state-manager + `/vsdd-factory:policy-add`.

### New BC routing (optional)

BC-4.16.001 Precondition 3 covers the restore of the artifact (its existence is a
precondition for the dispatcher to invoke the plugin). The parity check ACs are traced
to BC-4.16.001 Precondition 3 as the indirect anchor (the check exists to guarantee
Precondition 3 is satisfiable at build time).

If a dedicated BC for "registry-declared WASM artifacts must all be tracked in git" is
desired (e.g., BC-4.17.001 or a new clause in BC-4.16.001), proposed routing:
product-owner via standard BC authoring dispatch. This is optional — the AC traces to
BC-4.16.001 Precondition 3 suffice for Spec-First Gate purposes.
