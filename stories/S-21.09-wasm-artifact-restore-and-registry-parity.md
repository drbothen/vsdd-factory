# S-21.09: validate-factory-path-staging.wasm artifact restore + per-name registry parity check

## Narrative

- **As a** factory pipeline operator running any Bash tool call
- **I want** the `validate-factory-path-staging` WASM guard to actually execute (its `.wasm`
  artifact is committed and tracked in git) AND a per-name registry parity CI check that
  detects any future declared-but-missing artifact before it reaches production
- **So that** INV-E21-001 Layer-1 enforcement (BC-4.16.001) is not silently inert, and the
  structural class of failure — declared name absent from git — is permanently closed

## Context / Finding Summary

S-21.01 (merged PR #759, `7bb0e797`, 2026-07-23) created the crate source at
`crates/hook-plugins/validate-factory-path-staging/` and registered the plugin in
`hooks-registry.toml` with `event = "PreToolUse"`, `tool = "^Bash$"`, `priority = 140`,
`on_error = "continue"`. The WASM artifact was never built and committed.

**Root cause: release lag, not a parity-check gap.** `v1.0.0-rc.23` was tagged
2026-07-18 — five days BEFORE S-21.01 merged on 2026-07-23. The operator runtime at
rc.23 carries a `hooks-registry.toml` with ZERO occurrences of
`validate-factory-path-staging`, so the guard has been inert for 100% of its existence at
the operator level. The develop branch is 44 commits unreleased
(`v1.0.0-rc.23-44-g62fbcf1a`).

**The missing WASM on develop is a hygiene/self-hosting defect.** The release pipeline
splits across two jobs in `release.yml`, each containing an identically-named "Verify
registry-declared WASM plugins are staged" step — describing "the Verify step" in the
singular is ambiguous and was the source of earlier miscommunication. The `build-binaries`
job builds every declared WASM and runs the FIRST Verify step, which parses
`hooks-registry.toml` ONLY (inline comment on that step: "Only hooks-registry entries are
checked here; resolvers-registry is checked in the commit-binaries job"); a separate
"Stage artifact directory" step in `build-binaries` also carries two hardcoded
keep-assertions naming `vsdd-context-resolvers.wasm` specifically
(`test -f plugins/vsdd-factory/hook-plugins/vsdd-context-resolvers.wasm` and
`grep -q "hook-plugins/vsdd-context-resolvers.wasm"` against `resolvers-registry.toml`).
The `commit-binaries` job downloads the built artifacts, stages binaries and WASMs with
`git add -f`, and runs the SECOND Verify step — a general dual-registry parity check that
parses BOTH `hooks-registry.toml` and `resolvers-registry.toml` via the same
`grep -E '^\s*plugin\s*=\s*"hook-plugins/'` predicate applied twice. The resolver registry
read in this step is suppressed with `2>/dev/null`; if `resolvers-registry.toml` is
absent, renamed, or its `plugin =` lines change shape, `resolver_plugins` becomes empty
and the resolver half passes vacuously (no non-vacuity floor on the resolver arm; see
§Routing Proposals below). `origin/main` has 34-tracked/34-declared parity. The
develop-branch gap means develop's own tree cannot run its own guard — state-manager and
other agents invoking `git add` on develop are unprotected. This defect self-heals at
rc.24 release time (`commit-binaries` stages the WASM with `git add -f` and its
dual-registry Verify step covers both registries) but is a live self-hosting gap on
develop.

**Evidence of non-invocation in session logs.** Dispatcher log grep of
`plugin_name == "validate-factory-path-staging"` across all
`.factory/logs/dispatcher-internal-*.jsonl` files (2026-07-23 to 2026-08-10) returns
**0 records** for all event types. Same-matcher `PreToolUse`/`^Bash$` siblings show
substantially more invocations over the same window — for example, `verify-git-push`
registered ≥14,000 `plugin.invoked` events as of 2026-08-11 (this is a live counter;
exact value grows daily; siblings differ from each other). The 0-vs-non-zero contrast is
the load-bearing signal; the exact per-sibling figure is not fixed in this spec.
**Post-fix evidence (preliminary):** a test of the AC-001 fix on 2026-08-11 (WASM built
and force-tracked, not yet merged) produced 4 records for
`plugin_name == "validate-factory-path-staging"` (2 × `plugin.invoked`, 2 ×
`plugin.completed`, timestamped 2026-08-11T08:55) in a live dispatcher session —
confirming the guard is reachable once the artifact is tracked. These 4 records fall
outside the 2026-07-23 to 2026-08-10 gap window; the "0 records" claim for that range
still reproduces exactly.

**Why CI does not catch this.** `.github/workflows/ci.yml` has a step "Stage WASM plugins
for run-all.sh" that runs a full `--workspace` WASM build and copies every artifact into
the gitignored `plugins/vsdd-factory/hook-plugins/` directory, immediately BEFORE "Run
full bats suite (run-all.sh)". That step does NOT set `CI_REQUIRE_ARTIFACTS`, and
`_require_artifacts` skip-passes on absence of `CI_REQUIRE_ARTIFACTS`. CI validates the
SOURCE (the Rust crate compiles and its unit tests pass) but never the DELIVERY (the
artifact must be tracked in git for the guard to load in production sessions).

### Sibling weak-predicate sites in release.yml and pr-manager-hardening.bats (defer to follow-up story)

The same weak parse predicate (`grep -E '^\s*plugin\s*=\s*"hook-plugins/'`) that
S-21.09's BLOCKER-1 hardens in `bundle_orphan_check.rs` (`parse_plugin_refs` hardening)
survives at five sibling sites outside S-21.09's scope:

1. `.github/workflows/release.yml` — `build-binaries` FIRST "Verify registry-declared WASM
   plugins are staged" step (hooks-registry.toml parse; has `-lt 30` non-vacuity floor)
2. `.github/workflows/release.yml` — `commit-binaries` SECOND "Verify registry-declared WASM
   plugins are staged" step (hooks-registry.toml parse; has `-lt 30` non-vacuity floor)
3. `.github/workflows/release.yml` — `commit-binaries` SECOND "Verify registry-declared WASM
   plugins are staged" step (resolvers-registry.toml parse; `2>/dev/null`; **no** non-vacuity floor)
4. `plugins/vsdd-factory/tests/pr-manager-hardening.bats` — fixture-builder occurrence
5. `plugins/vsdd-factory/tests/pr-manager-hardening.bats` — T-017 mapfile negative control

All five use the same predicate that misses: (a) `./hook-plugins/…` alternate path prefix,
and (b) `plugin="…"` no-space TOML-legal form — the same false-negative polarity as
BLOCKER-1 in `bundle_orphan_check.rs`.

**Two additional findings beyond the weak predicate:**

- **Vacuous-pass on resolver arm.** In `commit-binaries`' Verify step (site 3 above),
  the `-lt 30` non-vacuity floor guards `hooks_plugins` ONLY. The `resolvers-registry.toml`
  read is suppressed with `2>/dev/null`; if the registry file is absent, renamed, or its
  `plugin =` lines change shape, `resolver_plugins` becomes empty and the resolver half
  passes vacuously — a zero result is indistinguishable from a correct empty parse and no
  error is emitted.

- **T-017 first-match-only extractor.** In `pr-manager-hardening.bats`, T-017 extracts
  the "Verify registry-declared WASM plugins are staged" step using
  `awk '... && !found { found=1 }'`. The `!found` flag pins extraction to the FIRST
  occurrence — i.e., `build-binaries`' Verify step (hooks-registry.toml only). The
  `commit-binaries` Verify step (the dual-registry one with the resolver arm) is not
  extracted or exercised by T-017. A predicate regression reintroduced in that step would
  pass the bats suite.

Additionally, the `>= 30` floor constant (guard against vacuous pass on empty parse) is
duplicated at three sites with no shared source: `release.yml` ×2 (one per Verify step)
and `bundle_orphan_check.rs` ×1 — a future declared-plugin-count change requires
synchronized updates in all three.

**POLICY 5 sibling-sweep disposition:** Per the human's standing ruling to keep S-21.09
narrow (WASM artifact restore + Rust parity test only), these five sites are not remediated
within S-21.09. Deferred to **S-21.14** (release-pipeline predicate + gate sweep) to address
all three concerns: (1) harden the five weak-predicate sites (matching the Rust implementation),
(2) add a non-vacuity floor for the resolver arm in `commit-binaries`' Verify step,
and (3) fix T-017's first-match-only extractor to also cover `commit-binaries`' dual-registry
Verify step.
