# S-21.04 — story-worktree factory artifact write-path discipline and teardown preflight

**Epic:** E-21 — Factory State Data-Loss Hardening
**Wave:** 2 (independent of Wave 1 stories; benefits from S-21.01 `validate-factory-path-staging` WASM guard being active as defense-in-depth, but is independently viable without it — no formal `depends_on` block)
**Depends on:** none (Wave 2 placement reflects shared-mutable-worktree theme adjacency with S-21.05; no hard prerequisite in E-21)
**Priority:** P1 (confirmed-live pilot-fleet data-loss with three confirmed instances; story-worktree teardown silently destroys factory artifacts written via CWD-relative paths)
**Subsystem anchor:** SS-06 (Skill Catalog) owns the `deliver-story` skill steps.

## Narrative

Issue #523 confirms three pilot-fleet instances where factory artifacts (DELIVERY ledger, engine-config file, pr-reviewer pr-review.md) were silently destroyed because story agents wrote to `.factory/**` using CWD-relative paths from the story-worktree root rather than canonical absolute paths. The story-worktree's shadow `.factory/` directory does not exist at checkout time — `.factory/` is gitignored on the product branch, so `git worktree add` checks out nothing there. The shadow directory is created by the errant CWD-relative write itself, which is why the misdirected write goes undetected at write time. When step G then ran plain `git worktree remove`, the shadow tree and all its contents were permanently deleted with no warning.

The **gitignored-shadow false-negative** mechanism is the proximate cause (BC-6.26.001 Invariant 5): `.factory/` is listed in `.gitignore` on the product branch, so the shadow `.factory/` content inside the story worktree is **gitignored** (not untracked). Stock git's clean-state check inside `git worktree remove` gates on *untracked* files only — gitignored files are explicitly excluded. The check therefore passes silently as a false negative even when the shadow tree contains stray factory artifacts, and the underlying `rm -rf <worktree-path>` destroys the gitignored shadow content with no warning. The `find`-based preflight is the correct fix because `find` reads the filesystem without gitignore filtering — it is the only mechanism that surfaces this category of stray content before destruction.

**Secondary note:** `--force` is prohibited by BC-6.26.001 as a BC mandate (it strips git's built-in unclean-worktree protection for non-gitignored untracked files; the prohibition is a BC mandate, not a guard-enforced constraint). If `--force` were used despite the prohibition, the preflight would still catch `.factory/` shadow content. The primary failure mode for the current codebase is the gitignored mechanism above; step-g-cleanup.md G.1 MUST use plain `git worktree remove` (no `--force`). BC-6.26.001 establishes the protocol requirements that close this loss window.

Two complementary changes close the loss window:

**Write-path discipline (INV-E21-002 via BC-6.26.001 PC1):** Extend `_shared-context.md` §Spec-Path Discipline to explicitly cover factory artifact *writes*. Add a "Write Discipline" clause: all `.factory/**` artifact writes (DELIVERY ledger, story-frontmatter files, pr-review.md, and any factory-side record) MUST use absolute paths anchored to the canonical main-checkout root. Canonical root is determined via `git -C <story-worktree-path> rev-parse --show-toplevel` on the main worktree, or from the orchestrator-provided `CANONICAL_FACTORY_ROOT` variable. CWD-relative paths are forbidden.

**Teardown preflight (INV-E21-004 via BC-6.26.001 PC2):** Add a mandatory sub-step to `step-g-cleanup.md` before every `git worktree remove` dispatch. The preflight applies a fail-closed four-step discrimination chain: (1) if nothing exists at `<worktree-path>/.factory` (`[ ! -e ]` is true) → PC2a sub-case (a), teardown authorized immediately; (2) if a symlink exists at that path (`[ -L ]`) OR if something exists but is NOT a real directory (regular file, device node, or any other non-directory inode) → PC2b BLOCKED — list the path, do NOT run `find`, do NOT proceed with `git worktree remove`; the `[ -L ]` test MUST precede any `[ -d ]` test because POSIX `test -d` follows symlinks and a symlink-to-directory satisfies `[ -d ]`, which would otherwise fall through to the `find` branch where `find "<worktree-path>/.factory/"` (trailing-slash form) dereferences the symlink via POSIX pathname resolution and enumerates files from the TARGET directory outside the worktree boundary; if the target is empty, `find` returns empty output, falsely authorizing teardown; `git worktree remove` then removes only the symlink entry — target NOT destroyed, but operator not notified; (3) if `.factory/` exists and IS a real directory (not a symlink), run `find "<worktree-path>/.factory/" -type f` (trailing-slash form; no blanket error suppression) — if `find` exits non-zero for any reason, HALT teardown and surface the exit code and stderr (PC2c fail-closed); (4) proceed with plain `git worktree remove` (no `--force`) only when `find` succeeds with empty output.

This story is entirely skill-doc. POLICY 21 satisfied (no new WASM or shell script).
