# S-21.04 — story-worktree factory artifact write-path discipline and teardown preflight

**Epic:** E-21 — Factory State Data-Loss Hardening
**Wave:** 2 (independent of Wave 1 stories; benefits from S-21.01 `validate-factory-path-staging` WASM guard being active as defense-in-depth, but is independently viable without it — no formal `depends_on` block)
**Depends on:** none (Wave 2 placement reflects shared-mutable-worktree theme adjacency with S-21.05; no hard prerequisite in E-21)
**Priority:** P1 (confirmed-live pilot-fleet data-loss with three confirmed instances; story-worktree teardown silently destroys factory artifacts written via CWD-relative paths)
**Subsystem anchor:** SS-06 (Skill Catalog) owns the `deliver-story` skill steps.

## Narrative

Issue #523 confirms three pilot-fleet instances where factory artifacts (DELIVERY ledger, engine-config file, pr-reviewer pr-review.md) were silently destroyed because story agents wrote to `.factory/**` using CWD-relative paths from the story-worktree root rather than canonical absolute paths. The story-worktree's shadow `.factory/` subtree (populated at `git worktree add` time, never updated) captured the write silently. When step G then ran plain `git worktree remove`, the shadow tree and all its contents were permanently deleted with no warning.

The **gitignored-shadow false-negative** mechanism is the proximate cause (BC-6.26.001 v1.3 Invariant 5): `.factory/` is listed in `.gitignore` on the product branch, so the shadow `.factory/` content inside the story worktree is **gitignored** (not untracked). Stock git's clean-state check inside `git worktree remove` gates on *untracked* files only — gitignored files are explicitly excluded. The check therefore passes silently as a false negative even when the shadow tree contains stray factory artifacts, and the underlying `rm -rf <worktree-path>` destroys the gitignored shadow content with no warning. The `find`-based preflight is the correct fix because `find` reads the filesystem without gitignore filtering — it is the only mechanism that surfaces this category of stray content before destruction.

**Secondary note:** If a future change introduced `--force` to the worktree remove command, that would additionally strip git's built-in unclean-worktree protection for any non-gitignored untracked files. The preflight would still catch `.factory/` shadow content in that scenario. The primary failure mode for the current codebase is the gitignored mechanism above; step-g-cleanup.md G.1 uses plain `git worktree remove` (no `--force`). BC-6.26.001 v1.3 establishes the protocol requirements that close this loss window.

Two complementary changes close the loss window:

**Write-path discipline (INV-E21-002 via BC-6.26.001 PC1):** Extend `_shared-context.md` §Spec-Path Discipline to explicitly cover factory artifact *writes*. Add a "Write Discipline" clause: all `.factory/**` artifact writes (DELIVERY ledger, story-frontmatter files, pr-review.md, and any factory-side record) MUST use absolute paths anchored to the canonical main-checkout root. Canonical root is determined via `git -C <story-worktree-path> rev-parse --show-toplevel` on the main worktree, or from the orchestrator-provided `CANONICAL_FACTORY_ROOT` variable. CWD-relative paths are forbidden.

**Teardown preflight (INV-E21-004 via BC-6.26.001 PC2):** Add a mandatory sub-step to `step-g-cleanup.md` before every `git worktree remove` dispatch: run `find <worktree-path>/.factory -type f 2>/dev/null`. If any files are found, halt teardown and require manual intervention (relocate or confirm redundant before retry). Only proceed with teardown after an empty result.

This story is entirely skill-doc. POLICY 21 satisfied (no new WASM or shell script).
