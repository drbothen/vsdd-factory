# S-17.02: verify-factory-lock WASM Guard Crate + Registry Entries

**Epic:** E-17 — Factory State Durability and Concurrency (brownfield-backfill #170)
**Wave:** 2 (depends on S-17.01 schema; schema must exist before guard can be built)
**Depends on:** S-17.01 (factory_lock schema in STATE.md)
**Blocks:** S-17.03 (skills should be delivered with guard already active)
**Priority:** P1 (primary enforcement mechanism for CAP-031)
**BC gate:** BC-4.13.001 v1.0 (draft; POL-14 auto-promotion on PR merge)

## Narrative

- **As a** developer working on the `factory-artifacts` orphan branch
- **I want** a native-WASM PreToolUse guard that reads the `factory_lock` block from
  STATE.md and blocks mutating tools (Edit, Write, Agent dispatch, factory-artifacts
  push Bash commands) when a foreign unexpired lock is held
- **So that** accidental concurrent work from another developer is intercepted before
  any mutations are applied, with an actionable refusal message naming the holder, the
  expiry time, and the break-glass `/factory-unlock --force` command

## Acceptance Criteria

### AC-001 (traces to BC-4.13.001 postcondition PC1 — foreign unexpired lock: block with actionable message)

When ALL conditions are true — `factory_lock.holder` is present and non-null,
`now ≤ factory_lock.expires_at`, and `factory_lock.holder != current_git_email` — the
guard MUST return `block_intent = true` (exit code 2) with a block message containing
ALL five required fields:
1. `holder` — exact git email of the current lock holder
2. `locked_at` — ISO-8601 timestamp when the lock was acquired
3. `expires_at` — ISO-8601 timestamp when the lock auto-expires
4. `time_remaining` — human-readable duration, e.g., "37 min remaining" (computed as
   `expires_at - now`, rounded down to the nearest minute)
5. `/factory-unlock --force` — the exact command string for break-glass force-release

The block path MUST run through `plugin_requests_block()` in
`crates/factory-dispatcher/src/executor.rs` (the `plugin_requests_block` function
invoked at `executor.rs:105–108` for sync-group plugins — `async = false` is required).

**Error variant:** `ForeignLockHeld`
**Test:** `test_BC_4_13_001_foreign_unexpired_lock_blocks_with_all_five_fields()`

### AC-002 (traces to BC-4.13.001 postcondition PC2 — expired lock: pass)

When `factory_lock.holder` is present but `now > factory_lock.expires_at`, the guard
MUST return `HookResult::Continue` immediately. No warning emitted (expired-lock
pass-through is the normal TTL expiry path, not an error).

**Error variant (internal only):** `LockExpired`
**Test:** `test_BC_4_13_001_expired_lock_returns_continue()`

### AC-003 (traces to BC-4.13.001 postcondition PC3 — self-held lock: pass unconditionally)

When `factory_lock.holder == current_git_email` (regardless of `expires_at`), the
guard MUST return `HookResult::Continue`. The developer who acquired the lock is never
blocked by their own lock. Latency MUST be sub-5ms under normal conditions (one
`read_file` + one `exec_subprocess` + one timestamp comparison per ADR-025 Decision 10
and ADR-020 Class A p95 ≤ 1500ms budget).

**Test:** `test_BC_4_13_001_self_held_lock_returns_continue()`

### AC-004 (traces to BC-4.13.001 postcondition PC4 — absent/null/malformed lock: pass fail-open)

When the `factory_lock` block is absent, present but null, or malformed (missing
required fields `holder`/`locked_at`/`expires_at`, or fields not parseable as their
required types), the guard MUST return `HookResult::Continue`. A malformed block MUST
emit `host::log_warn` with `"MalformedLockBlock: <details>"` (advisory only; non-blocking).

**Error variant:** `MalformedLockBlock` (log_warn; no block)
**Test:** `test_BC_4_13_001_malformed_block_returns_continue_with_log_warn()`

### AC-005 (traces to BC-4.13.001 postcondition PC5 — read-only tools: not triggered)

Tools NOT in the registry entry `tool` regex (Read, non-push Bash, mcp__* tools) are
NOT intercepted by this plugin at all — the guard is never invoked. A blocked developer
CAN always read `.factory/STATE.md` to inspect the lock state.

**Test:** (bats T-5 and T-7 from BC-4.13.001 canonical test vectors; see AC-012/AC-013)

### AC-006 (traces to BC-4.13.001 postcondition PC6 — STATE.md read failure: pass fail-open)

When `host::read_file(".factory/STATE.md")` returns any `HostError` variant
(`OutputTooLarge`, `Timeout`, `CapabilityDenied`, `InvalidArgument`, `Other(i32)`), the
guard MUST return `HookResult::Continue` after emitting `host::log_warn` with the error
variant name. A guard that cannot read STATE.md MUST NOT block.

**Error variant:** `StateReadError`
**Test:** `test_BC_4_13_001_read_file_host_error_returns_continue()`

### AC-007 (traces to BC-4.13.001 postcondition PC7 — git subprocess failure: pass fail-open)

When `host::exec_subprocess(["git", "config", "user.email"])` fails (non-zero exit,
empty output, or HostError), the guard MUST return `HookResult::Continue` after
emitting `host::log_warn`. Identity resolution failure MUST NOT block.

**Error variant:** `IdentityResolutionFailed`
**Test:** `test_BC_4_13_001_git_subprocess_failure_returns_continue()`

### AC-008 (traces to BC-4.13.001 postcondition PC8 — on_error behavior: always Continue)

The plugin's `on_error` field in `hooks-registry.toml` MUST be `"continue"`. A
crashed or timed-out plugin returns `HookResult::Continue`. The factory MUST NOT be
wedged by a broken guard.

**Test:** (registry inspection; bats T-8 graceful-degrade coverage)

### AC-009 (traces to BC-4.13.001 invariant 5 — registry shape: two entries, both capability blocks)

The canonical registration in `hooks-registry.toml` MUST include BOTH entries with
BOTH capability blocks:

```toml
[[hooks]]
name = "verify-factory-lock"
plugin = "hook-plugins/verify-factory-lock.wasm"
event = "PreToolUse"
tool = "Edit|Write|Agent"
async = false
on_error = "continue"
timeout_ms = 5000

[hooks.capabilities.read_file]
path_allow = [".factory/STATE.md"]

[hooks.capabilities.exec_subprocess]
binary_allow = ["git"]

[[hooks]]
name = "verify-factory-lock-bash"
plugin = "hook-plugins/verify-factory-lock.wasm"
event = "PreToolUse"
tool = "Bash"
async = false
on_error = "continue"
timeout_ms = 5000

[hooks.capabilities.read_file]
path_allow = [".factory/STATE.md"]

[hooks.capabilities.exec_subprocess]
binary_allow = ["git"]
```

Omitting EITHER capability block causes a silent no-op guard (capability-denied
graceful-degrade to Continue — the implementation-time footgun per ADR-025 D2 Rationale).
The bats test MUST cover the capability-omitted case (AC-011).

**Test:** `test_BC_4_13_001_registry_has_two_entries_with_both_capability_blocks()`
(grep `hooks-registry.toml` for both capability block forms — literal shell with
captured stdout per POLICY 5 Part B)

### AC-010 (traces to BC-4.13.001 invariant 6 — capability-denied graceful degrade)

If either `[hooks.capabilities.read_file]` or `[hooks.capabilities.exec_subprocess]`
is omitted from the registry (footgun scenario), the plugin MUST catch the
`CapabilityDenied` `HostError` variant and graceful-degrade to `HookResult::Continue`
(NOT panic). The degrade MUST emit `host::log_warn("capability_denied: read_file")` or
`host::log_warn("capability_denied: exec_subprocess")` as appropriate. The guard is
now silently inert but does not crash.

**Test:** `test_BC_4_13_001_capability_denied_graceful_degrades_to_continue()`

### AC-011 (traces to BC-4.13.001 invariant 7 — latency budget)

The guard's hot path (one `read_file` call + one `exec_subprocess` call + timestamp
comparison) MUST complete within ADR-020 Class A p95 budget of 1500ms. Under normal
conditions the budget is well within 100ms. `timeout_ms = 5000` in the registry is
the backstop for pathological conditions.

**Test:** (addressed by ADR-020 Class A invariant; no separate unit test required;
noted as architecture compliance rule)

### AC-012 (traces to BC-4.13.001 canonical test vector T-6 — Bash push arm blocked)

When a `Bash` PreToolUse event arrives with a command matching `git.*push.*factory-artifacts`
AND a foreign unexpired lock is held, the guard MUST return `HookResult::Block`.
The push-regex check is internal to the WASM plugin for Bash payloads — the registry
`tool = "Bash"` is the trigger; the internal regex filters to factory-artifacts pushes
only.

**Test:** `test_BC_4_13_001_bash_factory_artifacts_push_blocked_when_foreign_lock()`
(bats T-6)

### AC-013 (traces to BC-4.13.001 canonical test vector T-7 — non-push Bash: Continue)

When a `Bash` PreToolUse event arrives with a command NOT matching
`git.*push.*factory-artifacts` (e.g., `cat .factory/STATE.md`, `ls`, any non-push
command), the guard MUST return `HookResult::Continue` immediately (no STATE.md read,
sub-millisecond).

**Test:** `test_BC_4_13_001_non_push_bash_returns_continue_immediately()`
(bats T-7)

### AC-014 (traces to BC-4.13.001 edge case EC-010 — async=true is a misconfiguration)

The guard MUST be registered with `async = false`. If the registry has `async = true`,
the dispatcher discards `block_intent` (advisory-only per ADR-019), silently making
the guard a no-op blocker. Implementation MUST enforce `async = false` in the registry
entries and include a comment: `# async = false REQUIRED — see ADR-019 + ADR-025`.

**Test:** (registry grep confirms `async = false` on both entries — captured stdout
per POLICY 5 Part B)

### AC-015 (traces to BC-4.13.001 edge case EC-002 — expires_at boundary: treat now==expires_at as expired)

When `now == factory_lock.expires_at` exactly (boundary case), the guard MUST treat
the lock as just-expired and return `HookResult::Continue` (LockExpired path). The
comparison MUST use `now > expires_at` semantics: `now == expires_at` evaluates as NOT
greater-than, meaning the lock is expired at the exact boundary instant.

**Test:** `test_BC_4_13_001_expires_at_exact_boundary_treated_as_expired()`

## Architecture Compliance Rules

From ADR-016, ADR-019, ADR-020, ADR-025:

1. **`async = false` is a correctness requirement.** ADR-019 CI lint invariant:
   `on_error=block ⇒ async=false`. For `verify-factory-lock`, the blocking is the
   entire purpose — `async = true` would silently reduce it to a no-op blocker.
   Both registry entries MUST have `async = false`.

2. **BOTH capability blocks are REQUIRED on BOTH entries.** Omitting `read_file` or
   `exec_subprocess` block causes `CapabilityDenied` graceful-degrade — a silent no-op
   guard that is the primary implementation-time footgun (ADR-025 D2 Rationale §Capability
   blocks must be enumerated). The implementer MUST NOT scaffold the registry entry from
   a minimal template.

3. **`on_error = "continue"` (fail-open) is correct for an efficiency-class lock.**
   ADR-025 §Decision 7 + Kleppmann §8 distinction: a crashing guard that blocks all
   writes is worse than a missed block (which is bounded by S-17.01's CAS push safety net).

4. **No `regex` crate in the frontmatter scanner.** The frontmatter `factory_lock`
   scanner MUST use manual line-by-line scan within the `---\n` delimited region.
   Using `regex` adds ~200–600 KiB WASM binary bloat for a fixed-format parse that
   requires no regex. This is the same discipline as `validate-trajectory-tail` (ADR-025
   does not cite regex — the format is known and fixed).

5. **`HOST_ABI_VERSION = 1` is unchanged.** The dispatcher binary requires no changes
   for this story (ADR-025 Decision 1). `host::read_file` and `host::exec_subprocess`
   with `binary_allow = ["git"]` are already present in ABI version 1.

6. **Guard is read-only at runtime.** The guard MUST NEVER write STATE.md (BC-4.13.001
   Invariant 4). Writing the `factory_lock` block is exclusively state-manager's
   responsibility (TD-VSDD-053).

7. **Block path is synchronous.** `block_intent = true` is only effective when the
   plugin is in the sync-group (`async = false`). The block decision aggregates at
   `executor.rs:100–117`. Verified by T-1 canonical grep.
