# S-21.20: PC13 full-registry coverage — `on_error=Block` plugin-error fail-closed demonstrated across all 18 registry entries (BC-1.03.017 v1.25 Invariant 11; split seam 2 of 6 from S-21.11)

## Narrative

- **As a** factory pipeline operator relying on the PC13 fail-closed-on-plugin-error rule
  (delivered by S-21.19) to protect every `on_error="block"` gate, not only the six
  exhaustion-migration-targeted plugins
- **I want** the PC13 predicate's registry-wide reach demonstrated individually against all 18
  `on_error="block"` `hooks-registry.toml` entries (17 unique plugin names; `protect-secrets`
  registered twice by tool trigger)
- **So that** BC-1.03.017 v1.25 Invariant 11's full-coverage obligation is met with no sampled
  subset, and a future registry drift (e.g. an entry's `on_error` silently flipped away from
  `"block"`) is caught loudly by a dedicated per-entry test rather than silently

## Context / Finding Summary

**[Originally added to S-21.11 at v2.3, F-004 remediation]** The following eighteen ACs
implement BC-1.03.017 v1.25's **Invariant 11** (human-directed production-grade full-coverage
decision): PC13's `on_error = Block` + `PluginResult::Ok { exit_code != 0 }` → block rule is
dispatcher-level and plugin-name-independent, and MUST be demonstrated individually against
every `on_error = "block"` entry in `plugins/vsdd-factory/hooks-registry.toml` — **18
`[[hook]]` entries across 17 unique plugin names**, per BC-1.03.017 v1.25's PC13 Coverage Set
table (`protect-secrets` is registered twice — once for `tool = "^Bash$"`, once for
`tool = "^Read$"` — two independently dispatched entries sharing one plugin binary, each an
independent coverage unit) — NOT a sampled subset limited to the six PC1–PC12
exhaustion-migration-targeted plugins. Of the 18, five (`validate-factory-path-root`,
`validate-input-hash`, `validate-template-compliance`, `validate-pr-merge-prerequisites`,
`validate-wave-gate-prerequisite`) are ALSO among the six PC1–PC12-targeted plugins — for
these five, this section's PC13 coverage is an ADDITIONAL, independent obligation alongside
S-21.19's AC-009/AC-012 and S-21.23's AC-022 exhaustion-axis coverage; neither substitutes for
the other. `validate-cross-site-correspondence` (the sixth PC1–PC12-targeted plugin, owned by
S-21.22) carries `on_error = "continue"` and is therefore NOT in this coverage set at all
(PC13 is additive to `on_error = Block` only). The remaining thirteen entries below were
previously uncovered by any PC13-specific AC and are brought into scope here.

**Common assertion pattern (shared by all eighteen ACs below; stated once, not repeated per
AC):** for the named entry, a Cargo unit test MUST (a) parse the entry's live `on_error` value
from `plugins/vsdd-factory/hooks-registry.toml` and assert it equals `"block"` (a
registry-drift canary — if a future edit changes this entry's `on_error`, the coverage test
fails loudly instead of silently asserting a stale condition); (b) construct a synthetic
`PluginOutcome` whose `on_error` is DERIVED FROM the value parsed in step (a) (which step (a)
asserts is `Block`) — NOT hardcoded to `OnError::Block` independently of the parse
(F-S2120-P2-001, load-bearing correction to this shared description: this is the single site
that makes F-S2120-P1-001's per-entry-registry-genuineness requirement true for all 18 tests at
once) — and `result = PluginResult::Ok { exit_code: 1, .. }`; (c) assert S-21.19's Task-6-extended decision
function — `plugin_fail_closed_on_error_exit(result, on_error)`, per ADR-044 v1.3; the PC13 predicate is this function's `on_error==Block &&
Ok{exit_code!=0}` arm — returns `true` (`block_intent = true`;
dispatcher exit code 2 at the aggregate level). This is a pure unit-level test — no new
production code is required beyond S-21.19's single generic predicate extension; these 18
tests prove that predicate's registry-wide reach, per Invariant 11's entry-count-agnostic
full-coverage rule. No test in this section exercises `timeout_ms`, `fuel_cap`, or
`failure_policy` — PC13 is independent of the exhaustion/`failure_policy` axis governed by
S-21.19's AC-001–AC-012, and independent of the `Timeout`/`Crashed` paths per S-21.19's
narrowed predicate (F-001).

  independently of the parse. A test that hardcodes `on_error: OnError::Block` regardless of
  what step (a) parsed would still pass even if the registry entry's real `on_error` value
  drifted to something else (as long as step (a)'s separate assertion didn't itself catch it)
  — constructing the synthetic outcome FROM the parsed value closes that gap and makes each of
  the 18 tests genuinely exercise that entry's own live registry data, not a shared hardcoded
  fixture.
- **F-S2120-P1-002 (MEDIUM, deferred MEDIUM finding folded in):** AC-030
  (`test_pc13_coverage_protect_secrets_bash`) and AC-031
  (`test_pc13_coverage_protect_secrets_read`) MUST each select their registry entry by keying
  on BOTH plugin `name = "protect-secrets"` AND `tool` (`^Bash$` for AC-030, `^Read$` for
  AC-031) — keying by `name` alone is ambiguous between the two independently-dispatched
  `protect-secrets` entries and risks both tests silently reading the SAME entry (defeating
  the two-independent-coverage-units guarantee AC-030/AC-031's own header text already states).
