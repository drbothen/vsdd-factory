# S-23.04: Tier-1 INDEX-resolution mechanism (4-registry targeted lookup)

## Narrative

- **As a** WASM validation hook (the thin new-pin guard, S-23.03, and the amended `validate-cross-site-correspondence` gate, S-23.05)
- **I want** a mechanical function that, given a stable ID (`BC-S.SS.NNN`, `ADR-NNN`, `S-EE.NN`, `VP-NNN`), returns that ID's current version by looking it up in the appropriate INDEX registry (BC-INDEX / ARCH-INDEX / STORY-INDEX / VP-INDEX)
- **So that** no citing document needs to hand-author an inline version token anywhere — the version is always resolved mechanically, at lint time, from the authoritative registry

## Context / Problem Statement

ADR-045 Section Decision, Tier 1 states: "Version resolution operates mechanically at lint time against the project's existing INDEX registries: BC-INDEX for BCs, ARCH-INDEX for ADRs, STORY-INDEX for stories, VP-INDEX for VPs." ADR-045 Migration Plan Phase A step 3 requires this "wherever version-leg parity is checked — POLICY 7/8/14/17 gates."

S-21.13 already solved this problem for exactly one of the four registries: it added a `read_file_range(path, offset, len)` host function plus a BC-INDEX row-offset sidecar, so `validate-cross-site-correspondence` can locate a specific BC's row in O(1) fuel instead of a linear scan whose fuel cost grows with corpus size (measured: `fuel = 2,585,970 + 53.18 x var_bytes`, R^2=0.998790). This story generalizes that precedent to the other three registries — ARCH-INDEX, STORY-INDEX, VP-INDEX — each of which needs an equivalent row-offset sidecar (or a demonstrably-cheaper alternative lookup structure) and a resolver function keyed by that registry's own ID form.

This story does not change any INDEX file's content — it builds the read-side resolution mechanism against the INDEX files as they exist today (with inline version cells, per current convention) and as they will exist post-migration (stable IDs whose *row* still carries the authoritative version — the INDEX row itself is not migrated to a version-free form; ADR-045 explicitly resolves *from* the INDEX, meaning the INDEX retains the ground-truth version).

## Acceptance Criteria

### AC-001
Given a `BC-S.SS.NNN` ID, `resolve_version("BC-1.03.017")` returns the current version string found in BC-INDEX.md's row for that BC, reusing S-21.13's `read_file_range` + BC-INDEX row-offset sidecar mechanism rather than re-implementing a linear scan. (traces to ADR-045 Decision, Tier 1, "Version resolution operates mechanically... BC-INDEX for BCs"; S-21.13 precedent)

### AC-002
Given an `ADR-NNN` ID, `resolve_version("ADR-039")` returns the current version string found in ARCH-INDEX.md's row for that ADR, via a new ARCH-INDEX row-offset sidecar analogous to S-21.13's BC-INDEX sidecar. (traces to ADR-045 Decision, Tier 1, "ARCH-INDEX for ADRs")

### AC-003
Given an `S-EE.NN` story ID, `resolve_version("S-21.13")` returns the current version string found in STORY-INDEX.md's row for that story, via a new STORY-INDEX row-offset sidecar. (traces to ADR-045 Decision, Tier 1, "STORY-INDEX for stories")

### AC-004
Given a `VP-NNN` ID, `resolve_version("VP-079")` returns the current version string found in VP-INDEX.md's row for that VP, via a new VP-INDEX row-offset sidecar. (traces to ADR-045 Decision, Tier 1, "VP-INDEX for VPs")

### AC-005
`resolve_version` returns a named "not found" error (not a panic, not a silent default) when the ID does not exist in its corresponding INDEX. (traces to ADR-045 Decision, Tier 1 — implicit correctness requirement of a mechanical resolver; CLAUDE.md Conventions error taxonomy)

### AC-006
The resolver's fuel cost for a lookup is O(1) with respect to corpus size (targeted row-offset read via `read_file_range`), not O(corpus size) (linear scan), for all four registries — matching S-21.13's structural fix rather than reintroducing its palliative-only bridge-budget problem for the three new registries. (traces to S-21.13 Context/Problem Statement, "eliminates the fuel ceiling structurally"; ADR-042 Section Decision 5 Option C precedent)

### AC-007
Each of the four sidecar formats (BC-INDEX reused from S-21.13; ARCH-INDEX, STORY-INDEX, VP-INDEX new) is documented with its exact schema (columns, offset semantics, maintenance obligation — i.e., who updates the sidecar when the INDEX file is edited) in this story's File Structure Requirements. (traces to ADR-045 Consequences, Negative/Trade-offs — "a fingerprint sidecar schema... must be designed" analog applied here to the INDEX-offset sidecar, which is a Tier-1 mechanism, not a Tier-2 one)

### AC-008 (negative control)
`resolve_version` given a syntactically well-formed but nonexistent ID (e.g., `BC-9.99.999`) does not silently return a stale or default version — it returns the AC-005 "not found" error. (traces to ADR-045 Decision, Tier 1 — mechanical correctness; guards against false-negative staleness detection downstream in S-23.03/S-23.05)

## Purity Classification

| Module | Classification | Justification |
|--------|-----------------|----------------|
| `resolve_version` (dispatch + host-function call) | effectful-shell | Calls `read_file_range`, a host function crossing the WASM/host boundary |
| Sidecar-format parsing (byte offset lookup, given raw sidecar bytes already read) | pure-core | Given the sidecar bytes and an ID, returns an offset with no further I/O |
| Sidecar generator binaries (ARCH-INDEX/STORY-INDEX/VP-INDEX row-offset table builders) | effectful-shell | Read the INDEX file, write the sidecar file |

## Edge Cases

| ID | Description | Expected Behavior |
|----|-------------|--------------------|
| EC-001 | INDEX row for the ID spans multiple physical lines in the underlying INDEX markdown table (long descriptive cell wraps) | Sidecar offset points at the row's start byte; `read_file_range`'s length covers the full row regardless of internal wrapping |
| EC-002 | Two INDEX rows share a version-token substring (S-21.13's documented BC-1.17.001/BC-2.07.001 last-wins hazard) | Resolver anchors strictly on the target ID's own row, never on the last-matching row across the whole scanned range (S-21.13's corpus red-gate precedent) |
| EC-003 | Sidecar file is stale relative to the INDEX file it describes (INDEX edited without regenerating the sidecar) | Resolver detects a sidecar/INDEX mismatch (e.g., a checksum or line-count sentinel) and fails closed with a named error rather than returning a wrong offset silently |
| EC-004 | ID exists in the INDEX but its row was deleted/renumbered since the sidecar was generated | Same fail-closed behavior as EC-003 |

## Previous Story Intelligence

**From S-21.13:** the `read_file_range(path, offset, len)` host function already exists and is proven for BC-INDEX; do not redesign it. The corpus red-gate test pattern (BC-1.17.001/BC-2.07.001 last-wins hazard, EC-002 here) is a durable regression guard that must be replicated for the other three registries, not merely copy-pasted with BC identifiers swapped for ADR/Story/VP ones — the actual row-adjacency hazard differs per registry's table layout and must be independently verified against each registry's live file. S-21.13 also flagged (in its own frontmatter comments) that BC-INDEX sidecar maintenance obligation was a known follow-up at elaboration; this story is that follow-up, generalized to three more registries.

## Architecture Compliance Rules

- All four resolvers MUST use `read_file_range`, not a full-file read followed by a linear scan — this is the whole point of the story (AC-006); a linear-scan fallback defeats the fuel-ceiling fix S-21.13 established.
- No `unwrap()`/`expect()` on sidecar-parsing or host-function-call paths — a malformed or stale sidecar must produce a named error (EC-003/EC-004), not a panic.
- Sidecar files MUST live alongside their INDEX file (or in a clearly-scoped sidecar directory) and MUST NOT be confused with the INDEX file's own content — a sidecar mismatch (EC-003/EC-004) must never be interpreted as "resolve to whatever the sidecar last saw."
